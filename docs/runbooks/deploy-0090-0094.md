# Runbook: deploying migrations 0090–0094 to production

**Status:** not yet executed. Production is at `0089`; local is at `0094`.

## Why this matters

Production is missing the whole of NFR-018. On the live database today, a suspended gym can still write through the `SECURITY DEFINER` RPCs — the exact hole Stories 11.8 and 11.9 close. Also missing: the Supervisor permission fix, staff self-service password reset, and staff/member phone separation.

| Migration | What it does | Risk |
|---|---|---|
| `0090` | Suspension guard in 18 write-RPCs, 19 documented exclusions | Behaviour change for non-active gyms |
| `0091` | `tenant_active_gate` on 3 workout tables + guards 3 RPCs | Same; also adds RESTRICTIVE policies |
| `0092` | Adds `phone_has_staff_membership()` | Additive only, low |
| `0093` | Widens 26 policies + 7 RPC role gates for Supervisor | **Highest** — see below |
| `0094` | Trigger: a phone is staff **or** member, never both | Aborts if existing data violates it |

## The two things that make this non-trivial

**1. `0093` has an undocumented dependency on `0090`.**
All 7 functions `0093` replaces are *also* replaced by `0090`, and `0093`'s bodies were captured from a database where `0090` was already applied — so they carry `0090`'s suspension guard inline (verified: 7/7). Applied in order this is correct and the end state is right. Applied out of order, or `0093` cherry-picked onto `0089`, those 7 functions would silently gain suspension guards without the rest of `0090`. **Never apply `0093` without `0090` first.**

**2. `0093` was generated from a local catalog.**
Its 26 `ALTER POLICY` statements were machine-generated from `pg_policies` on the dev database. If production's policies have drifted from that shape, those statements would overwrite a *different* predicate than intended. Pre-flight check 5 verifies the count is 26 before you push.

## Procedure

### Step 1 — Back up. Non-negotiable.

These migrations replace function bodies and alter policies. There is no clean down-migration. Take a PITR restore point or a branch before touching anything.

### Step 2 — Pre-flight (read-only, writes nothing)

```
export PGPASSWORD=$(cat ~/.supabase-db-password)
psql -h aws-0-eu-west-1.pooler.supabase.com -p 5432 \
     -U postgres.vfxezibagiznrirdwkwh -d postgres \
     -f scripts/preflight-prod-deploy.sql
```

Do not proceed while any **STOP** is outstanding. Specifically:

- **Check 3** — if any account is both staff and member, `0094` raises and aborts the entire push. Resolve those accounts first.
- **Check 4** — must show `0090` not yet applied, or the ordering assumption above is void.
- **Check 5** — must be 26. Any other number means production drifted and `0093` needs regenerating against production's own catalog.
- **Check 6** — tells you which live gyms change behaviour the moment this lands. Warn their owners.

### Step 3 — Apply, in order

```
supabase db push          # applies 0090 -> 0094 sequentially
```

Every one of these migrations self-asserts at apply time (`0090`–`0094` each end in a `DO` block). A failure aborts that migration rather than half-applying it.

⚠️ Per `project_docker_no_network`: Supabase CLI container commands can fail silently and still exit 0 here. **Verify the migration head afterwards; do not trust the exit code.**

### Step 4 — Verify on production, not locally

```
-- head should now read 0094
select version from supabase_migrations.schema_migrations order by version desc limit 6;

-- the guard reached all 21 write-RPCs
select count(*) from pg_proc p join pg_namespace n on n.oid = p.pronamespace
where n.nspname='public' and p.prosrc like '%current_gym_status() is distinct from ''active''%';

-- no policy grants manager without supervisor
select count(*) from pg_policies where schemaname='public'
  and (coalesce(qual,'')||coalesce(with_check,'')) ilike '%manager%'
  and (coalesce(qual,'')||coalesce(with_check,'')) not ilike '%supervisor%';   -- expect 0

-- tenant_active_gate now covers 21 tables
select count(distinct tablename) from pg_policies
where schemaname='public' and policyname='tenant_active_gate';                 -- expect 21
```

### Step 5 — Deploy the app

The database is only half of it. The staff-login fix, password reset and Supervisor nav are application code. Deploy the app from `684714f` or later, then confirm on the deployed URL:

- a Supervisor sees Overview / Members / Subscriptions / Payments / Attendance / Audit Log
- a phone-only staff account can sign in
- "Forgot password?" accepts a phone number

### Step 6 — Smoke test as a real gym

The two blockers found today were found by *using* the product, not by reading it. Do one full pass on production: create a gym → add staff of each role → sign in as each → add members → take a payment → onboard a member on mobile → check in → renew.

## Rollback

No down-migrations exist. Recovery is the Step 1 restore point. If only `0094` misbehaves it can be reverted in isolation:

```
drop trigger if exists enforce_staff_member_phone_separation_trigger on members;
drop function if exists private.enforce_staff_member_phone_separation();
```

`0090`–`0093` cannot be cleanly reversed piecemeal — they replace function bodies. Restore from backup instead.
