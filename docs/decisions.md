This story's reading: the only "hook" this metric needs is that every captured event carries `gymId`, so a support-interaction log built later (in-app or, more likely, external) can be joined to PostHog activity by gym/week. No support-ticket stub, table, or event was built.

**(d) `staff_created`'s payload deliberately excludes `input.phone`/`input.name`** — a PII-minimization judgment call this story made unprompted (no AC requires it, none forbids it). Flagged for the user/PO to override on review if a narrower reading was actually wanted.

## 2026-08-19 — Class reminder notification (N-07): natural-key dispatch dedupe (opposite of Story 6.5's precedent), cron-cadence-bounded reminder timing, and cancellation-is-silent as a free payoff of Story 12.2's design — recorded during Story 6.6

**(a) Dispatch dedupe strategy — natural-key `unique(class_session_id, member_id)`, not Story 6.5's no-natural-key shape.** N-07 is a true one-shot event: a given `(class_session_id, member_id)` booking gets exactly one reminder, ever. This is the same shape as N-01/N-02/N-03 (`private.notification_dispatches`, migration `0045`, `unique(subscription_id, notification_code)`), not N-06's (`private.quiet_gym_alert_dispatches`, migration `0056`) rolling-rate-limit shape, which deliberately has no natural key because the same member can legitimately get a new N-06 dispatch every few hours. `private.send_class_reminder()` therefore copies `0045`'s `insert ... on conflict (class_session_id, member_id) do nothing returning id into v_dispatch_id; if v_dispatch_id is null then return; end if;` pattern — both the business-rule expression (one reminder per booking) and the concurrency-safety mechanism against overlapping cron runs, in one constraint. Story 6.5 was the most recent precedent in the codebase but was the wrong one to copy verbatim here; this is a deliberate divergence, not an inconsistency.

**(b) Reminder timing is cron-cadence-bounded, not exact-second.** FR-116/the epic AC phrase "60 minutes before the session starts" as an exact instant. `run_class_reminder_job()` runs every 5 minutes (`*/5 * * * *`) and dispatches any booking whose session `scheduled_at` falls in `(now(), now() + 60 minutes]` with no existing dispatch row. Because the natural-key dedupe guarantees exactly one dispatch per booking ever, the effective fire time is the first job run after the session crosses into the 60-minute window — anywhere from exactly 60 minutes before down to 55 minutes before, in the worst case. This is the same precision class as every other cron-dispatched notification in this codebase (N-06 at a 15-minute cadence, the subscription-lifecycle notifications at their own cadence) — none of them fire at exact-second precision, and neither does N-07. No tighter, per-session dynamically-scheduled `pg_cron` job was built — that would be new infrastructure this codebase has never used, for a precision gain no AC actually asks for.

**(c) Cancellation-is-silent — a direct, positive payoff of Story 12.2's `class_bookings` design, not new code this story wrote.** Story 12.2 deliberately gave `class_bookings` no `status` column — cancellation is a row `DELETE` (`cancel_class_booking()`), not a status transition. Because `run_class_reminder_job()` reads live `class_bookings` rows via a plain join, a member who cancels before the 60-minute mark simply stops appearing in the job's query results; there is no separate cancellation-check branch anywhere in this story's migration. ## 2026-08-18 — Class Creation & Scheduling: session-materialization design, 4-week rolling window, booking-count scope gap, delete-and-regenerate reschedule, and two real Zod/date-format bugs caught during manual verification — recorded during Story 12.1

No AC or PRD text specifies a window length — 4 weeks was chosen as long enough that a member always has bookable sessions to see, short enough that a schedule edit's `on conflict do nothing` idempotency and the reschedule path's `delete ... where scheduled_at > now()` stay cheap. **Two real bugs caught during manual browser verification (Task 8), not by pgTAP or typecheck — both fixed same-session:**

1. **`coachId` Zod validation rejected a real, valid selection.** `classSchema`'s `coachId` field used `z.string().uuid("Select a coach")`. 2. **Editing a recurring class silently no-opped on Save.** Postgres's `time` column round-trips as `"HH:mm:ss"` (e.g. `"18:00:00"`) via PostgREST, but `classSchema`'s `recurrenceTime` regex only accepts `"HH:mm"` and the `<input type="time">` widget expects the same. `ClassModal.tsx`'s edit-prefill (`formFromClass`) passed the DB value straight through unformatted — submitting without retouching the time field failed Zod validation on a field with no rendered per-field error message, so the Save button appeared to do nothing. Fixed by slicing to `HH:mm` on prefill (matching `toDateInputValue`/`toTimeInputValue`'s existing local-formatting discipline for the one-off fields) and by rendering the error for all three recurring fields (`recurrenceDays`/`recurrenceTime`/`recurrenceStartDate`) instead of only `recurrenceDays`, so a future validation failure on this path is visible instead of silent.

## 2026-08-08 — RLS deny-all: a direct `UPDATE` against a table with no `UPDATE` policy does not raise, unlike `INSERT` — recorded during Story 1.13

**Finding:** Story 1.13's Task 6 spec, following `payment_providers_rls.test.sql`'s precedent, called for asserting a direct `UPDATE messaging_provider_config ...` under a super-admin session is `throws_like('%row-level security%')`. It isn't — `pgTAP` confirmed empirically (`Failed test 3: no exception thrown`). `INSERT` and `UPDATE` behave differently under RLS deny-all: `INSERT` has no `USING` clause to filter against, so a missing `WITH CHECK` policy makes every attempted row fail validation and raise `new row violates row-level security policy`. `UPDATE`'s `USING` clause is what selects candidate rows in the first place — with no `UPDATE` policy at all, it silently matches 0 rows and returns success (`UPDATE 0`), the same as any `WHERE` clause matching nothing. `payment_providers_rls.test.sql` only ever exercised this via `INSERT`, so the distinction was untested precedent, not a verified pattern.

**Fix:** `messaging_provider_config_rls.test.sql`'s direct-`UPDATE` assertion is `lives_ok` (no exception) + a follow-up `is()` proving `instance_id` is unchanged (0 rows actually affected), instead of `throws_like`.

**Why recorded here:** any future "RLS deny-all + one `SECURITY DEFINER` write RPC" table (the established pattern for `payment_providers`, `audit_log`, and now `messaging_provider_config`) that writes a pgTAP test asserting a blocked direct `UPDATE` should use `lives_ok` + a value-unchanged check, not `throws_like('%row-level security%')` — the latter is only correct for a blocked `INSERT`.

## 2026-08-08 — Add Member form: two production bugs (RFC 4122-vs-Postgres UUID validation, missing dashboard `SUPABASE_SERVICE_ROLE_KEY`), a join-date timezone bug, and the create-flow's two-step redesign — recorded during a live production incident triaged via user bug report

**Finding 1 — `createMemberSchema`'s `planId: z.uuid(...)` rejected a real, currently-in-use Postgres row because Zod's `.uuid()` enforces RFC 4122's version/variant nibbles, which Postgres' own `uuid` column type does not.** The Play Store review demo gym ("Martin Fitness")'s only plan was hand-seeded with `id = "dddddddd-0000-0000-0000-000000000004"` — a syntactically valid Postgres `uuid` literal (32 hex digits, correct `8-4-4-4-12` grouping) but an invalid RFC 4122 UUID (the version nibble, the first character of the third group, is `0`; RFC 4122 requires `1`–`8` there). Reported by the user as "I select a plan but it keeps asking for select plan" — misleading because the plan genuinely was being selected correctly every time (confirmed live: direct DOM inspection of the `<select>`'s `.value`, and the auto-calculated Expiry Date field updating correctly off the real selection). The rejection happened silently downstream in Zod, unrelated to any UI/click interaction. Fixed in `packages/types/src/schemas/member.ts` by loosening `planId` to `z.string().min(1, "Select a plan")` — the real authority on whether a `planId` refers to a real row is `getPlanTypeForGym()`'s gym-scoped DB lookup (`apps/dashboard/services/members.ts`), which already handles a bogus id gracefully; Zod only needs to reject an empty selection. **The same landmine exists wherever `z.uuid()` validates a real, potentially hand-seeded/demo entity id** — confirmed via grep still present for `memberId` (`subscription.ts`, `sessionNote.ts`, `coachAssignment.ts`, `payment.ts`), `coachId` (`coachAssignment.ts`), `paymentId`/`alertId` (`payment.ts`, `frontDeskAlert.ts`), `tierId`/`gymId` (`gym.ts`) — none of these were touched by this fix; only `member.ts`'s `planId` was confirmed broken and fixed. Worth a full sweep if another hand-seeded demo/review id surfaces the same failure mode elsewhere.

**Finding 2 — the `dashboard` Vercel project's production environment was missing `SUPABASE_SERVICE_ROLE_KEY` entirely, silently blocking every single member creation regardless of gym or plan.** Discovered immediately after Finding 1's fix shipped: submitting with a validly-selected plan now got past Zod but failed with a generic "Something went wrong on our end," traced via `get_runtime_errors` (Vercel MCP) to `Error: supabaseKey is required.` inside `createAdminClient()` (`apps/dashboard/lib/supabase/admin.ts`), called by `provisionMemberRow` (`apps/dashboard/services/members.ts`) to create the new member's own `auth.users` login account — a step every member creation goes through, independent of which plan is chosen. `vercel env ls production` confirmed the `dashboard` project had only `NEXT_PUBLIC_SUPABASE_URL`/`NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`; the sibling `super-admin` Vercel project already had `SUPABASE_SERVICE_ROLE_KEY` configured correctly (same Supabase backend), confirming this was a one-off provisioning gap on the `dashboard` project specifically, not a missing/rotated secret. **This bug had been silently masking Finding 1's true blast radius**: because Zod's `planId` rejection (Finding 1) fired first for every submit, this deeper, universal blocker was never actually reached or observed until Finding 1 was fixed. The user added the key themselves (`vercel env add SUPABASE_SERVICE_ROLE_KEY production` — the assistant does not enter secrets into any field, even authorized) and a redeploy picked it up. Both fixes verified together end-to-end against live production: a real member created successfully on the "Martin Fitness" gym using the exact plan that originally failed.

**Finding 3 — `createMemberSchema`'s join-date "not in the future" check compared against UTC "today," rejecting a same-day local date for any UTC-ahead timezone during the first ~1 hour after local midnight.** `todayIso()` (`packages/types/src/schemas/member.ts`) computed `new Date().toISOString().slice(0, 10)` — always the UTC calendar date. For Cameroon (UTC+1, this product's market), the ~1-hour window right after local midnight has a local date one day ahead of UTC's, so entering today's real date failed as "in the future" while yesterday's (still UTC's current day) passed — exactly the reported symptom. Fixed by padding the boundary one full day ahead of UTC (`d.setUTCDate(d.getUTCDate() + 1)`), which covers every real-world timezone's true "today" (UTC-12 through UTC+14) without ever accepting a date genuinely in the future everywhere on Earth. This is a narrower, more defensible fix than trying to resolve "today" against the caller's real local clock, which niether the browser (via `.toISOString()`) nor the server (Vercel functions run in UTC) can determine correctly for a date-only comparison shared between client and server validation.

**Decision 4 — the create-member form (`MemberModal.tsx`, 11 fields in one continuous scroll) was split into a two-step "Personal Info" / "Membership" wizard, at explicit user request ("the form does not look good, even make it two step").** Edit mode is untouched (identity fields only, Scope Note's existing edit-mode boundary — too few fields to need stepping). Expiry Date is now auto-calculated from the selected plan's `duration_days` + Join Date (`computeExpiryDate()`), staying editable for manual override — this is also what actually resolves Finding 1's *reported symptom* (though not its root cause): before this change, Expiry Date had no default and was easy to submit empty, which failed a server-side "required for this plan" check whose French copy ("*...pour cette **formule***") reads like a plan-selection complaint. Phone now pre-fills `+237` instead of an empty field with only a placeholder (placeholders vanish on first keystroke, silently dropping the country code). A validation failure landing on a step-1-only field (name/phone/email/dob) after a step-2 submit auto-returns to step 1 so the error is actually visible.

**Why recorded here, not just in commit messages:** Finding 1 is a systemic Zod-vs-Postgres validation mismatch still present in ~9 other `z.uuid()` call sites across `packages/types/src/schemas/*.ts` — a future reader hitting the identical "correctly selected, still rejected" symptom on a different entity (coach, tier, payment) should find this instead of re-deriving it from scratch. Finding 2 is the kind of env-var gap that produces no local-dev signal at all (local `.env.local` has always had a real service-role key) and is easy to misdiagnose as a code bug rather than a deployment/provisioning gap — worth an explicit audit note that `dashboard`'s and `super-admin`'s Vercel projects can silently drift out of env-var parity even though they share one Supabase backend. Finding 3 is the same UTC/local date-boundary bug class `member.ts`'s own top-of-file comment already warns about, reintroduced once in the UI layer (already fixed once by an earlier code review, per the comment at line 57 in `MemberModal.tsx`) and here in the schema layer itself — worth cross-referencing so a future date-only validation in this codebase doesn't reintroduce it a third time.

**Why recorded here, not just in the story file:** the CLI-over-UI call and the service-role/RLS-trigger interaction are both the kind of reasoning a future story revisiting Super Admin provisioning or `protect_self_managed_user_columns` would otherwise have to re-derive from scratch.

## 2026-08-04 — Payment notifications (`0046_payment_notifications.sql`): payment-keyed transport, direct `payments`-row identity, the automated-vs-manual `flagged` boundary, a new webhook failure path, and a trigger `security definer` correction — recorded during Story 6.3

**Decision 1 — a parallel, payment-keyed dispatch/delivery table pair, not a generalization of Story 6.2's subscription-keyed tables.** `private.notification_dispatches`/`private.notification_deliveries` (0045) are read-only precedent here, not widened: their unique key is `(subscription_id, notification_code)`, and `payments.subscription_id` is `NULL` for every manual "Record Payment" ledger entry (Story 4.3, by design) and is still `NULL` at the exact moment `complete_verified_payment()`'s first `UPDATE` sets `status = 'verified'` (it is only backfilled by that function's second, later `UPDATE`). `private.payment_notification_dispatches`/`private.payment_notification_deliveries` are structurally identical siblings, uniquely keyed by `(payment_id, notification_code)` instead — `payment_id` is always present and unique, so no nullable-either-column unique-index ambiguity is introduced.

**Decision 2 — dispatch identity is derived directly from `payments.gym_id`/`payments.member_id`, never by joining through `subscriptions`.** Both columns are `NOT NULL` on every payment row (`0005_payments.sql`), unlike `payments.subscription_id`. `private.send_payment_push_notification()` reads `gym_id`/`member_id` straight off the triggering `payments` row and joins `members → users` from there for the recipient/language — the same derivation Story 6.2 used via `subscriptions` would silently fail to dispatch for every manual ledger entry and for the pre-backfill instant of a webhook-verified payment.

**Decision 3 — `OLD.status = 'processing' → 'flagged'` (automated) is the entire mechanism that keeps N-05 distinct from `OLD.status = 'pending' → 'flagged'` (manual "Flag for Review").** No new column or enum value was added to `payments` to carry this distinction — Stories 4.2/4.3 already left the two cases starting from different `status` values purely as a side effect of their own RLS policy scoping (`gym_staff_verify_own_payments` in `0031_manual_payment_verification_queue.sql` only ever operates on `OLD.status = 'pending'`). `private.notify_payment_status_change()`'s N-05 condition is `TG_OP = 'UPDATE' AND NEW.status = 'flagged' AND OLD.status = 'processing'` — deliberately not a bare `NEW.status = 'flagged'` check, which would have incorrectly notified members on every internal staff review flag. This is PRD FR-075's "Payment webhook failure event" contract, and AC #3's silence requirement for manual flagging, resolved by the same signal.

**Decision 4 — `complete_flagged_payment()` is a new, previously-nonexistent automated failure path, and it changes already-shipped Story 4.4 reconciliation-job timing.** Before this story, `payments.status` had no automated failure transition at all — `supabase/functions/payment-webhook/index.ts`'s `event.status !== "verified"` branch was a pure no-op (logged, no write). `complete_flagged_payment(p_payment_id)` mirrors `complete_verified_payment()`'s exact trust boundary (`security definer`, `service_role`-only grant, `revoke ... from public`) and transitions `processing → flagged` only (`where status = 'processing'` is the idempotency guard for a retried webhook delivery). Consequence: a *promptly delivered* declined webhook now transitions its payment to `flagged` immediately, rather than being caught roughly ten minutes later by Story 4.4's `run_payment_reconciliation_job()` `stale_processing` check (`0032_payment_reconciliation_job.sql`). This is a deliberate, positive behavior change to that story's existing logic, not an accidental side effect — `stale_processing` still exists as the catch-all for any payment that never received a webhook delivery at all.

## 2026-08-03 — Subscription lifecycle notification transport (`0045_subscription_lifecycle_notifications.sql`): direct Expo routing, two-level idempotency, exact-date semantics, post-grace N-03, and receipt-based cleanup — recorded during Story 6.2

**Decision 1 — database-owned delivery routes directly to the Expo Push Service through `pg_net`.** `private.send_push_notification(subscription_id, notification_code)` derives the member user, preferred language, gym identity, reviewed message copy, and every registered Expo token from the subscription; callers cannot supply arbitrary recipients or content. It posts Expo-shaped JSON only to `https://exp.host/--/api/v2/push/send`. No new Edge Function and no direct FCM/APNs integration are introduced, preserving the architecture's two-Edge-Functions boundary.

**Decision 2 — idempotency is split between one logical dispatch and independent per-device deliveries.** `private.notification_dispatches` is uniquely keyed by `(subscription_id, notification_code)`, making each N-01/N-02/N-03 event a once-per-subscription-lifecycle fact. Renewals already create a new subscription row, so future renewal cycles naturally receive new IDs. `private.notification_deliveries` fans that event out once per stored token and records each push request, ticket, receipt request, terminal status, and error independently. A repeated lifecycle run returns at the logical-dispatch conflict without creating another network request; a no-token event is retained as `no_tokens` so its no-op outcome is both deterministic and observable.

**Decision 3 — N-01 and N-02 use exact-date/no-backfill semantics; lifecycle state still catches up.** N-01 is emitted only when an `active` row with `expiry_date = current_date + 7` actually transitions to `expiring_soon`. N-02 is emitted only at `expiry_date = current_date + 1`, after the normal catch-up transition step. A late job still advances a +6 (or later) row according to Story 3.1, but never retroactively sends a missed reminder. Idempotency is deliberately stronger than retry convenience in V1: terminal transport failures remain observable and are not automatically resent.

**Decision 4 — N-03 fires on the actual `expired` transition after grace, resolving a source conflict in favor of the story acceptance criterion.** PRD FR-075 summarizes N-03 as firing "on expiry date," while Story 6.2 AC #3 requires it when status transitions to `expired`. GymOS deliberately has a configurable grace period and preserves access/state through that period; therefore the story AC is the implementation contract. N-03 is dispatched only from IDs returned by the job's `UPDATE ... SET status = 'expired'` when `expiry_date + grace_period_days < current_date`. The exact equality boundary remains `grace_period`, and already-expired rows are never notified again.

**Decision 5 — an Expo push ticket is acceptance by Expo, not proof of device delivery.** The every-minute `notification_delivery_processor` correlates completed `pg_net` responses to individual delivery rows. An accepted ticket queues `https://exp.host/--/api/v2/push/getReceipts` and remains `receipt_pending`; only a successful receipt becomes `delivered`. HTTP/transport failures, malformed responses, ticket errors, and receipt errors are retained per delivery without aborting later rows.

**Decision 6 — stale-token removal reuses Story 6.1's cleanup primitive.** `DeviceNotRegistered` from either a ticket or receipt calls `private.cleanup_invalid_device_push_token(expo_push_token)` for that delivery's token and marks the delivery terminal. Other Expo errors retain the token, and no delivery response can select an unrelated token row. The transport ledgers and helpers remain in the non-exposed `private` schema with RLS enabled and no anon/authenticated access.

**Generated-type outcome:** a clean-schema `supabase gen types typescript --local` comparison produced no semantic change to `packages/types/src/database.ts`; the raw diff was line-ending-only (checked-in CRLF versus generated LF). The private tables/helpers are absent from generated public types as intended, so the file was not rewritten solely to churn line endings.

## 2026-08-02 — Coach Portal Member Detail & Session Notes (`0041_coach_portal_member_detail_session_notes.sql`): the FR-055-vs-AC#4 spec-tension resolution, a second RLS-blocking-its-own-helper fix, why writes stay RPC-only, and the `expiring_soon` amber-bar cut — recorded during Story 5.3

**Decision 1 — `private.is_own_coach_id(p_coach_id uuid)` is a second `SECURITY DEFINER`, RLS-bypassing `private`-schema helper, mirroring `private.is_assigned_coach()`'s (`0040`) exact shape but answering a different question: "is this `members.id` mine," not "am I assigned to this member."** The same class of bug `0040`'s Decision 1 documents recurs here in a new spot: a note's author is `session_notes.coach_id` (a `members.id`), and checking "is this note mine" means comparing it against the caller's own identity — which requires reading the caller's own row in `members` by `user_id`. A coach has *no* SELECT access to their own `members` row (`0040`'s narrowing of `gym_staff_read_own_members` excludes `coach`, and `coach_read_assigned_members` only covers *assigned members*, never the coach's own row) — so a plain correlated subquery written directly inside a `session_notes` RLS policy would silently return **false for every coach, always**, the identical no-error, wrong-empty-result failure mode `0040` already hit once. `private.is_own_coach_id()` gets the same explicit `revoke ... from public; grant ... to authenticated;` discipline as `private.is_assigned_coach()`.

**Decision 2 — the genuine spec tension between FR-055/Story 5.1 AC#2 ("previous coach's notes stay visible to Owner/Manager only, not the new coach") and this story's own AC#4 (read literally, implies a reassigned note is visible-but-uneditable) is resolved in FR-055's favor.** A coach's own `session_notes` SELECT is scoped to **currently-assigned member AND self-authored notes only** (`private.is_assigned_coach(member_id) and private.is_own_coach_id(coach_id)`), not "any note on an assigned member." Under this design, a reassigned member's prior notes never reach the new coach's query at all — a stronger, simpler guarantee than "visible but not editable," and it means the Coach Portal UI (`CoachMemberDetailPageClient.tsx`) never needs a per-note "is this mine" branch: every note a coach's own query ever returns is, by construction, editable by them. `manager_or_owner_read_own_session_notes` gives Owner/Manager the FR-055-required full-visibility data-layer access (mirroring `manager_or_owner_read_own_coach_assignments`, `0039`), even though no Owner/Manager-facing notes UI consumes it in this story — the same "RLS ahead of UI" precedent `coach_assignments` already set. `coach_portal_member_detail_session_notes.test.sql`'s reassignment regression test (seed a note under coach-1, reassign via `assign_coach()`, assert coach-2's own query returns zero rows for that member while Owner/Manager's returns the full history) is the one assertion that actually proves this design works, not just that the edit RPC rejects a non-owner — a wrong RLS policy here would fail silently with a plausible-looking wrong result set, exactly like `0040`'s own central bug.

**Decision 3 — `add_session_note()`/`edit_session_note()` are `SECURITY DEFINER` RPCs, not direct RLS INSERT/UPDATE policies, deliberately diverging from `refunds`' (`0033`) direct-RLS-`with check` pattern in favor of `assign_coach()`'s (`0039`) RPC pattern.** Both writes must resolve the caller's own `coach_id` *and* their currently-active `coach_assignments` row entirely server-side, never trusting a client-supplied id (the same "never let the client supply an id the server can independently derive" discipline `confirm_renewal`/`renew_subscription` already apply to dates and amounts). Resolving that inside a plain RLS `with check` clause would hit the identical RLS-blocking-its-own-helper problem this migration's SELECT policies work around, this time against `coach_assignments`, which a coach has zero direct SELECT access to at all (`0039`). No INSERT/UPDATE policy is added for `authenticated` on `session_notes` — the RPC is the only real write path, the same shape `coach_assignments` already established. `edit_session_note()`'s own `where ... and coach_id = v_coach_id` clause is AC #4's actual enforcement backstop: an edit attempt against a note that isn't the caller's own resolved `coach_id` matches zero rows and raises, regardless of what the client sends. **Code-review addendum (same day):** that `where` clause alone checked authorship only, not current assignment — weaker than `coach_read_own_session_notes`'s SELECT policy (Decision 2), so a coach could keep editing their own note forever even after being reassigned away from the member, via a direct RPC call bypassing the UI. Fixed by re-checking `private.is_assigned_coach(member_id)` inside `edit_session_note()` too, matching the SELECT policy's own two-part check exactly — edit access is now revoked the same moment visibility is. Covered by a new pgTAP regression test in section (e) of the test file, alongside the existing reassignment/FR-055 test.

**Decision 4 — the AD-15 mockup's amber info bar builds only the `expired` variant; the Flow 5 narrative's `expiring_soon` variant is deliberately not built.** EXPERIENCE.md's own AD-15 component spec (the literal, authoritative UI definition) defines only one variant, shown when the member's status is `expired`. Flow 5's narrative walkthrough shows a second, undocumented `expiring_soon` variant with different copy that appears nowhere in the component spec itself, and no AC in this story mentions an info bar at all. Treated the component spec as controlling over the illustrative narrative that drifted from it — no invented copy string to reconcile the two.

**Decision 5 — no audit log entry for adding or editing a session note.** FR-080's enumerated action-type list (manual payment entries, verifications, refunds, member deactivations, coach assignment changes, Super Admin escalations, pg_cron job failures) does not include session notes, unlike `assign_coach()`. Neither RPC calls `log_audit_event()`.

## 2026-08-02 — Coach Portal Assigned Member List (`0040_coach_portal_member_list_rls.sql`): why `private.is_assigned_coach()` is `SECURITY DEFINER`, the `ALTER POLICY` narrowing that closes Story 5.1's deferred gap, and two scope cuts — recorded during Story 5.2

**Decision 1 — `private.is_assigned_coach(p_member_id uuid)` is `SECURITY DEFINER`, deliberately deviating from `private.gym_id()`/`private.is_super_admin()`'s plain-`STABLE` shape (`0009`/`0010`).** Those two helpers only ever read the JWT via `auth.jwt()`, never a table — `private.is_assigned_coach()` is the first `private`-schema helper to read a table (`coach_assignments` joined to `members`), and doing so under the *calling coach's own RLS* would silently break: a naive correlated subquery written directly inside the new coach RLS policies (no `SECURITY DEFINER`) would return **zero rows for every coach, always**, because `coach_assignments` has exactly one SELECT policy (`manager_or_owner_read_own_coach_assignments`, `0039`), scoped to `manager`/`owner` only — a coach session's own read of that table, even nested inside another policy's `USING` clause, returns nothing regardless of whether a real assignment exists, and the same problem re-hits the nested `members coach_m` read once `gym_staff_read_own_members` is narrowed below. ## 2026-08-02 — Coach Member Assignment (`0039_coach_member_assignment.sql`): grant shape, the coach-account-creation gap, the no-unassign cut, and the inherited Receptionist/Coach read scope — recorded during Story 5.1

**Decision 1 — `coach_assignments` gets the standard full-CRUD grant to `authenticated` (mirroring `job_runs`, `0008`), not a SELECT-only grant, even though `assign_coach()` is the only path that ever actually writes to it.** Every deny-all table in this schema (see `0002`-`0008`'s own GRANT comments) grants full CRUD at the table level and relies on RLS having zero write policies to block writes. ## 2026-08-01 — Member App Payment History & Receipt Detail (`0038_member_app_payment_history_receipt_detail.sql`): two new member-self-read RLS policies, why actor-name resolution stayed RLS-not-RPC, and `subscription_id`'s null-for-most-rows shape — recorded during Story 4.9

**Decision 1 — `payments` and `members` both needed a new member-self-read RLS policy, closing a gap every sibling table already had closed ahead of time.** `subscriptions` (`0018`), `plans` (`0017`), and `attendance_events` (`0026`) were all given a member-self-access clause the moment a member-facing screen first needed to read them (Story 2.7/3.10 for the first two, Story 3.7 for the third) — `payments` never got the same treatment, because no story before this one needed a member to read their own payment rows. `member_read_own_payments` closes that gap with the exact same shape as `member_read_own_attendance_events` (`m.user_id = auth.uid()` via an `exists` subquery against `members`, not a raw `member_id = auth.uid()` comparison — `payments.member_id` is a `members.id`, a different UUID from the auth user id). The second gap is narrower and easy to miss: a member session couldn't read *any* other `members` row at all, including a staff member's, which blocks resolving the receipt's "Recorded by" field (`payments.actor_id` is a `users.id`, not FK-joinable to `members` — the same non-embeddable shape `listPendingPayments()` in `apps/dashboard/services/payments.ts` already works around with a second batched query). `member_read_gym_staff_members` grants a member session read access to `members` rows scoped to `role in ('owner','manager','receptionist')` only — the exact role list `gym_staff_insert_own_payments`'s (`0030`) `with check` restricts `payments.actor_id` to, since those are the only 3 roles a payment's actor can ever resolve to. This is a deliberate, narrow broadening (a member can now see a staff name/phone/email/dob in their own gym) — never another member's row, never a coach's row, and it doesn't widen `self_read_own_membership` (`0013`) or `gym_staff_read_own_members` (`0018`), both of which coexist with it unchanged. One implementation snag worth recording: `members.role` is the `member_role` enum, not `text` — `role = any(array['owner','manager','receptionist'])` alone fails at migration time with `operator does not exist: member_role = text`; the array literal needs an explicit `::member_role[]` cast.

**Decision 2 — actor-name resolution for the receipt is a second RLS-scoped `.select()`, not a `SECURITY DEFINER` RPC.** Every read anywhere in `apps/mobile` to date goes through plain RLS-scoped queries — no mobile screen has ever called a read-RPC. Wrapping receipt assembly (payment row + actor-name lookup) in a `SECURITY DEFINER` function would have been the first one, a bigger precedent-setting decision than a narrow, precedented RLS broadening modeled directly on an existing shape (`gym_staff_read_own_members`). Given the two-query approach is already how the dashboard's own `listPendingPayments()` solves the identical actor-name problem, extending that same pattern to a member session via one new policy was the smaller, more consistent change. `getPaymentReceipt()` (`apps/mobile/src/services/payments.ts`) does the member/gym lookup, the payment-row fetch, and — only when `actor_id` is non-null — the second `members` lookup, all as plain client-side `.select()` calls.

**Decision 3 — `payments.subscription_id` being `null` on most real payment rows is expected behavior, not a bug the UI should "fix" or special-case as an error.** Verified against every INSERT site: `recordManualPayment()` (Story 4.3) never sets it — manual cash/bank-transfer/manual-momo payments stay `subscription_id = null` forever, even once verified. `initiatePayment()` (Story 4.2) also omits it at insert; it's only backfilled by `complete_verified_payment()` (`0030`) once a webhook confirms and creates a renewal subscription, so an online payment sitting in `processing` also has `subscription_id = null`. Only `confirm_renewal()`-driven payments (Stories 4.7/4.8's Renewal Modal / Subscriptions page "Renew" flow) set it at insert time. Both the Payments-tab list row and the MA-14 receipt screen render a `planUnavailable` fallback string for a `null` embedded plan name — never `null`/`undefined`/blank, and never a load error. Flagging this here so a future story doesn't "fix" it as a bug: it's the majority case, not an edge case.

**Why recorded here, not just in the story file:** same category as every other entry in this log — two new authorization-surface broadenings (one of them a cross-role read on a PII-bearing table) and a data-shape fact that looks like a bug at first glance are exactly the kind of decisions a future reader shouldn't have to re-derive from the migration diff or rediscover by querying production data.

## 2026-08-01 — Subscriptions Page & Manual Renewal (`0037_subscriptions_page_manual_renewal.sql`): the codebase's first `create view`, `confirm_renewal()`'s `p_backdate` flag design, the "Last Payment" column cut, and the inherited Receptionist/Coach read gap — recorded during Story 4.8

**Decision 1 — `subscriptions_current` is a new `security_invoker` view, the first `create view` anywhere in this codebase.** Every prior story used raw tables + RLS + `SECURITY DEFINER` RPCs. PostgREST cannot sort top-level rows by an embedded child resource's column, and `listMembers()`'s existing embed pattern (`members` → `subscriptions` → `plans`) reads subscription status/expiry as an *embedded* child — structurally unable to satisfy AC #1's "sortable by member name, status, and expiry date" requirement. A flat view sidesteps this entirely: one row per member's most-recent subscription, with `member_name`/`status`/`expiry_date` all plain top-level columns ordinary PostgREST `.order()` can target directly. `with (security_invoker = true)` is not cosmetic — it is the entire tenant-isolation guarantee for this view. Without it, the view runs with its owner's (the migration role's) privileges and bypasses every RLS policy on `subscriptions`/`members`/`plans`, leaking cross-gym data to any authenticated caller. Postgres 17 (this project's `major_version`) has supported `security_invoker` since PG15. `listSubscriptions()`/`exportSubscriptionsCsv()` still add an explicit `.eq("gym_id", gymId)` as defense-in-depth on top of it, matching every other service function's own discipline of never relying on RLS alone. `subscriptions_page_manual_renewal.test.sql`'s highest-priority assertion is a direct cross-gym query against this view under a gym-B-scoped role, proving `security_invoker` is actually enforcing RLS through the view and not silently bypassing it.

**Decision 2 — `confirm_renewal()` gains `p_backdate boolean default false`, a flag, not a client-supplied date.** Epics.md's AC #2 says back-dating goes to "the member's original expiry date" — a fixed, server-known value. When `p_backdate` is true, the function looks up the *existing* subscription's own `expiry_date` server-side and uses that as the new row's `start_date`; the client never sends a date at all. This mirrors `0022`/`0035`'s own established precedent of never trusting a client-supplied date (both `renew_subscription()` and `confirm_renewal()` already compute `current_date` server-side) and closes off any date-tampering surface a free-form date field would otherwise open. Back-dating is only valid when the member's current status is `grace_period` or `expired` **and** their existing subscription has a non-null `expiry_date` — a `pay_per_session` plan's subscription has `expiry_date = null` by `0018`'s own trigger, so back-dating it is meaningless and is rejected with a raise, not silently ignored. Postgres requires drop+recreate for this signature change (same reason `0036` had to drop+recreate `0035`'s version) — the role/tenant/deactivated/reason guards are otherwise byte-for-byte identical to `0036`'s version.

**Decision 3 — "Last Payment" (AD-08's own mockup column) is cut, not built.** None of epics.md's 3 literal ACs for this story mention it, and building it would require a second per-member `payments` lookup with no existing precedent to embed off `subscriptions_current` (`payments.subscription_id` is only populated for renewal-panel payments). Matches Stories 4.4/4.5/4.6's own repeated "don't build UI beyond what's asked" precedent. The Actions column instead shows "Renew" for any non-`active` status (matching the UX mockup's literal rule) — the back-date checkbox itself is the only piece narrowed further, to `grace_period`/`expired` rows with a non-null `expiryDate`, since an `expiring_soon` member's expiry date is in the future and can't be back-dated to.

**Decision 4 — the pre-existing Receptionist/Coach read-access gap on this Manager/Owner-only page is inherited, not introduced or fixed here.** `gym_staff_read_own_subscriptions` (`0018`) grants `owner|manager|receptionist|coach` read access — broader than this page's Manager/Owner-only intent (Sidebar hides the `/subscriptions` link from Receptionist/Coach, but a direct navigation still gets full read data). This is the exact same shape of gap `plans/page.tsx`'s and `members/page.tsx`'s own doc comments already document and accept by design (Sidebar hides it, RLS backstops writes, reads are intentionally left broader) — `subscriptions/page.tsx`'s own doc comment states this precedent identically rather than adding the app's first route-level role guard, which would be inconsistent with every sibling page.

**Decision 5 — `subscriptions_current`'s cross-gym tenant-isolation assertion lives only in `subscriptions_page_manual_renewal.test.sql`, not duplicated into `rls_tenant_isolation.test.sql`.** Task 10 asked to check that file's structure first before assuming it was the canonical home for this assertion. It isn't: `rls_tenant_isolation.test.sql` is a single-session sweep asserting every non-feature-specific table stays deny-all for one authenticated caller, not a two-gym cross-tenant comparison — every per-feature cross-gym check in this codebase (Story 3.9's `attendance_events`, Story 4.4's `payment_discrepancies`, etc.) already lives in that feature's own test file, matching this story's own choice.

**Why recorded here, not just in the story file:** same category as every other entry in this log — the first-ever `create view` in this codebase (a new authorization-surface *pattern*, not just a new feature) and a client-date-tampering-surface design choice on a live renewal RPC are exactly the kind of decisions a future reader (reviewer, or the next story adding a second view) shouldn't have to re-derive from the migration diff.

## 2026-08-01 — `payment_method`'s closed 5-value Postgres enum (`mtn_momo`/`orange_money`/`cash`/`bank_transfer`/`manual_momo`) opened to `text` (`0036_open_payment_method.sql`), removing the implicit Cameroon-only lock on TaraMoney-routed payments — user direction: "we shall rapidly move out of Cameroon"

**Decision — `payments.method` and `confirm_renewal()`'s `p_method` parameter are widened from the closed `payment_method` enum to open `text`; the enum type is dropped.** A full-repo grep confirmed these were the only two objects referencing the enum. `initiatePaymentSchema.method` (`packages/types/src/schemas/payment.ts`) is similarly widened from `z.enum(["mtn_momo", "orange_money"])` to an open, length-bounded string. `recordManualPaymentSchema`/`confirmRenewalSchema`'s 3-value manual-methods enum (cash/bank_transfer/manual_momo) is **not** touched — those represent genuinely distinct payment instruments a receptionist chooses in person, not a TaraMoney country/operator restriction.

Now normalizes any other operator string to a lowercase snake_case token instead of discarding it. This mapped value is currently unused downstream (`NormalizedPaymentEvent.vendor` has no consumer in `payment-webhook/index.ts` yet — confirmed via grep), so this is forward-looking hygiene, not a behavior change today.

**Explicitly out of scope, per user direction:** currency. `payments.currency`/`plans.currency` still default to `'XAF'`, and dashboard UI still formats amounts as XAF-only. TaraMoney's non-Cameroon markets (Wave) use XOF, not XAF — supporting a real non-XAF transaction would need dynamic currency handling across pricing, formatting, and likely a country/currency selection UI. Not built here; flagged for whenever an actual non-Cameroon market is being onboarded.

**Why recorded here, not just in the migration comment:** a schema/scope decision on a live payment integration a future reader (reviewer, or whoever eventually onboards a non-Cameroon gym) shouldn't have to re-derive from the migration diff — especially the "network is never actually sent to TaraMoney" finding, which is easy to miss and is the entire reason this change was safe to make without touching the provider integration itself.

## 2026-08-01 — Inline Renewal Panel (`0035_inline_renewal_panel.sql`): one atomic `confirm_renewal()` instead of two RPC calls, a directly-`verified` payment, and three scope cuts from the UX mockup — recorded during Story 4.7

Two separate RPC calls would create a real correctness gap under retry: if the first call (payment) succeeds and the second (subscription reset) fails, or vice versa, a retry could create a second pending payment row or leave a paid member unrenewed, with no unique constraint anywhere to catch it (unlike the provider-webhook path, which has `provider_transaction_ref`). `confirm_renewal()` self-checks the caller's role/tenant exactly like `renew_subscription()` and `check_in()` already do — an established pattern, not a new one.

A renewal-panel payment has no such gap — the same receptionist confirming the renewal is the one who just collected the cash in front of the member. `renew_subscription()`'s own AC also requires the subscription to reset to active *immediately* on confirm, which would be incoherent if the backing payment could still be flagged/rejected later. Safe because `confirm_renewal()` is `SECURITY DEFINER`, owned by the migration role, and bypasses RLS entirely — exactly like `renew_subscription()` already bypasses `manager_or_owner_insert_own_subscriptions`.

This is the one literal AC #2 clause this story cannot fulfill; it's a pre-existing sequencing fact (Epic 6 scheduled after Epic 4), not a defect introduced here.

Matches Story 4.6's own "documented deviation from the UX mockup" precedent for scope cuts.

**Why recorded here, not just in the story file:** same category as every other entry in this log — schema/scope decisions a future reader (reviewer, or Story 4.8 wiring the same `InlineRenewalPanel` into the Subscriptions page) shouldn't have to re-derive from the migration diff.

## 2026-08-01 — Real-Time Front-Desk Alert (`0034_real_time_front_desk_alert.sql`): `check_in()`'s throw→null contract change, a new `front_desk_alerts` table, first use of Supabase Realtime + TanStack Query, and the `[Renew]`/Overview scope cut — recorded during Story 4.6

**Decision 1 — `check_in()` no longer `raise exception`s for an expired/no-subscription check-in; it inserts the red alert row and returns `null` instead.** A `raise exception` with no enclosing `exception when ... end` block unwinds the *entire* transaction for a `SECURITY DEFINER` RPC call, including any row inserted earlier in the same function call — there is no `dblink`/autonomous-transaction extension enabled in this project, so the alert row and the deny-outcome could not both survive a thrown exception in the same call. `check_in()` now does a clean, non-error `return null;` (legal for a non-`setof` composite-returning function) after inserting the alert. This is a breaking change to an established client contract: `apps/mobile/src/services/checkin.ts#recordCheckIn` previously detected the expired case by matching the thrown error's message text; it now detects a null `data` on an otherwise-successful RPC call instead. `supabase/tests/check_in_one_open_session_enforcement.test.sql`'s three `throws_like(..., '%subscription is expired%', ...)` assertions were rewritten to assert a null return.

**Decision 2 — `front_desk_alerts` is a new, dedicated table, not a repurposing of `attendance_events`.** `attendance_events` has no row at all for a rejected (expired) check-in today, and never should — a denied entry did not happen, matching the existing "entry denied" semantics `check_in_one_open_session_enforcement.test.sql` already asserted before this story. Alerts also need `dismissed_at`/`dismissed_by`, which don't belong on a pure attendance ledger. Same "own table, don't overload an existing one" precedent as `payment_discrepancies` (4.4) and `refunds` (4.5).

**Decision 3 — this is the first story in the codebase to use Supabase Realtime (`supabase_realtime` publication, `postgres_changes` subscriptions) and TanStack Query (`@tanstack/react-query`).** architecture.md (lines 141, 176) names this exact combination as the intended pattern for the front-desk alert panel. Realtime security is RLS-driven, not filter-driven — the subscription's own `filter: gym_id=eq.${gymId}` is an efficiency optimization only; `gym_staff_read_own_front_desk_alerts` is the real, server-enforced gate. A mandatory polling degrade path (5s interval, `queryClient.invalidateQueries`) covers the case where the Realtime channel drops after connecting once, per architecture's explicit requirement that a retention-critical alert failing silently is worse than no alert.

**Decision 4 — deliberate scope cut: no `[Renew]` button on the alert panel, and no Overview stat cards/tables.** The UX mockup shows a `[Renew]` button on each alert row, but its target (`InlineRenewalPanel`) is Story 4.7 — rendering a button with nowhere to go was rejected in favor of building only what has a destination, matching Stories 4.4/4.5's own "don't build UI beyond what's asked" precedent. Only the `[✕]` dismiss action ships. Similarly, Overview (`AD-02`) gains only the alert panel — its stat cards and "Currently Checked-In"/"Expiring This Week" tables remain the deliberate stub they already were; no AC in the FR Coverage Map assigns them to 4.6.

**Why recorded here, not just in the story file:** same category as every other entry in this log — schema/scope/architecture decisions a future reader (reviewer or the next story touching front-desk alerts, renewal, or Realtime elsewhere in the app) shouldn't have to re-derive from the migration diff.

## 2026-08-01 — Refund Recording (`0033_refund_recording.sql`): a new `refunds` table rather than a `payments.status` mutation, and "one refund per payment" as the V1 ledger shape — recorded during Story 4.5

**Decision 1 — refunds live in a brand-new `refunds` table, entirely separate from `payments`.** `payment_status` (the enum) gets no `'refunded'` value. This repeats the exact "own table, don't mutate `payments.status`" precedent `0032`'s `payment_discrepancies` already established (Story 4.4) — a refund is a separate ledger fact, not a change to what was actually paid. Unlike `payment_discrepancies.gym_id` (nullable — some discrepancies are gym-unattributable by construction), `refunds.gym_id` is **not null**: a refund always targets a real, already-`verified` payment, so a gym is always resolvable at insert time — no "unattributable" case exists for refunds.

**Decision 2 — `refunds.payment_id` is unique: at most one refund per payment in V1.** This is a record-a-dispute ledger, not a partial/multiple-refund system — epics.md's Story 4.5 user story only asks that a dispute be tracked, not that partial or repeated refunds against the same payment be supported. A second refund attempt against an already-refunded payment is rejected by the unique constraint, surfaced as a friendly conflict error rather than a special-cased business rule.

**Decision 3 — the INSERT policy's `exists` subquery explicitly qualifies `refunds.gym_id`/`refunds.amount`, diverging from the story file's own literal Task 1 SQL block, which left both bare.** `payments` (the subquery's own correlated table) has columns named `gym_id` and `amount` too — standard SQL unqualified-name resolution binds a bare reference to the *innermost* scope containing a match, which is the subquery's own `payments p`, not the outer `refunds` row under check. The story's literal SQL silently reduced both conditions to a vacuous `p.col = p.col` self-comparison. `refund_recording.test.sql`'s own pgTAP coverage caught this directly: an over-amount refund (amount > the original payment's amount) was accepted, not rejected. The cross-gym half of the same bug happened to still deny correctly, but only as a side effect of `payments`' own `gym_staff_read_own_payments` SELECT policy already scoping the subquery to the caller's own gym — an accidental save, not a real gate; the amount cap had no equivalent backup and was genuinely bypassable pre-fix. Fixed by qualifying both (`refunds.gym_id`, `refunds.amount`) explicitly, matching the qualification Postgres itself already auto-injects for `payment_id` (`refunds.payment_id`, confirmed via `pg_get_expr` on the compiled policy — `payments` has no `payment_id` column, so that one bare reference was never ambiguous).

**Why recorded here, not just in the story file:** same category as Story 4.4's own entries — schema/scope decisions a future reader (reviewer or the next story touching refunds) shouldn't have to re-derive from the migration diff. Decision 3 specifically is worth remembering for any future RLS policy whose `exists`/correlated-subquery joins a table sharing column names with the table being checked -- always qualify the outer row's own columns with the target table's name inside the subquery, don't rely on bare references.

## 2026-08-01 — Payment Reconciliation code review: webhook-before-ref-persisted race accepted as a V1 gap — recorded during code review of Story 4.4

## 2026-07-31 — Manual Payment Entry & Verification Queue (`0031_manual_payment_verification_queue.sql`): AD-10's Date field dropped in favor of epics.md/FR-038, and the INSERT-policy hardening's safety alongside Story 4.2's existing path — recorded during Story 4.3

**Decision 2 — `gym_staff_insert_own_payments` (0030) is dropped and recreated with a `status` check, rather than edited in place or left alone.** `0030`'s version had no `status` constraint in its `with check` at all, meaning a gym-staff session could INSERT a payment row directly with `status = 'verified'`, bypassing the Verification Queue entirely — an authorization gap this story's own queue would otherwise make exploitable in a new way (a fabricated already-verified payment). **Implementation note (enum-vs-text array comparison):** both new/modified policies compare the `payment_status` enum column against a Postgres array literal (`array['verified', 'flagged']`, `array['pending', 'processing']`). Postgres infers an untyped array literal as `text[]`, and `payment_status = text` has no operator — the migration failed on the first `supabase db reset` with `ERROR: operator does not exist: payment_status = text` until each literal was cast explicitly (`::payment_status[]`). Worth remembering for any future policy comparing an enum column against an array literal.

**Why recorded here, not just in the story file:** same category as Story 4.2's own three schema-decision entries above — decisions that resolve a real conflict between the UX mockup and the literal spec/schema, plus a security-relevant policy-hardening rationale a future reader shouldn't have to re-derive from the migration diff alone.

## 2026-07-31 — Real payment orchestration (`0030_payment_initiation_and_renewal.sql`): schema decisions, and a real TaraMoney round-trip that passed in full — recorded during Story 4.2

**Decision 1 — `payment-webhook`'s internal routing is extended (initiate + receive), not a second Edge Function.** architecture.md reserves Edge Functions for "the webhook receiver only." Rather than add a second/third function, this story adds a `POST /payment-webhook/initiate/<providerKey>` route inside the same function, dispatched on URL path shape (`.../initiate/<key>` vs. the existing `.../<key>` receive route). The initiate route is the only place `apps/dashboard/services/payments.ts`'s `initiatePayment` ever talks to TaraMoney — Server Actions call it over HTTP (`supabase.functions.invoke`), never TaraMoney directly, keeping exactly one implementation of TaraMoney's real request/response shape (Deno-only code, cannot run in Next.js). The initiate route gets no separate JWT check — `verify_jwt = false` is required for the public receive route anyway, and the real authorization boundary is that the caller's own session already had to pass the `payments` INSERT RLS policy (Decision 3 below) before the Edge Function is ever called with a real, `processing`, not-yet-provider-linked `paymentId`.

**Decision 2 — `complete_verified_payment()` is a new function, deliberately not a call into `renew_subscription()` (`0022`, Story 3.2).** They serve different callers with different trust boundaries: `renew_subscription()` requires a real authenticated staff JWT and a mandatory human-entered reason; `complete_verified_payment()` is `service_role`-only (revoked from `public`/`authenticated`), callable only from the webhook's service-role context, with no human reason and no JWT to check. ## 2026-07-18 — Correction: `pg_cron` scheduled jobs run as `postgres`, not `service_role` — recorded during Story 3.1's code review

**Decision/correction:** `supabase/tests/audit_log_immutable.test.sql` (Story 1.4) contains a comment asserting "the actual production system-caller (pg_cron runs as service_role)". Story 3.1 is the first real `pg_cron` job this project has ever built, and its code review (Acceptance Auditor + Edge Case Hunter layers) surfaced this as a potential AC #4-breaking bug — if true, `run_subscription_lifecycle_job()`'s `revoke execute ... from public` (with no grant to `service_role`) would make every real nightly invocation fail with "permission denied" before the function body ever runs, silently defeating the whole feature.

**Verified false, for this project's actual setup.** Two independent lines of evidence: (1) direct query against the local instance — `select username from cron.job` after registering the job via a migration returns `postgres`, matching pg_cron's own documented behavior (confirmed against AWS RDS, Azure, and the upstream `citusdata/pg_cron` docs): a scheduled job executes as whichever role called `cron.schedule()`, with no special role substitution; (2) Supabase applies migrations — both locally and in production — as `postgres`, which is also a superuser and therefore bypasses the `revoke ... from public` regardless. The "service_role" reference in the Supabase ecosystem is a different, unrelated mechanism: a `pg_cron` job that calls an Edge Function over HTTP via `pg_net` typically authenticates that HTTP call with a `service_role` JWT bearer token — it does not mean the SQL/PL/pgSQL execution context itself runs as a Postgres role named `service_role`. Story 3.1's job calls a plain SQL function directly (no HTTP/`pg_net` hop), so that pattern doesn't even apply here.

**Why this is recorded here, not just fixed silently:** the incorrect assumption predates any real `pg_cron` job in this codebase (Story 1.4 wrote it speculatively, in anticipation of Epic 3) and will otherwise keep getting cited as precedent by the two remaining `pg_cron` jobs this project's architecture calls for (payment reconciliation, check-in auto-timeout — architecture.md's "three independent `pg_cron` jobs" decision). Whoever builds those should grant `EXECUTE` the same way Story 3.1 does (no grant needed beyond the implicit superuser bypass), not add an unnecessary `service_role` grant based on the older, unverified comment. `audit_log_immutable.test.sql`'s own test logic is unaffected by this correction — it uses `service_role` there only to simulate a session-less system caller for `log_audit_event()`, a reasonable and still-valid technique independent of what role `pg_cron` itself actually runs as.

## 2026-07-15 — `enable_signup=true` creates unconfirmed `public.users` rows before phone verification — accepted risk, not fixed here, recorded during Story 2.1 code review

**Finding:** Story 2.1's `[auth.sms] enable_signup: false → true` (needed — FR-002 requires phone-based registration) combined with `enable_confirmations: false` (unchanged) means calling `POST /auth/v1/otp` for a brand-new phone number creates a real `auth.users` row immediately, before the OTP is ever verified. `supabase/migrations/0003_members_and_users.sql`'s `handle_new_user()` trigger (`SECURITY DEFINER`, no `WHEN` clause) unconditionally inserts a corresponding `public.users` row on that same event — so an unconfirmed phone number gets a real row in `public.users`, not just an internal `auth.users` artifact.

**What this is NOT:** an authentication bypass. No session or access token is ever issued from `/otp` alone (confirmed via this story's own real testing — `/otp` returns only `{}`; tokens are issued only by `/verify`, which requires the actual code sent to the real phone). So the practical risk is narrower than "unverified accounts are usable" — it's phone-number squatting / unconfirmed-row accumulation (someone repeatedly calling `/otp` for numbers they don't own), not account takeover.

**Existing mitigation, not new:** `config.toml`'s pre-existing rate limits (`[auth.rate_limit] sms_sent = 30`/hour, `sign_in_sign_ups = 30`/5min, `token_verifications = 30`/5min) already bound how many such rows one IP can create.

**Decision — accepted as-is, not modified in this story.** `handle_new_user()` belongs to Story 1.3 (already shipped, reviewed, in Epic 1) — adding a `WHEN phone_confirmed_at IS NOT NULL`-style guard would be a real schema change to that migration, out of proportion for a code-review fix on Story 2.1 and out of Story 2.1's own scope. Flagged here for whoever builds Story 2.6 (real member onboarding) to consider hardening — e.g. a periodic cleanup of unconfirmed rows past some age, or the `WHEN` guard — if abuse in practice ever exceeds what the existing rate limits bound.

## 2026-07-10 — Bilingual (EN/FR) Platform Foundation: i18n architecture, users self-service RLS, pnpm/eslint-config-next toolchain fix, recorded during Story 1.10

**Decision 1 — `react-i18next` + static locale-file imports, no dynamic per-request backend.** The story initially specified `i18next-resources-to-backend` for dynamic per-locale loading, but with exactly two known locales (`en`/`fr`, tiny JSON files), both `lib/i18n/get-server-translation.ts` (server) and `lib/i18n/client-provider.tsx` (client) just statically import both locales' JSON and merge them into one `translation` namespace resource bundle at module load — synchronous, no async fetch, and critically lets the Sidebar/top-nav toggle call `i18n.changeLanguage()` with both locales already preloaded (no missing-string flash while a second locale loads). The `i18next-resources-to-backend` dependency was removed from both apps' `package.json` after being added — unused complexity for a fixed 2-locale set.

**Decision 2 — `users` gains `self_read_own_user`/`self_update_own_language` RLS policies + a `protect_self_managed_user_columns` `BEFORE UPDATE` trigger** (`0015_users_self_service_language_preference.sql`), mirroring Story 1.9's `protect_super_admin_only_gym_columns` pattern exactly: RLS is row-level only, and the table-wide `grant update on users to authenticated` (`0003_members_and_users.sql`) means the new self-update policy alone would let a session self-elevate `is_super_admin` or change its own `phone` (FR-023 requires admin intervention) via a raw UPDATE bypassing `updateLanguagePreference`'s single-column write. The trigger pins `phone`/`is_super_admin`/`display_name`/`created_at` back to `OLD` whenever `auth.uid() = new.id`, so a self-update can only ever change `preferred_language`. Unlike `0014`'s sibling trigger (flagged in Story 1.9's review for an unneeded `security definer`), this one is correctly declared without it from the start. `rls_tenant_isolation.test.sql`'s pre-existing "users: 0 rows, no business policy yet" assertion needed updating to "exactly 1 row — their own" — the same class of update Story 1.9 hit with `tiers_and_gym_lifecycle_rls.test.sql`.

**Decision 3 — locale resolution is a single primitive (`getRequestLocale()`, per app) with no cookie.** Priority: (1) an authenticated session's live `users.preferred_language` (a fresh DB read every call — not JWT-claims-cached, since the auth hook doesn't carry it and caching would delay a language change until token refresh), (2) the request's `Accept-Language` header, (3) English. No locale cookie was introduced: the authenticated case re-reads `users.preferred_language` per request (matching `session.ts`'s existing looseness re-deriving `gymName`/`memberName` per request rather than caching), and the unauthenticated case (login, forgot-password, etc.) has no documented language-selection UI in EXPERIENCE.md, so `Accept-Language`-only resolution is sufficient there.

This was deliberately chosen over parameter-threading, which would have touched every Server Action's signature in both apps for no benefit.

**Decision 5 — Zod schema validation messages (`packages/types/src/schemas/*.ts`) are explicitly out of this story's localization scope.** `packages/types` has no ESLint config and no `lint` script (confirmed: Turborepo's `lint` task silently skips it), so the new `i18next/no-literal-string` CI gate never reaches those files by construction — not via a special exclusion rule. Localizing Zod's own error-message strings needs a broader pattern (locale-aware Zod error maps) disproportionate to this foundation story; flagged as a known gap rather than silently expanded into.

**Decision 6 — Confirmed-dead Supabase-starter demo/tutorial scaffolding in `apps/super-admin` (`app/page.tsx`, `app/protected/**`, `components/tutorial/**`, and several unused starter components) is excluded from the ESLint config entirely** (a standalone `{ ignores }` flat-config object, not just from the i18next rule), rather than translating template marketing copy that isn't gym_os product surface. Verified dead by grep: nothing in the real `(admin)`/`auth` route trees imports any of these files, and their redirect targets (`/protected`) don't exist as real routes. `apps/dashboard` has no equivalent leftover scaffolding (already cleaned up by Story 1.1/1.8).

**Decision 7 — `next/core-web-vitals`/`next/typescript` are imported directly from `eslint-config-next`'s native flat-config exports, not through `FlatCompat.extends(...)`.** This is the first story to actually run `pnpm lint` (confirmed: `.github/workflows/ci.yml` never invoked it before, and no prior story's Dev Notes mention running it). The pre-existing `FlatCompat`-based `eslint.config.mjs` (from Story 1.1's `create-next-app` scaffold) crashes with `TypeError: Converting circular structure to JSON` against `eslint-config-next@16.2.10`'s modern self-referencing flat-config plugin objects — reproduced identically with zero i18n-related config present, confirming it predates and is unrelated to this story. ## 2026-07-10 — Gym Branding & Operational Settings: owner write-path, gym-logos bucket, column-level protection gap, recorded during Story 1.9

**Decision 1 — `owner_update_own_gym` closes the write-path gap `0011_super_admin_tier_gym_lifecycle.sql` explicitly deferred** ("owner/manager gym-settings edits (FR-069) are Story 1.9's job on a different table scope"). Migration `0014_gym_settings_owner_access.sql` adds one explicit, role-scoped RLS UPDATE policy on `gyms` (`id = private.gym_id() and app_role = 'owner'`), matching every prior story's discipline of per-action policies, never `FOR ALL`. No new SELECT policy was needed — `"read own gym"` (`0009_auth_hook_gym_claims.sql`) already exposes every settings column.

**Decision 2 — a `protect_super_admin_only_gym_columns` BEFORE UPDATE trigger closes a column-level gap the RLS policy alone leaves open.** RLS is row-level, not column-level: `owner_update_own_gym` authorizes an owner to UPDATE their own gym row, full stop — nothing in a `USING`/`WITH CHECK` clause can say "except this column." Left alone, an owner could flip `status`/`tier_id`/`member_cap_override` (all Super Admin-exclusive lifecycle/tier controls, Story 1.6) via a raw UPDATE bypassing the app's own `updateGymSettings` column allow-list. Column-level Postgres `GRANT UPDATE (cols)` can't fix this either: Super Admin and Owner sessions both run as the same `authenticated` Postgres role (the JWT's `role` claim, distinct from `app_role`, is what actually drives `SET ROLE`), so a grant restriction would bind to that shared role, not to `app_role`. The trigger is the only mechanism that can key off `app_role` per-statement: for any non-`super_admin` session, it silently pins `status`/`tier_id`/`member_cap_override` back to their prior values before the row is written, rather than rejecting the whole UPDATE. Caught by running the full `supabase test db` regression suite (per this project's own standing practice): `tiers_and_gym_lifecycle_rls.test.sql`'s pre-existing "owner cannot UPDATE their own gym" assertion (written when no owner UPDATE policy on `gyms` existed at all) needed updating to reflect the new, correct behavior — the row is now matched/returned (owner UPDATE succeeds at the row level), but the `status` column itself stays unchanged (protected by the trigger). Updated, not worked around.

**Decision 3 — `gym-logos` is a `public = true` Storage bucket, not a private one behind signed URLs.** The Member Mobile App's 24h branding cache (FR-011/012) reads the logo unauthenticated, and V1 has no signed-URL refresh mechanism to build instead (matches FR-013's "full theme systems out of V1 scope" discipline). `storage.objects` gets a full INSERT/SELECT/UPDATE/DELETE RLS policy set (owner, own-gym-folder-scoped via `(storage.foldername(name))[1] = private.gym_id()::text`) — **the SELECT policy was not optional**, despite the initial assumption during story creation that the bucket's own `public=true` setting (which does serve unauthenticated reads via the Storage HTTP API, independent of RLS) meant no SELECT policy was needed for anything. That assumption held for reads, but broke for `uploadGymLogo`'s own `upsert: true` write path: Storage implements upsert as `INSERT ... ON CONFLICT (bucket_id, name) DO UPDATE`, and Postgres's RLS enforcement for that statement shape requires a SELECT policy to resolve the conflict target's visibility. Confirmed hands-on against the real local Storage HTTP API during Task 7's manual verification: a plain INSERT (no `ON CONFLICT`) succeeded with only INSERT/UPDATE policies in place, but the identical write with `x-upsert: true` failed with "new row violates row-level security policy" — reproducible even for a brand-new path with no actual conflicting row. Adding `owner_select_own_gym_logo` (same owner/own-gym-folder scope as the others) fixed it. This is a real, general Postgres RLS + `ON CONFLICT DO UPDATE` gotcha, not specific to Supabase Storage — any future `upsert: true` Storage write against an RLS-protected bucket needs the same SELECT policy, or the upsert will fail even when the underlying INSERT/UPDATE policies are individually correct. `gym_settings_rls.test.sql`'s existence checks still use `reset role` (bypassing RLS entirely, matching `audit_log_immutable.test.sql`'s pattern) rather than relying on the inserting session's own now-available SELECT visibility, since that's the simplest, most direct check.

**Decision 4 — the Timezone field ships a small curated V1 list (Africa/Douala, Africa/Lagos, Africa/Bangui, Africa/Kinshasa, UTC), not a full IANA picker.** `EXPERIENCE.md`'s AD-13 mockup shows one example value with no exhaustive list — resolved in favor of a Cameroon-first curated set (NFR-010), revisit only if a future story needs broader coverage.

**Decision 5 — `qrcode` is added as `apps/dashboard`'s first new npm dependency since Story 1.1's scaffold.** No QR library existed anywhere in the repo; `qrcode` is the standard, dependency-light choice (`QRCode.toDataURL`, client-side, no server round-trip for the preview itself).

**Decision 6 — the Admin Dashboard's own chrome (Sidebar) is deliberately NOT recolored by the gym's `primary_color`, resolving the epics.md AC's ambiguous "sidebar reflects branding immediately" wording.** `DESIGN.md` is explicit: the gym's `primary_color` replaces `accent` only on "authenticated member-facing surfaces" (the Member Mobile App) — the Admin Dashboard is staff-facing, part of the platform shell, and per UX-DR1 "always uses the platform accent, never the gym color." "Reflects immediately" is satisfied instead by (a) the Settings page's own live in-form preview (logo thumbnail + color swatch, both client-side, pre-save) and (b) the Sidebar's existing `gymName` display (wired since Story 1.8) naturally showing an updated name on next render. Wiring `primary_color`/`logo_url` into the Member Mobile App's own header is out of this story's scope — that app has no runnable code yet (Epic 2 onward) and no current story owns it; flagged as an ownership gap, same posture as Story 1.8's Open Question 2.

**Why these are recorded here, not just in code comments:** Decision 2 is a real security-boundary fix a future column-adding story needs to know to replicate (any future "owner-writable column that must stay off-limits to certain roles" needs the same trigger pattern, not a GRANT); Decisions 3 and 6 are scope/architecture calls with no other permanent record once this story file's own Dev Notes are superseded by later stories.

Added a required **Owner Email** field to the Create Gym form and create the owner's `auth.users` account with both `email` (the login identifier) and `phone` (stored for display, matching SA-03's "Owner: Paul Nkusu (+237 6XX XXX XXX)") set via `supabase.auth.admin.createUser`. **Verified necessary, not just theoretical**, via manual end-to-end testing (story 1-5 Debug Log): without an email, the already-built AD-01/SA-01 login form has no way to authenticate a Story-1.5-created owner.

**Decision 6 — SMS invite delivery is stubbed, not real, for this story.** Story 2.1 (SMS/OTP Provider Sandbox Spike, Epic 2) — the story that validates Cameroon SMS deliverability via `TwilioSmsProvider` — is still backlog. Rather than ship unverified real SMS delivery in Epic 1 ahead of that gate (mirroring this project's own established principle: "neither epic begins on an unverified provider," applied to Notch Pay/OTP elsewhere), `createGym`'s invite-send step (`sendInviteSms` in `actions.ts`) logs the invite message (recipient phone + generated recovery link) via `console.info` instead of calling any real telecom API, and deliberately never throws — a failed/stubbed send must not roll back an already-successful gym/owner/member creation. The UI still shows SA-04's mandated toast ("Gym created. SMS sent to [number].") since the gym+owner creation itself did genuinely succeed; this is a known, accepted gap until Story 2.1 lands and this stub is replaced with a real `TwilioSmsProvider`-backed implementation.

**Why these are recorded here, not just in code comments:** the RLS scope (Decision 3), the tier seed shape (Decision 4), and the owner-identity model (Decision 5) are all hard to change once real gyms/owners exist and later stories (1.6, 1.7, 1.8) build on top of them — same category as every other entry in this log.

## 2026-07-08 — Append-only audit log foundation: schema deviations, recorded during Story 1.4

**Decision 1 — `audit_log.id` is a plain UUID primary key, not architecture.md's literal "bigint identity + separate UUID" text.** architecture.md's Data Architecture section names `attendance`/`audit_log` specifically as tables that should use `bigint identity` plus a separate UUID for external reference. In practice, `attendance_events` (Story 1.3, `0006_attendance.sql`) already used a plain `uuid primary key default gen_random_uuid()` instead, with no deviation recorded at the time. `audit_log` follows that actual in-repo precedent rather than architecture.md's unimplemented text, so it isn't the one bigint-PK table in an otherwise all-UUID schema. If this is later reconsidered, `attendance_events` should be revisited in the same pass for consistency.

**Decision 2 — `audit_log.gym_id` and `audit_log.actor_id` are both nullable**, unlike every other gym-scoped table's `gym_id not null`. `pg_cron` job-failure audit records (FR-027/FR-080) aren't scoped to any one gym — `job_runs` itself has no `gym_id` either (architecture.md Entity Relationships: "global, not gym-scoped") — and have no authenticated session to derive an actor from. No gym-switcher/sentinel-gym-row scheme was introduced; `NULL` is the direct representation of "platform-level, not gym-scoped."

**Decision 3 — `log_audit_event()` is the single canonical write path into `audit_log`.** A `SECURITY DEFINER` Postgres function (`0007_audit_log.sql`), mirroring the pattern established by `private.gym_id()`/`custom_access_token_hook()` in Story 1.3. Derives `actor_id`/`actor_display_name` from `auth.uid()` + `public.users.display_name` internally rather than accepting them as parameters, so no caller can spoof the audit trail's own actor field. System/cron callers (no session) pass an explicit label instead. Unlike the Story 1.3 hook functions, it deliberately does **not** swallow exceptions — a malformed call (e.g. a missing `action_type`) is a caller bug that should surface immediately rather than silently producing no audit record. Every future epic that needs to write an audit record (Epic 1 Stories 1.5–1.7, Epic 2, Epic 4, Epic 5) should call this function rather than inserting directly, which would fail under deny-all RLS for anything but `service_role` anyway.

**Decision 4 — `audit_log.action_type` is free text, not a Postgres enum**, breaking the pattern every other closed-set column in this schema follows (`gym_status`, `member_role`, etc.). The full list of action types spans five future epics that don't exist yet, and enum values, once added, cannot be removed or reordered without recreating the type — free text avoids forcing every future epic's story to modify this migration's enum.

**Why these are recorded here, not just in code comments:** same category as the region/claims decisions above — the schema shape (nullability, PK type, write-path convention) is hard to change once real audit records and calling code from later epics depend on it.

## 2026-07-06 — Tenant isolation foundation: three deviations from architecture.md, recorded during Story 1.3

**Decision 1 — RLS helper function lives in a new `private` schema, not `auth`.** architecture.md specifies `auth.gym_id()`. Verified hands-on (local Postgres 17) that migrations run as the `postgres` role, which does not have `CREATE` privilege on the `auth` schema (owned by `supabase_admin`) — confirmed via `permission denied for schema auth`. Supabase's own RLS documentation shows custom RLS helper functions living in a dedicated non-exposed schema (their example: `private`), not inside `auth`. Implemented as `private.gym_id()` instead; every RLS policy in this project should call it under that name. `private` is not in `supabase/config.toml`'s exposed `[api] schemas`, so it is not reachable via PostgREST.

**AC #1 note:** Story 1.3's AC #1 as literally worded ("the `auth.gym_id()` helper function exists") is not strictly met — the function is `private.gym_id()`. AC #1 is treated as satisfied via this accepted, documented schema-naming deviation (above), not a literal name match. Flagged and accepted during code review of Story 1.3 (2026-07-06), same pattern as Story 1.2's AC #1 tiebreak note.

**Decision 2 — the gym-scoped role claim is named `app_role`, not `role`.** FR-003 describes injecting "`gym_id`/`role` claims" into the JWT. Supabase's Custom Access Token Hook documentation lists `role` among the hook's required/reserved claims — PostgREST/GoTrue use it to `SET ROLE` to `anon`/`authenticated`/`service_role` for the Postgres session. Overwriting it risked breaking that mechanism platform-wide. Confirmed via manual end-to-end login testing that the real GoTrue-issued JWT's `role` claim stays `authenticated` as expected when the gym-role is injected under `app_role` instead. Any future RLS policy or app code reading the gym-scoped role must read `app_role`, not `role`.

**Decision 3 — multi-gym-membership resolution rule (V1 limitation).** FR-001 allows a user to hold `members` rows at more than one gym, but a JWT can only carry one `gym_id`/`app_role` pair. No PRD/epics/architecture text specifies which membership wins. V1 rule: the claims hook selects the single most-recently-created, non-deactivated `members` row for that user. No gym-switcher exists in V1 — a user active at two gyms simultaneously only ever sees the most recent one in their session. Revisit if this becomes a real pilot scenario (unlikely at NFR-009's ~30-members/1–3-gyms pilot scale).

**Why these are recorded here, not just in code comments:** all three are hard to change once real user data and JWT-reading code (RLS policies, future Server Actions) depend on the current shape — same category as the region decision above.

**Also caught during this story, fixed in-migration (not a "decision" needing sign-off, noted for context):** the claims hook's own internal lookups (`SELECT` on `users`/`members`) are themselves subject to RLS, since the hook runs as `supabase_auth_admin`, which does not have the `BYPASSRLS` attribute. With `users`/`members` deny-all (this story's own design), the hook could not read the very membership data it needs to compute claims — a bootstrapping deadlock. Fixed by marking `custom_access_token_hook` `SECURITY DEFINER` (runs as its owner, `postgres`, which does bypass RLS). Caught only via manual end-to-end login testing against the real GoTrue flow — pgTAP alone would not have caught it, since pgTAP calls the function directly as `postgres`, which was never subject to the bug.

## 2026-07-05 — Supabase Cloud region: EU West Ireland (`eu-west-1`) selected

**Decision:** EU West Ireland (`eu-west-1`). The already-existing Supabase Cloud project (`vfxezibagiznrirdwkwh`, created during Story 1.1) already lives here — **no project swap required**.

**Context:** NFR-010 requires the Supabase Cloud project to be in the AWS region closest to Cameroon among the two candidates — EU West Ireland (`eu-west-1`) or Frankfurt (`eu-central-1`) — to keep the front-desk alert's <3s end-to-end budget (FR-052) achievable. Region cannot be changed after data is written, so this had to be confirmed before any schema/data lands (Story 1.3+).

**Starting state:** The existing project was created during Story 1.1's dev-workflow course correction (see `1-1-monorepo-starter-initialization.md` Change Log, 2026-07-05) to unblock local dev speed — **before** this region decision was made. Confirmed via Supabase Dashboard → Project Settings → General: region `eu-west-1`.

**Methodology:** RTT measured from a device tethered to MTN/Orange Cameroon mobile data, using AWS's own regional S3 endpoints (`s3.eu-west-1.amazonaws.com`, `s3.eu-central-1.amazonaws.com`) as a proxy for network path latency to each region — Supabase Cloud's EU projects run on AWS in these same regions, so this measures the real network path without needing a live Supabase project in both candidates. `curl -w`'s `time_connect` (TCP handshake) was used as the RTT signal; `time_total` was not used since it's dominated by response-size/TLS variance rather than network distance. Two independent rounds were run (round 1: single sample each; round 2: 5 samples each), from the same Cameroonian mobile connection.

**Measured data (`time_connect`, seconds):**

| Round | Ireland (`eu-west-1`) | Frankfurt (`eu-central-1`) |
|---|---|---|
| 1 | 0.101 | 0.099 |
| 2 (5 samples) | 1.018*, 0.041, 0.053, 0.070, 0.073 | 0.149, 0.070, 0.046, 0.039, 0.078 |

\* Round 2's first Ireland sample (1.018s) is a clear cold-start outlier (DNS/TLS session not yet warm) — excluded from the statistics below, consistent with standard latency-measurement practice.

**Result:** Median `time_connect` across all valid samples — Ireland ≈ 70.0ms (5 valid samples), Frankfurt ≈ 74.0ms (6 valid samples). Trimmed-mean gives Ireland ≈ 67–74ms, Frankfurt ≈ 74–80ms depending on exact exclusion. **Both regions are within measurement noise of each other — a statistical tie, not a clear winner.**

**AC #1 note:** AC #1 as literally worded ("the lower-latency region is selected") is not strictly met — no region measured as clearly faster. AC #1 is treated as satisfied via an explicitly accepted tiebreak-on-tie rule (churn avoidance, below), not a measured win. Flagged and accepted during code review of Story 1.2 (2026-07-05).

**Rationale for selecting Ireland given the tie:** with no measurable latency advantage either way, the tie-breaker is avoiding unnecessary infrastructure churn — the existing project is already in `eu-west-1`, is empty (no data written), and recreating it in Frankfurt would deliver no latency benefit while costing a project swap, `.env.local` updates in two apps, and a re-verification of the Story 1.1 dev workflow smoke test. Ireland also came out marginally ahead in every calculation method tried (median and most trimmed-mean variants), even though the margin is not statistically meaningful on its own.

**Outcome:** No Supabase project swap needed. `apps/dashboard/.env.local` and `apps/super-admin/.env.local` are unchanged and remain correct.

**Follow-up:** Monitor real front-desk check-in-alert latency in production once Epic 3's check-in flow ships; revisit this region decision if the <3s end-to-end budget (FR-052) is at risk, since the region choice going in was a statistical tie rather than a clear win.
