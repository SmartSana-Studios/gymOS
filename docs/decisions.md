## 2026-07-18 — First physical-device walkthrough (Epic 2 retrospective follow-up) found a real photo-upload bug invisible to `tsc`/lint/two review rounds

**Decision:** Per the Epic 2 retrospective's decision to close the "no device-class testing" gap before Epic 3, the full 2.6→2.8 mobile onboarding + self-service profile flow was walked through on a real Android device (Expo Go, sideloaded SDK 57 build — the Play/App Store listings hadn't caught up yet). Onboarding (2.6, 2.7) verified clean end-to-end, including a real OTP delivered via Twilio WhatsApp to a live number. Story 2.8's photo upload (AC #1) failed: a real photo uploaded from the device's picker landed in Storage as a 14-byte corrupt object, with no error surfaced anywhere — `uploadPhoto()` in `photo-upload.ts` read the picked file via `fetch(uri).arrayBuffer()`, and `fetch()` against Android's local `file://`/`content://` picker URIs can resolve successfully while returning a near-empty body. Fixed by switching to `expo-file-system`'s new SDK 57 `File` class (`new File(uri).arrayBuffer()`), which reads the filesystem bytes directly. Since `onboarding/profile.tsx` (Story 2.6, MA-05) shares the same helper, this also silently fixes the identical latent bug there. Re-verified on-device post-fix: photo uploads and displays correctly.

**Why this is recorded here, not just in the story file:** this is the first bug in the epic that two code-review rounds and a fully green `tsc`/pgTAP/i18n-parity suite all missed — concrete evidence for why the retrospective treated device testing as a blocker rather than an optional nice-to-have. Also: the environment itself needed real repair to get here (Windows Developer Mode had never been enabled, breaking pnpm's symlinks across the whole monorepo in ways that only surfaced as scattered `EACCES` crashes in Metro; WSL2 needed mirrored networking mode for LAN-device reachability) — worth a permanent record in case either regresses.

**Decision 2 — "New account" (epics.md#Story 2.6 AC #4) is defined as `users.display_name IS NULL`.** No planning document defines this term. `users.display_name` has existed since Story 1.3 but was confirmed never populated by any shipped code (2026-07-10 Story 1.8 Decision 2) — Story 2.6 is the first to populate it, from the member's own self-entered name at MA-05 (Profile Setup). A new `users.photo_url` column was added alongside it for the same reason (`0019_member_onboarding_otp.sql`). This is a synthesized decision made during story creation/implementation, not a documented product requirement — the next story to touch member profile data (Story 2.8, Member Self-Service Profile Management, not yet created) should build on these same two columns rather than reinventing where self-entered profile data lives.

**Decision 3 — `phone_has_membership()` existence check runs before every `signInWithOtp` call, as a deliberate (partial) mitigation for the cost-abuse risk flagged in the 2026-07-15 `enable_signup=true` entries below.** A `SECURITY DEFINER` RPC, granted to `anon` for the first time in this codebase (every other grant deliberately excludes `anon`, per `0002_gyms_and_tiers.sql`'s own comment) — necessary because MA-02 (Phone Number Entry) runs before any session exists. This narrows the abuse surface (an unregistered/attacker-controlled phone number never reaches Twilio) but does not eliminate it (an attacker can still probe which numbers are registered, or spam a real member's already-registered number) — CAPTCHA remains explicitly out of scope, consistent with the 2026-07-15 entry's own reasoning that `[auth.captcha]` can't be enabled without a matching client widget no current mockup or AC calls for.

**Decision 4 — OTP resend/lockout enforcement (architecture.md's "server-side ... regardless of client behavior" requirement) is implemented as a new `otp_resend_attempts` table plus two `anon`-callable RPCs (`check_otp_resend_allowed`, `record_otp_resend`), not an Edge Function.** Resolves an ambiguity between epics.md's AC #3 ("3 failed attempts, the 4th request is locked") and EXPERIENCE.md's looser phrasing ("after 3 taps... navigate to MA-04") in favor of the AC's precise wording: 3 resends succeed, the 4th is rejected and triggers a 5-minute lock. Verified hands-on against the real local Supabase instance (direct RPC calls via the anon key over PostgREST, not just pgTAP) before this story was marked for review.

**Decision 5 — the `signInWithOtp({ options: { data: { locale } } })` → Send SMS Hook locale-threading idea (intended to fix `send-sms-hook/index.ts`'s hardcoded `"en"` OTP copy) was investigated and left unresolved.** The local Send SMS Hook consistently timed out (`hook_timeout`, 5s) because the Edge Functions runtime isn't served by plain `supabase start` in this environment, so the test couldn't isolate GoTrue's own metadata-merge behavior from the hook-timeout's effect on the transaction. Not fixed this session — recorded in `deferred-work.md` rather than left as a silent gap. English-only OTP delivery copy persists until this is revisited.

**Why these are recorded here, not just in code comments:** Decision 1 corrects a structural fact every future `apps/mobile` story depends on. Decisions 2–4 are schema/security-posture choices (self-writable profile columns, a first-ever `anon` function grant, the resend-limit's exact off-by-one resolution) that are expensive to get wrong after real onboarding data exists — same category as every other entry in this log. Decision 5 is an investigated-but-unresolved technical question the next reader needs on record rather than re-discovering.

## 2026-07-16 — Code review of Story 1.11: two accepted-risk findings, both extending already-accepted tradeoffs

**Decision 6 — `must_change_password` is enforced only at the `(dashboard)/layout.tsx` render level, not at the Server Action/API level. Accepted as-is.** The code-review's Blind Hunter layer flagged that an authenticated owner's session could in principle reach a Server Action or route without rendering the gating layout, meaning the forced-password-change requirement is a workflow nudge, not an RLS-enforced authorization boundary. Accepted: this is a UX/workflow gate, not a tenancy/permissions boundary (which remains RLS's job per this project's architecture), and the risk is bounded by the same pilot-scale/small-trusted-team reasoning as Decision 5 below. Revisit if this changes (e.g. before opening Super Admin/owner accounts beyond a small trusted team, or if this pattern is reused for something that *is* a real authz boundary).

**Decision 7 — the temp password remains a valid login credential indefinitely (no expiry/single-use enforcement) and is delivered as permanent plaintext over WhatsApp. Accepted as-is, extending Decision 5.** Decision 5 (below) already accepted the exposure window of the temp password sitting in the Super Admin UI toast. This finding extends the same acceptance to the WhatsApp message itself: unlike the superseded recovery link (single-use, expiring), the temp password stays valid until the owner completes `/auth/update-password`, and the WhatsApp message carrying it has no time bound the app controls. Accepted for the same reason as Decision 5 — pilot scale, staff-facing (not member-facing) surface. Revisit together with Decision 5 if the Super Admin/owner population grows beyond a small trusted team, e.g. by adding a bounded expiry or single-use enforcement on the temp password itself.

## 2026-07-16 — Gym Owner Activation: temp-password-over-WhatsApp replaces the recovery-link mechanism, recorded during Story 1.11

**Decision 1 — Story 1.5's `generateLink({type:"recovery"})` + link-delivered-over-SMS mechanism is replaced by a known temp password sent as plain text over WhatsApp**, before the flow's first real use (`sendInviteSms` was a stub, never wired to a real provider — no real owner was ever affected). Full rationale (why the link mechanism doesn't work on WhatsApp Business Platform, why link-via-email was evaluated and rejected) is recorded in the 2026-07-14 Sprint Change Proposal (`_bmad-output/planning-artifacts/sprint-change-proposal-2026-07-14.md` §4.2) and not re-derived here — this entry formalizes that proposal's drafted decisions 1–3 into the permanent log (they were never separately committed here before this story) and adds the implementation-time decisions below.

**Decision 2 — `email_confirm: true` is now required on owner account creation, for a different reason than before.** Previously, the recovery link's own GoTrue verify step proved email ownership implicitly, so `email_confirm: true` was set but not load-bearing for that proof. With no link at all, `email_confirm: true` is now the only thing establishing the account as usable — flagged explicitly per the Sprint Change Proposal's Decision 3, not a silent side effect.

**Decision 3 — WhatsApp was chosen over SMS or a new plain-text template, reusing Story 2.1's already-approved `verifications_2fa_template`.** WhatsApp Business Platform requires an approved template for any business-initiated message (no free-form text outside a 24h user-initiated session), so "just send free text over WhatsApp" was never actually available. Three options were weighed (full detail in the story's Dev Notes → Open Question 1): (a) submit a new plain-text template worded correctly for a temp password — cheapest long-term but needs a real Meta approval step and a fallback chain that doesn't exist in code; (b) reuse the existing `verifications_2fa_template` as-is — ships immediately, zero new approval; (c) SMS only — no template dependency, but doesn't use the already-verified WhatsApp channel and costs more per message. **Chosen: (b).** Accepted, deliberate tradeoff: the template's fixed body reads "**{{1}}** is your verification code. For your security, do not share this code." — worded for an OTP code, not a temp password. This wording mismatch is cosmetic and knowingly accepted, not a defect to silently work around (`apps/super-admin/lib/messaging/sendTempPasswordMessage.ts`). **No SMS fallback exists in code for this message** — `deferred-work.md` already tracks the equivalent gap for `send-sms-hook`'s `OTP_PROVIDER` selection; the same gap applies here (single-provider send, no automatic retry on a second channel).

**Decision 4 — `private.protect_self_managed_user_columns()` (0015) needed a same-migration fix, not a follow-up one.** This `BEFORE UPDATE` trigger on `users` pins every self-updated column back to `OLD` except an explicit allow-list (previously just `preferred_language`, Story 1.10). Left unmodified, this story's AC #5 (the owner flipping `must_change_password` to `false` via their own self-update after completing the forced password change) would have been **silently reverted by this trigger** — the UPDATE would appear to succeed (no error) but the row would read back unchanged, permanently trapping every temp-password owner behind the `/auth/update-password` gate. Fixed in the same migration (`0016_owner_must_change_password.sql`) that added the column, by adding `must_change_password` to the trigger's allow-list. **Recorded as a repeatable gotcha pattern**, the same way Story 1.9's Decision 2 (column-level RLS gap) was recorded: any future self-writable-but-otherwise-restricted `users` column needs the identical trigger-allow-list update, or it will silently fail to persist with no error surfaced anywhere. Verified via a dedicated pgTAP assertion (`supabase/tests/users_self_service_rls.test.sql`) proving the self-update actually persists and that the trigger's existing protections (`is_super_admin`/`phone`/`display_name`) weren't accidentally loosened by the same edit.

**Decision 5 — the temp password is surfaced in the Super Admin UI as a manual fallback, shown unconditionally.** Mirrors Story 1.5's own precedent exactly (commit `6049e7a`, "surface owner invite link in Super Admin UI"): `CreateGymResult.tempPassword` is always returned and always displayed in `GymsPageClient`'s toast on gym creation, not gated behind the WhatsApp send's reported `success`/`failure` — a `success: true` from Twilio doesn't guarantee the owner actually read/kept the WhatsApp message. Ephemeral only, not persisted to any log/table beyond the existing return value. **Accepted security tradeoff**: a reusable password sitting in a toast is a larger exposure window than the single-use, expiring recovery link Story 1.5 originally showed — accepted for this pilot's scale and staff-facing (not member-facing) surface; revisit if the Super Admin user base grows beyond a small trusted team.

**Why these are recorded here, not just in code comments:** Decision 4 (the trigger fix) is the one regression this story could most easily have shipped silently — worth recording explicitly as a pattern for the next self-writable `users` column, same category as every other trigger/RLS gotcha in this log. Decisions 3 and 5 are explicit, user-made tradeoffs (wording mismatch, no SMS fallback, password-in-toast exposure window) that the next reader needs on record, not just inferable from the diff.

## 2026-07-15 — Onboarding/account-recovery channel policy: WhatsApp-default OTP now, links deferred platform-wide, decided ahead of Stories 1.11 and 2.5

**Decision — no link of any kind (deep link, recovery link, or email link) ships in any onboarding or account-recovery flow for now, for any user type (gym owner or member).** SMS/WhatsApp OTP codes and plain-text messages are the only mechanism, platform-wide, until further notice. This resolves two separate open questions at once:

1. **Story 1.11 (Gym Owner Activation)** already established this for owners — a Supabase recovery link is replaced by a known temp password sent as plain text (see the 2026-07-14 entry below). This decision confirms the same rule applies to Story 2.5.
2. **Story 2.5 (Member Invitation via Deep Link, FR-082)** keeps its existing link-agnostic framing — the story is **not** renamed or narrowed to "WhatsApp-only" — but its actual V1 mechanism drops the deep link: staff shares a plain-text message (not a URL) via Copy/WhatsApp, the member manually enters their phone number on first app open, and the backend resolves the invitation by phone-number lookup against the `members`/`auth.users` row **Story 2.3's admin-side member creation already provisioned** — no new record is created at invite time; "Send Invite" is a client-side messaging convenience with zero persisted state of its own, not a lookup against a separate pending-invite record. *(Corrected 2026-07-17, `bmad-code-review`: this entry originally said "against a pending-member record created at invite time," which contradicted Story 2.5's own Scope Note #2/AC #4 and the actual shipped implementation — no such record exists or was ever built.)*

**Channel priority — WhatsApp is the default provider, SMS is the fallback, in that order.** This corrects the 2026-07-14 entry below, which set `TwilioSmsProvider`/SMS as `OTP_PROVIDER`'s default following Story 2.1's spike. Note: `send-sms-hook/index.ts`'s `getProvider()` selects exactly one provider from a single `OTP_PROVIDER` env var with no automatic runtime fallback chain between providers — "SMS follows" is operational/config guidance for whoever sets `OTP_PROVIDER` per environment (fall back to `twilio` if `twilio_whatsapp` is unavailable or misconfigured for a given deployment), not a claim that cascading fallback logic exists in code today. Building an actual automatic-fallback chain, if wanted, is new scope, not assumed by this decision.

**Why the two stories' link problems are NOT the same failure mode (recorded so neither gets miscited later):** Story 1.11's link died because Twilio/sent.dm's automated WhatsApp Business API send path requires Meta template approval for any URL/button component — the free pre-built OTP templates validated in Story 2.1 don't support it. Story 2.5's deep link, as originally specced, never went through that automated template pipeline at all — it was staff manually copying/pasting a message into their own SMS/WhatsApp app. Dropping 2.5's link is a deliberate consistency and reduced-attack-surface choice (one onboarding pattern to secure/debug/support, and no link that can be forwarded/replayed by someone other than the intended member), not a case of the same technical wall blocking both.

**Deferred, not rejected — email links.** Email-based links are planned as an **additional** future channel for both onboarding invitations and password reset, once the WhatsApp/SMS OTP mechanism has shipped and proven out in the pilot. This reopens, as a later option, what the 2026-07-14 Sprint Change Proposal below rejected as *immediate* replacement for Story 1.11 specifically (link-via-email was rejected there because email ownership was never validated for existing owners) — the objection was about replacing the owner-activation link right now with an unvalidated channel, not a permanent ban on ever using email. Tracked as a deferred item (see `deferred-work.md`) rather than left as an ambient intention, since it touches multiple future surfaces (FR-082's original link mechanism, a not-yet-designed password-reset flow) and needs its own scoping pass — including confirming whether member/owner email addresses are even collected anywhere in the current onboarding flow before it can be built.

**Why this is recorded here, not just decided in conversation:** this changes the OTP-provider default ordering set by Story 2.1's own decision (below) and formally closes what would otherwise be an undocumented scope reduction to FR-082 — the next person reading Story 2.5's file or `epics.md`'s literal "deep link" wording needs this decision, not just the story's own future Dev Notes, to understand why no link ships.

## 2026-07-15 — Correction to the entry below: `enable_signup=true` risk is cost-abuse (SMS-pumping/toll fraud), not just row-hygiene — recorded during Story 2.1's second code-review pass

**Correction, not a reversal.** The entry immediately below this one (same day, first review pass) accepted the `enable_signup=true` risk as "phone-number squatting / unconfirmed-row accumulation," bounded by existing rate limits, and explicitly "not an authentication bypass." That technical analysis is still correct — no session or token is issued from `/otp` alone. What was understated is the *cost* dimension: `POST /auth/v1/otp` for an unowned Cameroonian number triggers a real, billed Twilio SMS send ($0.317 USD/message, confirmed via Twilio's Pricing API in the 2026-07-14 entry below) before any ownership is verified.

**Why the original mitigation is weaker than it reads.** `supabase/config.toml`'s `[auth.rate_limit]` values (`sms_sent = 30`/hour, `sign_in_sign_ups = 30`/5min) are **per-IP** throttles, not account- or platform-wide caps, and `[auth.captcha]` is fully disabled in this config. An attacker rotating source IPs — or simply a patient single attacker — can sustain real, billed sends to arbitrary numbers indefinitely. This reframes the finding from "DB hygiene, low severity" to "unauthenticated SMS-pumping / toll-fraud cost-abuse vector, real financial exposure."

**Decision — still not fixed here, deferred to Story 2.6, but the risk record is corrected now.** CAPTCHA (`[auth.captcha]`) cannot be enabled in isolation: GoTrue would then reject every phone signup attempt until a matching client-side CAPTCHA widget (e.g. hCaptcha/Turnstile) exists and is wired into the actual signup form — which doesn't exist yet (Story 2.6 builds the real member-facing signup UI; this story is a backend spike with no consumer UI). Rather than let the original, milder characterization stand uncorrected until Story 2.6, this entry exists so whoever scopes Story 2.6's CAPTCHA integration starts from the accurate risk (real-money abuse), not the original's DB-hygiene framing.

## 2026-07-15 — `enable_signup=true` creates unconfirmed `public.users` rows before phone verification — accepted risk, not fixed here, recorded during Story 2.1 code review

**Finding:** Story 2.1's `[auth.sms] enable_signup: false → true` (needed — FR-002 requires phone-based registration) combined with `enable_confirmations: false` (unchanged) means calling `POST /auth/v1/otp` for a brand-new phone number creates a real `auth.users` row immediately, before the OTP is ever verified. `supabase/migrations/0003_members_and_users.sql`'s `handle_new_user()` trigger (`SECURITY DEFINER`, no `WHEN` clause) unconditionally inserts a corresponding `public.users` row on that same event — so an unconfirmed phone number gets a real row in `public.users`, not just an internal `auth.users` artifact.

**What this is NOT:** an authentication bypass. No session or access token is ever issued from `/otp` alone (confirmed via this story's own real testing — `/otp` returns only `{}`; tokens are issued only by `/verify`, which requires the actual code sent to the real phone). So the practical risk is narrower than "unverified accounts are usable" — it's phone-number squatting / unconfirmed-row accumulation (someone repeatedly calling `/otp` for numbers they don't own), not account takeover.

**Existing mitigation, not new:** `config.toml`'s pre-existing rate limits (`[auth.rate_limit] sms_sent = 30`/hour, `sign_in_sign_ups = 30`/5min, `token_verifications = 30`/5min) already bound how many such rows one IP can create.

**Decision — accepted as-is, not modified in this story.** `handle_new_user()` belongs to Story 1.3 (already shipped, reviewed, in Epic 1) — adding a `WHEN phone_confirmed_at IS NOT NULL`-style guard would be a real schema change to that migration, out of proportion for a code-review fix on Story 2.1 and out of Story 2.1's own scope. Flagged here for whoever builds Story 2.6 (real member onboarding) to consider hardening — e.g. a periodic cleanup of unconfirmed rows past some age, or the `WHEN` guard — if abuse in practice ever exceeds what the existing rate limits bound.

## 2026-07-14 — SMS/OTP Provider Sandbox Spike: Twilio passes, sent.dm fails on both channels, recorded during Story 2.1

**Decision 1 — `TwilioSmsProvider` is validated and becomes the `OTP_PROVIDER` default.** A real OTP was requested against a real Cameroonian number (`+237680811041`) via the local GoTrue Auth API → Send SMS Hook → `TwilioSmsProvider`, using the direct `TWILIO_FROM_NUMBER` (`+16802069590`) path. Twilio's own Messages API confirmed `status: "delivered"`, `error_code: null`. The user independently confirmed receipt on the physical device: *"Your GymOS code is: 430868."* The code was then submitted to `POST /auth/v1/verify`, which returned a real access/refresh token pair and set `phone_confirmed_at` — a full round-trip pass, not just delivery. **AC #1: PASS.**

Twilio's `TWILIO_MESSAGING_SERVICE_SID` path was also tested and failed with `error_code: 21704` (empty Sender Pool — no phone number attached to that Messaging Service in the Twilio Console). This is an account-configuration gap, not a code or deliverability problem; the direct From-number path is what's validated and in use. Revisit the Messaging Service path once a number is added to its Sender Pool (preferred long-term per the story's own Dev Notes, for easier number rotation).

**Decision 2 — `SentDmProvider` fails on both SMS and WhatsApp for this account, against the same real number — not currently a viable fallback.** Two independent, real failures, both confirmed via `messages.activities.list`:

- **WhatsApp** (sent.dm's auto-routing selected this channel first): failed with a Meta Graph API error — `GraphMethodException`, subcode 33, *"Object with ID '1128692860338387' does not exist, cannot be loaded due to missing permissions, or does not support this operation."* Sent.dm's own `ErrorCode`: `ERR_TEMPLATE_PARAMS_INVALID`. This looked at first like a template-parameter problem — the "ACCOUNT VERIFICATION" template (confirmed via `GET /v3/templates/{id}`) requires **two** variables, `code` and `var_2` (the latter is the WhatsApp "Copy Code" button's own separate variable slot, not a brand-name field as first assumed) — but the identical failure persisted across two different `var_2` values, ruling out parameter content as the cause. This points to a template/WhatsApp-Business-Account sync or permissions issue on sent.dm's platform side, not something fixable from this codebase.
- **SMS** (forced explicitly via `channel: ["sms"]`, bypassing auto-routing): failed with `ERR_NO_ROUTE_MATCHED` — *"No MessageRouting rule matched send for customer [account id] to 237680811041. Configure a rule covering this customer/recipient/template."* This account's free tier has no SMS carrier routing rule configured for Cameroon at all.

Both failures are real, diagnosable, and external to this codebase — not integration bugs. sent.dm's credentials and account (`SmartSana Technologies, ETS`) are otherwise valid and working (confirmed via successful template lookups and the connected Sent MCP tools). **AC #1's "at least one provider succeeding" is satisfied by Twilio alone; sent.dm is not currently usable and should not be relied on until its account's SMS routing and WhatsApp template sync are resolved directly with sent.dm** (likely requires their support, or a paid-tier upgrade for Cameroon SMS routing — not confirmed which).

**Decision 3 — the architecture.md "WhatsApp OTP explicitly deferred" tension did not actually materialize.** sent.dm's auto-routing did select WhatsApp first for this real number (confirmed via `messageStatusActivity: ROUTED, content: "SelectedChannel: auto"`), which is exactly the scenario architecture.md's Deferred Decisions section flagged as a real tension worth recording (WhatsApp becoming a V1 delivery path as a side effect of provider choice, not a built `WhatsAppOtpProvider`). In practice, since the WhatsApp send itself failed, no member ever actually received an OTP via WhatsApp — the tension is real in principle but did not produce an actual WhatsApp delivery this round. Flagged here for whoever next revisits sent.dm, since fixing its WhatsApp template issue would make this tension live again.

**Decision 4 — six real, non-hypothetical bugs were found and fixed only by running the actual spike, not by code review or docs research alone:**
1. `supabase/config.toml`'s `[auth.hook.send_sms]` used `secret = "env(...)"` (singular) — the CLI's actual accepted key is `secrets` (plural); the singular form fails config parsing outright.
2. The Supabase CLI hard-disables phone auth entirely (`WARN: no SMS provider is enabled. Disabling phone login`) unless a built-in SMS provider block (e.g. `[auth.sms.twilio]`) is also `enabled = true` — even when a custom Send SMS Hook is configured and enabled. Fixed by enabling `[auth.sms.twilio]` with placeholder credentials, which are never used for real sending since the hook takes priority at send time. This is undocumented in `config.toml`'s own comments and easy to miss.
3. `[auth.sms] enable_signup` defaults to `false` in the starter scaffold — this blocks phone OTP entirely and was never a deliberate choice for this app; set to `true`, which is what FR-002 actually requires.
4. GoTrue's Send SMS Hook payload delivers `user.phone` **without** a leading `+` (its internal storage convention). Twilio's Messaging-Service send path silently tolerated this; its direct From-number path did not (`21211: Invalid 'To' Phone Number`). Fixed by normalizing to `+`-prefixed E.164 once, at the `index.ts` payload boundary, rather than relying on per-provider leniency.
5. sent.dm's real template requires `var_2` in addition to `code` (see Decision 2) — confirmed only by inspecting the template's actual schema via its API, not from docs alone.
6. Twilio's Messaging Service had an empty Sender Pool — diagnosed by testing the direct From-number path as an isolation step.

None of these were guessable from documentation or static code review; all six were found by actually executing the spike end-to-end against real accounts.

**Why these are recorded here, not just in code comments:** Decision 1 sets the concrete `OTP_PROVIDER` default and is the direct spike outcome the story's AC requires recording. Decision 2 is a real, currently-open external-account gap a future story (or whoever manages the sent.dm account) needs to know about before trusting sent.dm as a fallback. Decision 4's six bugs are exactly the kind of "worked on paper, broke on contact with the real provider" findings this spike existed to surface, and the config-level ones (1–3) will otherwise silently re-trip for the next Edge Function/auth-hook this project builds (Notch Pay's webhook is next).

## 2026-07-14 — Twilio WhatsApp added as a fourth `OtpDeliveryProvider`, pulling forward architecture.md's deferred WhatsApp OTP decision, recorded during Story 2.1

## 2026-07-10 — Bilingual (EN/FR) Platform Foundation: i18n architecture, users self-service RLS, pnpm/eslint-config-next toolchain fix, recorded during Story 1.10

**Decision 1 — `react-i18next` + static locale-file imports, no dynamic per-request backend.** The story initially specified `i18next-resources-to-backend` for dynamic per-locale loading, but with exactly two known locales (`en`/`fr`, tiny JSON files), both `lib/i18n/get-server-translation.ts` (server) and `lib/i18n/client-provider.tsx` (client) just statically import both locales' JSON and merge them into one `translation` namespace resource bundle at module load — synchronous, no async fetch, and critically lets the Sidebar/top-nav toggle call `i18n.changeLanguage()` with both locales already preloaded (no missing-string flash while a second locale loads). The `i18next-resources-to-backend` dependency was removed from both apps' `package.json` after being added — unused complexity for a fixed 2-locale set.

**Decision 2 — `users` gains `self_read_own_user`/`self_update_own_language` RLS policies + a `protect_self_managed_user_columns` `BEFORE UPDATE` trigger** (`0015_users_self_service_language_preference.sql`), mirroring Story 1.9's `protect_super_admin_only_gym_columns` pattern exactly: RLS is row-level only, and the table-wide `grant update on users to authenticated` (`0003_members_and_users.sql`) means the new self-update policy alone would let a session self-elevate `is_super_admin` or change its own `phone` (FR-023 requires admin intervention) via a raw UPDATE bypassing `updateLanguagePreference`'s single-column write. The trigger pins `phone`/`is_super_admin`/`display_name`/`created_at` back to `OLD` whenever `auth.uid() = new.id`, so a self-update can only ever change `preferred_language`. Unlike `0014`'s sibling trigger (flagged in Story 1.9's review for an unneeded `security definer`), this one is correctly declared without it from the start. `rls_tenant_isolation.test.sql`'s pre-existing "users: 0 rows, no business policy yet" assertion needed updating to "exactly 1 row — their own" — the same class of update Story 1.9 hit with `tiers_and_gym_lifecycle_rls.test.sql`.

**Decision 3 — locale resolution is a single primitive (`getRequestLocale()`, per app) with no cookie.** Priority: (1) an authenticated session's live `users.preferred_language` (a fresh DB read every call — not JWT-claims-cached, since the auth hook doesn't carry it and caching would delay a language change until token refresh), (2) the request's `Accept-Language` header, (3) English. No locale cookie was introduced: the authenticated case re-reads `users.preferred_language` per request (matching `session.ts`'s existing looseness re-deriving `gymName`/`memberName` per request rather than caching), and the unauthenticated case (login, forgot-password, etc.) has no documented language-selection UI in EXPERIENCE.md, so `Accept-Language`-only resolution is sufficient there.

**Decision 4 — `mapSupabaseError(error, locale)` becomes locale-aware; `mapAndLog` becomes `async` in both apps, resolving locale internally rather than threading a `locale` parameter through every Server Action/service call chain.** Every existing `mapAndLog(x)` call site (~30 across both apps) became `await mapAndLog(x)` — a mechanical, one-word change, since every caller was already an `async` function. This was deliberately chosen over parameter-threading, which would have touched every Server Action's signature in both apps for no benefit.

**Decision 5 — Zod schema validation messages (`packages/types/src/schemas/*.ts`) are explicitly out of this story's localization scope.** `packages/types` has no ESLint config and no `lint` script (confirmed: Turborepo's `lint` task silently skips it), so the new `i18next/no-literal-string` CI gate never reaches those files by construction — not via a special exclusion rule. Localizing Zod's own error-message strings needs a broader pattern (locale-aware Zod error maps) disproportionate to this foundation story; flagged as a known gap rather than silently expanded into.

**Decision 6 — Confirmed-dead Supabase-starter demo/tutorial scaffolding in `apps/super-admin` (`app/page.tsx`, `app/protected/**`, `components/tutorial/**`, and several unused starter components) is excluded from the ESLint config entirely** (a standalone `{ ignores }` flat-config object, not just from the i18next rule), rather than translating template marketing copy that isn't gym_os product surface. Verified dead by grep: nothing in the real `(admin)`/`auth` route trees imports any of these files, and their redirect targets (`/protected`) don't exist as real routes. `apps/dashboard` has no equivalent leftover scaffolding (already cleaned up by Story 1.1/1.8).

**Decision 7 — `next/core-web-vitals`/`next/typescript` are imported directly from `eslint-config-next`'s native flat-config exports, not through `FlatCompat.extends(...)`.** This is the first story to actually run `pnpm lint` (confirmed: `.github/workflows/ci.yml` never invoked it before, and no prior story's Dev Notes mention running it). The pre-existing `FlatCompat`-based `eslint.config.mjs` (from Story 1.1's `create-next-app` scaffold) crashes with `TypeError: Converting circular structure to JSON` against `eslint-config-next@16.2.10`'s modern self-referencing flat-config plugin objects — reproduced identically with zero i18n-related config present, confirming it predates and is unrelated to this story. Fixed by importing `eslint-config-next/core-web-vitals` and `eslint-config-next/typescript` directly as native `Linter.Config[]` arrays (their actual shape per `eslint-config-next`'s own `.d.ts`), which is what these exports are designed for in ESLint 9.

**Decision 8 — `eslint-config-next`'s `dist/parser.js` does `require('next/dist/compiled/babel/eslint-parser')` without declaring `next` as its own dependency**, which resolves fine under npm/yarn's flat `node_modules` (implicit hoisting) but fails under pnpm's isolated layout with `Cannot find module`. Fixed via a scoped `packageExtensions` entry in `pnpm-workspace.yaml` (`eslint-config-next` → `dependencies: { next: "*" }`), not a global `public-hoist-pattern` — the latter was tried first and works, but risks altering dependency resolution for unrelated packages (verified: `apps/mobile`'s own pre-existing, unrelated typecheck errors reproduce identically before and after, confirming no regression either way, but the scoped fix is the correct minimal lever). Also fixed in passing (both apps): `tailwind.config.ts`'s `require("tailwindcss-animate")` → `import tailwindcssAnimate from "tailwindcss-animate"` (the only other pre-existing lint error, `@typescript-eslint/no-require-imports`, surfaced by this being the first real lint run) and the CI `lint` step is scoped to `--filter=@gymos/dashboard --filter=@gymos/super-admin` (not the full `pnpm run lint`), since `apps/mobile` has no runnable code yet and its own `expo lint` has an unrelated, pre-existing dependency gap.

**Why these are recorded here, not just in code comments:** Decisions 2, 7, and 8 are toolchain/security-boundary facts a future story needs to know to avoid repeating (the trigger pattern for any future self-writable-but-restricted-column table; the FlatCompat incompatibility if anyone reverts to `compat.extends`; the pnpm packageExtensions fix if `eslint-config-next` is ever upgraded again). Decisions 1, 3, 5, and 6 are scope/architecture calls with no other permanent record once this story's own Dev Notes are superseded by later stories.

## 2026-07-10 — Gym Branding & Operational Settings: owner write-path, gym-logos bucket, column-level protection gap, recorded during Story 1.9

**Decision 1 — `owner_update_own_gym` closes the write-path gap `0011_super_admin_tier_gym_lifecycle.sql` explicitly deferred** ("owner/manager gym-settings edits (FR-069) are Story 1.9's job on a different table scope"). Migration `0014_gym_settings_owner_access.sql` adds one explicit, role-scoped RLS UPDATE policy on `gyms` (`id = private.gym_id() and app_role = 'owner'`), matching every prior story's discipline of per-action policies, never `FOR ALL`. No new SELECT policy was needed — `"read own gym"` (`0009_auth_hook_gym_claims.sql`) already exposes every settings column.

**Decision 2 — a `protect_super_admin_only_gym_columns` BEFORE UPDATE trigger closes a column-level gap the RLS policy alone leaves open.** RLS is row-level, not column-level: `owner_update_own_gym` authorizes an owner to UPDATE their own gym row, full stop — nothing in a `USING`/`WITH CHECK` clause can say "except this column." Left alone, an owner could flip `status`/`tier_id`/`member_cap_override` (all Super Admin-exclusive lifecycle/tier controls, Story 1.6) via a raw UPDATE bypassing the app's own `updateGymSettings` column allow-list. Column-level Postgres `GRANT UPDATE (cols)` can't fix this either: Super Admin and Owner sessions both run as the same `authenticated` Postgres role (the JWT's `role` claim, distinct from `app_role`, is what actually drives `SET ROLE`), so a grant restriction would bind to that shared role, not to `app_role`. The trigger is the only mechanism that can key off `app_role` per-statement: for any non-`super_admin` session, it silently pins `status`/`tier_id`/`member_cap_override` back to their prior values before the row is written, rather than rejecting the whole UPDATE. Caught by running the full `supabase test db` regression suite (per this project's own standing practice): `tiers_and_gym_lifecycle_rls.test.sql`'s pre-existing "owner cannot UPDATE their own gym" assertion (written when no owner UPDATE policy on `gyms` existed at all) needed updating to reflect the new, correct behavior — the row is now matched/returned (owner UPDATE succeeds at the row level), but the `status` column itself stays unchanged (protected by the trigger). Updated, not worked around.

**Decision 3 — `gym-logos` is a `public = true` Storage bucket, not a private one behind signed URLs.** The Member Mobile App's 24h branding cache (FR-011/012) reads the logo unauthenticated, and V1 has no signed-URL refresh mechanism to build instead (matches FR-013's "full theme systems out of V1 scope" discipline). `storage.objects` gets a full INSERT/SELECT/UPDATE/DELETE RLS policy set (owner, own-gym-folder-scoped via `(storage.foldername(name))[1] = private.gym_id()::text`) — **the SELECT policy was not optional**, despite the initial assumption during story creation that the bucket's own `public=true` setting (which does serve unauthenticated reads via the Storage HTTP API, independent of RLS) meant no SELECT policy was needed for anything. That assumption held for reads, but broke for `uploadGymLogo`'s own `upsert: true` write path: Storage implements upsert as `INSERT ... ON CONFLICT (bucket_id, name) DO UPDATE`, and Postgres's RLS enforcement for that statement shape requires a SELECT policy to resolve the conflict target's visibility. Confirmed hands-on against the real local Storage HTTP API during Task 7's manual verification: a plain INSERT (no `ON CONFLICT`) succeeded with only INSERT/UPDATE policies in place, but the identical write with `x-upsert: true` failed with "new row violates row-level security policy" — reproducible even for a brand-new path with no actual conflicting row. Adding `owner_select_own_gym_logo` (same owner/own-gym-folder scope as the others) fixed it. This is a real, general Postgres RLS + `ON CONFLICT DO UPDATE` gotcha, not specific to Supabase Storage — any future `upsert: true` Storage write against an RLS-protected bucket needs the same SELECT policy, or the upsert will fail even when the underlying INSERT/UPDATE policies are individually correct. `gym_settings_rls.test.sql`'s existence checks still use `reset role` (bypassing RLS entirely, matching `audit_log_immutable.test.sql`'s pattern) rather than relying on the inserting session's own now-available SELECT visibility, since that's the simplest, most direct check.

**Decision 4 — the Timezone field ships a small curated V1 list (Africa/Douala, Africa/Lagos, Africa/Bangui, Africa/Kinshasa, UTC), not a full IANA picker.** `EXPERIENCE.md`'s AD-13 mockup shows one example value with no exhaustive list — resolved in favor of a Cameroon-first curated set (NFR-010), revisit only if a future story needs broader coverage.

**Decision 5 — `qrcode` is added as `apps/dashboard`'s first new npm dependency since Story 1.1's scaffold.** No QR library existed anywhere in the repo; `qrcode` is the standard, dependency-light choice (`QRCode.toDataURL`, client-side, no server round-trip for the preview itself).

**Decision 6 — the Admin Dashboard's own chrome (Sidebar) is deliberately NOT recolored by the gym's `primary_color`, resolving the epics.md AC's ambiguous "sidebar reflects branding immediately" wording.** `DESIGN.md` is explicit: the gym's `primary_color` replaces `accent` only on "authenticated member-facing surfaces" (the Member Mobile App) — the Admin Dashboard is staff-facing, part of the platform shell, and per UX-DR1 "always uses the platform accent, never the gym color." "Reflects immediately" is satisfied instead by (a) the Settings page's own live in-form preview (logo thumbnail + color swatch, both client-side, pre-save) and (b) the Sidebar's existing `gymName` display (wired since Story 1.8) naturally showing an updated name on next render. Wiring `primary_color`/`logo_url` into the Member Mobile App's own header is out of this story's scope — that app has no runnable code yet (Epic 2 onward) and no current story owns it; flagged as an ownership gap, same posture as Story 1.8's Open Question 2.

**Why these are recorded here, not just in code comments:** Decision 2 is a real security-boundary fix a future column-adding story needs to know to replicate (any future "owner-writable column that must stay off-limits to certain roles" needs the same trigger pattern, not a GRANT); Decisions 3 and 6 are scope/architecture calls with no other permanent record once this story file's own Dev Notes are superseded by later stories.

## 2026-07-08 — Super Admin gym provisioning: schema/RLS deviations and open-question resolutions, recorded during Story 1.5

**Decision 1 — `private.is_super_admin()` is a new `STABLE` SQL helper**, mirroring `private.gym_id()`'s (Story 1.3) shape: `coalesce((auth.jwt() ->> 'app_role') = 'super_admin', false)`. Reused across every Super Admin RLS policy this story adds, rather than repeating the inline check `log_audit_event()` (Story 1.4, `0007_audit_log.sql`) already duplicates once. That landed migration was not modified — the duplication there is accepted, not retrofitted.

**Decision 2 — `idx_gyms_name_unique on gyms (lower(name))`** enforces AC #2's gym-name uniqueness at the DB level (case-insensitive), closing the race window a pure app-side pre-check can't. Added in `0010_super_admin_gym_provisioning.sql` since `0002_gyms_and_tiers.sql` is already shipped.

**Decision 3 — RLS policy scope for Super Admin, including a mid-implementation refinement.** `gyms`: SELECT + INSERT (not UPDATE — Story 1.6's job). `tiers`: SELECT only (not CRUD — Story 1.6's job). `members`: INSERT restricted to `role = 'owner'` via `WITH CHECK`. **Originally planned as INSERT-only** (see story 1-5's Scope Boundary, as first drafted), but implementation surfaced that SA-02/SA-03 both display "Owner: <name> (<phone>)" for every gym, which is unreachable without some read access to `members`. Resolved by adding a **SELECT policy scoped to `role = 'owner'` rows only** (`using (private.is_super_admin() and role = 'owner')`) — deliberately narrower than a general members-SELECT grant, and kept distinct from Story 1.7's audit-logged escalation (FR-072) to a gym's full member/payment data: a Super Admin can see who owns each gym they provisioned, never a coach/receptionist/member row, without triggering an escalation.

**Decision 4 — Default tier seed data (FR-073), with a provisional cap for Elite.** No prior story seeded the three default tiers; the Create Gym form's tier dropdown needs at least one to exist. Seeded via fixed well-known UUIDs + `ON CONFLICT DO NOTHING` using SA-06's mockup numbers (the only concrete source in the planning artifacts): Hustle (cap 30, XAF 15,000/150,000), Grind (cap 100, XAF 35,000/350,000), Elite (XAF 75,000/750,000). **Elite's "no cap" cannot be represented** — `tiers.member_cap` is `integer not null` with no sentinel/nullable convention. Used a large sentinel (1,000,000) as a stopgap; the real schema decision (e.g. nullable `member_cap` = unlimited) is left to Story 1.6, which owns tier CRUD and has the actual UI/enforcement context to decide it properly.

**Decision 5 — Owner authentication identity: dual email + phone, deviating from SA-04's literal 3-field mockup.** architecture.md specifies dashboard/Super Admin auth as Supabase email+password (confirmed by the already-scaffolded `login-form.tsx` in both `apps/dashboard` and `apps/super-admin`, both using `signInWithPassword({ email, password })`), but SA-04's mockup collects only Gym Name/Owner Name/Owner Phone/Tier/Status — no email. Added a required **Owner Email** field to the Create Gym form and create the owner's `auth.users` account with both `email` (the login identifier) and `phone` (stored for display, matching SA-03's "Owner: Paul Nkusu (+237 6XX XXX XXX)") set via `supabase.auth.admin.createUser`. **Verified necessary, not just theoretical**, via manual end-to-end testing (story 1-5 Debug Log): without an email, the already-built AD-01/SA-01 login form has no way to authenticate a Story-1.5-created owner.

**Decision 6 — SMS invite delivery is stubbed, not real, for this story.** Story 2.1 (SMS/OTP Provider Sandbox Spike, Epic 2) — the story that validates Cameroon SMS deliverability via `TwilioSmsProvider` — is still backlog. Rather than ship unverified real SMS delivery in Epic 1 ahead of that gate (mirroring this project's own established principle: "neither epic begins on an unverified provider," applied to Notch Pay/OTP elsewhere), `createGym`'s invite-send step (`sendInviteSms` in `actions.ts`) logs the invite message (recipient phone + generated recovery link) via `console.info` instead of calling any real telecom API, and deliberately never throws — a failed/stubbed send must not roll back an already-successful gym/owner/member creation. The UI still shows SA-04's mandated toast ("Gym created. SMS sent to [number].") since the gym+owner creation itself did genuinely succeed; this is a known, accepted gap until Story 2.1 lands and this stub is replaced with a real `TwilioSmsProvider`-backed implementation.

**Why these are recorded here, not just in code comments:** the RLS scope (Decision 3), the tier seed shape (Decision 4), and the owner-identity model (Decision 5) are all hard to change once real gyms/owners exist and later stories (1.6, 1.7, 1.8) build on top of them — same category as every other entry in this log.

## 2026-07-08 — Append-only audit log foundation: schema deviations, recorded during Story 1.4

**Decision 1 — `audit_log.id` is a plain UUID primary key, not architecture.md's literal "bigint identity + separate UUID" text.** architecture.md's Data Architecture section names `attendance`/`audit_log` specifically as tables that should use `bigint identity` plus a separate UUID for external reference. In practice, `attendance_events` (Story 1.3, `0006_attendance.sql`) already used a plain `uuid primary key default gen_random_uuid()` instead, with no deviation recorded at the time. `audit_log` follows that actual in-repo precedent rather than architecture.md's unimplemented text, so it isn't the one bigint-PK table in an otherwise all-UUID schema. If this is later reconsidered, `attendance_events` should be revisited in the same pass for consistency.

**Decision 2 — `audit_log.gym_id` and `audit_log.actor_id` are both nullable**, unlike every other gym-scoped table's `gym_id not null`. `pg_cron` job-failure audit records (FR-027/FR-080) aren't scoped to any one gym — `job_runs` itself has no `gym_id` either (architecture.md Entity Relationships: "global, not gym-scoped") — and have no authenticated session to derive an actor from. No gym-switcher/sentinel-gym-row scheme was introduced; `NULL` is the direct representation of "platform-level, not gym-scoped."

**Decision 3 — `log_audit_event()` is the single canonical write path into `audit_log`.** A `SECURITY DEFINER` Postgres function (`0007_audit_log.sql`), mirroring the pattern established by `private.gym_id()`/`custom_access_token_hook()` in Story 1.3. Derives `actor_id`/`actor_display_name` from `auth.uid()` + `public.users.display_name` internally rather than accepting them as parameters, so no caller can spoof the audit trail's own actor field. System/cron callers (no session) pass an explicit label instead. Unlike the Story 1.3 hook functions, it deliberately does **not** swallow exceptions — a malformed call (e.g. a missing `action_type`) is a caller bug that should surface immediately rather than silently producing no audit record. Every future epic that needs to write an audit record (Epic 1 Stories 1.5–1.7, Epic 2, Epic 4, Epic 5) should call this function rather than inserting directly, which would fail under deny-all RLS for anything but `service_role` anyway.

**Decision 4 — `audit_log.action_type` is free text, not a Postgres enum**, breaking the pattern every other closed-set column in this schema follows (`gym_status`, `member_role`, etc.). The full list of action types spans five future epics that don't exist yet, and enum values, once added, cannot be removed or reordered without recreating the type — free text avoids forcing every future epic's story to modify this migration's enum.

**Why these are recorded here, not just in code comments:** same category as the region/claims decisions above — the schema shape (nullability, PK type, write-path convention) is hard to change once real audit records and calling code from later epics depend on it.

## 2026-07-06 — Tenant isolation foundation: three deviations from architecture.md, recorded during Story 1.3

**Decision 1 — RLS helper function lives in a new `private` schema, not `auth`.** architecture.md specifies `auth.gym_id()`. Verified hands-on (local Postgres 17) that migrations run as the `postgres` role, which does not have `CREATE` privilege on the `auth` schema (owned by `supabase_admin`) — confirmed via `permission denied for schema auth`. Supabase's own RLS documentation shows custom RLS helper functions living in a dedicated non-exposed schema (their example: `private`), not inside `auth`. Implemented as `private.gym_id()` instead; every RLS policy in this project should call it under that name. `private` is not in `supabase/config.toml`'s exposed `[api] schemas`, so it is not reachable via PostgREST.

**AC #1 note:** Story 1.3's AC #1 as literally worded ("the `auth.gym_id()` helper function exists") is not strictly met — the function is `private.gym_id()`. AC #1 is treated as satisfied via this accepted, documented schema-naming deviation (above), not a literal name match. Flagged and accepted during code review of Story 1.3 (2026-07-06), same pattern as Story 1.2's AC #1 tiebreak note.

**Decision 2 — the gym-scoped role claim is named `app_role`, not `role`.** FR-003 describes injecting "`gym_id`/`role` claims" into the JWT. Supabase's Custom Access Token Hook documentation lists `role` among the hook's required/reserved claims — PostgREST/GoTrue use it to `SET ROLE` to `anon`/`authenticated`/`service_role` for the Postgres session. Overwriting it risked breaking that mechanism platform-wide. Confirmed via manual end-to-end login testing that the real GoTrue-issued JWT's `role` claim stays `authenticated` as expected when the gym-role is injected under `app_role` instead. Any future RLS policy or app code reading the gym-scoped role must read `app_role`, not `role`.

**Decision 3 — multi-gym-membership resolution rule (V1 limitation).** FR-001 allows a user to hold `members` rows at more than one gym, but a JWT can only carry one `gym_id`/`app_role` pair. No PRD/epics/architecture text specifies which membership wins. V1 rule: the claims hook selects the single most-recently-created, non-deactivated `members` row for that user. No gym-switcher exists in V1 — a user active at two gyms simultaneously only ever sees the most recent one in their session. Revisit if this becomes a real pilot scenario (unlikely at NFR-009's ~30-members/1–3-gyms pilot scale).

**Why these are recorded here, not just in code comments:** all three are hard to change once real user data and JWT-reading code (RLS policies, future Server Actions) depend on the current shape — same category as the region decision above.

**Also caught during this story, fixed in-migration (not a "decision" needing sign-off, noted for context):** the claims hook's own internal lookups (`SELECT` on `users`/`members`) are themselves subject to RLS, since the hook runs as `supabase_auth_admin`, which does not have the `BYPASSRLS` attribute. With `users`/`members` deny-all (this story's own design), the hook could not read the very membership data it needs to compute claims — a bootstrapping deadlock. Fixed by marking `custom_access_token_hook` `SECURITY DEFINER` (runs as its owner, `postgres`, which does bypass RLS). Caught only via manual end-to-end login testing against the real GoTrue flow — pgTAP alone would not have caught it, since pgTAP calls the function directly as `postgres`, which was never subject to the bug.

## 2026-07-05 — Supabase Cloud region: EU West Ireland (`eu-west-1`) selected

**Decision:** EU West Ireland (`eu-west-1`). The already-existing Supabase Cloud project (`vfxezibagiznrirdwkwh`, created during Story 1.1) already lives here — **no project swap required**.

**Context:** NFR-010 requires the Supabase Cloud project to be in the AWS region closest to Cameroon among the two candidates — EU West Ireland (`eu-west-1`) or Frankfurt (`eu-central-1`) — to keep the front-desk alert's <3s end-to-end budget (FR-052) achievable. Region cannot be changed after data is written, so this had to be confirmed before any schema/data lands (Story 1.3+).

**Starting state:** The existing project was created during Story 1.1's dev-workflow course correction (see `1-1-monorepo-starter-initialization.md` Change Log, 2026-07-05) to unblock local dev speed — **before** this region decision was made. Confirmed via Supabase Dashboard → Project Settings → General: region `eu-west-1`.

**Methodology:** RTT measured from a device tethered to MTN/Orange Cameroon mobile data, using AWS's own regional S3 endpoints (`s3.eu-west-1.amazonaws.com`, `s3.eu-central-1.amazonaws.com`) as a proxy for network path latency to each region — Supabase Cloud's EU projects run on AWS in these same regions, so this measures the real network path without needing a live Supabase project in both candidates. `curl -w`'s `time_connect` (TCP handshake) was used as the RTT signal; `time_total` was not used since it's dominated by response-size/TLS variance rather than network distance. Two independent rounds were run (round 1: single sample each; round 2: 5 samples each), from the same Cameroonian mobile connection.

**Measured data (`time_connect`, seconds):**

| Round | Ireland (`eu-west-1`) | Frankfurt (`eu-central-1`) |
|---|---|---|
| 1 | 0.101 | 0.099 |
| 2 (5 samples) | 1.018*, 0.041, 0.053, 0.070, 0.073 | 0.149, 0.070, 0.046, 0.039, 0.078 |

\* Round 2's first Ireland sample (1.018s) is a clear cold-start outlier (DNS/TLS session not yet warm) — excluded from the statistics below, consistent with standard latency-measurement practice.

**Result:** Median `time_connect` across all valid samples — Ireland ≈ 70.0ms (5 valid samples), Frankfurt ≈ 74.0ms (6 valid samples). Trimmed-mean gives Ireland ≈ 67–74ms, Frankfurt ≈ 74–80ms depending on exact exclusion. **Both regions are within measurement noise of each other — a statistical tie, not a clear winner.**

**AC #1 note:** AC #1 as literally worded ("the lower-latency region is selected") is not strictly met — no region measured as clearly faster. AC #1 is treated as satisfied via an explicitly accepted tiebreak-on-tie rule (churn avoidance, below), not a measured win. Flagged and accepted during code review of Story 1.2 (2026-07-05).

**Rationale for selecting Ireland given the tie:** with no measurable latency advantage either way, the tie-breaker is avoiding unnecessary infrastructure churn — the existing project is already in `eu-west-1`, is empty (no data written), and recreating it in Frankfurt would deliver no latency benefit while costing a project swap, `.env.local` updates in two apps, and a re-verification of the Story 1.1 dev workflow smoke test. Ireland also came out marginally ahead in every calculation method tried (median and most trimmed-mean variants), even though the margin is not statistically meaningful on its own.

**Outcome:** No Supabase project swap needed. `apps/dashboard/.env.local` and `apps/super-admin/.env.local` are unchanged and remain correct.

**Follow-up:** Monitor real front-desk check-in-alert latency in production once Epic 3's check-in flow ships; revisit this region decision if the <3s end-to-end budget (FR-052) is at risk, since the region choice going in was a statistical tie rather than a clear win.
