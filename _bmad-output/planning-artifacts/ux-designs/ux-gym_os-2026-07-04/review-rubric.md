# Spine Pair Review — gym_os

## Overall verdict
The mechanical spine — UJ→Flow mapping, FR citations, Story citations, absence of dangling mockup references — is exceptionally clean; every one of the 11 PRD user journeys has a corresponding Key Flow, and every FR-/Story- reference in EXPERIENCE.md resolves to a real ID in the PRD/epics.md. There is one substantive, repeatedly-relied-upon gap that would actually stall a developer: no hex values exist anywhere for the green/red/orange/amber/gray semantic status colors that status badges, front-desk alerts, check-in overlays, and the new V1.5 trend chart all depend on — despite an explicit "see DESIGN.md for token values" pointer (line 2314) that resolves to nothing, since DESIGN.md defines only `primary`/`accent`/`background`. Everything else found is a minor consistency or specification nit, not a blocker.

## 1. Flow coverage — strong
Extracted all 11 UJs from the PRD (UJ-1, UJ-2a, UJ-2b, UJ-3 through UJ-10) and matched each against EXPERIENCE.md's `## Key Flows` section (Flow 1 through Flow 11). Every UJ has a corresponding flow with a named protagonist, numbered steps, and an explicit "Climax beat" line. No missing flows.
### Findings
- **low** Flows 1–6 (the V1.0 carryover flows) are not tagged with their source UJ ID the way Flows 7–11 explicitly are (e.g. "Flow 7 · Grace Staffs Her Gym *(V1.5, UJ-6)*"). Flows 1–6 rely on protagonist-name matching alone (EXPERIENCE.md lines 2368–2459 vs. prd.md lines 159–195). *Fix:* add `(UJ-N)` tags to Flow 1–6 headings for symmetry with the V1.5 flows.

## 2. Token completeness — thin
Extracted DESIGN.md's three frontmatter/table tokens (`primary` #1B2A41, `accent` #E0971F, `background` #FAFAF7 — DESIGN.md lines 8-11, 29-33), all of which carry hex values. Searched EXPERIENCE.md for `{path.to.token}`-style references — none exist; all color mentions are informal prose ("accent color," "primary color"). By the letter of the formal-syntax check this is a clean pass. But EXPERIENCE.md's Accessibility Floor section explicitly delegates to DESIGN.md for exactly the values that are missing.
### Findings
- **high** EXPERIENCE.md line 2314 reads: "Color contrast: All text meets WCAG 2.1 AA... See `DESIGN.md` for token values" — but DESIGN.md has no tokens for the green/orange/red/amber/gray status-semantic colors that this line's own context (badges, alerts) depends on. A developer following this pointer to check contrast on a status badge finds nothing to check against. *Fix:* either add `success`/`warning`/`danger`/`neutral` color tokens with hex values to DESIGN.md, or change EXPERIENCE.md's cross-reference to point at wherever those values will actually live.
- **high** The status-badge color vocabulary (Green/Orange/Red/Gray, defined once at MA-09 lines 627-633) is reused by name across at least 6 other surfaces — AD-03 (line 1089), AD-08 (line 1277), AD-11, AD-14, SA-07 (line 1855, which explicitly says "same badge visual language as member subscription status elsewhere in the product") — and by the front-desk alert panel (yellow/red, lines 1878-1885) and check-in result overlays (green/red/amber, lines 700-748) — with no hex value defined anywhere in either file. This is pre-existing (not introduced by V1.5) but V1.5's SA-07 Billing view explicitly leans on it by name. *Fix:* same as above — define the semantic color tokens once in DESIGN.md.

## 3. Component coverage — thin
Extracted new V1.5 UI components: weight trend line chart (MA-15), photo grid/timeline with lock-icon overlay (MA-15), segmented control (MA-11/MA-16, reused pattern), toggle (MA-12 notifications, MA-15 photo share), drag-to-reorder exercise list (AD-15 Workout Plan tab), status badges (reused everywhere). DESIGN.md's lack of a Components section is a stated, deliberate choice (DESIGN.md lines 26-27) and is not itself a defect. Judged each new component against that stated deferral.
### Findings
- **medium** The weight trend line chart (MA-15, EXPERIENCE.md lines 908, 925) specifies axes, interaction (tap-for-tooltip), and an accessibility fallback, but never specifies a charting library/approach or the line's color/style — unlike typography/shadows/radius, "which library renders this chart and what color is the line" is not a thing framework defaults resolve for free the way a `<Button>` component's shadow is. This is a genuinely new visual decision with no owner in either file. *Fix:* name a charting approach (or explicitly state "framework default RN chart lib, accent-colored line") in DESIGN.md or EXPERIENCE.md.
- **medium** Same root cause as Section 2's status-color finding: status badges, alerts, and the progress-delta color rule ("green if trending toward goal, otherwise neutral gray, never red" — MA-15, line 924, itself flagged `[ASSUMPTION]` in .memlog.md) are components that are behaviorally well-specified but visually undefined. Segmented controls, toggles, and the drag-reorder list, by contrast, are adequately covered by the framework-defaults deferral — no further action needed on those three.

## 4. State coverage — adequate
Walked every V1.5-tagged surface in the Surface Index (MA-15, MA-16, AD-16, AD-17, AD-18, AD-19, SA-07) against the Empty States (lines 2078-2107), Loading States (2109-2138), and Error States (2144-2183) tables plus each screen's own Screen Reference section.
### Findings
- **medium** MA-15 Progress has Empty (line 2100) and Loading (line 2134) coverage but no entry in the Error States per-screen table (lines 2153-2183) for a screen-load failure (e.g., chart/measurement data fails to fetch on first open with no cache yet) — MA-09's equivalent home-load failure has an explicit treatment ("Couldn't load your info. Pull down to refresh," line 2164) that MA-15 lacks a parallel for. *Fix:* add an MA-15 row to the Error States table.
- **medium** SA-07 Billing's four row-override actions (mark payment received, apply credit, trigger retry, suspend/reactivate — lines 1859-1863) have no specified failure treatment if the underlying action fails (e.g., suspend action errors mid-request). Given "Suspend" denies access to an entire gym's staff and members, an unspecified failure mode here has real downstream stakes. *Fix:* add SA-07 override-failure rows to the Error States table.
- **low** AD-16 Staff List and AD-18 Classes List have Empty (2105, 2106) and Loading (2136, 2137) coverage but no Error States entry (e.g., list load failure, or a Deactivate/mark-attendance action failing server-side beyond the role-ceiling case AD-17 already covers).

## 6. Bloat & overspecification — adequate
Checked for pixel-level specs where a token would do, restated source content, prose-vs-table mismatches, and decorative narrative untied to a decision.
### Findings
- **low** Avatar/photo-circle sizes are specified ad hoc per screen with no stated system: 36px (MA-09 header avatar, line 614), 40px (Front-Desk Alert Panel avatar, line 1894), 56px (AD-15 header, line 1657), 64px (MA-12 avatar, line 802), 72px (AD-04 header, line 1112), 80px (MA-05 photo upload circle, line 450). None of these is wrong individually, but the lack of a stated avatar-size scale is exactly the kind of "typography/shadows/radius" decision DESIGN.md says it defers to framework defaults — yet these are spine-authored numbers, not framework defaults. *Fix:* not urgent; a future pass could define 2-3 avatar-size tiers.
- **low** A few implementation-level identifiers leak into the behavior-level spine: `private.current_gym_status()` (SA-07, line 1863), `saas_billing_payments` / `payments` table names (Flow 11, line 2527), `book_class_session()` (MA-16, line 972). These read as architecture-spine content bleeding into the UX spine's stated scope ("governs behavior, layout, and interaction" — line 16). Not incorrect, just a scope-boundary blur; harmless for a developer who has both docs open.

## 7. Inheritance discipline — adequate
Cross-checked every `FR-NNN` citation in EXPERIENCE.md against the PRD (none undefined — full diff came back empty) and every `Story N.N` citation against epics.md (all 12 distinct story references resolve). Checked component-name consistency and the FR-087–FR-140 range specifically.
### Findings
- **medium** `AD-21` is cited twice in EXPERIENCE.md (line 972: "`book_class_session()`, AD-21"; line 2200: "Class capacity race (FR-105, AD-21)") referring to an *architecture-decision* ID from epics.md's separate AD-numbering system (epics.md has AD-3, AD-6, AD-14, AD-15, AD-21, AD-24 as architecture decisions). This collides with EXPERIENCE.md's own Surface Index, which uses `AD-01` through `AD-19` for Admin Dashboard page IDs. A reader relying on EXPERIENCE.md's own Surface Index to resolve "AD-21" will find nothing (max page ID is AD-19), and may confuse it with a missing screen rather than an architecture decision. *Fix:* rename the architecture-decision citations to a distinguishable form (e.g. "Architecture Decision AD-21" or "ARCH-AD-21") wherever they appear in EXPERIENCE.md.
- **low** Flow titles in Key Flows use the protagonist's name/scenario ("Flow 7 · Grace Staffs Her Gym") rather than the PRD's verbatim UJ title ("UJ-6: The Owner staffs their gym") — correspondence is unambiguous (matching protagonist names, and V1.5 flows carry explicit `(UJ-N)` tags) but titles are not literal matches. Not a defect, just worth noting for anyone doing an automated UJ↔Flow string match.
- **none** Status-badge terminology and "Progress tab" / "Workout Plan tab" naming is used consistently across every section that references them (Surface Index, IA diagrams, Screen Reference, State Patterns, Key Flows).

### Findings
- **low** "Component Patterns" is satisfied in spirit by Screen Reference + Cross-Cutting Components, but the one place a literal Component Patterns section would have added value — a single canonical Status Badge definition — is instead redefined per-screen with slightly different enumerations each time (MA-09's table omits "Deactivated" since members never see it; AD-03's inline list adds "Deactivated (gray)"; SA-07 defines its own Active/Past due/Grace period/Suspended set and explicitly gestures back at "elsewhere in the product" rather than citing a specific canonical definition). Content is consistent in practice, just not centralized. *Fix:* not urgent given DESIGN.md's stated no-Components-section policy, but a single canonical Status Badge sub-section under Cross-Cutting Components would remove the redefinition pattern.
