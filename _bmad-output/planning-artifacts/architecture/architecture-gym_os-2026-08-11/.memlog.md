- (decision) [ADOPTED, 2026-08-08 proposal] OTP delivery becomes an ordered fallback chain, not single-provider selection: EvolutionApiProvider -> TwilioWhatsAppProvider -> TwilioSmsProvider -> SentDmProvider, all implementing the existing OtpDeliveryProvider interface. Chain runner replaces send-sms-hook's OTP_PROVIDER-env-var switch; advances to next provider only on failure (network error, non-2xx, or DeliveryResult.success:false); each attempt logged. EvolutionApiProvider gated by its own sandbox spike (Story 2.9, backlog) before joining the production chain -- a spike failure leaves the existing 3-provider chain as production path. Binds: any future OTP-sending code path must call the chain runner, never a single provider directly. Prevents: a new call site re-introducing single-provider coupling.
- (decision) [ADOPTED, 2026-08-08 proposal] New WhatsAppMessageProvider interface (send(phone, message, locale) -> DeliveryResult, free text, no code/template constraint) added alongside OtpDeliveryProvider for non-OTP sends -- starting with member invitations (FR-082, Story 2.10 backlog). V1 ships one implementation, EvolutionApiMessageProvider, called from a Next.js Server Action (sendMemberInvite), following the established Deno-to-Node porting pattern (sendTempPasswordMessage.ts). No new Edge Function -- the two-Edge-Function boundary (notch-pay-webhook, send-sms-hook) is unchanged. - (decision) Immediate role/session revocation (FR-090, extended to FR-089 per proposal's Reviewer Gate finding): RLS stops trusting the JWT's app_role claim for authorization. New STABLE helper private.current_member_role() performs a live lookup against members (scoped by auth.uid() + private.gym_id()) on every RLS evaluation, replacing app_role-claim reads in every policy that gates on role (not just Epic 9's new tables -- an existing-policy migration). gym_id itself stays claim-derived (rarely mutates; the accepted multi-gym-membership edge case is unchanged). A role change or deactivation takes effect on the member's very next query -- no token refresh, no separate revocation-list mechanism. Binds: every RLS policy checking role (existing and future) reads private.current_member_role(), never auth.jwt() ->> 'app_role' directly. Prevents: a new policy re-introducing the stale-claim window this AD exists to close. User-chosen over short-TTL-tokens-plus-refresh-revocation (rejected: platform-wide session-lifetime cost for a staff-only problem, and still not literally immediate).
- (decision) Staff account creation (Epic 9, FR-087) follows Story 1.5/1.11's existing shape: role-ceiling check runs first inside the Owner/Supervisor's normal RLS session (via the create_staff_member RPC, see next decision), then a Server Action uses the service-role admin client to call supabase.auth.admin.createUser (Postgres functions cannot call the Auth Admin API directly -- confirmed precedent from Story 1.5). New staff activation reuses Story 1.11's existing temp-password-over-WhatsApp mechanism as-is, no new activation flow. Binds: staff creation is a Server Action + service-role step, not a pure RLS-native insert. Prevents: inventing a second, divergent activation UX for staff vs. the owner-activation path already shipped.
- (decision) Role-ceiling check (caller cannot create/edit an equal-or-above role -- FR-087 creation, FR-089 edit + self-edit, NFR-013) lives in one canonical SECURITY DEFINER RPC pair (create_staff_member, update_staff_role), internally checking caller-role-vs-target-role against a hard allowlist, mirroring log_audit_event()'s internal-authorization-check pattern rather than deriving actor/role from caller-supplied parameters. Reused by both creation and edit/self-edit call sites so the ceiling rule (Owner creates Supervisor/Manager/Receptionist/Coach; Supervisor creates Manager/Receptionist/Coach only, never Supervisor/Owner; Manager creates nothing) can't drift between them. Rejected: a plain RLS WITH CHECK comparing ranks via a private.role_rank() helper -- viable for the check alone, but the RPC is still needed to gate the admin-client step (previous decision), so centralizing the ceiling logic in that same RPC avoids a second place the rule could diverge. New member_role enum value: supervisor, inserted between owner and manager in the hierarchy.
- (decision) SaaS billing (Epic 11, Flow B: gym-to-GymOS) gets its own saas_billing_payments table, Super-Admin-scoped RLS, distinct from the gym-scoped payments table (Flow A: member-to-gym). Mirrors this codebase's own established precedent (job_runs, audit_log: platform-level/global concerns get their own table rather than a nullable gym_id bolted onto a gym-scoped one -- see docs/decisions.md audit_log Decision 2). PaymentProvider gains a discriminated routing context, {type:'gym', gym_id} | {type:'platform'}, selecting which credential set (per-gym Tara Money via Vault, vs. GymOS's own platform Tara Money account) to use at initiation, verification, and reconciliation -- but each flow's payment rows live in the table shaped for its own RLS audience and its own reconciliation/discrepancy rules (FR-036/FR-137's 4th discrepancy category -- wrong-account settlement -- applies within a flow, not across the two tables). Rejected: a unified payments table with nullable gym_id + a flow enum -- would require every existing Flow-A-only RLS policy and reconciliation query to add a flow/gym_id-null branch it doesn't otherwise need, for a table whose two flows already have fully disjoint audiences.
- (decision) Class booking capacity enforcement under concurrency (FR-105): a SECURITY DEFINER book_class_session() RPC row-locks the class_sessions row (SELECT ... FOR UPDATE) before counting existing bookings and inserting -- atomic check-then-insert in one transaction, self-checking caller role/tenant like check_in()/confirm_renewal() already do (established pattern per docs/decisions.md). Not the partial-unique-index technique used for one-open-check-in (Story 3.4) -- that technique enforces uniqueness (0 or 1), capacity enforcement is a bounded count (0..N), a different invariant needing row-lock + count, not a index constraint. Flagged as an extrapolation from precedent, not a proposal-sourced decision -- confirm during Epic 12 story-writing if a lighter mechanism suffices at pilot scale.
- (decision) Offline-safe workout completion logging (FR-110) extends the offline-queue pattern to a second domain, narrowing but not violating V1.0's 'offline scope limited to check-in queue only' decision (architecture.md Working Decisions: generic-action queueing was rejected for consistency risk on sync). Workout completion is a simple idempotent upsert keyed by client_id (mark exercise/session complete, no financial or state-machine complexity, no analogous timeout-backfill concept) -- the consistency risk the V1.0 decision guarded against (ambiguous partial-import-like conflicts) does not apply here. Mobile app's existing offline-queue infrastructure (built for check-in) is reused with a second queue-item type, not a second bespoke sync mechanism. Flagged as an extrapolation, not a proposal-sourced decision.
