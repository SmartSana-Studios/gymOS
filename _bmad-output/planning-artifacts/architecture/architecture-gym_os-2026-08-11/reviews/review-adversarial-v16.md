# Adversarial review: ARCHITECTURE-SPINE V1.6 ADs (AD-4 amended, AD-21 last sentence, AD-27..AD-32)

Reviewer stance: construct two independently built stories that each obey every AD literally and still clash; verify every claim about existing code against `supabase/migrations`. The spine was not edited.

Verdict: NOT READY to hand to story-writing as is. Four ADs (AD-29, AD-30, AD-31, AD-32) contain a rule that is either contradicted by shipped code or leaves a shared-data shape open for two stories to fill differently. All fixes are spine edits of one or two sentences each; none requires re-architecture.

## Findings (severity: H high, M medium, L low)

### F1 [H] AD-29 "a denial is a returned result row carrying a stable code" is incompatible with `check_in()`'s contract and with older mobile builds; the [ASSUMPTION] is false as written
- `check_in()` is `RETURNS attendance_events` (0090 line 413); a denial today is a **null** return (0034/0090). The mobile client (`apps/mobile/src/services/checkin.ts` lines 82-97) does `if (!data) return {status:'expired'}; return {status:'success', checkedInAt: data.checked_in_at}`.
- Consequence A: if a story returns a non-null "result row" (new composite/jsonb type, which also needs DROP+CREATE as 0028 did), every older build treats it as **success** with `checkedInAt: undefined`. A denied guest looks admitted: the exact bypass NFR-021 forbids.
- Consequence B: if a story keeps null, older builds show the **expired-membership** copy, not "see the front desk" (FR-159). The spine's assumption ("older builds map an unknown code to see-the-front-desk copy; verify against 0027") is already answerable: they do not. Offline sync (`checkin.ts` ~line 148) also deletes the queued record whenever `error` is null, so a null denial is silently dropped locally (acceptable per FR-161 only if the server wrote the attempt + alert, which F4 shows is under-specified).
- Class path: `mark_class_attendance()` returns `class_bookings` and null on denial (0068/0090 ~line 1346); "a class-attendance denial uses the same code" has no carrier either.
- Two stories (check-in vs class marking) will each pick a different carrier. The AD must fix: new function name/overload for new builds vs. keep old signature returning null + side-channel, and state what old builds will show. Recommend: keep `check_in()` null-on-denial for old builds (accept expired copy or ship a client gate), add `check_in_v2` returning the coded row, and say which one the old offline queue calls.

### F2 [H] AD-29 "called by `check_in()` and class marking and by nothing else; no other path may write `attendance_events`" has no enforcement mechanism, and `attended_at` has the same hole
- `0006_attendance.sql:20` grants `insert, update, delete` on `attendance_events` to `authenticated, service_role`; only the absence of an INSERT policy blocks `authenticated`. `service_role` (Server Actions admin client, Edge Functions, scripts) bypasses RLS. Same for `class_bookings` (0058 line 52 grants insert/update/delete; no UPDATE policy).
- NFR-021 says "any dashboard or script". The AD states a rule but names no DB-level guard (revoke of insert/update on those columns, or a BEFORE INSERT trigger on `attendance_events` that requires a GUC set by `consume_guest_session` or an uncharged-gym path). A story author obeying the AD to the letter writes only the RPC and leaves the service-role door open.
- Also: `mark_class_attendance` does `update class_bookings set attended_at = now() where id = ...` with no `attended_at is null` guard. A second mark for the same booking re-runs the dispatcher; if consume is called before the update (as AD-29/AD-21 imply), re-marking a booking consumes a second session or re-awards a stamp. The AD must require idempotency per booking (no-op when `attended_at` is already set) and say whether the consume call is skipped.
- NFR-021 "never more than one session consumed per gym-local day" is only guaranteed by the lock. No partial unique index on `guest_sessions (member_id, covered_day) where consumed_at is not null and voided_at is null` is specified; AD-22's own philosophy ("DB-level enforcement of record, not app-side") is not applied here.

### F3 [H] AD-27 lock order is incomplete and its own cited precedent (0100) does not take the member lock the way the AD implies; deadlock reachable
- AD-27: "Lock order is payment row -> member row -> `guest_sessions` rows, everywhere (0100)". Actual 0100 `complete_verified_payment()` (lines 217-350): it updates `payments` (row lock) and then, for fees, updates `members`; for subscriptions it **reads** `members.deactivated_at` with no `FOR UPDATE` and inserts into `subscriptions` (FK key-share only). Only the `record_*`/`initiate_*`/`waive` RPCs use `for update` on the member. AD-30 requires the renewal stamp "in the same transaction", and AD-29 requires "SELECT ... FOR UPDATE on the member row" for consumption, so `complete_verified_payment()` and `confirm_renewal()` must start locking the member; the AD never says so, and a story that adds `award_renewal_stamp()` without the member lock races a concurrent consume on `loyalty_progress`.
- The order list omits every other row lock that actually exists: `attendance_events` open row (`check_in()` takes `FOR UPDATE` at 0090 ~line 530, *before* any member lock in the current body), `class_sessions` (`book_class_session`, 0058 line 172), `class_bookings`, `loyalty_progress`, `loyalty_events`, `front_desk_alerts`, `subscriptions`. Concrete clash: Story X places `consume_guest_session()` after the open-row lock (attendance -> member); Story Y (staff check-out / deactivate / any member-first function) goes member -> attendance. Both obey AD-27/AD-29 text.
- `FOR UPDATE` on `members` conflicts with the key-share lock that any FK insert (payments, attendance_events, front_desk_alerts) takes on the member row. A transaction that inserts a row referencing the member first and then requests `FOR UPDATE` (the desk session-payment RPC inserting its payments row, then locking the member) deadlocks against a concurrent one doing the same. `FOR NO KEY UPDATE` or "lock the member before any insert" must be stated.
- The daily sweep (AD-30) is a third actor: it updates `guest_sessions` (lapse) and `loyalty_progress` (reset). Whether it takes the member lock first, and in which order it touches sessions vs progress, is unspecified; consume does member -> sessions -> progress.

### F4 [H] AD-31 `kind` column: the shipped call sites, the column-pin trigger and the dismissal paths are not accounted for; `scan_id` has no source for online or class denials
- Five existing statements use `on conflict (member_id, status) where dismissed_at is null do nothing` (0034 check_in, 0068 mark_class_attendance, 0090 lines ~511, ~596, ~1332 for check_in and class marking). If the index becomes `(member_id, kind, status)` and the old index is dropped, every one fails at runtime ("no unique or exclusion constraint matching the ON CONFLICT specification"). The AD does not tell stories that all five must be re-issued in the same migration, nor that `kind` needs `default 'subscription_status'` so unamended code keeps inserting valid rows.
- `front_desk_alerts.status` is `subscription_status NOT NULL` with `front_desk_alerts_status_check in ('expiring_soon','grace_period','expired')` (0034). The AD says `status` "stays the three subscription values", so a session-denial alert must carry a fake subscription status. Which one? Two stories (check-in denial, class denial) will pick differently and renewal-dismissal logic ("recording a renewal dismisses FR-049 alerts") will then dismiss or ignore session alerts depending on the pick. The AD must name the status value and require every dismissal path to filter on `kind`.
- `front_desk_alerts_protect_columns()` (0034) lists the pinned columns explicitly (gym_id, member_id, status, expiry_date, created_at). A new `kind` column is **not pinned**; any staff UPDATE through `gym_staff_dismiss_own_front_desk_alerts` could rewrite `kind`. The AD needs "trigger amended to pin `kind`".
- `session_attempts` unique on `(gym_id, scan_id)`: `check_in()` receives `p_client_scan_id` which is **null for every online scan** (0090 header). Null scan ids are distinct in a unique index, so online repeats are never deduped and the NOT NULL question is open. Class marking has no scan id at all. The AD needs a rule for generating a server scan id (e.g. booking id for class, a generated uuid for online) and for dedup semantics when `scan_id` is server-generated ("repeated scans carrying the same scan id are one attempt" is only about offline retries).
- Also: `front_desk_alerts_read` / dismiss policies use `auth.jwt() ->> 'app_role'` over `owner, manager, receptionist` (0034), amended by 0093 to add supervisor. The PRD wants Owner/Supervisor/Manager on the card and receptionist alerts; the new tables' RLS roles are not stated (see F8).

### F5 [M] AD-32 mis-describes the 0098 shape and leaves the shared trigger as a last-writer-wins hazard
- Claim: setters check role "via `private.current_member_role()` (AD-3)" in "the `set_registration_fee()` shape, 0098". Actual 0098 `set_registration_fee()` checks `(auth.jwt() ->> 'app_role') = any(array['supervisor','owner'])` and then `private.gym_id()`, not `current_member_role()` (which exists since 0061 and is what AD-6 uses). The AD is internally inconsistent with the code it points at; a story copying 0098 verbatim will violate AD-3 as AD-3 states it, a story following the AD will diverge from the shape.
- "the sole holder of **the** GUC that `protect_super_admin_only_gym_columns()` honors": 0098 uses a GUC **per setting** (`app.registration_fee_update_bypass`; 0072/0077 each add their own). If three new setters reuse one GUC name, any one of them can write any pinned column in that transaction. If each gets its own, each story must `CREATE OR REPLACE` the whole trigger function; 0072, 0077 and 0098 each copied the prior body "verbatim plus", so two parallel stories (charging flag, loyalty) will each overwrite the other's pin. The AD must say "one GUC per column; each migration re-reads the current body from the DB and appends a single clause" or move to a table-driven pin.
- Backfill/default trap: "`charge_guests_per_session` is backfilled `false` for all existing gyms and defaults `true` for new ones". `ADD COLUMN ... NOT NULL DEFAULT true` fills every existing row with `true`: production gyms (live since 2026-09-10) would start blocking guest check-ins on deploy. The AD should require add-with-default-false, then `ALTER ... SET DEFAULT true`, plus a post-condition assertion like 0099 does.
- Super Admin: FR-171 says Super Admin "can edit it afterwards". The AD pins the column against "every other writer, Super Admin included" and names the setter role set as Owner/Supervisor only. Under escalation (AD-5) `current_member_role()` is null for a Super Admin, so no one on the platform side can correct a wrong category. Either the setter admits `is_super_admin()` or the PRD line is unmet.
- Loyalty "enabled/N/K/R" and "one setter per setting": unclear whether that is one RPC or four, and whether N/K/R live as `gyms` columns (pinned by the trigger) or a `loyalty_programs` row (a second owner of the same data). The 2-50/3-24/1-30 bounds (FR-164) belong to the setter; not stated.

### F6 [M] AD-30 ledger key is ambiguous and the grant-source linkage is circular
- "`loyalty_events` ... unique-keyed on the originating event (the consumed `guest_sessions.id`, or the verified renewal `payment_id`)". One consumed session produces `stamp_earned` and, at the N-th, `reward_granted`; a refund of that session produces `stamp_reversed` against the same origin id. A unique index on origin id alone rejects the second and third. Story A will key `(origin_id)`; Story B `(event_type, origin_id)`; the first breaks reward grants and reversals. The AD must define the key as `(gym_id, member_id, event_type, origin_id)` and name the origin for `reset`, `lapse`, `reward_consumed` (sweep events have no originating event).
- AD-28: free session "linked to ... a loyalty grant (CHECK XOR)". Which column: `loyalty_event_id` on `guest_sessions`? Then `reward_granted` (loyalty_events) must exist before the session row, while `loyalty_events` for `reward_consumed` references the session id: a cycle, unless the grant event owns the FK. Not specified; two stories (guest rule vs consumption) will disagree on which table holds the FK.
- Subscriber path: `complete_verified_payment()` inserts a **new** `subscriptions` row with `expiry_date = current_date + duration_days` (0100 lines ~315-330), then the "most recent subscription" is the new row. `award_renewal_stamp()` needs the *previous* expiry for on-time-ness and "one stamp per subscription period", but its signature is not specified; a story reading `subscriptions` after insert evaluates against the new row and always passes as on time. The K-th reward "extends the renewed subscription's expiry by R days" must be defined relative to this insert order. The `enforce_registration_fee_settled` BEFORE INSERT trigger on `subscriptions` (0098) is not an obstacle but is untouched by the AD.
- Reset semantics split: FR-168 says reset is "evaluated when progress is next read or earned and audit-logged then"; AD-30 persists it in a daily sweep and says reads never write. The *earn* path must apply a pending reset itself (else a stamp lands on a stale counter in the window between expiry and the sweep) and must write exactly one `reset` event even if the sweep races it; no key is given for that.
- Citation error: "platform config row (mirrors `tiers`, AD-12)". `tiers` is cited in AD-26 / AD-14 context; AD-12 is the WhatsApp provider interface.

### F7 [M] AD-27 / AD-28: refund and void have no wiring, and "only place" is false for the shipped payment paths
- Refund of a session payment is, today, a plain INSERT into `refunds` under `manager_or_owner_insert_own_refunds` (0101 line ~141: only `purpose <> 'registration_fee'` and `voided_at is null` are excluded). Nothing voids the session. FR-162 requires an atomic "full refund of an unused session voids it, a racing consumption resolves to one outcome". The AD says the void is a definer function but names no trigger/RPC that couples `refunds` insert to it. A refund story (existing refund UI inserts directly) and a session story (builds the void function) each obey their AD and never meet. Needs the 0101 pattern: a BEFORE INSERT trigger on `refunds` that calls the void function under payment -> member -> session lock order, covering service_role, plus partial/consumed rules (full+unused void; consumed -> `stamp_reversed`; partial none).
- Two "void" concepts: `payments.voided_at` (0099/0101, today only meaningful for fees, and excluded from `gym_revenue_mtd`) vs `guest_sessions.voided_at` (AD-28). 0101's comment notes "today only a fee payment can be voided". Does a fully refunded session set `payments.voided_at`? If not, 0101's revenue exclusion and `payment_voided_not_refundable` do not apply; if yes, the 0101 trigger then forbids the refund order. Undefined.
- "`complete_verified_payment()` is the **only** place a verified payment's purpose-specific effect happens": false today. `confirm_renewal()` (0090 ~line 744) and `renew_subscription()` renew directly, and the staff queue policy `gym_staff_verify_own_payments` (0031) lets staff UPDATE a `pending` row to `verified` directly with no effect at all. AD-30 itself lists the three renewal paths, so AD-27 contradicts AD-30. For `session`: if the in-flight index admits `pending` rows and staff can verify one by direct UPDATE, you get a verified session payment, revenue, and no `guest_sessions` row. The AD should say session payments are never `pending` (the staff insert policy is already pinned to `purpose = 'subscription'`, 0099) and that the 0031 verify policy must exclude `purpose = 'session'`.
- "Late session confirmation **is** applied" vs "flagged ... to the wrong account never creates a session": both end states are `payments.status = 'flagged'`. 0100 `complete_verified_payment()` only completes rows `status = 'processing'` and gives the late branch to fees. The expiry helper marks stale rows `flagged`; wrong-account flags are `complete_flagged_payment()` (0046) or staff flag. The dispatcher has no discriminator between "expired-then-confirmed" and "settled to wrong account". A story must add one (reason/flag-cause column, or a status), and the AD should require it.
- "the `protect_payment_purpose_and_void` pin" is listed as something to amend for `session`: that trigger (0099 lines 84-97) is purpose-agnostic (it only restores `purpose`/`voided_at` for `authenticated`/`anon`); nothing to amend. The CHECK named `payments_purpose_check`, the staff insert policy and the notification trigger `WHEN` clause are real touch points.
- In-flight index: the existing index (`payments_one_registration_fee_per_member`, 0099) is "one non-voided non-flagged ever", not "in flight". For sessions the AD uses `pending`/`processing`. A *desk* session payment is inserted already `verified` (immediate), so it is outside that index: the PRD's "desk payment refused while a Tara payment is in flight" and "no two sessions from desk-plus-app overlap" are not met by the index; the check must run under the member lock in the desk RPC, and Tara initiation must conversely refuse when... (nothing to refuse; the late-confirmation rule then grants a second session). State the rule.

### F8 [M] New tables lack the tenancy/suspension scaffolding stories must replicate, and the 0090 coverage test will reject them
- Every table touching gym data has a `tenant_active_gate` restrictive policy (0073; `front_desk_alerts` line 201, `attendance_events` line 141, `class_bookings` line 165) and every writer function carries the fail-closed `is distinct from 'active'` guard (0090 header, its coverage test scans for write statements before the guard). AD-28/AD-30/AD-31 specify "RLS: staff and member read own gym's rows" but not the gate nor the guard; `consume_guest_session()` (private) is called from guarded RPCs, but the sweep and `award_renewal_stamp()` are not. A suspended gym's pg_cron sweep and webhook path will either write into a suspended tenant or be skipped inconsistently.
- Per-role read sets are not stated for `guest_sessions`, `loyalty_*`, `session_attempts` (staff roster in AD-28 is "staff"; 0093 shows `owner, manager, receptionist, supervisor`, coach excluded). Coach roster (FR-174 mentions it) is a plausible fifth reader.

### F9 [M] AD-4 and AD-28/30: "per member row, hence per gym" collides with reactivation
- AD-4 states sessions/loyalty/fee are per `members` row. `idx_members_active_gym_user` (0003) permits a deactivated historical row to coexist with a new active row for the same user/gym (check_in comment, 0090 ~line 470). OQ-17 (reactivation) is undecided. Keyed on `member_id`, a re-registered guest loses stamps and unused sessions to the old row; keyed on `(user_id, gym_id)`, a story reading `members.id` splits. One story picks one. The AD should fix the key now (recommend `member_id` and say reactivation re-uses the row, or state the break).
- AD-4 claim "`list_own_active_gym_memberships()` (0074), the one read allowed to cross the current gym's suspension gate": 0090 line ~1689 lists several functions deliberately exempt (`custom_access_token_hook`, `switch_active_gym`, ...). "the one read" is loose; "the one *list-memberships* read" is accurate. Hook/fallback behaviour (0065 lines 105-135) otherwise matches the amended rule; `switch_active_gym` is 0065; `private.current_member_role` is 0061.

### F10 [L] AD-21 text is stale vs 0068, and AD-29/AD-21 time rules conflict with shipped offline semantics
- AD-21 still says class attendance "is a status column on `class_bookings`". 0068 shipped `attended_at timestamptz` (recorded deviation). The new last sentence builds on a column the AD misnames.
- AD-29: "a client scan time is honored only for an offline scan within the gym's auto-timeout window (FR-045)". Shipped `check_in()` honours any past `p_scanned_at` (clamps only future values) and immediately auto-closes an older one (0090 ~lines 560-600), preserving the true visit time. The AD changes this to "treated as a new visit at receipt time" for older scans at charging gyms only; the AD does not say whether `attendance_events.checked_in_at` is rewritten (distorting history/occupancy) or the coverage day alone moves. Two stories will differ between `checked_in_at` and `covered_day`.
- "Current plan is Pay-per-session" is read from the latest `subscriptions` row by `created_at` in both existing functions; the AD should say that is the definition so the class path and floor path cannot diverge (e.g., one using `members.plan_id`-like shortcuts).
- AD-29 "denied ... writes no `attendance_events` row" interacts with the idempotent-replay short-circuit placed above the suspension guard: a replay of a *denied* offline scan (no row exists) re-enters the full function; this is fine only if `session_attempts` insert is `on conflict do nothing` and the front-desk alert is created exactly once. State it.

## Suggested spine edits (summary)
1. AD-29: name the return carrier and the old-build behaviour; add DB-level guard on `attendance_events` and `class_bookings.attended_at`; add per-booking idempotency and a partial unique index per covered day.
2. AD-27: complete the lock-order list (add `attendance_events`, `loyalty_progress`, `class_*`, `subscriptions`), require the member lock in `complete_verified_payment`/`confirm_renewal`, require `FOR NO KEY UPDATE` or lock-before-insert; wire refund -> void by trigger; session payments never `pending`; add a late-vs-wrong-account discriminator.
3. AD-30: define the ledger unique key with `event_type`; specify the grant FK direction and `award_renewal_stamp()` signature (prior expiry passed in).
4. AD-31: list the five `on conflict` sites, the `kind` default, the status value for session alerts, the column-pin trigger update, and the server-side scan id for online and class sources.
5. AD-32: correct the `current_member_role()` claim, one GUC per column with append-only trigger edits, safe default/backfill migration order, Super Admin edit path.
