# Adversarial re-review: V1.7 Step 1 amended spine, AD-33..AD-41

Reviewed 2026-10-15 against the amended ARCHITECTURE-SPINE.md (AD-3, 4, 6, 17, 20, 26, 27, 32 and AD-33..AD-41), the three first-pass reviews in this folder, migrations 0001, 0003, 0007, 0009, 0018, 0033, 0034, 0052, 0054, 0060, 0061, 0062-0065, 0090, 0093, 0107-0123, and apps/dashboard + apps/super-admin.

**Verdict: yes with conditions.** The amendments close the structural problems of the first draft (support is a distinct role value so denial is default, the gate is split, the actor is a write-time proxy, the hash binds the secret, credentials are versioned, the late webhook is rejected before a write). What is left are holes at the seams with code that already exists: the Super Admin app and its service-role actions decide from the claim alone, about fifteen definer functions and triggers still write `auth.uid()` into attribution columns, `role != 'member'` staff predicates treat the support membership as editable staff, the proxy user needs an `auth.users` row the AD never mentions, and the proposal's displayed values are not bound to the secret. All are fixable by amending AD text and adding story ACs; none requires redesign. Fix N-C1, N-C2 and N-H1 to N-H4 in the spine before cutting; the rest can be story ACs.

Counts of new findings: critical 2, high 7, medium 6, low 5.

## Part 2. New findings from attacking the amended design

### CRITICAL

#### N-C1. The Super Admin app and its service-role actions decide from the JWT claim; AD-38's "is_super_admin() enforces aal2" does not reach them
AD-38, AD-34, AD-5. `apps/super-admin/app/(admin)/layout.tsx:56` and `admins/actions.ts:121` check `claims.app_role !== 'super_admin'` and then act through the service-role admin client (create gym, create admin, and in V1.7 create support accounts, record identity checks, reset factors). The hook (0009/0065) emits `app_role = 'super_admin'` from `users.is_super_admin` with no `aal` check. Enforcing aal2 inside a SQL function protects only database paths that call it; every Server Action that authorizes from the claim and then uses `service_role` is unprotected. A stolen Super Admin password therefore performs support-account creation and factor reset at AAL1 once the flag is "on". That is the control AD-38 exists to provide.
**Fix (AD-38 + AD-34):** once the platform flag is on, the hook omits the `super_admin` app_role claim unless `event.claims.aal = 'aal2'` and emits `aal` into the token; the Super Admin layout and every action that uses the admin client assert `claims.aal = 'aal2'` through one shared `requireSuperAdminAal2()` helper; add the Super Admin app to the AD-34 generated claim-inventory (apps and edge functions, not only policies); support-account creation and factor-reset functions are also definers that call `private.is_super_admin()` (aal2) so the DB refuses even if an action forgets.

#### N-C2. The attribution guarantee is not forced: `auth.uid()` is assigned in about fifteen definer functions and triggers, and the proposed test only catches column DEFAULTs
AD-39 (and its Step 1 gate). Real call sites found: `v_actor_id := auth.uid()` in 0035, 0036, 0037, 0061, 0063, 0090, 0093, 0099, 0100, 0108, 0119, 0121; `connected_by = auth.uid()` in 0052/0054/0083; `updated_by = auth.uid()` in 0050; `new.dismissed_by := auth.uid()` in trigger 0034/0110; `log_audit_event` reads `auth.uid()` and joins `users.display_name`. Refunds (0033, `actor_id not null references users(id)`) are direct inserts where the client supplies `actor_id`. There is no `DEFAULT auth.uid()` in migrations, so the AD's test ("fails if a column defaults to `auth.uid()`") passes vacuously while every one of those paths writes the real support id into a gym-readable column on the first opted-in support write. `private.actor_id()` replaces nothing unless each site is rewritten.
**Fix (AD-39):** (1) a CI gate over `pg_proc` bodies and `pg_trigger` functions that fails any occurrence of `auth.uid()` outside an allow-listed set (RLS self-checks, `private.actor_id()` itself), analogous to the AD-3 grep gate, with the 15 sites migrated as a named story, not a follow-up; (2) for direct inserts, a BEFORE INSERT/UPDATE trigger on each attribution column that overwrites it with `private.actor_id()` when the caller is support (client value ignored); (3) a behavioural pgTAP test per support-writable surface that performs the write as a support session and asserts no column in the gym's rows or audit rows equals the real id; (4) `log_audit_event` display name is "GymOS Support" taken from the proxy row, never looked up from the real user.

### HIGH

#### N-H1. `role != 'member'` staff predicates treat the support membership as an editable staff row
AD-33, AD-35, AD-6. 0062:64, 0063:75 and :215, 0064:205 and 0090 resolve edit/deactivate/resend-password targets with `role != 'member'`. A row with `role = 'support'` satisfies it. Consequences: an Owner or Supervisor can `update_staff_role` the support row to `manager` (allow-list `p_role not in (...)` checks the new role, not the target's current one), converting a time-boxed, AAL2-gated person into permanent non-AAL2 staff with a real name and phone in `members`; `deactivate_staff` ends the membership while the assignment stays `active`, breaking the AD-33 invariant; `resend password` mints a temp password for the support account, bypassing the invite and activation of AD-38. The AD-35 catalog test classifies policies "mentioning `'supervisor'`", which does not find these.
**Fix (AD-33):** every function that targets a staff row must filter `role not in ('member','support')`; replace the `!= 'member'` pattern by one `private.is_staff_role(role)` predicate; add a BEFORE UPDATE/DELETE trigger on `members` that refuses any change to a row with `role = 'support'` or to `role := 'support'` unless a transaction-local GUC set only by the AD-33 assignment function is present; extend the catalog test to flag any function body containing `!= 'member'`, `<> 'member'` or `not in` over `member_role`.

#### N-H2. The support `members` row is readable by every gym staff policy and carries real identity
AD-39. Existing members SELECT policies are `gym_id = private.gym_id() and app_role in (...)`; a `role = 'support'` row in that gym matches. `members.name` is NOT NULL and `phone`, `email` exist (0003), so the row exposes the person's real name and contact to Owner, Manager, Receptionist and via PostgREST embeds. AD-39 states "unreadable to every non-Super-Admin" with no mechanism; `users` has only self-read (so is fine), `members` does not.
**Fix (AD-39):** two layers. (a) Store the support `members` row with `name = 'GymOS Support'`, `phone`, `email`, `dob`, `photo_url` NULL; the real identity lives only in `support_assignments`/`users` (Super Admin-only). (b) Add a RESTRICTIVE SELECT policy on `members`: `role <> 'support' or user_id = auth.uid() or private.is_super_admin()`; also add the exclusion to definer functions that enumerate members (staff list, counts, notification fan-out) via `private.is_support_member()` as AD-33 says, enumerated in the catalog test.

#### N-H3. The proxy `users` row requires an `auth.users` row; the AD never says how it is created or what stops it signing in
AD-39. `public.users.id` is `references auth.users(id) on delete cascade` (0003) and the `on_auth_user_created` trigger inserts the `users` row from `auth.users`. A "proxy users row" therefore means a real `auth.users` identity per gym, including backfill for every live gym. Open questions the AD must answer: unique `phone`/`email` constraints (use a non-routable unique email per gym, phone NULL), sign-in prevention (no password, `banned_until = infinity`, hook returns no claims for `is_support_proxy`), whether anything treats every `users` row as a person (member-app login lookup, notification recipient resolution, exports, MAU, Sentry user context), and failure mode when a gym has no proxy (a NOT NULL attribution column such as `refunds.actor_id` would either fail the write or tempt a fall-back to the real id).
**Fix (AD-39):** gym creation (Story 1.5 service-role step) creates the proxy via the admin API; a one-off service-role script backfills existing gyms before the migration that enables `private.actor_id()`; `users.is_support_proxy` plus `users.proxy_gym_id` with a CHECK that they are set together; the hook, member login and every users enumeration exclude it; `private.actor_id()` raises (fails closed) if the proxy is missing, it never falls back to `auth.uid()`; add a CI test that no `members` row ever references a proxy.

#### N-H4. Nothing calls the gate's VOLATILE touch on direct PostgREST traffic, so idle and velocity limits are unenforced on exactly the paths AD-8 makes primary
AD-34, AD-40, AD-41. `support_gate_touch()` is called by RPCs and edge functions that call `authorize_support_action`. Support reads and the direct table inserts/updates AD-8 allows (refunds in AD-28, notes, check-ins) never reach it. Effect: `last_seen_at` is never refreshed, so the 15-minute idle rule cuts off an active reading session, while the velocity limit (10/hour/gym, 20/hour/account) never counts direct writes, so the cap protects nothing for the highest-volume surface.
**Fix (AD-34/AD-35):** support gets no direct write policies: every write policy gains `private.current_member_role() <> 'support'` by default (RESTRICTIVE policy per table, enforced by the catalog test) and each opted-in write is a definer RPC that calls `support_gate_touch()` first. Define "activity" for idle as RPC call or an explicit heartbeat RPC the support UI fires on navigation and user input; reads do not count toward velocity.

#### N-H5. `owner_reauth` and `stepup_until` are time windows, not single-use, action-bound records
AD-36, AD-40. Both are "recorded within 5 minutes". An Owner who re-authenticated for any purpose, or a stolen Owner session that wins a race with a legitimate reauth, can approve a different proposal inside the window; within a step-up window any number of refunds run. Writer is unspecified: if either table has a client-writable policy the record can be forged. Mechanism feasibility: GoTrue's phone `verifyOtp` mints a new session; a server action can call it on a throwaway client and discard the session, but that creates a session row and counts against OTP rate limits; the AD-11 delivery chain is the send path, so the verify must be GoTrue's own for the record to be trustworthy.
**Fix (AD-36/AD-40):** `owner_reauth(id, user_id, proposal_id, decision, verified_at, consumed_at)`; created only by a service-role server action after a successful provider verify; the approve/reject function requires an unconsumed row for that exact proposal and decision, sets `consumed_at`, `verified_at > now() - interval '5 minutes'`. `support_session_state.stepup_until` is written only by service role, scoped by capability, and money-moving RPCs also take a per-window action count (default 1 for payment-connection, N for refunds). No RLS policy of any kind on either table. Spike: confirm `verifyOtp` side effects.

#### N-H6. The proposal's displayed values are not bound to the secret
AD-36. `hash` covers "merchant fingerprint" without defining it, and `business_id_masked` is a column on the proposal. If the service-role creation function accepts these from the support request, the Owner sees a masked id or holder name chosen by the proposer while the Vault secret holds a different merchant. The digest then binds the secret and the lie together. Recomputing the digest at apply only proves the secret did not change after approval, not that it matches what the Owner was shown.
**Fix (AD-36):** the creation function decrypts the submitted payload inside a definer function, derives `business_id_plain`, `business_id_masked` and the fingerprint (SHA-256 of canonical `business_id_plain`) from it, and stores them; client-supplied display fields are ignored. The hash input list names those derived fields. Apply recomputes them from Vault and refuses on any mismatch, rechecks `state = 'approved'`, `now() < expires_at`, and that `gym_payment_credentials` active row id equals `replaces_credentials_id` stored on the proposal. Confirmation shows the full `business_id_plain` (it is not secret, 0054 stores it plain), not last four. Define the canonical payload serialization (sorted keys, UTF-8, no whitespace) in the AD. Vault read from a definer function is feasible (same pattern as 0052 `vault.create_secret`); verify `vault.decrypted_secrets` access for the function owner in the spike.

#### N-H7. `private.gym_id()` on the hot path becomes a multi-table lookup, and as written would recurse under RLS
AD-34 (amendment to AD-3), AD-4. `private.gym_id()` is `stable`, invoker rights, parses a claim and touches no table (0009). It appears about 280 times across policies and functions, and `current_member_role()` (0061) already calls it per row. AD-34 makes it check assignment, setting, gym status, `auth.sessions` and session limits for support claims. Problems: (a) per-row evaluation of a multi-table lookup in a policy USING is a performance cliff for support sessions on large tables; (b) if left as invoker rights, its queries on `members` run under RLS whose policies call `private.gym_id()`, which is infinite recursion; (c) switching to `security definer` needs an explicit `search_path`, a grant check that the owner can read `auth.sessions`, and re-stating the `revoke ... from public` (0009 note on PUBLIC default execute); (d) non-support callers must stay on the cheap path.
**Fix (AD-34):** `private.gym_id()` reads the claim once, returns immediately when `app_role <> 'support'`; for support it calls a separate `private.support_gate_live(user, gym, session)` marked `stable security definer`, `set search_path = public`, owner postgres; add a performance acceptance test (10k-row table under a support session vs a Manager session, p95 within a stated ratio); document that the function is called once per row and rely on STABLE caching within the statement only for non-support. Verify in the spike that the function owner can `select` from `auth.sessions` on hosted Supabase.

### MEDIUM

#### N-M1. Credentials lock must be shared for initiation, exclusive for apply; initiation order changes AD-27 call sites
AD-33, AD-36, AD-37, AD-27. "Initiations wait on the credentials lock while apply runs" with `pg_advisory_xact_lock` (exclusive) makes every member's payment initiation in a gym serialize against every other. 0100/0109 initiation RPCs currently take the member lock then payment checks; adding the credentials lock "before any row lock" means those functions are reordered or deadlock with apply (which locks credentials and may touch payments). Cap trigger (0018:86) takes its lock on every `members` INSERT of any role, before the role check, so the support membership insert and support-created staff both queue on it: order support, credentials, then cap holds, but state it.
**Fix:** initiation uses `pg_advisory_xact_lock_shared` on `gym:<id>:credentials`, apply uses the exclusive form; `lock_timeout` on initiation so a member waits seconds, not indefinitely; list 0100, 0109 and the desk RPCs as amended call sites; add the namespace to AD-27's "canonical lock order, everywhere" text so there is one list.

#### N-M2. Hook failure path is fail-open for stale claims
AD-34, AD-4. 0009/0065 `exception when others ... return event` returns the unmodified incoming event; the clear-then-set of `gym_id`/`app_role` happened on a local `claims` variable. If a refresh echo carries a prior support `gym_id`/`app_role`, an error in the new support branch (e.g. reading `auth.sessions`) lets the old claim ride. The live check in `private.gym_id()` still denies, so the exposure is claim-only consumers (apps, edge functions).
**Fix:** in the exception handler strip `gym_id`, `app_role` and `is_support` from `event.claims` before returning; add a unit test that forces an error in the support branch.

#### N-M3. Identity separation is one-time; later collisions are unchecked
AD-33 (FR-193). Member self-onboarding (0019) with a phone equal to a support person's, `users.is_super_admin` set on an account with a support assignment (the hook's `is_super` branch wins and ignores the membership), `create_staff_member(p_user_id)` for a user with an active support row, a support person who is a normal member in another gym.
**Fix:** triggers refusing the reverse paths (`users` UPDATE of `is_super_admin` and `members` INSERT of a non-support role where an assignment exists); onboarding phone check against `support_assignments`; state explicitly that a support person may or may not hold member rows in other gyms and how the hook picks (at aal1 the hook must skip `role = 'support'` rows and fall through to other memberships).

#### N-M4. AD-33 invariant is tested, not enforced; membership row lifecycle unspecified
AD-33. "Active support membership implies assignment active and `allow_gymos_support`" is asserted by test only. Owner toggling `allow_gymos_support` runs through an AD-32 setter that does not (yet) end memberships; direct `members` writes by the setters in N-H1 break it. "Exists only while active": delete vs `deactivated_at`. Delete breaks FK from audit and `created_by_support` tags; soft delete interacts with the partial unique `(gym_id, user_id) where deactivated_at is null` (fine) and the hook's `deactivated_at is null` contract (fine).
**Fix:** use `deactivated_at` (soft); a constraint trigger on `members` for `role = 'support'` requiring an `active` assignment and the gym setting; the setter for `allow_gymos_support` calls the assignment function under the support lock and ends memberships in the same transaction; transition table and partial unique index from A-H5.

#### N-M5. Step-up via TOTP verify rotates tokens and may sign out other sessions
AD-38, AD-40. AD-38 accepts that verifying a factor signs out the user's other sessions "at activation and reset". A step-up is a fresh `challengeAndVerify`; if each one revokes other sessions and issues new tokens, a second tab or device is logged out at every refund, and if `session_id` changes, `support_session_state` keyed to the old id loses `started_at` (an 8-hour limit that resets on step-up is not an 8-hour limit).
**Fix:** spike this as a named item; anchor `started_at` to `auth.sessions.created_at` of the session, not a row created lazily by the first touch; key state by `session_id` but carry `started_at` forward if the id rotates, and cap by `user_id`-level `first_aal2_at` for the day; record the verified new session id in the same server action that sets `stepup_until`.

#### N-M6. Support surface and MFA screen are unowned; enum rollout checklist missing
AD-38, AD-33, AD-6. No MFA or aal code exists in apps/dashboard or apps/super-admin; the dashboard layout treats a token without `gym_id` as "no gym". With the hook emitting claims only at aal2, the aal1 step of a support sign-in has no gym claim, so the AD must say which app hosts support and that it routes on `mfa.getAuthenticatorAssuranceLevel()` (`currentLevel aal1`, `nextLevel aal2`) to a challenge screen before any claim-based gating. The MFA API works from the session alone, so rendering the challenge is feasible. Enum: `ALTER TYPE member_role ADD VALUE 'support'` must be its own migration (0060 precedent, "unsafe use of new value" within one transaction); consumers to enumerate in the story: generated types in `packages/types`, dashboard role literals (`AddStaffModal`, `EditStaffModal`, `StaffPageClient`, `Sidebar`, `SettingsForm`, `MemberModal`), the hook's `member_role_value::text` mapping, and the positive allow-lists in `create_staff_member`/`update_staff_role` (0061/0064/0090 use `p_role not in (...)`, so `support` is already refused as a target role, which is correct).
**Fix:** name the host app and the challenge route in AD-38; add the consumer list above as story ACs for the enum migration.

### LOW

1. **L1. Single proxy per gym** makes two support persons indistinguishable to the Owner; intended, but timestamps correlate. State that the Owner's disclosure request (AD-39) is the only path.
2. **L2. Super Admin escalation writes (AD-5/FR-072)** still store the Super Admin's real `users.id` in gym-readable columns; carry-over from A-M9. State whether FR-182 applies to Super Admin and, if so, route escalated writes through `private.actor_id()` as well.
