# Adversarial review — V1.8 spine decisions AD-53–AD-61 and the "Counting attendance (V1.8)" row

Reviewed 2026-11-15. Read-only except this file. Inputs: ARCHITECTURE-SPINE.md (AD-1, 18, 19, 22, 25, 28, 29, 30, 31, 32, 34, 35, 39 and AD-53–61), PRD v1.8 FR-219–FR-251 and NFR-027–029, and the shipped code the new decisions amend (`0111_check_in_session_gate.sql`, `0097_gym_local_period_bounds.sql`, the 0025/0026 attendance policies, Settings `timezone`).

## Verdict

The set is directionally sound (one write path, one view, one ledger, one consume function), but **not ready to story-split as written**. Two things are specified by name only and break on contact: the ledger's correction semantics (AD-53) and the `attendance_counted` view's privilege model (AD-56). Two collide with shipped code (AD-55 against the 0111 `covered_day` CHECK; AD-56's closing "gap AD-29 names" is already closed, so the statement is stale and `check_out`/auto-close writers are not accounted for). A fifth, the stored local day, is needed to make NFR-028's timezone sentence true. Each hole below has a pair of independently built units that both obey every AD to the letter.

Findings: 3 critical, 5 high, 6 medium, 5 low.

---

## CRITICAL

### C1 — `attendance_counted` can be a tenancy hole, and the base table stays readable (AD-56, Convention row, AD-1, NFR-027)

**Pair.** Story A (the view/migration story) writes `create view attendance_counted as select * from attendance_events where voided_at is null` and, so the dashboard occupancy query and the mobile calendar can use it, `grant select ... to authenticated`. Story B (mobile calendar) reads `from('attendance_counted')` through PostgREST. In Postgres a view runs with its owner's rights unless `security_invoker = true`, so the view bypasses the base table's RLS (0025 staff policy, 0026 member policy) and returns every gym's attendance to any signed-in user.
**Second pair, same root.** The Attendance page, member Home and the Overview ("checked in today") already select from `attendance_events` through PostgREST under the 0025/0026 SELECT policies. AD-56 says "no count reads the base table", but nothing removes those policies or lists the existing readers, so a legacy reader keeps counting voided rows while the view's readers do not. Occupancy disagrees with the ring.

**Why both comply.** AD-56 requires only that counts read the view and that writes go through `record_check_in`. It names no view options, grants, or reader inventory. AD-1 is about tables ("every table enables RLS"), and a view is not a table.

**Fix (new AD-56 rule).**
1. `attendance_counted` is created `with (security_invoker = true)` (PG15+; verify the project version at story time), grants SELECT to `authenticated` only, and a pgTAP test proves a member of gym A selecting it sees only their own rows and nothing of gym B.
2. Aggregates over many members (leaderboard, challenge, reminder) read the view only inside `SECURITY DEFINER` functions that filter `gym_id = private.gym_id()` themselves.
3. Replace the base-table SELECT policies with ones that exclude `voided_at is not null` for the member role (a voided visit is not "their visit"), and for staff keep it visible only through the attendance-log read function that returns the `voided_*` columns. Then a legacy reader cannot count a voided row even by accident.
4. Like AD-30, the story enumerates every existing reader of `attendance_events` by grep (apps, packages, functions, edge functions, views), not from this list, and a CI grep fails on `attendance_events` outside an allowlist (`record_check_in`, the void function, the closers in H-10, the view, the backfill).

### C2 — The ledger's correction rule cannot be expressed in its own unique key (AD-53, FR-220, FR-222, NFR-028)

Four concrete collisions, each reachable by two stories that both follow AD-53 literally.

1. **One correction per week.** `week_corrected` is unique on `(member_id, event_type, origin_key=week start)`. Story A (offline sync) appends `week_corrected` when a late visit lands in week W. A second late visit in the same week W, or a void-then-redo, tries the same key and "inserts nothing": the second correction is silently lost.
2. **Day versus week keys.** FR-222 lets a Shield save a missed *day* (daily streak), AD-53's `origin_key` is "the week start date or the milestone number". A Shield used for Monday-the-day and a Shield used for the week starting that same Monday have the same `(member, 'shield_used', date)` key; whichever story writes second is dropped. The daily streak is also "read from `attendance_counted`", so a daily-Shield spend has no home at all.
3. **No reversal of earned things.** The event list has `shield_returned` but no way to undo `shield_earned`, `streak_broken`, `comeback_started` or a `badge_earned`. A correction to week W changes the streak length of every later week, so which weeks are multiples of 4 (where Shields are earned) changes too. Story A appends `week_corrected` and `shield_returned`; story B, settling W+1..W+3, already wrote `shield_earned` at a week that is no longer the fourth.
4. **NFR-028's own test.** `rebuild_engagement` builds a "fresh ledger" from attendance and the test is "matches the live ledger". The live ledger holds correction rows and `acknowledged_at`; the fresh one does not. Either the test can never pass after the first late visit, or it compares only derived state, which AD-53 does not say. Repair by "fresh ledger" also contradicts append-only and would drop `acknowledged_at` (re-celebrating, or losing `silent`).

**Why both comply.** Every one of these follows the text: append-only, keyed, correcting rows "never an edit".

**Fix (rewrite AD-53's rule).**
- Key on `(member_id, event_type, period_kind, period_start, revision)`. `period_kind ∈ {week, day, milestone, badge}`; for a milestone or badge `period_start` is replaced by its code (`7`, `30`, `100`, `first_visit`, `four_weeks`).
- **State is a pure fold.** Streak, best streak, Shield balance (cap 2), comeback and the daily streak are *derived* by one function from `week_closed` rows (each stores `week_start, goal_in_force, visit_days, met`) in week order, plus the Shield spends. Shield spends are decided by the fold, not stored as free-standing facts that later weeks assume. `shield_earned`/`shield_used` rows are a cache of the fold, written by settle and *replaced by a new revision* when a correction changes the fold from week W onward.
- A correction recomputes from the earliest dirty week W to the present in one transaction under the member lock, and appends one `revision = max+1` row per event whose derived value changed (including reversal event types: add `shield_revoked`, `streak_restored`, `comeback_cancelled`). Revision is incremented only when the derived value actually differs, so replay inserts nothing and an A to B to A sequence still flips back.
- Badges and milestones are earned once and are not reversed by a correction or void (FR-230), see H-05; their `visit_day` marker is derived, not stored.
- NFR-028's test becomes: the fold of the live ledger equals the fold of `rebuild_engagement`'s output, compared on derived state. `rebuild_engagement` is a test and diagnostic tool that returns the derived state; a repair appends the diff, preserving `acknowledged_at` and `silent`, and never truncates.
- Add an explicit `engagement_state(member_id, settled_through, dirty_from)` row: the job needs a per-member watermark to find work, and a closed week with no events cannot be told from an unsettled one otherwise.

### C3 — Settle versus a backdated or concurrent check-in is a lost update (AD-53, AD-56, AD-29)

**Pair.** Unit A is shipped `check_in()` (0111:338-341): it takes the member row lock **only when the gym's charging flag is on**. Unit B is `settle_engagement` (job or first-open), which takes the member lock. A gym with charging off (almost all of them) therefore has no common lock between a check-in and a settle.
Interleaving: an offline scan stamped Sunday 23:50 is syncing (honoured within the auto-timeout window, AD-29, 0111:414-434). Settle runs at Monday 00:05, reads `attendance_counted` (visit not yet committed), decides week W missed and writes `streak_broken` or burns a Shield. The check-in commits. Whichever step "appends a correcting row when the week is already settled" ran before settle committed, saw "not settled", and did nothing. The week stays missed with the visit present. No later job repairs it, because settle is idempotent on its own key.

**Why both comply.** AD-53 only says settle takes the member lock; AD-56 never says `record_check_in` takes it; AD-29's lock is conditional by its own scope.

**Fix.** (a) `record_check_in`, `void_staff_check_in` and `settle_engagement` all take the member row lock `FOR NO KEY UPDATE` **first, unconditionally**, in that order, before touching `attendance_events`; the order "member, then attendance, then ledger" is stated once and tested by a concurrency test (two sessions, advisory sequencing). (b) In the same transaction `record_check_in` and the void write `engagement_state.dirty_from = least(dirty_from, week_of(visit))`; settle always starts from `least(dirty_from, settled_through+1)` and clears it. That removes the need for the writer to decide "is the week settled", so the check cannot race. (c) Per-member locking costs one row lock per scan; accept it.

## HIGH

### H-01 — AD-55 collides with shipped `covered_day` rules and cannot answer FR-239 (AD-55, AD-29, AD-28)

- **Shipped constraints.** 0111:107 adds `CHECK (consumed_at is null or covered_day is not null)` and AD-29 specifies a partial unique index on `guest_sessions (member_id, covered_day) where consumed_at is not null`. AD-55 says "covered_day stays for whole_day rows".
  Story A (single-use) writes `covered_day` anyway (the CHECK demands it): the second single-use visit of the day violates the unique index. Story B (single-use) leaves it null: the CHECK fails. Both obey AD-55.
- **No mode snapshot.** `consume_guest_session` "reads the setting inside the same function". Whole-day to single-use at 10:00: a session consumed at 09:00 has `covered_day=today` and a null `covered_attendance_id`. A return visit at 11:00 sees `single_use`, finds no `covered_attendance_id` match and consumes a second session, which breaks FR-239 ("a session already consumed keeps the coverage it had"). The existing 0111 `covered` lookup (`covered_day = v_day`) would accept it only if the function still honours the old mode.
- **Class marking.** FR-238 consumes a session for a class without a visit; AD-21 says class marking never writes `attendance_events`, so `covered_attendance_id` is null. Single-use's "covered only for the visit it was consumed for" has no visit to point at.
- **Insert ordering.** `covered_attendance_id` needs the attendance id, but the denial contract (AD-29: no attendance row on denial, return null) means consume must decide before the insert. The id exists only after.

**Fix (tighten AD-55).** `guest_sessions.validity_mode` (`whole_day|single_use`, written at consumption, never changed) plus `covered_kind ∈ {day, visit, class}` with `covered_attendance_id` or `covered_class_booking_id` (CHECK exactly one per kind). Rebuild the AD-29 unique index as `(member_id, covered_day) where consumed_at is not null and validity_mode = 'whole_day'`, and add `unique (covered_attendance_id)`. Coverage tests are evaluated from the row's own mode, never the gym's current one. `record_check_in` order: lock, FR-031, AD-22 open-visit handling, consume decision (no write for denial), insert attendance, then set `covered_attendance_id` on the consumed session in the same transaction, with a DEFERRABLE CHECK that a consumed single-use visit-kind row carries an id by commit. The AD-22/open-visit check runs **before** consume, so a rejected "already checked in" scan consumes nothing (FR-237).

### H-02 — A void does not touch sessions, stamps or the open-visit index (AD-56, AD-55, AD-28, AD-30, AD-22)

**Pair.** Receptionist checks in the **wrong** member B (a Pay-per-session member with a paid session) through `staff_check_in`; `record_check_in` applies AD-29 and consumes B's session and awards B a stamp. The Manager calls `void_staff_check_in`. AD-56: "appends reversing rows to the ledger (AD-53) and deletes nothing". That is the engagement ledger only. B's paid session stays consumed and B's loyalty stamp stands: the correction of a staff mistake costs the wrong member a paid session and awards a stamp for a visit that never happened. (AD-28's "void" means a different thing, `guest_sessions.voided_at`; the two will be confused.)
**Second pair.** AD-22's partial unique index is on `checked_out_at is null` of the base table, and the FR-044 stale/open lookup (0111:350-353) reads base. A voided open visit still occupies B's one-open slot: B's real scan is refused "already checked in", or a later scan auto-closes a voided row and writes audit noise. AD-56's "no count reads the base table" does not cover lookups.
**Third.** Whole-day: the voided staff entry at 09:00 consumed the session, a real QR visit at 14:00 is "covered" by it. Un-consuming at void time would leave the 14:00 visit uncovered and unpaid.

**Fix (add to AD-56).** `void_staff_check_in` runs under the member lock and in one transaction: sets the `voided_*` columns and **closes the visit** (`checked_out_at = now()`, `checkout_type = 'void'`, or add `voided_at is null` to the AD-22 predicate and to every open-visit lookup); if the visit consumed a session of kind `visit`, or a whole-day session with no other counted attendance on that gym-local day, it releases the session (`consumed_at`, `covered_*` back to null, `usable_until` still honoured) and appends `stamp_reversed` through `private.reverse_session_stamp()`; if another counted visit exists that day under whole-day, the void is **refused with a message** (or the session is re-bound to the remaining visit) rather than orphaning it. A desk payment taken for that visit is not reversed by a void; the refund path (FR-040) owns it and the void message says so. Name the session transition `unconsume`, not `void`.

### H-03 — Local day is recomputed from the current timezone, so NFR-028's "past days do not move" is false (Convention row, AD-53, AD-54, AD-56)

Settings lets an Owner change `gyms.timezone` (apps/dashboard settings, `LocalizationSection`), with no database validation (deferred-work line 1128).
**Pair.** Every count obeys the Convention row: "use the gym's timezone through the one existing gym-local helper". The helper takes the **current** `gyms.timezone`. Story A derives visit days for the ring, story B the leaderboard month and challenge, story C the week close. After an Owner flips Africa/Douala (UTC+1) to Africa/Nairobi (UTC+3) a 23:30 Douala visit is now a day later: a past day moves, a week boundary moves, a closed `week_closed` row disagrees with a re-derivation, and `rebuild_engagement` no longer matches the live ledger. All three obey the row.

**Fix.** `attendance_events.visit_day date` (and `visit_week_start date`, generated or set) is written by `record_check_in` from the visit's recorded time and the gym's timezone **at that moment**, never recomputed, and `attendance_counted` exposes it. A view `member_visit_days(member_id, gym_id, visit_day, first_at)` is the single definition of "a visit day" (distinct per member per day, FR-225) that ring, calendar, leaderboard, challenge, milestones and reminder all read, so none re-derives `count(distinct …)`. `week_closed` rows store their `week_start` and the goal; month membership of the leaderboard uses `visit_day` against a stored month label, not an instant range under the current timezone. Add `timezone` change to the audited-setter list (AD-32 style, it is unaudited today) and validate against the IANA list; a change does not rewrite `visit_day` (backfill-free by construction). Date arithmetic is on `date`, not on timestamptz (the 0097 DST rule, already stated; keep it for week and month end). Weeks start Monday via `date_trunc('week', local_ts)`, and "days left in the week" for FR-233(b) is `week_start + 6 - today` on dates.

### H-04 — AD-58 definer functions can cross tenants and reach body data indirectly (AD-58, AD-1, AD-35, NFR-011/016)

**Pair.** Story A writes `coach_roster(p_coach_id)` `SECURITY DEFINER`, gated by the live AD-34 role check ("Owner, Supervisor or Manager of the caller's gym") and filtering by `p_coach_id`. Story B writes `coach_assigned_members(p_coach_id)` returning the member profile as `to_jsonb(m)`/`select m.*`. Both pass the "body scan" (no reference to measurements, photos, progress notes, completion data).
- A definer function ignores RLS. The AD-34 role check proves the caller manages *a* gym, not that `p_coach_id` belongs to *that* gym. A Manager of gym A passes any gym B coach id and reads gym B's classes, rosters and members. AD-58 says "caller's gym" only for the role, not for the filter.
- The CI check "scans their bodies for those objects" is by name, in the function body. It misses a call through a helper function or view that joins a progress table, and `to_jsonb(row)` or `*` picks up a column added later (Epic 26 already added profession and neighborhood).
- Session notes and authored plans are free text; the PRD accepts that (OQ-34), but the picker also shows "assigned-member profile": confirm no health or injury column exists on `members`.

**Fix.** Each function sets `where gym_id = private.gym_id()` on every table it touches and first asserts the coach belongs to `private.gym_id()` (null-safe), with a pgTAP cross-gym test per function. Return types are `RETURNS TABLE` with a named allow-list of columns, never `*`, row types or JSON of a row. The CI scan walks `pg_depend` transitively (functions called, views read) and fails on any reference to the body-data objects, and a positive test seeds measurements, a photo, a progress note and a completion for a coach's member, then calls every picker function as Owner, Supervisor and Manager and asserts none of those values appears. The functions are `revoke … from public, anon`, and absent from `support_capabilities` (as AD-58 says), checked by the AD-35 catalog test.

### H-05 — Milestone, badge and comeback issuance has no writer, and void or sync moves them (AD-53, AD-56, FR-229, FR-230, FR-223)

**Pair.** Story A (check-in) writes `milestone_reached` for the 7th visit day inside `record_check_in`. Story B (app home read) also computes "total visit days" and inserts the milestone if missing. AD-53 says `settle_engagement` "settles closed weeks"; milestones fire mid-week, so neither it nor the cron covers them. The unique key stops a double row, but the two paths may disagree: with a backdated offline visit the 7th visit **day** is a different date; after a void the count drops below 7 while `acknowledged_at` is set and "a badge is never lost". The number 7 is reached again by a later visit; the key forbids a second row, so the calendar marker is derived from the view (moves) while the row says celebrated. A check-in-path write also puts ledger work on the critical path that NFR-029 says nothing may slow.

**Fix.** One function `private.award_milestones(member_id)` called from settle's tail (job and first-open) and from `record_check_in` via the dirty watermark (C3), never inline in the scan transaction: the scan only sets `dirty_from`/`milestone_check = true`; the app read that follows runs the award. State in AD-53: a milestone or badge row is never reversed; its date comes from the view (`member_visit_days`, the n-th day), not stored; after a void that lowers the count below an awarded milestone the row stays (FR-230) and the calendar marker follows the derived n-th day; `comeback_*` and `shield_*` are folds (C2). The release migration writes `silent` milestone and badge rows from history per gym using each gym's stored `visit_day` (H-03) and an `engagement_epoch` platform config date, so there is one definition of "first full week after release".

## MEDIUM

### M-01 — Leaderboard: the client chooses the month, any session can call it, and cache plus hide can resurrect a name (AD-54, AD-3, AD-34, AD-35)

- **`p_month` from the device.** The signature takes the month from the caller, while the Convention row says boundaries are "never computed on a client". A device a day ahead near month end requests next month's (empty) board; a crafted value scans any range. Fix: `gym_leaderboard(p_months_ago smallint default 0)` limited to 0 or 1 (or an enum), with "current" resolved on the server from the gym's timezone.
- **Gym from a claim only.** AD-3 reads live state for role and status; `private.gym_id()` is claim-derived for non-support roles. A member removed or deactivated keeps a valid JWT for up to its lifetime and can read the board and its names. Fix: the function resolves the caller's **live** `members` row (`user_id = auth.uid()`, that gym, `deactivated_at is null`, gym not suspended) and returns nothing otherwise; staff and support callers get an error (no member row), which also honours FR-251 ("no member-app capability"). Deactivated members are excluded from the ranking itself (state this; the FR is silent).
- **Cache versus hide.** AD-54 forbids a stored board that keeps a name after a hide, then allows a per-gym cache. A cache of `(rank, label, visits)` for the top 10 holds names. Fix: a cache may hold only `(member_id_internal, visits)` ranks and never labels; labels are joined at read from the live setting; or no cache until NFR-029 fails (already the stated default), with the cache invalidated by the hide/notice function in the same transaction.
- **Settings keyed by user across gyms.** If the "member's own settings row" is keyed by user (AD-4 multi-gym), a notice seen in gym A names the same person in gym B before they saw its notice, against FR-227. Fix: the choice and notice-seen time are columns on the per-gym `members` row (or keyed `(member_id)`), and `acknowledge_leaderboard_notice(p_hide boolean)` is the only function that sets `notice_seen_at`; opening the board never marks it seen.
- **Rank order leakage.** Hidden members keep rank and visits (the PRD's choice); ties are ordered by "who reached the count first", which is stable and not an identifier. To keep it that way, ordering uses `(visits desc, first_reached_at asc, member_id)` where `member_id` is only a final deterministic tiebreak and is never returned; the "behind the one above" figure is computed from visits, not from the above row's identity. A test asserts the output set has no column beyond `(rank, label, visits, is_self)` and that two viewers see identical rows for the same top 10 except `is_self`.

### M-02 — `record_check_in` is not the only writer, and its side effects are not source-aware (AD-56, AD-31, AD-29, AD-39, AD-35)

- **Closers.** Check-out, auto-close and FR-044 stale close (0024, 0111:358-366) UPDATE `attendance_events`. AD-56 says `record_check_in` is "the only writer". With INSERT/UPDATE/DELETE already revoked (0111:546, so the sentence "Direct INSERT, UPDATE and DELETE … are revoked … (the gap AD-29 names)" is already done and must say "keeps revoked" and also cover `service_role`), the remaining writers are definer functions: enumerate them by grep and state "`record_check_in` is the only inserter; the closers are the listed set".
- **Alerts and blocked counts on the staff path.** `record_check_in` applies the FR-031 outcome and AD-29, which write `front_desk_alerts` (kind `subscription_status`, `session_required`) and `session_attempts` (source `check_in|class`). FR-249 says no real-time alert for the staff's own entry. A shared function with no `source` guard raises the alert and inflates the Guest-sessions card's blocked counts (the AD-31 sole source). Fix: `session_attempts.source` gains `staff` and is excluded from the card's counts unless wanted; alert creation is suppressed when `source='staff'`; the outcome is returned to the caller in place (the AD-29 "null" is a scan contract; `staff_check_in` returns a coded result since it has no old builds, and says so).
- **Support check-in (AD-35).** FR-251 gives support staff check-in "as a Supervisor". A support person is outside the gym; a remote check-in lights a member's streak, the occupancy count, the leaderboard and the challenge, and can consume a paid session. Fix: `staff_check_in` and `void_staff_check_in` are opted into the registry with `support_step_up_ok()` (money-moving: it consumes a session), logged as velocity-counted by `support_gate_touch()`, and the attribution columns (`entered_by`, `voided_by`) are written through `private.actor_id()` (the AD-39 inventory must include the new columns). Raise to the owner, as a PRD question, whether remote support check-in should count toward the challenge and the leaderboard at all (a `counted_for_engagement` flag is the cheap answer).

### M-03 — Stale-visit rule has two clocks (AD-55, FR-044, FR-045, FR-237)

The gym's auto-timeout (`checkin_timeout_hours`, per gym) closes a stale open visit at `checked_in_at + timeout` (0111:361). AD-55 adds a platform "visit limit" of 3 hours that ends the visit for coverage and says a scan after it "closes it through FR-044's stale handling". If a gym's timeout is 12 h, FR-044 does not consider the visit stale at hour 4: the scan is rejected "already checked in" at hour 3.5-12, the opposite of FR-237. If it does close it, at what `checked_out_at`: the limit, the timeout, or now? Occupancy and the attendance log differ by story. Fix: define `visit_end = least(checked_out_at, checked_in_at + visit_limit)` for single-use gyms only, make the stale test `least(timeout, visit_limit)` there, and close at that instant with `checkout_type='auto'`. Whole-day gyms keep today's timeout unchanged.

### M-04 — First-open settle is a read that mutates, and the job holds locks across a batch (AD-53, AD-19, AD-30, NFR-029)

- AD-30 states "a read is never a mutation". AD-53 makes the member's app open a write. A function exposed as a PostgREST GET RPC is read-only (STABLE) and fails, or on a read replica; and any analyst reading the ring triggers a write. Fix: a separate `POST`-called `settle_my_engagement()` (VOLATILE, own-member only, no member id parameter, no IDOR) that the app calls once per open, and a pure read `my_engagement()` that computes the open week and the *would-be* closed weeks without writing, so a read is still never a mutation. Say so in AD-53, and note it amends AD-30's principle for this one function.
- AD-19 says each cron trigger is its own function and transaction. One transaction over all members holds each member lock until the end, blocking scans (now unconditional, C3) and deadlocking with first-open settles taking locks in a different order. Fix: `engagement_settle` is a procedure that commits per batch of N members ordered by `member_id`, with a per-member exception handler writing the failure to `job_runs` and continuing; one bad member never fails the run (AD-19's independence). It skips suspended gyms (the tenant gate) and deactivated members.

### M-05 — Correct plan: lock scope and "original start date" (AD-59, AD-18, AD-28)

- The member row lock only protects against paths that also take it. The renewal paths AD-30 lists (`confirm_renewal`, `renew_subscription`, `complete_verified_payment`, the staff verification queue) and session purchase do not all lock the member. A Tara Money payment inserted after the "no standing payment" check but before commit slips in, and the correction then overwrites its extension with `original_start + new duration`. Fix: every payment-creating and payment-completing path takes the member lock, or `correct_subscription_plan` re-checks the standing-payment predicate with `FOR UPDATE` on the subscription and its payment rows and fails closed on any row inserted since. Name the AD-18 job: the lifecycle job updates status in bulk without the member lock, so the correction recomputes status inside the lock and the job's UPDATE is guarded with `where updated_at = …` or takes `SKIP LOCKED` on the member row.
- "Original start date": `confirm_renewal` sets `start_date` (deferred-work line 1585). After a payment is voided or fully refunded the start date is already the renewed one, so correction computes from the wrong base. Fix: store `subscriptions.original_start_date` once (the first `start_date`, never updated), backfilled from the earliest start; the audit row records which date was used.

### M-06 — Slot edits race bookings and orphan sessions (AD-57, AD-21)

- AD-21's booking function row-locks the *session*. AD-57's "regenerates only future sessions with no bookings" checks and deletes without the same lock; a booking arriving between the check and the delete is lost or cascade-deleted. Fix: regeneration locks the candidate session rows `FOR UPDATE` and re-checks bookings under the lock, never deletes a session with a booking row even if cancelled-and-restored, and cancels (flags) rather than deletes where bookings ever existed.
- Moving Monday 07:00 to 07:30 leaves the booked 07:00 session as an orphan (no slot) beside a freshly generated 07:30 session the same day, and the next idempotent regeneration lists the orphan again forever. Fix: sessions carry `slot_id` (nullable `on delete set null`) and an `orphaned` flag; the editor list shows orphans once with "keep / move / cancel", and generation keys on `(class_id, slot_id, local_date)` so a slot time change updates the same session when it has no bookings.
- Slot times are naive `time`. Generation converts with the gym's timezone **at generation**; a later timezone change leaves old sessions where they were (consistent with H-03) and the horizon job must run in the gym's zone. The existing ClassModal one-off timezone gap (deferred-work line 682) is untouched, which is acceptable only if stories say so.
- Coach gate `classes.coach_id = the caller` must check the **new** row as well as the old (WITH CHECK): else a Coach edits their own class to set another coach, or edits a class they are about to be assigned. A deactivated coach loses the gate through a live check (AD-3), not through the claim.

## LOW

### L-01 — Weekly goal history (AD-53, AD-61, FR-219, NFR-028)

- **Default has two sources.** FR-219 says default 3 and "a member who has not set a goal uses the default". If the default is read from a constant or platform config at settle time, a later config change re-derives past weeks differently from the ledger. Fix: the default is **materialised** as the member's first `member_weekly_goals` row (effective the first gym-local week they are counted, at creation or at the release migration for existing members) and never read from config again.
- **Who computes `effective_week`.** The member-owned function takes only the goal, computes `effective_week` server-side as the next gym-local Monday (never a parameter), and a trigger rejects any row with `effective_week <= current local week`. A second change in the same week **replaces the pending future row** (explicitly allowed, since it takes effect later and is not history yet; audit via `created_at`), so the unique `(member_id, effective_week)` never raises. Two stories otherwise disagree (one inserts and errors, one upserts).
- **Mid-week change versus open ring.** The open week uses the goal in force this week (the row at or before this week's Monday), so a change made today does not move today's ring; test it.

### L-02 — Reminder job (AD-60, FR-233, NFR-029)

- Claim before send: `insert … on conflict do nothing returning` first, call `send_push_notification()` only if a row was returned, so two overlapping runs never double-send. Re-evaluate "not visited today" immediately before the send and do not hold any lock a scan takes (AD-60 already says no shared lock; also add: read `attendance_counted` only).
- (a) says "a daily streak that would end today", but a held Shield would save it (FR-222); the story decides whether the reminder is suppressed or still sent. Record the answer in AD-60.
- Default-on at release pushes N-08 to every existing member the first evening; add a rollout flag or start date (`engagement_epoch`).

### L-03 — Gym challenge (AD-61, FR-234)

- `unique (gym_id, month)` plus `cancelled_at`: cancelling before the month starts and re-creating hits the unique key. State that create on a cancelled-and-not-yet-started month updates the same row (clearing `cancelled_at`, audited). "Month has started" is the gym-local month (stored `month` is a `date`), evaluated with the current gym timezone through the one helper, and refuses atomically under a row lock so a setter and the first visit of the month cannot interleave into a mid-month change.
- Progress is a sum over members of distinct visit days in the month: it must use `member_visit_days` (H-03), exclude deactivated members only if decided (state it), and exclude support-proxy rows (`is_support_proxy`, AD-39).
- A challenge row written through the Settings general save is prevented by AD-32's pin pattern; add that `gym_challenges` has no direct write policy and `session_validity` has its own pin trigger function and GUC (AD-61 says "the AD-32 pattern" but does not repeat the one-trigger-per-setting rule that AD-32 made load-bearing for parallel stories).
