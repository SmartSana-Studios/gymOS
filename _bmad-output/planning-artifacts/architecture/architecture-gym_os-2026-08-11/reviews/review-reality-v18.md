# Reality check: ARCHITECTURE-SPINE V1.8 (AD-53 to AD-61, "Counting attendance (V1.8)" row) against the codebase

Reviewer: read-only pass, 2026-11-15. Code state: migrations 0001-0172 in `supabase/migrations`, `apps/*`, `packages/*`, `supabase/tests`, `scripts`.
Path prefix `M/` = `/workspaces/gym_os/supabase/migrations/`.

## Verdict

The direction holds and no proposed name collides with anything that exists. But the spine rests on **five claims that are false or materially wrong** and **six more that need rewording or an explicit migration step**. The worst are:

1. AD-56 says direct INSERT/UPDATE/DELETE "are revoked from `authenticated` (the gap AD-29 names)". It was already revoked, from `authenticated` AND `service_role`, in 0111. The gap is closed, so this is stale, not new work.
2. AD-55 and FR-238 assume class attendance goes through a path that has an `attendance_events` row. Class attendance never writes `attendance_events` (it sets `class_bookings.attended_at`), so `covered_attendance_id` cannot anchor a class-consumed session, and "every count reads `attendance_counted`" will not count class-only visits.
3. AD-55 would collide with an existing unique index and CHECK on `guest_sessions` that forbid more than one consumed session per member per day.
4. AD-60 names `send_push_notification()` and a `notification_log` table. The former takes a `subscription_id` and supports only N-01..N-03; the latter does not exist.
5. AD-59 says "recomputes status through the AD-18 function". No such function exists; the transitions are inline UPDATEs in a cron job and never move a row back to `active`.

## 2. check_in() and the session gate

- Live definition: `public.check_in(p_scanned_at timestamptz DEFAULT NULL, p_client_scan_id uuid DEFAULT NULL) RETURNS attendance_events`, SECURITY DEFINER, `search_path public`, in 0124:765. History: 0023, 0027, 0028, 0034, 0090, 0110, 0111, 0124. Returns SQL NULL for a refusal (expired member and denied session). Role gate is `private.current_member_role()` = 'member' (0124:785), gym from `private.gym_id()`. Mobile calls it as RPC `check_in` (`apps/mobile/src/services/checkin.ts`).
- **FR-044 stale-open handling lives inside check_in()** (0124:895-933): `select ... from attendance_events where member_id = ... and checked_out_at is null ... for update`; if `checked_in_at + make_interval(hours => checkin_timeout_hours) <= now()` it sets `checked_out_at = checked_in_at + timeout`, `checkout_type='auto'` and calls `log_audit_event('attendance_stale_check_in_auto_closed')`, else raises `already has an open check-in`. The timeout is the **per-gym column `gyms.checkin_timeout_hours integer not null default 8`** (M/0023:28), not a platform constant. Same close is done by the cron job (0024:44-50) per gym.
  - **AD-55 inconsistency:** "a scan on an open check-in older than the limit closes it through FR-044's stale handling" with a "3 hours" platform limit. FR-044's handling uses `gyms.checkin_timeout_hours` (default 8, configurable, FR-045). Closing at 3 h in single_use mode requires either parameterising the stale branch with a second threshold (visit limit < gym timeout) or defining the visit limit as the effective `least(checkin_timeout_hours, 3)`. Say which. Also say what the closed row's `checked_out_at` and `checkout_type` are (the CHECK allows only 'manual'/'auto').
- **Session gate call:** `private.consume_guest_session(p_member_id uuid, p_gym_id uuid, p_receipt_at timestamptz) RETURNS TABLE(outcome text, session_created_at timestamptz)` (M/0111:128-210, not changed since; confirmed callers are check_in at 0124:941 and mark_class_attendance at 0124:1943). It returns `exempt|covered|consumed|denied`. check_in calls it **before** the attendance insert (gate at 0124:937-961, insert at 984). Order in check_in: replay short-circuit, suspension, deactivation, expired alert, flag read, member lock (FOR NO KEY UPDATE) when charging, open-session lock/stale close, consume, clamp time, insert.
  - **AD-55 consequence:** `covered_attendance_id` cannot be set inside `consume_guest_session` because the attendance row does not exist yet. It must be set by `record_check_in` after the insert (a second UPDATE of `guest_sessions`), or the consume function must be given the attendance id up front (insert first, roll back on denied, which breaks the "denied commits an attempt row" contract at 0124:944-956). The AD should name the choice.
  - `record_check_in` must also keep `private.on_session_consumed()` (0111:116; loyalty stamp hook) and the lock order in AD-29 (class_sessions, payment, member, attendance_events, subscriptions, guest_sessions, loyalty_progress).
- **Class attendance does NOT call check_in() and does NOT write attendance_events.** `public.mark_class_attendance(p_booking_id uuid) RETURNS class_bookings` (live: 0124:1841; session-gate version M/0112_class_attendance_session_gate.sql:68) sets `class_bookings.attended_at`, and calls `consume_guest_session` itself (0124:1943). AD-21 (spine line 153) and AD-29 (line 201: "Class attendance still never writes `attendance_events`") both say so. Consequences for the new ADs:
  - AD-55 "Class attendance marking calls the same function" is true (same `consume_guest_session`), but `covered_attendance_id` has no class analogue; in single_use mode a class-consumed session needs its own anchor (`covered_class_booking_id`, or `covered_class_session_id`). `session_attempts.class_session_id` (0112:56) already exists as the precedent for tagging class events.
  - AD-56/FR-225 "every count reads attendance_counted": class-only visits are not in `attendance_events`, so they are not counted for visit days, leaderboard, streaks, challenge. Either the PRD intends that (state it in the convention row) or class marking must also insert an attendance row (which contradicts AD-21).

**guest_sessions vs single_use (AD-55) collision:** M/0107:219-222 `guest_sessions_one_consumed_per_member_day` is a unique index on `(member_id, covered_day) where consumed_at is not null and voided_at is null`, and M/0111:106-108 adds CHECK `guest_sessions_consumed_has_covered_day` (consumed implies covered_day not null). In single_use mode a member who leaves and returns the same day consumes a second session with the same gym-local day: the unique index rejects it. "`covered_day` stays for `whole_day` rows" is therefore insufficient. The migration must make that index partial to whole_day rows (needs a per-row discriminator, e.g. a `validity` column copied from the gym at consume time, because "no setting change alters an existing row") and relax or conditionalise the CHECK. Also `consume_guest_session`'s "already covered today" lookup (0111:171-182) keys on `covered_day`. Client code reading `covered_day` must change too: `apps/mobile/src/lib/sessionState.ts` (query `covered_day.eq.<day>`, see `sessionState.test.ts:123`), `apps/dashboard/services/guestSessions.ts:42,68,102`, audit label text at `auditLabels.ts:121`, and the 0113 refund trigger metadata (`'covered_day', new.covered_day`, 0113:136). Loyalty stamping (`private.on_session_consumed`) also fires once per consumption, so single_use gives several stamps a day; confirm that is intended (FR-165 wording).
