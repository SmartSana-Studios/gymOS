# Rubric Review (v1.6 update) — ARCHITECTURE-SPINE.md, gym_os

Target: `ARCHITECTURE-SPINE.md` (updated 2026-10-11: AD-4 amended, AD-27..AD-32 added)
Cross-checked against: PRD v1.6 (`prd.md` 6.27-6.29, NFR-021/022, FR-147..155), `supabase/migrations` (0001-0105), `.github/workflows/ci.yml`, `supabase/functions/`.
Not edited: the spine. Prior reviews in this folder (`review-adversarial.md`, `review-rubric-walker.md`, `review-version-verification.md`) predate AD-27..AD-32 and are not repeated.

## Verdict

**Revise before the V1.6 stories are cut (conditional pass).** AD-27..AD-32 are the strongest block in the spine: each names a mechanism, most are enforceable, and they ratify 0097-0100 correctly (purpose set, lock order, gym-local day bounds, setter RPC shape). But three things block "fixes every divergence point": (1) AD-29's denial contract is not reconciled with `check_in()`'s actual return type, which is the single most divergence-prone point in V1.6; (2) the deployment/operations dimension is asserted rather than decided, and one assertion is false; (3) AD-3's lint gate, which AD-27/29/30 lean on, does not exist and has already been violated. A handful of FR-164..FR-174 items have no AD home.

## Top findings (severity ordered)

### F1 — HIGH — AD-29 denial contract contradicts the brownfield `check_in()` and leaves old-build behavior unresolved
- `public.check_in(p_scanned_at, p_client_scan_id)` (0034, last redefined 0090) is declared `returns attendance_events` and signals "blocked" by returning `null` (0034 header lines ~101-111, line 211); other refusals `raise exception`. AD-29 says a denial is "a returned result row carrying a stable code, not a raised exception" and writes no `attendance_events` row. Those cannot both hold: a result-row type changes the function's return type (needs DROP/CREATE, breaks `create or replace` ACL carry-over, and breaks every shipped mobile build's parse of the composite), while keeping the composite gives no place for a code.
- The spine parks this as an `[ASSUMPTION]` ("verify against 0027 result-state handling before the story ships"). That is a decision that must be made in the spine, because mobile, dashboard, and offline sync (0028) all read it. Pick one: (a) keep `check_in()` signature, return `null` for denial and read the code from a new `session_attempts` row / a sibling function; (b) new `check_in_v2()` returning a result row, old name kept as a thin wrapper that maps denial to `null`. Either way state the rule for `mark_class_attendance(uuid)` (0068), which today returns a booking row/raises.
- Also unaddressed: AD-9 says expected errors return `{data, error}`, but at the SQL boundary the precedent is `raise exception` (permission denied, deactivated, already open). The AD should say which SQL-level convention "returned, not raised" extends.

### F2 — HIGH — Deployment/environments/operations: asserted, partly false, and mostly undecided
- **False claim:** the spine says CI runs "pgTAP against a Supabase preview branch (Supabase Branching, not a hand-provisioned staging project)". `ci.yml` runs `supabase start -x edge-runtime,...` and `supabase test db` against a *local* stack in the runner; there is no Supabase Branching. Same file runs a Playwright E2E job (8 specs), which makes Deferred's "E2E test baseline (NFR-015) — mechanism not yet chosen" stale.
- **Local != hosted is a proven hazard, with no AD:** 0104 exists because the hosted project's default privileges grant EXECUTE to `anon`, so 70 functions were exposed in production while every pgTAP run passed. The Conventions row handles new functions, but nothing in CI asserts hosted-equivalent privileges (e.g. a pgTAP check that no `public` function is anon-executable), so AD-27's definer RPCs and AD-30's functions rely on a convention that CI cannot see.
- **Undecided dimensions (neither decided, deferred, nor open questions):** how migrations reach the hosted project and in what order relative to Edge Function and mobile releases (the Epic 18 order lives only in memory/ops notes); rollback/forward-fix policy for a migration that changes a payment or check-in path on a live system; backup/PITR and restore ownership; a staging environment (none; "ship behind a flag" is the only mitigation, and `charge_guests_per_session` defaults **true** for new gyms, so the flag does not protect new tenants); secrets inventory and rotation (Vault, Evolution API, Twilio, Tara webhook secret, `SMS_TEST_OTP` removal is a "checklist" but the checklist is not referenced); `pg_cron` runs UTC (0021 note) while AD-30 adds a daily gym-local sweep; Sentry is "sole observability tool" but mobile crashes are unsymbolicated (sourcemap gap) and there is no stated alerting on `job_runs` failures, on webhook failures, or on the new `session_attempts` volume.
- Recommendation: add one AD (or a Deployment section with an explicit Deferred/Open-Question list) covering release order, flag-gating policy, hosted-privilege assertion in CI, backup/restore, and job-failure alerting.

### F3 — HIGH — AD-3's CI grep-lint gate is not implemented, and has already been bypassed
- AD-3 says a gate "fails the PR" for new `auth.jwt() ->> 'app_role'` call sites and that "27 existing migrations ... are grandfathered". `ci.yml` has no such step (only typecheck, lint incl. i18n gate, locale parity, unit, pgTAP, E2E). 52 migration files now contain the pattern, including the V1.6-adjacent 0099 (3 hits), 0100 (3), 0102 (2), 0090 (several definer bodies). `mark_class_attendance` (0068) and the 0090 RPCs read the claim inside SECURITY DEFINER bodies.
- Consequence for the new ADs: AD-27 (amend the 0099 staff-insert policy, which itself reads the claim), AD-29 (modifying `check_in()`/`mark_class_attendance`) and AD-32 (setters "check role via `private.current_member_role()`") each touch code that still carries the stale pattern, with no mechanical guard. Rule is unenforceable as written; either ship the gate (with a grandfather list keyed by migration number, e.g. "<= 0105") or change the AD to say "when an AD-27..32 migration redefines a function, it replaces the claim read" and say that in each Rule.
- Also AD-3 should say what the live-role helper costs inside the consumption hot path (one extra `members` lookup per check-in) so nobody "optimizes" it back to the claim.

### F4 — MEDIUM — AD-31 alert change under-specified against the shipped index and `check_in()` inserts
- Shipped: `idx_front_desk_alerts_one_active_per_member_status on (member_id, status) where dismissed_at is null`, `status` CHECK limited to `expiring_soon|grace_period|expired`, and `check_in()` inserts `ON CONFLICT (member_id, status) ... DO NOTHING` (0034). AD-31 changes the index to `(member_id, kind, status)` and keeps `status` at the three subscription values. Gaps: (a) what `status` value does a `kind='session'` row carry (NOT NULL + CHECK)? (b) `ON CONFLICT` inference fails if `check_in()` is not redefined in the same migration that swaps the index; the AD should say they ship together; (c) `protect_front_desk_alert_columns` trigger (0034, "only dismissed_at/dismissed_by may be updated") must be taught `kind`; (d) AD-20's channel `gym:<id>:alerts` and the dashboard panel/React Query key must filter or branch on `kind`, or the existing red-alert component will render a session denial as an expired-subscription alert.
- The class-path denial (FR-174) writes the same alert and an attempt; AD-31 lists `source check_in|class` but the dismissal rule ("dismissed by the session-payment definer function") needs to state it dismisses by member across both sources.

### F5 — MEDIUM — AD-27 in-flight rule does not match the 0100 mechanism it claims to extend
- 0099 gives `payments_one_registration_fee_per_member` (one *non-voided, non-flagged* row per member), not an in-flight index; 0100 prevents overlap with the member row lock plus an expiry helper (`expire_stale_registration_fee_payment`, ten-minute threshold from 0032) that flips an abandoned `processing` row to `flagged` before the new attempt. AD-27 specifies "a partial unique index over `status in ('pending','processing')`" per member and purpose and says "cf. AD-22". A partial unique index alone will wedge a member at "payment in progress" until something flips the stale row; the Rule must say the expiry helper (or an equivalent) runs in the same transaction, under the AD-27 lock order, before the insert, and what the threshold is. Also decide whether `pending` (desk, awaiting verification) and `processing` (Tara) share one slot, since FR-158 says a desk payment is refused while a Tara one is in flight.
- "A late session confirmation is applied" vs "a late registration-fee confirmation is not": good, explicit. But the *wrong-account/flagged* path for `session` must also say what happens to a session already consumed-then-flagged (reconcile finds the discrepancy after consumption). FR-158 only covers "never produces a session"; AD-28/29 should say the visit stays counted and the stamp is reversed or not.

### F6 — MEDIUM — AD-30 renewal-path inventory is incomplete or unverified
- AD-30 binds "every renewal-verification path (`confirm_renewal`, `renew_subscription`, `complete_verified_payment`)" and requires one `private.award_renewal_stamp()`. Brownfield also has a staff-verify UPDATE on `payments` guarded by trigger `protect_payment_columns_on_staff_verify` (0031) and `complete_flagged_payment`; the spine does not say which of these actually performs renewal and therefore which must call the award function. Add a path inventory with the migration that defines each, and a pgTAP test that fails if a new function writes `subscriptions.expires_at` for a payment without calling the award function.
- AD-18 interplay (stale): the K-th reward "extends the renewed subscription's expiry by R days". AD-18's four-state machine is derived by the cron from expiry; the extension must happen before the next cron tick re-derives `expiring_soon`/`grace_period`, and must not leave a stale alert or push (AD-25: N-01..N-05 trigger on state change). AD-18 should be amended to say state is recomputed in the same transaction, or that the next tick is authoritative and N-0x dedupe on expiry date.
- AD-30 does not list who awards the **guest** stamp. NFR-021 puts "award the stamp, maybe grant a free session" inside the consumption lock; AD-29 returns covered/consumed/denied and never mentions stamping. Say that `consume_guest_session()` calls the guest award step inside the same lock (and what the `loyalty_events` unique key is for a second class on the same day).
- `stamp_reversed` appears in the event list, but no AD states the refund hook (partial refund no-op, full refund of unused voids session, refund of consumed reverses stamp, free session already earned is kept, floor at 0). FR-162 is a data-layer rule like FR-153; it needs a named function and lock order (payment -> member -> guest_sessions) as AD-27 requires.
