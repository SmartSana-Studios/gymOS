# Rubric review, v1.7 Step 2 (AD-42..AD-48)

Scope: ARCHITECTURE-SPINE.md lines 275-315, against FR-196..FR-208, NFR-024..026, AD-3, AD-4, AD-19, AD-25, AD-33..41 and the "Function privileges" convention. Reviewed 2026-10-15. Spine not edited.

Verdict: the section picks the right seams (views-only schema, snapshot, pure template module, name rows). Four things do not hold as written: the CSP/rendering model, the revalidation path, where `PageContentV1` validation runs, and the "wildcard needs Vercel nameservers" premise behind the DNS move. Detail below.

## Part 1. Findings (ranked)

Severity: C = critical, H = high, M = medium, L = low.

### H-1 (H) AD-44 / NFR-026: `default-src 'none'` + "no inline script" is not achievable with default Next.js rendering, and the fix collides with AD-46 and NFR-025
- Next.js applies nonces only on dynamically rendered pages; static pages and ISR cannot carry a nonce. Nonce CSP disables static optimization/ISR and CDN caching and is incompatible with PPR. The only static-compatible route is experimental SRI (`experimental.sri`).
- App Router emits inline bootstrap/flight scripts. With `default-src 'none'` and no `script-src`, there is no JS at all (scripts fall back to default-src); with a nonce, the pages are dynamic.
- The AD lists only `default-src`, `img-src`, `style-src`, `frame-ancestors`. Missing: `script-src`, `font-src`, `connect-src`, `base-uri`, `form-action`, `object-src`. `style-src 'self'` with no nonce also blocks React/Next inline style attributes.
- Consequence: either (a) pages are dynamic per request (kills the CDN-cache + on-demand revalidation model of AD-46, strains NFR-025 p75 LCP and cost), or (b) CSP quietly gains `'unsafe-inline'` (breaks NFR-026 "no inline script"). The spine does not choose.
- Fix: state the rendering mode and the full CSP as a pinned string; make a spike in Epic 22/24 prove "static/ISR page + zero inline script + hydration-free" (or SRI, or hash-based CSP via build step) before AD-44 is marked decided. Name the PRD fallback trigger for this specific failure, not only the cookie one.

### H-2 (H) AD-46: revalidation path is not buildable as specified
- `revalidateTag` cannot be called from Proxy; it is callable only from Server Functions and Route Handlers. Unpublish/takedown/suspension/rename are DB-side events (trigger, cron, SECURITY DEFINER function). Nothing in the spine calls a Route Handler. It needs a `pg_net` call (the AD-25 pattern) to an authenticated route on `apps/landing`, with a secret, retry, and `job_runs` row. Unspecified, and it is a new credential and a new failure mode.
- Next 16 requires a second argument. `profile: 'max'` is stale-while-revalidate: the next request after takedown is served the stale page. FR-207 needs `{ expire: 0 }` (blocking revalidate). The spine says only "on-demand revalidation".
- "Tags every response by gym" works through `fetch` tags or `'use cache'` + `cacheTag`; a pg driver read is not a `fetch`, so the data function must be wrapped. Not stated.
- "origin <= 60 s, CDN purge <= 5 min" are PRD figures with no mechanism: Next docs say a CDN keeps serving until `s-maxage` unless purged; Vercel's own propagation time was not confirmed (see facts).
- `public_sitemap_refresh` is a Postgres cron (AD-19) but the sitemap is generated by Next; same missing webhook.
- Negative caching: wildcard + not-found response means an unpublished/unknown label caches a 404; the first publish must also invalidate "name not found" entries or the new page is invisible for the 404's lifetime.

### H-3 (H) AD-46 / AD-48: "validates against `PageContentV1` (Zod)" inside a `SECURITY DEFINER` Postgres function is impossible
- Zod lives in `packages/types` (TypeScript). `publish_gym_page()` is SQL. Either the Server Action validates and passes `content` (then the function is not the "only writer" with server-side validation, and a caller of the RPC bypasses Zod), or the DB validates (e.g. `pg_jsonschema` generated from the Zod schema, or hand-written CHECKs), which the spine does not say.
- Interaction with NFR-024: the view column list is pinned by snapshot test, but `content jsonb` is one column; extra keys inside the blob (a stray internal id, `gym_token`, login phone) pass the column-list test. The pin must extend to the JSON keys (strict schema with `additionalProperties: false`, enforced in the DB, plus a test that publishes a seeded gym and asserts the key set).

### H-4 (H) AD-43: "a wildcard certificate requires Vercel's nameservers" is overstated, and the owner's option-A decision rests on it
- Vercel documents a supported alternative for external DNS: delegate only `_acme-challenge` to Vercel via two NS records and keep a wildcard CNAME to `cname.vercel-dns-0.com` at the existing provider. That removes the riskiest step of the AD (moving MX/SPF/DKIM/DMARC and cPanel records, mail outage) and keeps A2 as the authoritative zone. Caveat from Vercel: it can block other providers' certificates that use the same challenge name (A2 AutoSSL for `*.` would be affected only if it used DNS-01 for that name; check).
- The AD should record why full nameserver migration is chosen over delegation, or the decision should be re-opened with this as option A2. Also confirm the Vercel plan supports wildcard domains.
- If nameserver migration stays, gaps in the runbook: DNSSEC DS record at the registrar (must be removed or re-keyed or resolution fails), CAA records, NS-level TTL (lowering record TTLs 24 h ahead does not shorten the registrar/TLD NS cache; rollback by re-pointing NS is also bounded by it), records that A2 cPanel creates (autodiscover, autoconfig, webmail, cpanel, ftp, `_domainkey`), and "A2 zone untouched for 14 days" needs the rule that nobody edits the Vercel zone in the meantime without mirroring (split-brain on rollback).
- No rehearsal environment: nothing says the runbook is dry-run against a throwaway domain/zone first.

### H-5 (H) AD-42: the stated fallback defeats the AD's own Prevents and NFR-024
- Fallback "PostgREST with the schema exposed and a signed role claim": a token for a custom role must be signed with the project JWT secret, which can also mint `service_role`. That is a privileged key in `apps/landing`, i.e. exactly "the public site growing a service-role key". Also exposing a schema via PostgREST makes it reachable by `anon` and `authenticated` through default privileges unless explicitly revoked (the Epic 18 trap named in Prevents).
- Fix: make the fallback "a small separate read-only function/edge endpoint that holds the DB credential, or Supabase direct connection via a Vercel-side secret", or accept failure of the spike as a stop condition; do not offer a fallback that violates NFR-024.

### H-6 (H) AD-42: "no other privilege on any relation or function" is not verifiable by `information_schema` alone
- Postgres default PUBLIC privileges (EXECUTE on functions, USAGE on `public`, CONNECT on database, TEMP) apply to a new login role. The test should assert effective privileges: `has_function_privilege` / `has_table_privilege` / `has_schema_privilege` over `pg_proc`/`pg_class`/`pg_namespace` for the role, including PUBLIC-inherited ones, and role memberships (`pg_auth_members`: not a member of `authenticated`, `anon`, `service_role`, `postgres`).
- Missing role hardening: `ALTER ROLE ... CONNECTION LIMIT`, `statement_timeout`, `default_transaction_read_only = on`, password rotation procedure, and views declared `security_invoker = false` explicitly with owner without BYPASSRLS surprises (views owned by `postgres` skip RLS on `gym_pages` by design; say so, and say the base table has RLS enabled with no policy for this role).
- "Function privileges" convention is not restated for the new functions (`publish_gym_page`, `claim_page_name`, takedown/report functions, `gym_support_status` analogues): each needs the revoke-from-public/anon/authenticated + explicit grant lines. The AD-42 test only covers the public role; `claim_page_name()` is `SECURITY DEFINER` and callable by `anon` under default privileges until revoked.

### H-7 (H) AD-46 / FR-200: a plan marked private after publish stays public (immutable snapshot)
- The trigger "re-evaluates the gate on every change", but a change that does not break the gate (plan flipped private, price edited, address corrected, about text edited to remove a name) leaves the old snapshot live until someone republishes. FR-200 and FR-205 intend private to mean not public. The AD must say: such changes either force an unpublish, or auto-rebuild the snapshot, or the Owner screen shows "unpublished changes" and the retraction of a field is immediate. Without it, "a tenant-side edit appearing publicly before publish" is prevented but "a retraction not taking effect" is not.

### H-8 (H) AD-47: unpublish-deletes-object, logo copy, and CDN lifetime
- Supabase Storage objects deleted via SQL (trigger/cascade) are not removed from the bucket; only the Storage API deletes them. "Unpublish or image deletion removes the object" therefore needs the upload/unpublish server function to call the Storage API (or a service-role job), with retry and an orphan sweep. State it.
- Deleting on unpublish destroys the gallery; republish then needs re-upload or retained private originals. PRD FR-205 says "purged when unpublished", so the choice (private originals bucket) is a design decision to record.
- Public images sit behind Supabase's CDN: invalidation up to 60 s and only on Pro and above (Smart CDN). On a lower plan, or with browser `Cache-Control`, a removed image may remain fetchable. FR-205/FR-207 want purge within minutes: state plan assumption and max-age for `gym-page-media`.
- "The page logo is copied into the new bucket at publish": a raw copy keeps EXIF/XMP from the old logo. Logo and banner must pass through the same sharp re-encode (and the 0014 `gym-logos` objects were stored un-re-encoded). Also no `gym_id` in the logo's key.
- Disallow listing: public bucket needs no `SELECT` policy on `storage.objects` for anon (random keys are the only protection against enumeration); add to the test list.
- Storage origin is `<project-ref>.supabase.co`, a different registrable domain and cookieless (good), but it also exposes the project ref and shares an origin with the Supabase API; acceptable, state it. A vanity/custom domain on it is not covered by the Supabase docs read.

### M-1 (M) AD-43: the proxy trusts only the "first label"
- Must require that the Host is exactly `<one label>.gymosapps.com` (strip port, lowercase, strip trailing dot, reject multi-label such as `a.b.gymosapps.com` which a DNS wildcard also resolves though the certificate will not cover it). Otherwise `acme-landing-xyz.vercel.app` or a preview URL whose first label equals a valid page name serves a gym page on a foreign origin.
- Reserved list should be generated from the DNS zone (every existing label: `mail`, `webmail`, `cpanel`, `ftp`, `autodiscover`, `ns1`, ...), not only the FR-202 list; otherwise a gym can claim a name that today exists only as an explicit record and later loses it when a record is deleted (and FR-202 omits several cPanel names).
- Naming mismatch: AD-43 says "`page_names` reserved table"; AD-45 defines `page_name_words`. One source.
- Observability: no log/metric for proxy 404 rates, wildcard probing, or ISR cache fill; cost of unbounded unknown-host traffic (every random label costs a function invocation and cache entry) is not addressed; no rate limit/WAF stance.

### M-2 (M) AD-44: cookie mechanics are right in principle but under-specified
- See fact check: `cookieOptions.name` is supported, so no custom adapter that "renames and rewrites reads" is needed; a hand-rolled rename is the riskier path.
- `@supabase/ssr` defaults are `path:'/'`, `sameSite:'lax'`, `httpOnly:false`, `maxAge` 400 days, no `secure`: `__Host-` requires `Secure` set explicitly. The browser client writes via `document.cookie`, so `HttpOnly` is impossible for any app that uses the browser client ("where the client allows" hides that the session is script-readable).
- `__Host-` cookies are rejected over plain HTTP (non-localhost dev, LAN device testing, some Safari cases): dev/staging story needed.
- Changing the cookie name logs every existing dashboard/super-admin user out at deploy (storage key change): rollout note and AD-4 `active_gym_id`/session continuity check.
- Test "fails the build if an app emits an auth cookie without the prefix" must cover the code-verifier and chunk cookies (`.0`, `.1`, `-code-verifier`): the prefix is a prefix of the storage key so they inherit it, but the test should assert it.
- "`apps/landing` ignores inbound cookies" is fine, but note `Vary: Cookie` should not be emitted, or CDN caches fragment.

### M-3 (M) AD-46: single-writer claim contradicted inside the AD
- Prevents says "two writers of public state"; Rule says `gym_pages` is "written only by `publish_gym_page()`", then adds a trigger that unpublishes, takedown/report Super Admin functions that write `taken_down_at`, and rename handling. Name the column ownership: snapshot columns (`content`, `published_at`) only by publish; `unpublished_at` by publish/unpublish/trigger; `taken_down_at` by takedown only; with a pgTAP test per column.
- Audit/attribution: publish, unpublish, takedown and rename must write `log_audit_event()` with `private.actor_id()` (AD-39) when the caller is support; AD-46 does not say, and `gym_pages` has no actor column. Support-publish is listed as allowed ("assigned support") but no AD-35 registry opt-in, AD-40 step-up, or AD-41 velocity is mentioned for a public-visible action.
- "Owner is told why" and report/takedown notices should go through AD-25 (pg_net dispatch), not ad-hoc.

### M-4 (M) AD-48: attribute-level injection and the JSON-LD vs lint rule
- "Text nodes only" does not cover attribute values: gym-entered website/WhatsApp/map links rendered into `href` allow `javascript:`; the module needs a scheme allowlist (`https`, `tel`, `https://wa.me/...`) and `rel="noopener noreferrer nofollow ugc"`; image `src` limited to the media origin.
- JSON-LD in a `<script type="application/ld+json">` needs either `dangerouslySetInnerHTML` or text children (React HTML-escapes script text children and breaks JSON). The AD forbids `dangerouslySetInnerHTML` "anywhere in the module" and also requires a serializer: state where the single allowed use lives (outside the module, in `apps/landing`, whitelisted by the lint rule).
- "Immutable snapshot" (AD-46) vs "migration of stored snapshots" (AD-48): say snapshots are replaced only by migration scripts that re-run validation; and a template change shipping a new `schema_version` needs a read path for both versions during rollout.
- Locale: `render(content, locale)` but FR-208 says language alternates are declared only where translated content exists; no `hreflang` ownership stated.

### M-5 (M) AD-45: DB-level guarantees weaker than the Rule's wording
- One name per gym and two renames per 12 months are enforced only in `claim_page_name()`; direct DML is blocked only if privileges are revoked (not stated). Add a partial unique index `(gym_id) WHERE state IN ('held','active','reserved')` and revoke write on `page_names` from every API role.
- Homoglyph/distance-1 folding is function-only; the unique index is `lower(name)` only. State that no other path inserts.
- FR-203 "redirects dropped immediately on takedown or force-rename" is missing; chain handling (A to B to C stays one hop, A repoints to C) is missing; `Cache-Control` <= 5 min is stated.
- Super Admin path: `claim_page_name()` authorizes via `private.current_member_role()`, but Super Admin is not a member role (AD-38 uses `private.is_super_admin()` with AAL2). Rule should name both.
- Held names: "decided within 2 business days" has no job/visibility (a `support_inactivity_sweep`-style table-driven job or queue view) and no SLA reminder.

### L-1 (L) Operations, rollback, environments, cost (cross-cutting silence)
- Rollback is specified only for DNS. No rollback for: `public_site` schema/role (drop order), the new bucket, a bad template release (snapshots pinned to `schema_version` helps), or an unpublish storm.
- No staging or preview story for `*.gymosapps.com` (FR-202 reserves `staging`/`dev` but there is no `*.staging` zone plan; Vercel preview URLs bypass the wildcard).
- Observability: nothing for publish failures, revalidation webhook failures, sitemap job runs (should log to `job_runs` per AD-19, say so), Postgres connection count from the public role, or 404 ratio.
- Cost: Vercel on-demand/ISR writes, function invocations from wildcard probing, Supabase egress for public media on the Free plan (no Smart CDN), connection pooler limits. None is estimated or capped.
- Pooler: transaction-mode pooling (port 6543) and prepared statements for the pg driver in serverless; state the driver config.

### L-2 (L) Consistency with existing ADs

- AD-4: no conflict; note that `claim_page_name` is per gym and uses the active gym, not a client-supplied gym id.
- AD-19: `public_sitemap_refresh` as its own cron is consistent; also the cleanup of released names and expired redirects (12 months) needs its own job, not stated.

## Part 3. Decisions the spine still needs

1. Rendering model for public pages (static + SRI/hash, or dynamic + nonce) and the exact CSP string; adjust NFR-025/NFR-026 or AD-46 caching to match (H-1).
2. The revalidation transport: DB event, `pg_net`, authenticated Route Handler, `{ expire: 0 }` semantics, retry, `job_runs` (H-2).
3. Where `PageContentV1` is enforced (DB-side schema vs Server Action) and how the jsonb key set is pinned (H-3).
4. Re-open DNS option with the `_acme-challenge` delegation as the lower-risk variant, or add DNSSEC/CAA/NS-TTL/rehearsal steps (H-4).
5. Replace the AD-42 fallback with one that holds no signing secret (H-5); strengthen the privilege test (H-6).
6. Retraction semantics for edits after publish (H-7); Storage API deletion path, originals, CDN assumption, logo re-encode (H-8).
