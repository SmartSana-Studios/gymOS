# Story 1.16: Super Admin — In-App Admin Management UI

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a Super Admin,
I want to view existing Super Admins and create or promote new ones from the Super Admin dashboard,
so that granting the platform's highest-privilege role no longer requires CLI/repo access for the routine case.

**Context — not derived from `epics.md`.** Raised directly by the user (2026-09-07) after finding no in-app way to add a Super Admin. Investigation found this was not an oversight: Story 1.12 (`1-12-super-admin-provisioning-cli.md`, done 2026-08-05) explicitly discussed and rejected an in-app "invite Super Admin" flow in favor of `provision-super-admin.mjs`, reasoning that the platform-staff team is small and an in-app flow adds authorization-sensitive surface for a rarely-exercised capability. The user chose to reverse that decision. Formalized via `bmad-correct-course` as `sprint-change-proposal-2026-09-07.md`, which added PRD FR-141 (amends FR-071) and NFR-020, and a `docs/decisions.md` entry superseding (not editing) the 2026-08-05 decision. This story is that proposal's Story 1.16, same title and scope, with the technical approach refined below — twice — where research surfaced things the proposal, and then this story's own first draft, didn't know yet (see "Corrections" in Dev Notes).

## Acceptance Criteria

1. **Given** the Super Admin dashboard, **when** a Super Admin opens a new "Admins" nav destination, **then** they see a list of every current Super Admin (email, display name, and "since" — when they were provisioned or promoted, resolved from `audit_log`, blank if no such record exists), sourced via a new narrow `SECURITY DEFINER` RPC (`list_super_admins()`), not a new RLS policy or a raw service-role table read — see Dev Notes for why both alternatives were rejected.
2. **Given** the Admins page, **when** a Super Admin submits an email with no matching `auth.users` row, **then** a new Super Admin account is created (Admin API `createUser` + a generated temp password, mirroring `createGym`'s `CreateGymResult.tempPassword` pattern), `is_super_admin` is set `true`, `display_name` is derived from the email's local part if not already set, an `audit_log` row is written with `action_type = 'super_admin_provisioned'` attributed to the **real calling Super Admin** (not a system label), and the temp password is shown once in the UI (never emailed/logged elsewhere — there is no phone number to send it to, unlike `createGym`'s WhatsApp path). The action's result distinguishes this outcome (`created`) from the other two below so the UI shows accurate copy.
3. **Given** the Admins page, **when** a Super Admin submits an email matching an existing `auth.users` row whose `public.users.is_super_admin` is currently `false`, **then** that row's `is_super_admin` flips to `true`, `display_name` is set only if currently unset, and an `audit_log` row is written with `action_type = 'super_admin_promoted'` attributed to the real calling Super Admin. Result outcome: `promoted`.
4. **Given** the Admins page, **when** a Super Admin submits an email matching an existing Super Admin (`is_super_admin` already `true`), **then** the action no-ops — no write, no audit-log row — and the result outcome (`already_super_admin`) is distinguishable from `promoted` so the UI cannot claim a fresh promotion that didn't happen. Mirrors the CLI's own idempotency guard (`provision-super-admin.mjs`'s `promoteExistingUser`).
5. **Given** the Add Admin modal, **when** a Super Admin has entered an email and is about to submit, **then** the submit button names the target explicitly ("Add {email} as Super Admin"), per this app's existing destructive/sensitive-action confirmation convention (UX-DR12, `EscalateAccessDialog.tsx`/`RevokeAccessDialog.tsx`/`ChangeTierDialog.tsx` precedent) — no separate preview/confirmation *screen* is added. **Superseded/refined post-review (2026-09-07, `docs/decisions.md`):** the modal also requires the acting Super Admin to re-enter their own account password (step-up re-authentication, verified server-side via `signInWithPassword`) immediately before submit — a stronger proof-of-presence guard than the named-target button alone, added as one more required field on the same single-step form, not a second screen.
6. **Given** this story ships, **then** `provision-super-admin.mjs` (Story 1.12) keeps working unmodified in behavior — its pure identity-mutation logic (email lookup, display-name derivation, the create/promote writes) is extracted into a shared module the new Server Action also calls (see Dev Notes); its own audit-logging call is **not** extracted and stays exactly as it is (see Dev Notes for why the two callers must log differently). Its header usage comment gains one line pointing to the new in-app path as the ordinary case.
7. **Given** this action mints the platform's highest privilege, **when** the new Server Action runs, **then** it re-verifies the caller's own session claims (`app_role === "super_admin"`) at the top of the function body, in addition to the existing `(admin)` layout guard — a deliberate, narrow exception to this app's usual convention of relying on the layout guard alone (`createGym` etc. do not re-check), justified because NFR-020 requires server-side self-enforcement for this specific action and a Server Action endpoint is reachable independently of the rendered page.
8. **Given** this story's scope, **then** no demote/revoke UI or RPC is added — matching the CLI's own never-had-this scope. Explicitly out of scope, not deferred-and-forgotten.

### Review Findings

## Dev Notes

### Corrections made during story creation (read first)

This story went through two review passes before reaching this state, each catching a different mistake — worth reading both so the same mistakes aren't reintroduced during implementation.

**Correction 1 (sprint-change-proposal → this story's first draft):** the proposal suggested "a new narrow RLS policy on `public.users` scoped to `is_super_admin = true` rows" for the list view. This doesn't work: `public.users` has no `email` column at all (`0003_members_and_users.sql:7-14` — only `phone`, `display_name`, `preferred_language`, `is_super_admin`, `created_at`). Email lives exclusively in `auth.users`, unreachable via RLS/PostgREST regardless of any policy on `public.users`. Listing by email needs the Admin API either way.

**Correction 2 (this story's first draft → this version):** the first draft's fix for Correction 1 over-corrected — it proposed reading `public.users` directly through the raw service-role admin client for a plain table SELECT. `apps/super-admin/lib/supabase/admin.ts`'s own header comment forbids exactly this: *"Its only sanctioned use in this app is `supabase.auth.admin.*` ... every other read/write in this app should go through the regular session client instead."* Story 1.15's own code review separately rejected a `security definer` bypass to read `public.users` for this identical problem (resolving a Super Admin's display name) as *"a strictly wider bypass than needed."* The corrected design (Task 1) is a narrow, self-enforcing `SECURITY DEFINER` RPC — no wider than `escalate_gym_data_access()`/`revoke_gym_data_access()` already are, and callable through the ordinary session client rather than handing a Server Action the full service-role client for something that doesn't need it. This does mean **one new migration is needed after all** — narrower than the proposal's rejected RLS-policy idea, but not zero as the first draft claimed.

The first draft also made a third mistake, folding the audit-log call into the shared extracted module — see "Why audit logging is not shared" below, since it's substantial enough to warrant its own section.

### Why audit logging is not shared between the CLI and the Server Action

The CLI (`provision-super-admin.mjs`) runs with **no real user session** — it authenticates only via the service-role key. Its `log_audit_event` call necessarily goes through the admin client and relies on `p_system_actor_label = 'system:provision-super-admin-cli'`, because `auth.uid()` has nothing to resolve to. The new Server Action runs inside a **real, authenticated Super Admin session** — the whole point of AC #2/#3 attributing the action to the actual person who clicked the button, not a system label. `log_audit_event()` derives `actor_id`/`actor_display_name` from `auth.uid()` when called through a real session (`0007_audit_log.sql`'s actor-derivation branch), but resolves to `null`/the system-label branch when called through the admin client, which carries none. **This story's own first draft called `log_audit_event` through the admin client from the Server Action** — the same mistake it would have been to reuse the CLI's exact call — silently mislabeling every UI-driven creation/promotion as `system:...` instead of the real admin. The fix is not to share this piece of logic at all: Task 2's shared module owns only the identity mutation (which genuinely is identical between the two callers); Task 4's Server Action makes its own `log_audit_event` call through the regular session client, and the CLI keeps its own unchanged. Two different logging calls for two structurally different callers is the correct outcome here, not a duplication to clean up.
