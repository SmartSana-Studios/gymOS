# Story 11.1: PaymentProvider Routing Context & SaaS Billing Table

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As the platform,
I want the `{type:'gym', gym_id}` routing context Epic 4's Story 4.14 introduced extended with a `{type:'platform'}` variant, plus a dedicated table for platform-level billing,
so that Flow B (gym→GymOS) payments are structurally separate from Flow A (member→gym) payments, never sharing RLS audience or credentials.

## Acceptance Criteria

1. **Given** the new `saas_billing_payments` table, **when** it is created, **then** it is Super-Admin-scoped RLS, distinct from the gym-scoped `payments` table — mirroring the `job_runs`/`audit_log` platform-level-concern precedent (AD-14).
2. **Given** the `PaymentProvider` routing context (Story 4.14 introduced the `{type:'gym', gym_id}` variant for Flow A), **when** Flow B is added, **then** the context gains a `{type:'platform'}` variant selecting GymOS's own platform credentials at initiation, verification, and reconciliation (FR-138); adding this variant changes only the adapter and context, not any Flow A calling code.
3. **Given** the single shared `payment-webhook` Edge Function, **when** a webhook is received, **then** it dispatches on the routing context carried in the webhook's own reference/metadata to decide whether the event resolves against `payments` or `saas_billing_payments` — no second Edge Function is created, and `payment_webhook_events` remains one shared idempotency log for both flows.

## Tasks / Subtasks

- [x] **Task 1 — `saas_billing_payments` table + Super-Admin RLS + completion RPCs (AC #1)**
  - [x] New migration `supabase/migrations/0069_saas_billing_payments.sql` (0068 is the last migration on disk — confirm still true at implementation time). Table shape, minimal and scoped to only what this story's ACs need (Stories 11.2/11.3 will `ALTER TABLE` to add lifecycle/reminder-specific columns — do not anticipate their schema):
    ```sql
    create table saas_billing_payments (
      id uuid primary key default gen_random_uuid(),
      gym_id uuid not null references gyms(id),
      amount integer not null,
      currency text not null default 'XAF',
      status payment_status not null,
      provider text references payment_providers(provider_key),
      provider_transaction_ref text unique,
      provider_fee_amount integer,
      created_at timestamptz not null default now()
    );
    create index idx_saas_billing_payments_gym_id on saas_billing_payments(gym_id);
    ```
    `status` reuses the existing `payment_status` enum (`processing`/`verified`/`flagged`) — do not create a second enum. `gym_id` is `not null`: every Flow B payment is *for* a specific gym even though the RLS *audience* is Super-Admin-only (the AC's "Super-Admin-scoped RLS" describes who can read the table, not whether it's gym-attributed — see AD-14's own wording, which keeps `gym_id` on the table). No `member_id`/`subscription_id`/`method`/`actor_id`/`reason` — those are `payments`-table concepts (member-driven, staff-actor-driven) that don't apply to a gym-Owner-driven platform charge; add only if a later task in this same story genuinely needs one, not speculatively.
  - [x] RLS: `enable row level security`, baseline `grant select, insert, update, delete ... to authenticated, service_role` (0002's discipline), then exactly one policy:
    ```sql
    create policy "super_admin_read_saas_billing_payments" on saas_billing_payments
      for select
      using (private.is_super_admin());
    ```
    Use `private.is_super_admin()` (the JWT-claim `STABLE` helper from `0010_super_admin_gym_provisioning.sql`) — **not** `private.is_super_admin_live()` (`0063_staff_edit_deactivation.sql`, a narrower live-lookup sibling used inside one `SECURITY DEFINER` function's caller-role check, not the RLS-policy pattern). `private.is_super_admin()` is the exact helper `payment_providers` (`0029`), `job_runs`-adjacent `audit_log` (`0012_super_admin_data_access_escalation.sql`), and `messaging_provider_config` (`0050`) all use for this identical "Super-Admin-scoped platform table" shape — the AC's own precedent citation. No INSERT/UPDATE/DELETE policy for any role — the two RPCs below (`security definer`, `service_role`-only grant) are the only write path, matching `payment_providers`'/`payments`' own "single blessed write path" posture.
  - [x] `payment_webhook_events` gains one new nullable column so a Flow B event's matched row (which lives in a different table than `matched_payment_id`'s `payments` FK) can still be recorded in the one shared log AC #3 requires:

      add column matched_saas_billing_payment_id uuid references saas_billing_payments(id);

Do not touch `payment_discrepancies` or `run_payment_reconciliation_job()` — reconciliation for Flow B is explicitly Story 11.6's scope ("Cross-Flow Reconciliation & Beta Accommodation"), not this story's.
  - [x] Two new `SECURITY DEFINER` RPCs, service-role-only (`revoke ... from public, authenticated; grant execute ... to service_role`), mirroring `complete_verified_payment()`/`complete_flagged_payment()` (`0030_payment_initiation_and_renewal.sql`, `0046_payment_notifications.sql`) in idempotency shape (`where status = 'processing'` as the idempotency guard) but with **no subscription-renewal side effect** — Flow B has no member/subscription to renew:
    ```sql
    create function complete_verified_saas_billing_payment(p_payment_id uuid, p_fee_amount integer)
    returns void
    language plpgsql
    security definer
    set search_path = public
    as $$
    begin
      update saas_billing_payments
      set status = 'verified', provider_fee_amount = p_fee_amount
      where id = p_payment_id and status = 'processing';
      -- no-op (0 rows) on a replayed webhook -- same idempotency contract as complete_verified_payment().
    end;
    $$;

    create function complete_flagged_saas_billing_payment(p_payment_id uuid)
    returns void
    language plpgsql
    security definer
    set search_path = public
    as $$
    begin
      update saas_billing_payments
      set status = 'flagged'
      where id = p_payment_id and status = 'processing';
    end;
    $$;
    ```
    Story 11.2/11.3 own actually *creating* `saas_billing_payments` rows (the billing-cycle/reminder job) and any audit-log write around them (FR-080) — this story only needs the completion path to exist so the webhook has somewhere to write, matching how Story 4.13 built `gym_payment_credentials` storage a full story ahead of Story 4.14 actually wiring it into `initiate()`/verification.

Assert `complete_verified_saas_billing_payment`/`complete_flagged_saas_billing_payment` idempotency (second call on an already-`verified`/`flagged` row is a no-op, no exception).

## Dev Notes

- **This story is backend/infrastructure-only.** No dashboard, super-admin, or mobile UI changes — confirmed via `EXPERIENCE.md`: the only Epic 11 mockup (SA-07, Billing view) explicitly belongs to Story 11.5, not this one. Do not add any UI.
- **Scope discipline — read this before starting Task 1.** Epic 11 splits SaaS billing across 6 stories on purpose: this story owns *only* the routing-context/table-split infrastructure (AC #1–#3, verbatim above). Story 11.2 owns the billing-lifecycle state machine and actually *writing* `saas_billing_payments` rows on a schedule; Story 11.3 owns the one-tap-pay initiation UI/Server Action and the `handleInitiate()`-side platform caller; Story 11.5 owns the Super Admin Billing view UI (the only consumer of this story's new RLS-readable table); Story 11.6 owns cross-flow reconciliation. Resist building ahead of any of those — it will very likely conflict with how the owning story actually shapes its own columns/RPCs, mirroring this project's own established discipline (see Story 4.13's `docs/decisions.md` entry: it built `gym_payment_credentials` storage a full story ahead of Story 4.14 wiring it in, and explicitly did not try to anticipate 4.14's design).
- **`initiate()`'s platform branch is not new work — it's already real.** `TaraMoneyProvider.ts`'s `{type:'platform'}` initiate path was added in Story 4.14 as forward-compatible scaffolding ("this story's `PaymentProvider` implementations do not implement its behavior, only the type constant" — that comment is now stale and should be removed/updated once this story lands, since the behavior is real). It reads the exact same `TARAMONEY_API_KEY`/`TARAMONEY_BUSINESS_ID`/`TARAMONEY_WEBHOOK_SECRET` env vars that were live-verified against GymOS's real `9FmIZg9GBB` account in Story 4.10 (2026-08-13) and again in Story 4.12's MTN round-trip (2026-08-17) — before Story 4.14 moved Flow A onto per-gym `gym_payment_credentials`. Those three env vars are still set (uncommented) in `supabase/.env` today. The real, previously-missing half is verification (Task 2) and dispatch (Task 3) — do not re-verify or re-spike `initiate()` itself; it has no code path this story changes.
- **`PaymentRoutingContext` and the interface it lives in:** `supabase/functions/payment-webhook/_shared/payment-providers/PaymentProvider.ts`.
