This insert happens unconditionally (regardless of whether any Expo push token exists / the eventual dispatch `status` ends up `no_tokens`) — a member with no registered device should still see the notification in their in-app history.
3. **Given** the mobile app's Home screen header (`apps/mobile/src/app/(tabs)/index.tsx`'s `styles.header` row: gym branding on the left, profile avatar on the right), **when** a member is on Home, **then** a bell icon button sits between them, opening a new `/notifications` screen; the bell shows a small badge with the count of the member's own `public.notifications` rows where `read_at is null` (capped at a reasonable display max, e.g. "9+", matching this codebase's existing badge-count conventions if any exist, otherwise a simple uncapped number is acceptable — no source doc specifies a cap).

No Preferences section exists on the Notifications screen.
5. **Given** a history row that is currently unread (`read_at is null`), **when** the member views/taps it, **then** its `read_at` is set (a single-row update via the RLS policy from AC #1, optimistic UI update matching this codebase's established optimistic-update/rollback pattern already used by the two preference toggles) and the Home bell badge count decrements accordingly on next Home focus/refresh.

## Dev Notes

### This Story's Core Design Decision — Piggyback on the Existing Dispatch-Claim Boundary, Don't Invent a New One

The single most important idea in this story: **every notification history row is created inside the same transaction, at the same moment, using the same idempotency check, as the existing push dispatch.** There is no separate "did we already record history for this event" check to get wrong — the `on conflict (...) do nothing returning id into v_dispatch_id; if v_dispatch_id is null then return; end if;` pattern that already exists in all 4 send functions is reused as-is; the history insert is simply one more statement on the "we own this dispatch" branch, using the `v_title`/`v_body` variables those functions already compute for the push payload. Resist any temptation to build a separate notifications-writing mechanism (a trigger on the dispatch tables, a new dedup table, a post-hoc backfill job) — none of that is needed and all of it would introduce a second idempotency boundary that could drift from the first.

### Why a New Table, Not RLS on the Existing Dispatch Tables

`private.notification_dispatches`/`private.payment_notification_dispatches`/`private.quiet_gym_alert_dispatches`/`private.class_reminder_dispatches` are 4 differently-shaped tables (different natural keys, different foreign key targets — `subscription_id`, `payment_id`, no natural key, `class_session_id`+`member_id`), none of which carry the actual notification copy (title/body are computed in-function and sent straight to Expo, never persisted). Exposing all 4 via RLS to build a unified history view would mean 4 different per-table policies plus a `UNION` read path in the mobile app, and still wouldn't have message content to show. A single dedicated `public.notifications` table, written once per send from inside each function (Task 2), is simpler and is the actual member-facing contract this feature needs — the dispatch tables remain exactly what they've always been: internal delivery-idempotency/ledger bookkeeping, untouched in shape or purpose.
