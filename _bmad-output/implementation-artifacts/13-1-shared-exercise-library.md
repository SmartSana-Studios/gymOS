# Story 13.1: Shared Exercise Library

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a Coach,
I want a library of exercises to draw from when building a workout plan, with the ability to add my own,
so that I'm not typing every exercise name from scratch each time.

## Acceptance Criteria

1. **Given** the exercise library, **when** a Coach starts building a plan, **then** they see platform-default exercises available to every gym (FR-112).
2. **Given** a Coach needs an exercise not in the platform defaults, **when** they add a custom entry, **then** it is gym-scoped — visible to coaches (and members reading their own assigned plan) at that gym only, not leaking into other gyms' libraries (tenant isolation, same as all other data).

### Review Findings

- [x] [Review][Defer] No uniqueness enforcement on exercise names [supabase/migrations/0079_shared_exercise_library.sql] — deferred, pre-existing gap in this story's own new table. `exercise_library` has no DB-level uniqueness guard at all, deviating from this codebase's established "descriptive-unique-name convention" (`idx_gyms_name_unique`, `idx_tiers_name_unique`, `idx_plans_gym_name_unique`, all case-insensitive unique indexes). A Coach can insert a duplicate name (exact or case-variant) — either re-duplicating another custom entry in their own gym or shadowing an existing platform default — with nothing preventing it. Reason for deferring: low real-world risk (cosmetic annoyance, no security/data-integrity impact), the picker UI where duplicates would actually surface doesn't exist until Story 13.2, and the correct constraint shape is ambiguous given the nullable `gym_id` (Postgres treats each NULL as distinct, so a plain `(gym_id, lower(btrim(name)))` unique index wouldn't catch duplicate platform-default rows against each other — needs a partial index or `coalesce()` expression) — better decided alongside 13.2's actual duplicate-handling UX (e.g. an autocomplete "did you mean an existing exercise?" flow) than guessed at blind here.
- [x] [Review][Patch] No DB-level constraint blocking a blank or oversized exercise name [supabase/migrations/0079_shared_exercise_library.sql] — `exerciseNameSchema` enforces `.trim().min(1).max(100)` at the app layer only; the `name text not null` column had no matching CHECK. ## Dev Notes

- **Scope boundary — this story ships zero dashboard UI.** Mirrors the established "ship the field, defer the UI" precedent from Story 10.1 → 10.2 → 10.3 (progress data shipped backend-only across two stories before any screen consumed it) and Story 12.2 (class booking, backend-only). AC #1's "when a Coach starts building a plan" is satisfied by `listExerciseLibrary()` existing and being correct, not by a picker screen — "building a plan" is literally Story 13.2's Coach Portal Workout Plan tab (`EXPERIENCE.md` AD-15), which does not exist in the codebase yet (`apps/dashboard/app/(dashboard)/coach/[memberId]/components/CoachMemberDetailPageClient.tsx` currently renders only Session Notes + Progress tabs, per Story 10.4). Story 13.2 is the one that will build the actual exercise picker/autocomplete UI (including the "+ Add new exercise" affordance that calls `addCustomExercise()`) inside its own new Workout Plan tab component — do not build that picker here.
- **New RLS pattern: nullable `gym_id` for platform-wide + gym-scoped rows in one table.** Every existing gym-scoped table in this schema uses `gym_id uuid not null` (`classes`, `progress_entries`, etc.); every platform-wide table (`tiers`, `messaging_provider_config`) has no `gym_id` column at all. `exercise_library` is the first table to mix both audiences in one table via a nullable `gym_id` — confirmed as the right shape here since AC #1 and #2 explicitly require both "visible to every gym" and "gym-scoped" rows to coexist in what the UX mockup treats as a single combined list (`EXPERIENCE.md`: "Exercises are added from the shared library — platform defaults plus this gym's own custom entries"). Do not split into two tables.
- **AD-3 compliance:** use `private.current_member_role()` (defined `0061_staff_creation_role_ceiling_enforcement.sql`), never `auth.jwt() ->> 'app_role'`, for the new INSERT policy's role check. `0068_class_attendance_marking.sql` (Story 12.3, shipped 2026-08-27, well after AD-3's 2026-08-11 adoption) still used the legacy pattern for its own RLS policy — that is pre-existing, out-of-scope drift, not a precedent to follow. The CI grep-lint gate AD-3 describes against new `auth.jwt()` call sites is confirmed **not actually wired into `.github/workflows/ci.yml`** yet (per Story 11.3's own create-story research) — nothing will fail the build if this is gotten wrong, so get it right by design, not by relying on CI to catch it.
- **`private.gym_id()` and `private.current_member_role()` are both `STABLE`/`SECURITY DEFINER` helpers already defined** — do not redefine them. `private.gym_id()` (0009) reads the JWT claim; `private.current_member_role()` (0061) does a live `members` lookup scoped to the caller.
- **No RPC needed.** This is plain CRUD (a bare SELECT and a bare INSERT, no capacity check, no multi-table side effect) — per AD-8, RLS-gated direct INSERT is correct here, matching `classes`' own INSERT-policy-not-RPC precedent (`0057_class_creation_scheduling.sql`), not `book_class_session()`'s RPC treatment (AD-21 is scoped to bounded-capacity actions, which this is not).
- **`AD-9`: `{ data, error }`, never throw for expected errors.** RLS-denied writes (non-Coach attempting an insert) are an *expected* case here (any staff role can technically call the service function; only Coach's insert succeeds under RLS), not a bug — must resolve to `{ data: null, error }`, matching every other service file's discipline in this codebase.
- **Uncommitted tree state at story creation time:** `git status` shows uncommitted work for the *previous* story (12-4, Member App Classes Surfaces — migration `0078`, new `apps/mobile/src/app/(tabs)/classes/` directory, `supabase/tests/member_app_classes_surfaces.test.sql`) still sitting in the working tree, even though sprint-status.yaml already marks 12-4 `done`. Do not fold that pre-existing diff into this story's own commit(s) — treat it as separate, prior work to commit on its own (or confirm with the user it's meant to be included) before starting 13.1's own changes, per this project's own action-item ("commit immediately when a story's Status is set to done"). The next available migration number is confirmed as **0079** (0078 is the last file on disk, including the uncommitted one).
