# Story 13.2: Coach-Authored Workout Plans

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a Coach,
I want to author a named workout plan with an ordered list of exercises for an assigned member,
so that I can give them a structured program to follow between sessions.

## Acceptance Criteria

1. **Given** an assigned member, **when** I create a workout plan from the Coach Portal's Workout Plans tab, **then** I give it a name and an ordered list of exercises, each with sets, reps, and an optional note. [FR-109, FR-122]
2. **Given** a plan I've authored, **when** I edit it, **then** changes save and the member sees the update on their next app open (no push notification for plan edits — mockup-confirmed, `EXPERIENCE.md` AD-15).
3. **Given** a plan, **when** it is assigned, **then** it belongs to exactly one member — plans are not shared across members. [FR-110]
4. **Given** a member not assigned to me, **when** I attempt to author or view a plan for them, **then** RLS blocks it — the same assignment boundary that governs progress data (Story 10.4) and session notes (Story 5.3) governs workout plans.

    1. `v_gym_id := private.gym_id(); if v_gym_id is null then raise exception 'permission denied'; end if;`
    2. Resolve the caller's own coach id — **do not trust a client-supplied coach id**: `select id into v_coach_id from members where user_id = auth.uid() and gym_id = v_gym_id and role = 'coach'; if v_coach_id is null then raise exception 'create_workout_plan: caller is not a coach in this gym'; end if;`
    3. Assignment check (AC #4): `if not private.is_assigned_coach(p_member_id) then raise exception 'create_workout_plan: member % is not currently assigned to caller', p_member_id; end if;`
    4. Validate `p_exercises` is a non-empty JSON array: `if jsonb_typeof(p_exercises) is distinct from 'array' or jsonb_array_length(p_exercises) = 0 then raise exception 'create_workout_plan: at least one exercise is required'; end if;` (a workout plan with zero exercises serves no purpose the feature exists for — the empty state, "No workout plan yet," already covers the zero-*plans* case; this covers the zero-*exercises*-within-a-plan case, which is not the same thing and is not covered by any existing empty state).
    5. Insert the parent row: `insert into workout_plans (gym_id, member_id, coach_id, name) values (v_gym_id, p_member_id, v_coach_id, btrim(p_name)) returning id into v_plan_id;` (the `idx_workout_plans_member_unique` backstop from Subtask 1.1 fires here if a plan already exists for this member — let it raise, do not catch it; Task 3's service layer maps it to a friendly error per Subtask 2.3).
    6. Fan out the exercise rows, validating each `exercise_id` belongs to the caller's own gym or is a platform default — **this is a real tenant-isolation check, not decorative**: a client could otherwise pass another gym's custom `exercise_id` (a `security definer` function does not inherit `exercise_library`'s own SELECT RLS just because it happens to be readable to the caller under a *different* policy branch — it must be checked explicitly against the resolved `v_gym_id`):
       ```sql
       insert into workout_plan_exercises (gym_id, member_id, plan_id, exercise_id, order_index, sets, reps, note)
       select
         v_gym_id, p_member_id, v_plan_id,
         (elem->>'exercise_id')::uuid,
         idx,
         (elem->>'sets')::smallint,
         (elem->>'reps')::smallint,
         nullif(btrim(elem->>'note'), '')
       from jsonb_array_elements(p_exercises) with ordinality as t(elem, idx)
       where exists (
         select 1 from exercise_library el
         where el.id = (elem->>'exercise_id')::uuid
           and (el.gym_id is null or el.gym_id = v_gym_id)
       );
       ```
       Then `if (select count(*) from workout_plan_exercises where plan_id = v_plan_id) < jsonb_array_length(p_exercises) then raise exception 'create_workout_plan: one or more exercises are invalid for this gym'; end if;` — the row-count mismatch is how a cross-gym or nonexistent `exercise_id` gets caught and rolled back (the whole function is one transaction; raising here rolls back the parent insert too).
    7. `return v_plan_id;`
    - `revoke execute on function create_workout_plan(uuid, text, jsonb) from public; grant execute on function create_workout_plan(uuid, text, jsonb) to authenticated;`

A workout plan is structurally different: one parent row plus an ordered list of child rows that must be created/replaced atomically, an authorization check (`is_assigned_coach()`) that a coach cannot resolve from inside a plain RLS `with check` without hitting the same RLS-bootstrapping problem `session_notes`/`coach_assignments` already solved via `security definer` functions, and (via Subtask 1.6) a forward-looking ownership gate that only a server-side function can enforce correctly. Grandfathered migrations stay as they are; this story's new RLS policies and RPCs must use `private.current_member_role()` throughout.
