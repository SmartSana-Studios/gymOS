# Story 10.2: Progress Data & Photo Privacy

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a member,
I want my body data and progress photos private by default, with explicit control over what I share with my coach,
so that this sensitive information is never exposed without my active consent.

## Acceptance Criteria

1. **Given** my progress data (measurements, weight, notes), **when** any role attempts to read it, **then** only I can always read/write it, and my currently-assigned Coach (if any) can read it — no Receptionist, Manager, Supervisor, Owner, or other member can ever read it, enforced by RLS. [Source: epics.md Story 10.2, AC #1; prd.md FR-095]
2. **Given** my coach assignment ends, **when** the `ended_at` timestamp is set (FR-055), **then** that former coach's read access ends at that instant — re-verified live on every request, no caching window. [Source: epics.md Story 10.2, AC #2; prd.md NFR-016] — **Already structurally satisfied once AC #1's helper is reused correctly:** `private.is_assigned_coach()` (the Epic 5 helper this story's new RLS policies must call, not reimplement) is `STABLE` and re-runs its `ended_at is null` check on every row evaluation, with no memoization anywhere in this codebase. No extra code is needed for this AC beyond correctly wiring AC #1's coach policies through that helper.
3. **Given** a progress photo I upload, **when** it is stored, **then** it lands in a dedicated private Storage bucket — never the existing public `member-photos` bucket used for profile photos — with non-guessable object paths. [Source: epics.md Story 10.2, AC #3; AD-24, NFR-011] — **Already fully shipped by Story 10.1**, which created the `progress-photos` bucket (`public = false`, folder-scoped, non-guessable `{auth.uid()}/{client_entry_id}.{ext}` paths) specifically so the photo field worked before this story existed (`docs/decisions.md`, 2026-08-21, decision (b)). This story adds nothing new for the bucket's existence — only the coach-read grant on top of it (AC #1/#4).
4. **Given** a photo I've shared with my coach, **when** I revoke that sharing, **then** access is revoked immediately — no outstanding signed URL survives the revoke, achieved via short-lived signed URLs; the revocation is forward-only and doesn't retroactively track whether the coach already viewed it. [Source: epics.md Story 10.2, AC #4; NFR-011] — **Narrowed, see "Signed URLs Are Not Live-Revocable" in Dev Notes:** Supabase Storage signed URLs are bearer tokens valid until their own TTL expiry once minted; there is no mechanism to invalidate one already handed out. This story's mechanism instead guarantees no *new* signed URL can ever be minted for a revoked photo (storage RLS re-checked live at every `createSignedUrl` call, same no-caching-window property as AC #2) — "immediately" is satisfied to the extent achievable: mint-time enforcement plus a short recommended TTL for whichever story first mints a coach-side signed URL. This story ships the enforcement; it does not mint any coach-side signed URL itself (see Scope Boundary — no Coach Portal UI exists yet, that's Story 10.4).
5. **Given** a new photo I upload, **when** it is saved, **then** sharing defaults to off — an explicit per-photo opt-in action, never a blanket setting. [Source: epics.md Story 10.2, AC #5] — Satisfied by a `not null default false` column, enforced at the DB layer regardless of any client bug (a client could omit the field entirely and the row still defaults closed). The opt-in *toggle action* itself is a backend service function shipped by this story (see Scope Boundary) — no UI exists yet to trigger it, since the photo timeline it belongs on is Story 10.3's screen.

### Scope boundary — this story's resolution of an epics-stub/UX sequencing gap (same class as Story 10.1's own)

Read literally, epics.md's Story 10.2 ACs (and `EXPERIENCE.md:927,932`, which attributes the "per-photo share toggle" interaction textually to "(Story 10.2)") describe end-user-facing sharing/revoke behavior as if a UI already exists to trigger it. It does not: the photo timeline and full-screen photo viewer that toggle lives on is `EXPERIENCE.md`'s MA-15 screen (lines 895–940), which is explicitly **Story 10.3's** deliverable (`epics.md` Story 10.3, "Member Progress Screen") — Story 10.1 built no photo-viewing/browsing UI at all, only a write-only `LogEntrySheet`. This is the identical class of epics-stub/UX cross-reference gap Story 10.1 already hit and resolved for its own AC #4 (soft-delete has no UI until a list view exists) and the Progress tab itself (deferred to 10.3 without inventing a placeholder tab).

**Resolution:** this story ships the complete mechanism — schema, RLS (member ownership + coach read-if-shared), the storage policy tying a coach's photo read to the live `shared_with_coach` flag, and a backend service function to toggle it — fully satisfying every AC at the data/logic layer. It does **not** build a throwaway photo-list screen just to host a toggle button; that would duplicate Story 10.3's actual MA-15 deliverable (a full trend/photo-timeline screen) and be discarded once 10.3 ships. Story 10.3 wires the toggle onto its new photo detail view exactly as it already plans to mount Story 10.1's `LogEntrySheet` onto its new screen without rework — the toggle service function is built now, called later. Manual verification of the toggle in this story is via pgTAP (RLS-level) plus a hands-on throwaway-script check of the actual `createSignedUrl` mint-time behavior (Task 1/Task 6) — not a UI click-through, since no UI exists yet to click through. This is a deliberate scope decision, not a gap in this story's coverage.

Story 10.4 (Coach Portal Progress tab, FR-098) is likewise not built here — confirmed via this story's own research that `apps/dashboard/app/(dashboard)/coach/[memberId]/` currently has exactly one view (member-info card + Session Notes) with no tab component of any kind; adding a Progress tab is 10.4's job, this story only makes the underlying data legally readable to a coach.

## Dev Notes

### Why a Separate Table, Not a Column

FR-095 draws two different visibility lines over what is currently one table: weight/measurements/notes are coach-visible whenever an assignment is active (no per-item consent), while the photo specifically needs its own default-off, explicitly-toggled, per-item consent gate. Postgres RLS policies operate at row granularity — a policy can allow or deny an entire row to a caller, but cannot expose some columns of an allowed row while hiding others from that same caller in that same query. Since both the member and the coach connect through the same `authenticated` Postgres role (role-based column `GRANT`s can't tell them apart — only row data does, via `private.is_assigned_coach()`/ownership checks), there is no way to keep `photo_path` on `progress_entries` and still make a coach's read of that row's *other* columns unconditional while gating just that one column. The only two structurally sound options were: (a) a security-invoker view or RPC that nulls the column for non-owners — rejected, because it doesn't stop a coach client from querying the base table directly for `photo_path`, silently defeating the whole gate; or (b) move the photo into its own table with its own row-level policy, where "shared" is a genuine row-existence condition a coach's query either satisfies or doesn't. (b) is what this story does. It costs a migration that moves already-shipped data and touches Story 10.1's write path, but it's the only version of this that's actually enforced by RLS rather than by client discipline — consistent with AD-1's "RLS is the sole authorization layer," which this story treats as binding on the *mechanism*, not just the *intent*.

### AD-3 Compliance — `private.current_member_role()`, Not `auth.jwt() ->> 'app_role'`

The Epic 5 coach policies this story's new policies otherwise mirror exactly (`coach_read_assigned_members`/`coach_read_assigned_subscriptions`, `0040` lines 81–95) use `(auth.jwt() ->> 'app_role') = 'coach'` directly. That was correct when written, but `ARCHITECTURE-SPINE.md` AD-3 (adopted for Epic 9 onward, `0061`) explicitly retires that pattern for all **new** RLS policies and `SECURITY DEFINER` functions — role authorization must read live state via `private.current_member_role()`, because a demoted-but-not-logged-out staff member would otherwise retain stale access until their next token refresh. AD-3's own text says the 27 migrations that already use the JWT-claim form are grandfathered, "but no new one may." This story's migration is new, so every new policy it adds (`coach_read_assigned_progress_entries`, `coach_read_shared_progress_photos`, `coach_select_shared_progress_photo`) uses `private.current_member_role() = 'coach'` — this is a deliberate divergence from the literal Epic 5 precedent being otherwise mirrored, not an inconsistency to "fix" back to match it.

### Why a Plain RLS Update, Not an RPC (Again)

Same reasoning Story 10.1 already established for `progress_entries` itself (`docs/decisions.md`, 2026-08-21, decision (a)): the sharing toggle is a pure ownership-gated column flip with no cross-row invariant to protect (no capacity check, no state machine, no second row that must change atomically with it) — the pin-back trigger already restricts a self-update to touching only `shared_with_coach`. A `SECURITY DEFINER` RPC would add a maintenance surface with nothing for it to guard. The one place a two-step write does need care is `logProgressEntry()`'s entry-insert-then-photo-upsert sequence (Task 5) — that's handled by making the photo upsert idempotent on `progress_entry_id` (the same partial-unique-index-as-idempotency-key pattern this codebase already uses for `client_entry_id`/`client_scan_id`), not by wrapping both writes in a transaction-owning RPC. A partial failure between the two (network drop after the entry insert succeeds) leaves an entry temporarily without its photo row, recoverable by retrying just the upsert — an acceptable, non-corrupting intermediate state, not a violated invariant.

### Signed URLs Are Not Live-Revocable

`apps/mobile/src/lib/photo-upload.ts`'s existing `getProgressPhotoSignedUrl()` doc-comment already flags this: a Supabase Storage signed URL is a self-contained bearer token, checked against RLS only at `createSignedUrl()` mint time — once issued, it remains valid until its own TTL expires regardless of any later RLS/flag change, with no server-side revocation lever short of deleting or renaming the underlying object (which this story doesn't do, since the member's own access to their photo must be unaffected by a coach-sharing revoke). This means AC #4's "no outstanding signed URL survives the revoke" cannot be made literally instantaneous for a URL already handed to a coach's device — the achievable guarantee, and the one this story actually ships, is: (1) no *new* signed URL can ever be minted for a coach once `shared_with_coach` flips to `false` (enforced live by the new storage RLS policy, re-checked on every `createSignedUrl` call, zero caching — Task 6 hands-on-verifies this), and (2) whichever story first mints a coach-facing signed URL (Story 10.4) should use a short TTL (recommended ~60s, distinct from the member's own 3600s convenience TTL) so that even an already-outstanding URL's exposure window is small. This story ships (1) completely; (2) is a recommendation recorded for Story 10.4, not code this story writes, since no coach-side signed-URL consumer exists yet.
