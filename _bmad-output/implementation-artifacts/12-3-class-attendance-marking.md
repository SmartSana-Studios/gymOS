# Story 12.3: Class Attendance Marking

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a Receptionist,
I want to mark which booked members actually attended a class session,
so that the gym has an accurate record separate from general floor check-in.

## Acceptance Criteria

1. **Given** the Classes admin page (`/classes`), **when** a Receptionist, Manager, Supervisor, or Owner clicks a class row, **then** it expands to show that class's next session's booked members (name, current attendance state) — FR-107, AD-18 mockup. Coach cannot see this (matches the existing Classes/Attendance role-visibility exclusion).
2. **Given** an expanded session's booked-member list, **when** staff clicks "Mark attended" for a member with a non-expired subscription, **then** the booking's attendance is recorded — a new `attended_at timestamptz` column on `class_bookings` (AD-21: "a status column on `class_bookings` — never a write to `attendance_events`"), set via a new `mark_class_attendance()` `SECURITY DEFINER` RPC, never a direct client `UPDATE`.
3. **Given** a booked member whose subscription status is `null` or `expired`, **when** staff attempts to mark them attended, **then** the RPC rejects it the same way `check_in()` rejects an expired floor check-in (no `attended_at` write) **and** fires the same real-time front-desk alert (`front_desk_alerts` insert, status `'expired'`) — FR-107, FR-049, mirroring `check_in()`'s existing rejection branch exactly. `expiring_soon`/`grace_period` members can still be marked attended (same eligibility rule as `book_class_session()`, not a stricter `active`-only filter).
4. **Given** class attendance is recorded, **when** it happens, **then** it never writes to `attendance_events` and never calls `check_in()` — floor check-in and class attendance remain fully distinct tables/concepts (AD-21).
5. **Given** the session-attendance view, **when** it renders, **then** it reads real data from `class_bookings`/the members it references — no hardcoded/mocked attendance state.

**Scope note — read this before building:** no "unmark" / undo action is in scope. No AC in the epic or PRD (FR-107) asks for reversing a mark, and `book_class_session`/`cancel_class_booking` (Story 12.2) already establish booking-cancellation as a wholly separate, member-initiated action. The UX mockup (`AD-18`) shows a checkbox, which visually implies a toggle — this story ships it as a **one-way action**: clicking "Mark attended" on an already-attended row is a harmless idempotent re-submit (RPC just re-sets `attended_at = now()`), and the UI need not literally render an `<input type="checkbox">` if a button/label reads more naturally as one-way. **[Review][Decision]** flag this for confirmation if a true undo affordance turns out to be wanted — it is a small addition (a second RPC + button) once this scope is confirmed.

## Dev Notes

### This Story's Real Crux — Read This First

This story fills in the one piece of `class_bookings` that Stories 12.1/12.2 explicitly deferred: 12.2's own migration comment says outright, *"class_bookings has no status column... Story 12.3... will ALTER TABLE to add that column when it needs it."* AD-21 already names this exact design (a status column on `class_bookings`, distinct from `attendance_events`) and already flags the reuse of `check_in()`'s expired-member-rejection-plus-alert behavior (FR-107 cites FR-049 explicitly). The genuinely new design surface is narrow: one nullable column, one RPC that's mostly a copy-paste of `check_in()`'s rejection branch, and — the one real judgment call this story makes — deciding whether Supervisor can use this feature at all (see below).

### The Supervisor RLS Gap — Read Before Touching `class_bookings`' Policies

`gym_staff_read_own_class_bookings` (Story 12.2) copied its role list (`owner`, `manager`, `receptionist`) verbatim from `gym_staff_read_own_attendance_events` (0025, Story 3.6) — but 0025 predates the Supervisor role (Epic 9), so neither policy has ever included it. `deferred-work.md` already documents this as a known, accepted, codebase-wide gap ("~30 other call sites... a future dedicated story should retrofit... incrementally, matching AD-3's own accepted grandfathered migration path") — **do not** interpret this story as a mandate to fix that gap everywhere. But `EXPERIENCE.md`'s Role visibility matrix (dated after Supervisor's introduction, so it is the current source of truth) explicitly lists Supervisor as ✓ for "Classes — view/attendance (AD-18)" — the exact feature this story builds. Leaving `class_bookings`' policy as-is would ship a feature this story's own UX text says Supervisor should have, but Supervisor literally could not see any booked-member rows to act on. The fix scoped into this story (Task 1) is narrow and justified: widen only `gym_staff_read_own_class_bookings`, touch nothing else. If this reasoning is judged wrong during review, reverting is a one-line role-array change.

### Architecture Compliance

- **AD-21** is this story's central binding constraint: class attendance is "a status column on `class_bookings`, never a write to `attendance_events`/`check_in()`" and explicitly reuses "the same member-status rules" (expired rejection + front-desk alert) as floor check-in. `mark_class_attendance()` must never touch `attendance_events` or call `check_in()`.
- The `attended_at timestamptz` (vs. literal "status column") choice is a deliberate, reasoned implementation detail — see Task 1's own bullet and the `docs/decisions.md` entry (Task 4) for the full reasoning. Do not treat AD-21's wording as mandating a `text`/enum column.
- **FR-049**'s front-desk alert only names two triggers: accepted check-in with `expiring_soon`/`grace_period` (yellow "grace" alert) and rejected check-in (red "denied" alert). FR-107 only asks for the rejection-side parity ("an expired member cannot be checked in and triggers the front-desk alert") — it does **not** ask for a yellow grace alert on a *successful* attendance-mark of an `expiring_soon`/`grace_period` member. This story implements **only** the rejection-side alert, matching FR-107's literal text. Do not add a grace-alert branch to `mark_class_attendance()` — out of scope, no AC asks for it.
- `check_in()`'s subscription-eligibility query (`order by created_at desc limit 1`, reject only `null`/`expired`) is copied verbatim, matching the same precedent `book_class_session()` (Story 12.2) already established for this exact scenario — do not tighten to `status = 'active'` only.
