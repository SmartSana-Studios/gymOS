# Story 9.4: Multi-Gym Staff Binding Rules

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As the platform,
I want to enforce that one phone number maps to exactly one role per gym,
so that a person's access at each gym is unambiguous even if they hold different roles across gyms.

## Acceptance Criteria

1. **Given** a phone number with an existing role binding at Gym A, **when** that same person is granted a role at Gym B, **then** a separate binding is created for Gym B — the person now holds two independent role bindings, one per gym, per FR-001's one-phone-one-platform-user model. [Source: epics.md Story 9.4] **(See Dev Notes "The Real Bug: `createStaffMember()` Always Calls `admin.auth.admin.createUser()`" — today this AC cannot even be reached; the second gym's creation attempt fails outright with a raw `phone_exists` error.)**
2. **Given** a phone number already bound to a role at a specific gym, **when** an Owner/Supervisor at that same gym assigns them a different role, **then** the new role replaces the prior binding at that gym (not a second binding), and the replacement is audit-logged. [Source: epics.md Story 9.4] **(See Dev Notes "AC #2 Is Reached Through the *Add Staff* Form, Not `update_staff_role()`" and "AC #2 Mechanically Closes `deferred-work.md`'s Promote-Existing-Member Gap Too" — both are important scope clarifications, not obvious from the AC text alone.)**
3. **Given** a Coach account with no members currently assigned, **when** they log into the Coach Portal, **then** they see an empty state reading "No members have been assigned to you yet. Ask your Manager, Owner, or Supervisor to assign members." — amending Story 5.2's copy, which predates the Supervisor role, to include all three roles that can now perform assignment-adjacent staff actions. [Source: epics.md Story 9.4] **(See Dev Notes "AC #3 Is a Pure Copy Change" — the exact target string is already written out in EXPERIENCE.md, no component logic changes.)**

## Dev Notes

### The Real Bug: `createStaffMember()` Always Calls `admin.auth.admin.createUser()`

`apps/dashboard/services/staff.ts`'s `createStaffMember()` (as shipped by Story 9.1, unmodified by 9.2/9.3) unconditionally calls `admin.auth.admin.createUser({ phone: input.phone, password: temporaryPassword, phone_confirm: true })` for every staff-creation attempt, with no prior lookup for whether `input.phone` already resolves to an existing `auth.users`/`public.users` row. Since `auth.users.phone` is platform-unique (Supabase Auth enforces this — the exact `phone_exists` GoTrue error `errors.ts:110-129` already maps, currently to the unrelated `owner_phone_taken` copy), **AC #1's scenario cannot even be attempted today**: adding an existing member/staff person as staff at a second gym fails outright with a raw, misleadingly-labeled "phone already taken" error, not a successful second binding. This is the actual bug this story fixes — not a missing validation rule, a missing *lookup*.

`apps/dashboard/services/members.ts`'s `findOrCreateUserByPhone()` (`members.ts:369-417`, built for Story 2.3's member-creation flow) already solves the identical "does this phone already have a platform account" problem — but its own creation branch is member-shaped (`phone_confirm: false`, no password, OTP-based first login), incompatible with staff's password-based model. Task 4 borrows its *lookup* query shape (`admin.from("users").select("id").eq("phone", phone).maybeSingle()`) without importing the function itself, keeping staff's own `phone_confirm: true` + temp-password creation branch intact for the genuinely-new-person case.

### AC #2 Is Reached Through the *Add Staff* Form, Not `update_staff_role()`

Story 9.3's own Dev Notes ("Do not build") already drew this exact boundary: *"Do not build: ... the existing-phone multi-gym lookup / one-role-per-gym binding-replacement logic (Story 9.4 — a role *edit* via this story's `update_staff_role()` is a same-gym role change on an existing binding, not the cross-gym binding-replacement scenario Story 9.4 covers)."* AC #2's scenario — "an Owner/Supervisor at that same gym assigns them a different role" — is specifically about someone typing an *already-bound* phone number into the **creation** form (`AddStaffModal.tsx`), not about using the Edit modal on a known row. `update_staff_role()` already handles the "I know this is member X, editing their role" case (Story 9.3, unmodified by this story). This story's actual new mechanism lives entirely inside `create_staff_member()` (Task 2).

### AC #2 Mechanically Closes `deferred-work.md`'s Promote-Existing-Member Gap Too

`deferred-work.md`'s `story-9-1` entry flags: *"the same `admin.auth.admin.createUser()` failure path also blocks the more everyday case of promoting an existing gym member/customer to a staff role... Deliberately deferred per the story's own scope boundary; flagging the framing/frequency gap for PO awareness before Story 9.4 is scoped."* The schema-level invariant both AC #2 and this deferred item collide with is the same one: `idx_members_active_gym_user`, a unique index on `(gym_id, user_id) where deactivated_at is null` (`0003_members_and_users.sql:39`) — it has **no role filter**. A second active `members` row for the same `(gym_id, user_id)` pair is rejected by Postgres regardless of whether the existing row's role is `coach`, `manager`, or `member`. Task 2's find-active-binding lookup is therefore written **without** a `role != 'member'` filter (unlike `update_staff_role()`'s target lookup, which deliberately excludes `role = 'member'` since that RPC is staff-edit-only) — this is what makes the promote-existing-member case fall through to the exact same replace-in-place branch as a staff-to-staff role change, for free. This is confirmed as a deliberate, in-scope inclusion, not scope creep: the alternative (filtering out `role = 'member'` targets) would leave the more common real-world trigger — hiring a gym member as a Receptionist or Coach — still broken after this story ships, contradicting the deferred item's own framing that Story 9.4 was the right place to resolve it.

### A New Self-Targeting Path This Story Must Guard

Before this story, `create_staff_member()` could never legitimately target the caller's own row (there was no lookup-and-replace branch at all — every call was a plain insert). Task 2's new replace branch makes self-targeting reachable for the first time via this RPC: an Owner typing their *own* phone number into the *Add Staff* form would resolve to their own `user_id`, find their own active binding, and (absent a guard) silently rewrite their own name/role. This is a new, real path to the same "self-escalation must be structurally impossible" concern NFR-013/AC #2-of-Story-9.3 already establish for `update_staff_role()`. Task 2 closes it with an explicit guard, mirroring `update_staff_role()`'s shape but simpler (no name-only carve-out — there is no meaningful reason for an Owner to "re-add themselves" through this specific form).

### Why No Password Rotation for an Existing Account

If Task 4 resolved an existing user and still called `generateTempPassword()` + rotated their auth password, it would silently invalidate a password that person currently uses to log into their *other* gym (AC #1) or *this same* gym under their prior role (AC #2) — a real lockout bug, not a cosmetic one, discovered by working through the two-step creation sequencing (Dev Notes precedent: Story 9.1's own "Creation Sequencing" reasoning). No AC, FR, or EXPERIENCE.md mockup describes messaging behavior for this specific case (AD-17's own text only describes the brand-new-person path: "an SMS with a temporary password... is sent automatically"). This story adds a lighter, no-password notification (Task 4/5) rather than staying silent, on the reasoning that a person's access changing at a gym without their knowledge is a legitimate transparency concern, not that any planning artifact requires it — **flagged as a genuinely new, story-invented UX surface**, recommended but not drawn from an existing mockup. If the user would rather ship silently (no notification at all) for this path, that's a one-line change to Task 4 (skip the `sendEvolutionApiMessage` call when `isExistingAccount`), and Task 5's two new i18n keys become unnecessary.

### No New Confirmation Step in the UI

AC #2's text describes the replace happening as a direct consequence of the Owner/Supervisor's submission ("assigns them a different role... the new role replaces the prior binding"), with no mention of a warning or confirmation step, and no EXPERIENCE.md mockup shows one for this scenario (AD-17's own Add/Edit modal spec predates this story). This story does not add one — the *Add Staff* form behaves exactly as it does today from the user's perspective, succeeding on submit; only the resulting toast copy (Task 6) tells the caller what actually happened (new binding vs. existing-account/replace). This keeps the story's UI surface minimal and matches this codebase's established narrow-FR-literal-scope discipline. If the user would prefer an explicit "this person is already staff at this gym — replace their role?" confirmation before submitting, that's a materially larger UI addition (a pre-submit lookup + confirm dialog) not currently scoped here — flagged for reconsideration, not silently decided against.

### Reusing `staff_role_updated`, Not a New Audit Action Type

`update_staff_role()` (Story 9.3) already logs `staff_role_updated` for a direct role edit. Task 2's replace branch reuses the same `action_type` string for the identical underlying fact (a `members` row's role/name changed), distinguished only by a new `replaced_via: 'create_staff_member'` metadata key — rather than inventing a new action type (e.g. `staff_binding_replaced`) that would need its own entry in `AUDIT_ACTION_TYPE_LABEL_KEY` (`apps/dashboard/app/(dashboard)/audit/auditLabels.ts`) to render nicely on the Audit Log page. Note that map is **already stale** — it has no entries at all for `staff_created`/`staff_role_updated`/`staff_deactivated` (added by Stories 9.1/9.3), so both currently fall back to the map's own documented raw-string rendering path. That gap is pre-existing and out of this story's scope to fix (not introduced or worsened by reusing `staff_role_updated` here) — do not touch `auditLabels.ts`.

### The Race-Window Backstop Stays Generic

After Task 2, `create_staff_member()`'s own check-then-branch logic means the raw `idx_members_active_gym_user` unique-violation should no longer fire on any normal call — but a genuine concurrent race (two overlapping `create_staff_member()` calls targeting the same `(gym_id, user_id)` pair, both passing the `select ... into v_existing` check before either commits its write) could still hit it, exactly the same TOCTOU class every sibling staff RPC in this codebase already has (documented, deferred, unfixed elsewhere — see Story 9.3's Review Findings "no row-locking" deferral). The existing `member_already_active_at_gym` / `memberPhoneTaken` mapping (`errors.ts:65-70`) is left as-is; it remains accurate enough as a rare-race backstop message.

### Multi-Gym Login Is a Pre-Existing, Documented V1 Limitation — Out of Scope

`custom_access_token_hook()` (`0009_auth_hook_gym_claims.sql:52-54`) already documents: *"Multi-gym resolution: FR-001 allows a user to have `members` rows at multiple gyms, but a JWT can only carry one gym_id/role pair. V1 rule (documented limitation, no session/gym switcher yet): the most recently created, non-deactivated membership wins."* This story does **not** change that — after AC #1's cross-gym binding is created, that person's *next login* resolves to whichever gym's `members` row is now newest (per this pre-existing tie-break), and there is still no in-app switcher to move between their two gym contexts in one session. AC #1 is a **data-model** correctness fix (both bindings persist, are independently readable via each gym's own `listStaff()`, and independently audit-logged), not a login/session-UX fix. **Do not build a gym switcher or any session-side multi-gym awareness as part of this story** — that would be a materially larger, differently-shaped feature with no AC asking for it.
