# Story 2.3: Manager/Owner — Create, Edit & Deactivate Members

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a Manager or Owner,
I want to create, edit, and deactivate member records,
so that I can maintain an accurate member roster without ever losing history.

## Acceptance Criteria

1. **Given** the Members page, **when** I create a member with name, phone, and a plan configured in Story 2.2, plus optional email, date of birth, profile photo, and emergency contact, **then** a member record is created with join date and subscription status, and appears in the Members list. [Source: epics.md#Story 2.3]
2. **Given** the gym is at its tier's member cap, **when** I attempt to create another member, **then** creation is blocked with "You've reached your plan limit ([N]/[Max] members). Contact GymOS to upgrade." — enforced both as a fast-fail check in the create action and as a database trigger backstop. [Source: epics.md#Story 2.3, prd.md#FR-086]
3. **Given** an existing member, **when** I deactivate them and provide a mandatory reason, **then** their subscription is set to `expired`, they lose check-in access, they retain app history access, no automated push is sent, and the action is audit-logged. [Source: epics.md#Story 2.3, prd.md#FR-083]
4. **Given** the Members page, **when** I search by name or phone, or filter by subscription status, **then** the list updates accordingly (300ms debounce), and I can export the current filtered view to CSV (max 1,000 rows, standard export columns). [Source: epics.md#Story 2.3]
5. **Given** a Receptionist (not Manager/Owner), **when** they view the Members page, **then** they can search, filter, view, and export records but cannot see create/edit/deactivate actions. [Source: epics.md#Story 2.3]

## Scope Note — Read Before the Tasks

This story hits more schema/RLS gaps than usual because it is the **first** story to actually write to `members` beyond owner-provisioning and the **first** to write to `subscriptions` at all. Eight decisions below, each forced by a real gap discovered while researching this story — read before writing code.

1. **A member's platform account (`users`/`auth.users`) does not exist yet when a Manager/Owner creates the member record.** Real phone verification only happens in Story 2.6 (member app OTP onboarding), which is later. But `members.user_id references users(id) not null` — a `members` row cannot exist without one. Resolution, mirroring `createGym`'s exact precedent (`apps/super-admin/app/(admin)/gyms/actions.ts` Step 3): `createMember` uses the Supabase **Admin API** (`admin.auth.admin.createUser({ phone, phone_confirm: false })` — no password, no email; **unlike** `createGym`'s owner account, a member authenticates via phone/OTP only, so `phone_confirm` stays `false` so the member's *real* first OTP verification in Story 2.6 is what actually confirms the phone) to provision a placeholder `auth.users` row, which `handle_new_user()` (0003) mirrors into `public.users` automatically. **Before calling `createUser`**, look up `public.users` by phone via the admin client first (FR-001: "a user may be a member at multiple gyms via separate members rows" — the same phone may already have a platform account from another gym's membership, or from being staff somewhere). If found, reuse that `user_id` instead of creating a second account. If `admin.auth.admin.createUser` itself still races and returns a `phone_exists` GoTrue error (another session created the same brand-new phone a moment earlier), **do not surface it as an error** — re-query `public.users` by phone and continue with the now-existing row. This needs a new `apps/dashboard/lib/supabase/admin.ts` (copy `apps/super-admin/lib/supabase/admin.ts` verbatim — same `SUPABASE_SERVICE_ROLE_KEY` pattern, not yet present in `apps/dashboard`) and a new `SUPABASE_SERVICE_ROLE_KEY` entry in `apps/dashboard/.env.example`.
2. **`subscriptions.expiry_date` is `not null`, but Pay-per-session plans have no fixed expiry** (AD-05's mockup literally hides the Expiry Date field when the selected plan is Pay-per-session — same "no fixed duration" concept Story 2.2 already resolved for `plans.duration_days`). Resolution: this story's migration makes `subscriptions.expiry_date` **nullable**, valid only when the subscription's plan has `plan_type = 'pay_per_session'`. Unlike `plans.duration_days`'s CHECK constraint (single-table), this invariant spans two tables (`subscriptions.plan_id → plans.plan_type`), which a Postgres `CHECK` constraint cannot reference — enforce it with a `BEFORE INSERT OR UPDATE` trigger on `subscriptions` instead, written with explicit `is not null`/`is null` guards (Story 2.2's Review Round 2 found a real three-valued-logic CHECK bug from an implicit-NULL comparison — don't repeat it in trigger form either).
3. **`subscriptions` RLS has zero business policies and Story 2.2 explicitly deferred all of it to "Story 3.1/3.2's job."** That deferral doesn't hold once a real feature needs to write to the table — this story is that feature (member creation inserts a `subscriptions` row; deactivation updates one to `expired`). Add exactly what this story needs: manager/owner-scoped INSERT (member creation) and UPDATE (deactivation only touches `status`, but RLS authorizes by role not by column, same discipline as every other UPDATE policy in this codebase) on `subscriptions`, plus a SELECT policy so the Members list can show status/expiry (any gym-staff role, same ungated-by-role shape as `gym_staff_read_own_plans` — Receptionist needs to view/export status too, AC #5). Story 3.1/3.2 still own the *lifecycle* policies (cron-driven status transitions, renewal) — those run as `service_role`/their own future policies, not this one.
4. **Member cap counts active AND deactivated members — deactivating does not free a slot.** This is explicit, not an inference: PRD FR-086 states "Active and deactivated members both count toward the cap" verbatim, and architecture.md's Gap 2 resolution says the same ("comparing active+deactivated count"). Do not implement normal SaaS "deactivate frees a slot" semantics — count every `members` row for the gym, full stop. Cap = `gyms.member_cap_override` if non-null, else `tiers.member_cap` via `gyms.tier_id` (both nullable = unlimited, per Story 1.6). The enforcing trigger must be `security definer` (a Manager/Owner session has **no** SELECT policy on `tiers` at all — only `super_admin_read_tiers` exists, 0010 — so a non-security-definer trigger would silently read 0 rows for `tiers.member_cap` under RLS and either mis-block or, worse, silently treat every gym as uncapped). Mirrors `platform_metrics()`/`gym_member_count()`'s established SECURITY DEFINER pattern (0011).
5. **AD-05's mockup "Assigned Coach" dropdown has no backing table yet** — `coach_assignments` doesn't exist in any migration (confirmed via grep). It's Epic 5, Story 5.1's job. **Do not build it here.** Create/Edit forms in this story omit the Assigned Coach field entirely — same "don't invent scope the schema doesn't support yet" discipline as Story 2.2's Scope Note.
6. **AD-05's "Billing Interval" field is not a new column** — `subscriptions` has no `billing_interval` of its own; `plans.billing_interval` (Story 2.2) is already the single source of truth for a plan's billing cadence. Surface it as a **read-only display** next to the Plan selector (mirrors 2.2's own "access-scope description" resolution for `plan_type`'s "access type"), not an independent editable input.
7. **No Manager/Owner SELECT policy exists on `tiers` anywhere** (confirmed: `0010`/`0011` only ever grant `super_admin_read_tiers`; `rls_tenant_isolation.test.sql:63` still asserts 0 rows for a `member`-role session). AC #2's fast-fail cap check needs the gym's effective cap (`gyms.member_cap_override` or `tiers.member_cap`), which a plain gym-staff session cannot read today. Opening a broad `tiers` SELECT policy would leak platform-wide tier pricing to every gym's staff — disproportionate to what this check needs. Resolution: a `security definer` RPC, `gym_effective_member_cap()` (no args, resolves the caller's own gym via `private.gym_id()` internally, mirrors `platform_metrics()`/`gym_member_count()`'s exact pattern from `0011`), returns the caller's own gym's effective cap only (nullable = unlimited) — not a general `tiers` table policy. `memberCountForGym`'s fast-fail check (Task 3) calls this RPC instead of joining `tiers` directly.
8. **AD-04 (Member Detail, its own tabbed page with Subscription/Payments/Attendance/Coach Notes tabs) is out of scope for this story** — three of its four tabs depend on data from epics that don't exist yet (Payments: Epic 4, Attendance: Epic 3, Coach Notes: Epic 5), so building it now means building three dead tabs. AD-03's "View" action and row-click, for this story, open the same `MemberModal` used for Edit — in read-only mode for Receptionist (AC #5: "view" is explicitly allowed), in edit mode for Manager/Owner. A dedicated `/members/:id` detail route is deferred to whichever future story first needs one of those tabs.

**Edit-mode scope, to keep this story bounded:** the Edit form (AD-05 in edit mode) covers identity fields only — Name, Email, Date of Birth, Profile Photo, Emergency Contact. It does **not** include Phone (FR-023's "phone changes require admin intervention" is a real future capability, but changing a member's phone touches their `auth.users` identity, not just the `members` row, and no AC in this story tests it — defer to a dedicated future story) or Plan/Join Date/Subscription Status/Expiry (changing a member's plan/subscription is renewal/lifecycle territory — Story 3.2's job, not "editing a record"). None of this story's ACs require either.
