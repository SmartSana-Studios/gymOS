### New findings from 22-8, the QA and the deploy

**N1. The local CI gate reported failures as passes.** Disposition: **fixed**; **process lesson**.
- `stage_pgtap`, `stage_unit` and `stage_e2e` in `scripts/ci-local.sh` relied on `set -e`, which is ignored when `run_stage` calls them inside an `if`, so only the last command's status counted. The `static` stage had been fixed for the same bug on 2026-10-12, but the other three were not.
- Evidence: my local pgTAP log for `d4f65c1` showed three `FAIL` lines while the stage printed `PASS` (log `/tmp/ci-local-logs/pgtap.log`); the GitHub `rls-tests` job failed on the same files. Fixed in `c09cdee` (`|| return 1` per command); proof: the pgtap stage then reported FAIL on the broken fixtures.
- Consequence: every local "green" on `epic/22` between roughly the start of 22-8 and `d4f65c1` was unreliable for pgTAP, including the ones I reported to the owner. Nothing reached production unverified, because the pre-merge GitHub run caught it, but the merge gate was a single point of failure that did not fail.

**N2. Migration 0130 and the 0127/0128 helpers broke older pgTAP files that the gate hid (see N1).** Disposition: **fixed** (`c09cdee`, `e654213`).
- Three fixtures made one account both gym owner and Super Admin (`audit_log_immutable`, `staff_edit_deactivation`, `super_admin_aal2_flag`), which 0130 now refuses. Fixtures now use a separate Super Admin account.
- `suspension_rpc_coverage.test.sql` failed because `private.session_gate_touch`, `stepup_record_failure` and `recovery_audit` (0127/0128) write `audit_log` without a gym-status check; they now sit on the documented exclusion list with reasons.
- This is the first retro's process lesson (item 66, "a story that introduces a gate lists its consumers") happening again: the new trigger's consumers were not enumerated.

**N3. Under load, `pgtap-run.sh` loses output (plan=none) for files that pass alone.** Disposition: **mitigated**; the root cause is still open.
- Evidence: 10 files failed on 2026-10-18 and 3 on 2026-10-19 with `plan=none ok=0 errors=0` while `static` ran beside it (static took 295 s); all passed alone. `pgtap-run.sh` now retries up to 3 times and prints only the final attempt.
- This is `epic-20-retro-item-39` (still `in-progress`): the retry is a mitigation, not the cause. The false green in N1 had been hiding the frequency.

**N4. The production data had no backup when the migrations ran.** Disposition: **owner action**; open.
- Evidence: Supabase management API `/database/backups` returned `backups: []`, `pitr_enabled: false`, 2026-10-17. The deploy went ahead on the owner's decision with a read-only definitions snapshot (functions, policies, triggers, ledger) in the session scratchpad as the only fallback. `epic-19-retro-item-26` (run `docs/restore-test.md`) is also still open.

**N5. The first deploy path did not work from the dev container.** Disposition: **worked around; document**.
- `scripts/deploy-0098-0103.sh` and `scripts/prod-db.sh` depend on `docker exec` psql, which fails silently here (confirmed 2026-10-17: no output, exit 0). The Epic 22 deploy was rebuilt on the Supabase management API (`scripts/deploy-0124-0130.sh`), one transaction per migration, with a read-only preflight. It worked, but it was written during the deploy window.
- The Vercel CLI hung and has no login in this container; the operator scripts need an uninstalled `pg` module (`scripts/lib/operator-pg.mjs:12-15`), installed to a scratch directory each time.

**N6. Production recovery-email setup failed four times on a mail configuration, and the app hid why.** Disposition: **partly fixed**; two items open.
- Evidence: Vercel log `[mail] send failed EMESSAGE` (owner paste, 2026-10-19 12:06 UTC); `MAIL_FROM="GymOS <hello@gymosapps.com>"` was refused by Resend, the bare `hello@gymosapps.com` worked (owner finding). Registration then succeeded at 13:57 UTC (audit `super_admin_recovery_email_set`, `super_admin_recovery_code.consumed_at`).
- Fixed: the log now carries the SMTP refusal text, scrubbed (PR #78, `lib/mail.ts` `smtpReason`); `MAIL_FROM_NAME` lets the mailer build the header (PR #79).
- **Open (verified in code and production):** (a) the audit row `super_admin_recovery_requested` with outcome `sent` means a code was issued, not that mail was delivered, which misled a diagnosis during this deploy; (b) a failed send does not void the code and still counts against the 3-requests-per-hour limit (`0128_...sql:149`, `recovery-actions.ts:98-101`), so three failed sends locked the owner out of retrying for an hour; (c) the build warns that `MAIL_*` are missing from `turbo.json`.

**N7. Stale tab after a deploy shows a generic error; adding a second authenticator from a password session shows a generic permission message.** Disposition: **defer / small UX fix**.
- Evidence: owner paste, `POST /security` 404 on deployment `dpl_EWtc...` from a page loaded on `dpl_CAFU...` (server-action skew); `enrollFactor` returns `errors.permissionDenied` when a verified factor exists and the session is not aal2 (`security/actions.ts`, "A second factor needs aal2"). ## Open questions

- ~~Does any flow reactivate a deactivated gym through payment?~~ **Answered 2026-10-20: no.** Checked in code and in the live local database. Every SaaS payment path refuses a deactivated gym twice: `initiate_saas_billing_payment`, `record_out_of_band_saas_billing_payment` and `apply_saas_billing_credit` raise, and the four functions that set `status = 'active'` (those three plus `complete_verified_saas_billing_payment` and the lifecycle job) all carry `and status <> 'deactivated'` on the update (`0072`, `0075`, `0077`; `pg_get_functiondef` on the live functions). The only reactivation is a Super Admin `reinstateGym` (`apps/super-admin/app/(admin)/gyms/actions.ts`, audited with a reason). So item 62 (`billing.saas_pay` exempt for suspended only) reverses nothing: today the Owner of a deactivated gym passes `authorize_action` and is then refused by the RPC; the change only makes the refusal come first with reason `gym_not_active`. One edge, not a reactivation: a payment started before the gym was deactivated and completed after is marked `verified` by `complete_verified_saas_billing_payment` (the payment row is updated first) while the gym update is skipped, so the money is recorded and nothing else happens; it needs a manual refund or credit.
- Why did Resend refuse the `Name <address>` form? Unknown. It may be how the Vercel value was stored, or Resend's reading of the header; `MAIL_FROM_NAME` is untested in production until the owner sets it.
- Should the production recovery path be rehearsed on a non-production project before relying on it?
