# Story 4.13: Per-Gym Tara Money Account Connection

Status: done

## Story

As a gym Owner,
I want to connect my own gym's Tara Money account from Settings,
so that member mobile-money payments settle directly into my gym's account, never GymOS's.

**Context — read this before touching any AC below.**

**⚠️ Environment-state warning, not this story's scope but blocks a clean diff for it:** as of this story's creation, Story 4.12's entire implementation (RenewalModal.tsx, payments/actions.ts, subscriptions.ts, featureFlags.ts, migration `0051_payments_realtime_publication.sql`, etc.) is **uncommitted** on top of `baseline_commit` above (`git status` shows it all as working-tree changes, not a merged commit — `git log` HEAD is still `666a686`, the Story 4.11 commit). `sprint-status.yaml` already carries an open action item about this exact pattern ("Commit immediately when a story's Status is set to done, before starting the next story's work"). **Recommend committing Story 4.12's work before starting this story's implementation** — otherwise this story's own diff will be inseparable from 4.12's in `git diff`/code review. This is an environment observation, not an AC of this story.

**Scope boundary vs. Story 4.14 (read this to avoid overbuilding):** this story is the *storage and UI* half of per-gym Tara Money accounts — Settings UI, Vault-encrypted storage, connection-status visibility gating. It does **not** wire these credentials into actual payment initiation or webhook verification. `TaraMoneyProvider.ts`'s `initiate()`/`verifyWebhookSignature()` still read the platform-wide `TARAMONEY_API_KEY`/`TARAMONEY_BUSINESS_ID`/`TARAMONEY_WEBHOOK_SECRET` env vars, unchanged — every payment (even for a gym that has just "connected" via this story) still settles into GymOS's single `9FmIZg9GBB` account until Story 4.14 ("Flow A Explicit Gym-Account Routing & Auditability", FR-124/FR-128, the `{type:'gym', gym_id}` `PaymentProvider` routing context) actually consumes what this story stores. Story 4.12's own Dev Notes said this explicitly: *"Flow A's eventual per-gym-account routing (FR-124/FR-126, Story 4.13/4.14) does not exist yet... Do not attempt to add gym-scoped credential resolution here; that is explicitly out of scope until Story 4.13"* — meaning 4.13 is where the *storage* begins, 4.14 is where it becomes *load-bearing*. **Do not touch** `TaraMoneyProvider.ts`, `PaymentProvider.ts`, `supabase/functions/payment-webhook/index.ts`, `0029_payment_provider_registry.sql`, or `activate_payment_provider()`.

**Is AC #3's visibility gating premature, then?** No — confirmed intentional by `prd.md` FR-127's literal text: *"the app simply does not surface the automated 'pay by Tara Money' action until the Owner connects... Connecting is an enhancement, never a prerequisite [to operating by cash]."* So this story **does** change today's behavior: right now (post-4.12), the `mobile_money` renewal option is visible to every gym gated only by the platform-wide `TARAMONEY_INITIATION_ENABLED` kill switch — this story adds a second, per-gym gate (has this gym connected?) on top of it. That the underlying money still routes to the platform account until 4.14 is a known, accepted interim state per the epics' own 4.13→4.14 sequencing, not a defect to fix here.

**The 3 credential fields this story must capture** are dictated by what `TaraMoneyProvider.ts` already reads today (`initiate()` line 124-125, `verifyWebhookSignature()` line 187) — capturing exactly this shape now means Story 4.14 only has to change *where* the values come from, not renegotiate what they are:
- `apiKey` (↔ `TARAMONEY_API_KEY`)
- `businessId` (↔ `TARAMONEY_BUSINESS_ID`)
- `webhookSecret` (↔ `TARAMONEY_WEBHOOK_SECRET`)

None of these are returned to any client after saving (FR-126, NFR-017 — "never returned to any client... never logged"). A saved connection is write-only from the UI's perspective; the UI only ever sees a masked identifier + a connected timestamp back.

## Acceptance Criteria

1. **Given** the Settings page, **when** I open "Connect payment account", **then** I can authorize my gym's Tara Money merchant credentials, which are stored in Supabase Vault (AD-15) — encrypted, readable only by the server-side payment service, never returned to any client, and tenant-isolated (NFR-017). [Source: epics.md#Story 4.13; prd.md#FR-126, NFR-017; ARCHITECTURE-SPINE.md#AD-15]
2. **Given** a gym that has not connected Tara Money, **when** members and staff use the gym, **then** cash and the other manual payment methods (FR-033) work exactly as before — connecting is additive, never a prerequisite for operating (FR-127). [Source: epics.md#Story 4.13; prd.md#FR-127]
3. **Given** a gym with Tara Money connected, **when** a member or receptionist looks for a mobile-money payment option, **then** the automated "pay by Tara Money" action is now visible, alongside cash/manual entry, not replacing them. [Source: epics.md#Story 4.13; prd.md#FR-127]
   - **Design:** this is a *second* gate layered on top of Story 4.12's existing `TARAMONEY_INITIATION_ENABLED` platform kill switch, not a replacement for it — both must pass for the option to show. Story 4.12's code review already found and fixed one instance of "the same boolean check duplicated across 4 call sites with no shared helper" (`isMobileMoneyInitiationEnabled()` in `apps/dashboard/lib/featureFlags.ts`) — do not reintroduce that mistake for this story's new gym-connection check. Combine both checks in one exported helper and update all 4 of Story 4.12's call sites through it: `apps/dashboard/app/(dashboard)/page.tsx`, `apps/dashboard/app/(dashboard)/attendance/page.tsx`, `apps/dashboard/app/(dashboard)/subscriptions/page.tsx` (client-visibility hide, all three read `isMobileMoneyInitiationEnabled()` today) and `apps/dashboard/app/(dashboard)/payments/actions.ts`'s `initiatePaymentAction` (the real server-side enforcement).
4. **Given** Supabase Vault's GA/beta status, **when** this story is implemented, **then** its current status is confirmed against Supabase's documentation before treating it as a hard dependency (flagged in `ARCHITECTURE-SPINE.md`), and the outcome is recorded in `docs/decisions.md`. [Source: epics.md#Story 4.13; ARCHITECTURE-SPINE.md#AD-15, Stack table]
   - **Pre-seeded research (must be reconfirmed hands-on, not trusted as-is — see Dev Notes' Latest Technical Research):** as of this story's creation, `supabase.com/docs/guides/database/vault` still carries "Vault is in beta" language; Vault does **not** depend on `pgsodium` (whose own deprecation is unrelated/unblocking). Local `supabase/config.toml` has `[db.vault]` present but commented out — meaning this project's local stack has never actually exercised Vault before. **If Task 1's hands-on check finds Vault unusable or impractical in this project's actual Supabase version, stop and raise a `[Review][Decision]` finding instead of silently substituting a different encryption scheme** — AD-15 chose Vault specifically over pgsodium/app-layer encryption as "the least code to own and maintain," so a fallback is a real architecture decision, not an implementation detail.

### Latest Technical Research — Supabase Vault (confirm hands-on in Task 1, do not trust this section alone)

- Current public docs (`supabase.com/docs/guides/database/vault`, fetched during this story's creation) still describe Vault as beta, and explicitly warn: *"you should ensure that you protect access to this view [`vault.decrypted_secrets`] with the appropriate SQL privilege settings at all times, as anyone that has access to the view has access to decrypted secrets"* — reinforces why this story grants **no** role direct access to `gym_payment_credentials` or any Vault view; only the 3 `security definer` functions ever touch decrypted material.
- Vault's dependency on `pgsodium` is being actively removed by Supabase (in progress industry-wide as of this research) — `pgsodium`'s own pending deprecation does not block or threaten Vault's availability.
- Documented API surface: `vault.create_secret(secret, name, description) returns uuid`, `vault.update_secret(uuid, secret, name, description)`, `select * from vault.decrypted_secrets` (columns include `id`, `name`, `decrypted_secret`, `created_at`, `updated_at`). No documented `vault.delete_secret()` — plan on a plain `delete from vault.secrets where id = ...`, but confirm this actually works from a `security definer` function context during Task 1, since the docs snippet fetched for this story did not cover that case explicitly.
