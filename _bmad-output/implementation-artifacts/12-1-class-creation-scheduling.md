# Story 12.1: Class Creation & Scheduling

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a Manager or Owner,
I want to create classes with a name, description, assigned coach, capacity, and schedule,
so that my gym can run a structured weekly program.

## Acceptance Criteria

1. **Given** the new Classes admin page (`/classes`, FR-121), **when** a Manager or Owner creates a class, **then** they set name, description (optional), assigned coach (a dropdown of this gym's own `coach`-role `members` rows), capacity (positive integer, minimum 1), and a schedule that is either **one-off** (a single date+time) or **recurring** (≥1 day-of-week, a time, and a start date) — FR-104. The class is tenant-isolated (`gym_id`-scoped RLS) like every other table in this schema.
2. **Given** any gym staff role, **when** they view the Classes admin page, **then** it lists this gym's classes: name, assigned coach, schedule (one-off date/time or the recurring pattern), the next upcoming session's date/time, and that session's booking count vs. capacity — FR-121. **Scope note (read this before building):** this story ships the booking-count column reading `0 / {capacity}` for every session, because `class_bookings` (Story 12.2, not yet built) does not exist. The column is a real, wired-up query against a real (currently-always-zero) count — not a stub or a hardcoded `0` — so it will start reflecting real numbers automatically once Story 12.2 ships, with no follow-up change to this story's own query. This is a genuine, unavoidable sequencing gap between the epic's own AC wording and its story order, not a shortcut to fix here.
3. **Given** a Receptionist, **when** they open the Classes page, **then** the "+ Create class" button and every class row's "Edit" action are absent from the DOM (not merely disabled) — Manager/Owner-only, matching the "+ Add Plan"/Settings precedent. The real enforcement is RLS (`manager_or_owner_insert_own_classes`/`manager_or_owner_update_own_classes`); the UI hiding is defense-in-depth only. Booking/attendance-marking (Story 12.3) is explicitly out of scope for this story's Receptionist view — this story's list has no row-expand at all.
4. **Given** a class created with `schedule_type = 'one_off'`, **when** it is created, **then** exactly one `class_sessions` row is materialized immediately at the specified date/time.
5. **Given** a class created with `schedule_type = 'recurring'`, **when** it is created, **then** upcoming `class_sessions` rows are materialized immediately for a rolling window ahead of today (this story's Dev Notes recommend 4 weeks), matching the configured day(s)-of-week/time/start date — and a daily scheduled job keeps extending that window forward indefinitely, so a recurring class always has a bookable next session without anyone re-triggering anything by hand.
6. **Given** an existing class, **when** a Manager or Owner edits its name, description, coach, or capacity, **then** the change saves and is reflected immediately in the Classes list — no session regeneration needed for these fields.
7. **Given** an existing class, **when** a Manager or Owner edits its schedule (the one-off date/time, or any part of the recurring pattern), **then** its not-yet-occurred `class_sessions` rows are deleted and replaced with freshly materialized ones matching the new schedule; already-past sessions are left untouched (historical record preserved). **[Review][Decision] flag:** this delete-and-regenerate approach is safe only because `class_bookings` does not exist yet — there is nothing to lose. Story 12.2 must add a bookings-exist guard (e.g. refuse to delete/reschedule a session with confirmed bookings, or require explicit cancellation) before this path is safe to keep as-is; this story does not add that guard, since the table it would guard against doesn't exist.

### Review Findings

- [x] [Review][Patch] **[Decision: single-transaction RPC]** Partial-failure asymmetry between `insertClass` and `updateClass` — `insertClass` compensating-deletes the just-inserted `classes` row if `materialize_class_sessions` fails, but never checks whether that delete itself succeeded (a failed delete leaves a session-less orphan class with no self-healing path for a one-off class, since the daily cron only tops up `recurring` classes). `updateClass` has zero compensating action if `materialize_class_sessions` fails after the row `UPDATE` has already committed — `classes` and `class_sessions` are left permanently out of sync until another successful edit. **Fixed:** added `create_class()`/`update_class()` SECURITY DEFINER RPCs (migration 0057) that do the row write and materialization in one transaction; `insertClass`/`updateClass` (services/classes.ts) now call these instead of two separate round trips. [apps/dashboard/services/classes.ts, supabase/migrations/0057_class_creation_scheduling.sql]
- [x] [Review][Patch] **[Decision: DB trigger]** `coach_id` has no DB-level enforcement that the referenced member belongs to the same gym as the class, nor that they hold the `coach` role — only the UI's gym-scoped `listCoaches()` dropdown narrows the choice, so a direct RPC/API caller (or a future regression in `listCoaches()`) could assign a cross-gym or non-coach member as a class's coach. This matches Task 1's literal SQL (`coach_id uuid not null references members(id)`) but conflicts with AC #1's "this gym's own coach-role members" / "tenant-isolated... like every other table" intent. **Fixed:** added `private.classes_validate_coach()` `BEFORE INSERT/UPDATE` trigger on `classes` validating `coach_id`'s member row has `gym_id = NEW.gym_id and role = 'coach'`, enforced on every write path. [supabase/migrations/0057_class_creation_scheduling.sql]
- [x] [Review][Patch] `scheduleChanged` in `editClass` is a near-permanent false positive due to timestamp/time format mismatches — `existing.oneOffSessionAt` (DB `"+00:00"`-style format) compared against `cls.oneOffSessionAt` (client `.toISOString()`'s `".000Z"` format), and `existing.recurrenceTime` (`"HH:mm:ss"` from Postgres `time`) compared against `cls.recurrenceTime` (`"HH:mm"` from the form) — so nearly every edit, even a pure name-only change, triggers `p_reschedule = true`, deleting and regenerating future `class_sessions` rows unnecessarily and defeating AC #6's "no session regeneration needed" guarantee. **Fixed as part of the single-transaction RPC change above:** `update_class` now computes `scheduleChanged` itself, in SQL, via typed `IS DISTINCT FROM` comparisons against the pre-update row — no more JS-side string comparison. `editClass` (actions.ts) no longer computes or passes this flag at all. Proven by new pgTAP coverage (a name-only edit leaves the session row's id untouched; a genuine schedule change regenerates it). ## Dev Notes

### This Story's Real Crux — Read This First

Epic 12 is the first story in a brand-new feature area: no `classes`, `class_sessions`, or any scheduling concept exists anywhere in the current schema, dashboard, or mobile app (confirmed via full-repo grep before this story was written — the only prior "class"/"session" hits are `check_in`'s own unrelated "open session" concept and Story 5.3's `session_notes`, neither related). `ARCHITECTURE-SPINE.md`'s own Deferred section says as much: *"Class/workout entity detail (columns, exact cardinalities beyond the ERD above) — left to Epic 12/13 story-writing; the ERD fixes only what another epic could build incompatibly against."* This story is where that detail gets fixed for the first time — the schema design in Task 1 (columns, the one-off/recurring discriminator, the materialization job shape) is this story's own invention, grounded in the ERD's fixed points (`CLASSES ||--o{ CLASS_SESSIONS`, gym-scoped, `MEMBERS ||--o{ CLASS_BOOKINGS : books` for the *next* story) and in the established `private`-helper/public-RPC/cron-job pattern Story 6.5 (`0056`) already proved out for a different feature. Treat every schema/function name in Task 1 as a recommendation to implement as specified, not as something to independently re-derive — but flag any place reality (e.g. Postgres version quirks with `generate_series`/`extract(dow from ...)` in this environment) forces a deviation, the same way prior stories have flagged environment-specific surprises.

### Booking-Count Scope Gap — Read This First

FR-121 and this story's own AC #2 both say the Classes list shows "booking counts vs. capacity." **`class_bookings` does not exist — it is Story 12.2's table.** This is not a gap to close by building booking functionality early (Story 12.2 has its own capacity-race RPC design, `book_class_session()`, that this story must not preempt or duplicate) and not a gap to close by silently dropping the column either (the AC and the AD-18 mockup both show it). The resolution: ship the column wired to a real query that today always evaluates to `0` (no `class_bookings` table to join against), documented plainly in code and in `docs/decisions.md`, so Story 12.2 only has to change the one line computing `bookedCount` — not add a new column, a new query, or new UI.

### `class_sessions` Is Not This Story's Booking Boundary

`class_sessions` rows are pure schedule metadata (when a session happens) — they carry no capacity snapshot, no booking list, no attendance state. Story 12.2 (`AD-21`) will add `class_bookings` referencing `class_sessions.id`, and its own `book_class_session()` RPC will read `classes.capacity` live (via the session's `class_id` FK) rather than a per-session snapshot — this story does not add a capacity column to `class_sessions` in anticipation of that, since nothing here asks for point-in-time capacity snapshots and Story 12.2 may decide it doesn't want one either.

### Architecture Compliance

- **AD-21** ("Bounded-capacity actions are a row-locked check-then-insert RPC... **Binds:** Epic 12 class booking (FR-105), class attendance (FR-107)") is explicitly scoped to Story 12.2/12.3's booking and attendance RPCs, **not** this story's class *creation*. Class creation has no concurrency/capacity race to guard against (a Manager creating a class is not competing with anyone), so it correctly follows the simpler direct-RLS-write pattern `plans`/`0017` already established, not a `SECURITY DEFINER` RPC. Do not build `materialize_class_sessions()` as a capacity-checking RPC — it has nothing to check capacity against.
- **AD-19** (Independent scheduled jobs, one `job_runs` table) — `run_class_session_materializer_job()` follows this exactly, same `job_runs` insert/`log_audit_event`-on-failure shape as `run_subscription_lifecycle_job`/`run_quiet_gym_alert_job`.
- Every new table follows the RLS-enabled-in-same-migration, `gym_id`-carrying convention (Consistency Conventions table) — no exceptions taken here.
- `recurrence_days`/`recurrence_time`/`recurrence_start_date` are plain columns, not JSON — this schema has no precedent for JSON-typed structured config columns, and a fixed, typed shape is simpler to query (the materializer's `extract(dow from d) = any(recurrence_days)` comparison) than JSON-path extraction would be.
