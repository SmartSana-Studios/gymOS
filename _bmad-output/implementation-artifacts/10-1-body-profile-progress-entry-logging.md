# Story 10.1: Body Profile & Progress Entry Logging

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a member,
I want to log an optional body profile and ongoing progress entries (weight, measurements, a photo, a note),
so that I can track my fitness journey over time without any of it being mandatory.

## Acceptance Criteria

1. **Given** the new `progress_entries` table and body-profile columns, **when** they are created, **then** RLS is enabled with a member-own-row-only default in the same migration (matching the project's no-open-table-window convention) — Story 10.2 later adds the assigned-coach read grant on top of this baseline; it does not establish privacy from scratch. [Source: epics.md Story 10.1, AC #1]
2. **Given** my member profile, **when** I complete the optional "Complete your profile" step, or visit Progress at any later time, **then** I can enter height, starting weight, and optional baseline measurements (FR-093) — none of it is required to use the app. [Source: epics.md Story 10.1, AC #2; prd.md FR-093]
3. **Given** the Progress screen, **when** I log an entry, **then** I can include any subset of weight, measurements (waist/chest/hips/arms/thighs — all five fields ship per OQ-10), a photo, and a note; the entry is stamped with a timestamp and a `client_entry_id` for offline-safe dedupe. [Source: epics.md Story 10.1, AC #3; prd.md FR-094, OQ-10]
4. **Given** a progress entry I logged, **when** I choose to remove it, **then** it is soft-deleted — I can only delete my own entries, never another member's. [Source: epics.md Story 10.1, AC #4] — **Narrowed by code review (2026-08-21):** this story ships the full soft-delete capability at the data layer (RLS `self_soft_delete_own_progress_entries` policy, the pin-back trigger, pgTAP coverage), satisfying "I can only delete my own entries, never another member's." The member-facing delete *affordance* is deferred to Story 10.3 — this story never builds an entries list/history view for a delete action to live on (see Scope boundary below), the same sequencing gap already resolved for the Progress tab/route itself.
5. **Given** I am offline, **when** I log a progress entry, **then** it queues locally (SQLite) and syncs on reconnect via `client_entry_id` idempotency (FR-097, amending FR-061) — the only V1.5 flow other than check-in that supports offline. [Source: epics.md Story 10.1, AC #5; prd.md FR-097]

### Scope boundary — this story's resolution of two epics-stub sequencing gaps

The epics stub sequences Epic 10 as 10.1 (this story) → 10.2 (privacy/photo-sharing) → 10.3 (Progress screen/trends) → 10.4 (Coach Portal). Read literally, two of its ACs are ahead of what earlier stories in that sequence deliver. Both are resolved here, explicitly, so `dev-story` does not re-litigate them:

- **The Progress tab/route does not exist yet.** `epics.md` Story 10.3's own AC #1 states the app's Progress tab is *that* story's deliverable (FR-123), and the current mobile tab bar (`apps/mobile/src/components/app-tabs.tsx:20-38`) still has only 4 triggers (`index`, `checkin`, `history`, `profile`) — no `progress` tab exists, and the V1.5 5-tab restructure (`EXPERIENCE.md:172`) hasn't landed. This story does **not** add the tab or the `/progress` route. Instead: it builds a reusable `LogEntrySheet` component (AC #3's log-entry mechanism, any subset of fields) and gives it two interim entry points that already exist — a new optional onboarding step (AC #2's "Complete your profile" step) and a new row on the existing Profile tab (AC #2's "at any later time"). Story 10.3 mounts the *same* `LogEntrySheet` onto its new Progress screen without rework — build it route-agnostic (props in, callback out), not hardcoded to either call site.
- **AC #4's delete affordance is Story 10.3's, not this story's.** (Added by code review, 2026-08-21, resolving a [Review][Decision] finding.) This story ships soft-delete completely at the data layer (RLS policy, pin-back trigger, pgTAP coverage) — the only thing genuinely deferred is a member-facing UI to trigger it, because this story builds no entries list/history view at all (only the write path: `LogEntrySheet` + its two interim entry points). Story 10.3 owns the Progress screen, which is the first place a list of past entries — and therefore a delete action — has anywhere to live.
- **The private photo bucket is created by this story, not deferred to 10.2.** `epics.md` AC #1's own wording attributes "the dedicated private photo bucket" to Story 10.2. But this story's own AC #3 requires a photo to be a loggable field *now* — a feature that doesn't functionally work until a later story ships isn't acceptable. Resolution: this story creates the `progress-photos` bucket (private, non-guessable paths, per AD-24's baseline) with **member-only** access (no coach grant, no sharing/consent, no revoke — that layer is 100% Story 10.2's). This satisfies AD-24's structural requirement now; Story 10.2 adds the sharing/consent/revoke logic on top, exactly as it does for the RLS row-level grant.

## Dev Notes

### Why a Plain RLS Insert, Not a `check_in()`-Style RPC

`check_in()` (`0028_member_app_offline_check_in_queueing.sql`) is a `SECURITY DEFINER` RPC because it enforces a real business invariant beyond row ownership — one-open-check-in-per-member (AD-22, a row-locked check-then-insert) plus auto-timeout backfill logic. `progress_entries` has no equivalent invariant: any number of entries, no capacity check, no cross-row state to protect. The only two things a write needs are (a) row ownership (member can only insert/update their own rows) and (b) idempotent replay on retry (`client_entry_id`) — both are fully expressible as RLS + a partial unique index, with no window where a plain client-side insert could violate an invariant an RPC would otherwise guard. Manufacturing a `SECURITY DEFINER` RPC here would add a maintenance surface with no corresponding requirement — resist the temptation to copy `check_in()`'s shape just because it's the nearest offline-write precedent in this codebase.

### Why `deactivated_at`, Not `deleted_at`

The architecture's own Consistency Conventions table (`ARCHITECTURE-SPINE.md` line 195: "Soft delete | `deactivated_at` timestamp, never a boolean flag") names one soft-delete column convention for the whole codebase, with no carve-out for log-type rows. No existing table in this codebase soft-deletes a "log entry" (as opposed to deactivating an account/entity) — this is the first — but there is also no second, `deleted_at`-named convention to diverge to. Reusing `deactivated_at` here, even though "deactivated" reads a little oddly for a progress-entry row, keeps the codebase's one soft-delete idiom singular rather than forking it on this story's account. If this reads wrong during review, it's a one-column rename, not a design change.

### Open UX Gap — No Mockup for the "Complete Your Profile" Step

`EXPERIENCE.md`'s full Member App screen inventory (lines 40-60) has no MA-ID for FR-093's "optional 'Complete your profile' step" — MA-05 through MA-08 cover the existing onboarding flow (Phone → OTP → Profile Setup → Goal → Experience → Plan Confirmation) and MA-15 (Progress) is Story 10.3's screen. This story's own body-profile step, and the "log an entry" reachability before the Progress tab exists, are both genuinely unspecified by UX and resolved by this story's own judgment (Task 6) — a minimal two-field form with a skip action, and a Profile-tab entry point. Flag this resolution explicitly in Completion Notes; it is a scope decision made in the absence of a mockup, not an interpretation of one.

### `height_cm`/`starting_weight_kg` vs. "Baseline Measurements"

FR-093 groups "height, starting weight, and optional baseline measurements" together, but they don't belong on the same table: height and starting weight are one-time facts about the member (hence new `members` columns, following `0020`'s exact precedent for `goal`/`experience_level`), while "baseline measurements" are inherently the same repeatable shape as every other logged measurement — there is no separate baseline-measurements schema. This story treats "optional baseline measurements" as satisfied by letting the member open `LogEntrySheet` (the same component used for every later entry) immediately after the body-profile step, logging their first `progress_entries` row with measurement values if they choose. No new schema or table needed for "baseline" as a distinct concept.
