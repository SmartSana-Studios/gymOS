# Story 2.2: Membership Plan Configuration

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a Manager or Owner,
I want to configure my gym's membership plans,
so that members can be assigned pricing and billing terms specific to my gym.

## Acceptance Criteria

1. **Given** the plan configuration UI, **when** I create a plan of type Pay-per-session, Monthly, Coach-inclusive, or Class-only, **then** I can set its name, price in XAF, duration, access type, and billing interval (monthly or annual). [Source: epics.md#Story 2.2]
2. **Given** an annual billing interval, **when** I set an annual price, **then** the gym-configured discount is reflected and stored independently of tier/price fields. [Source: epics.md#Story 2.2]
3. **Given** any monetary field, **when** it is stored, **then** it is an integer XAF value with an explicit `currency` column — never a float. [Source: epics.md#Story 2.2]

## Scope Note — Read Before the Tasks

**Two schema gaps exist between the PRD/epics wording and the already-shipped `plans` table (`0004_subscriptions_and_plans.sql`, Story 1.1 scaffold), both resolved by this story's decisions below — read this before writing any code:**

1. **`duration` (AC #1) has no column today.** `plans` currently has `id, gym_id, name, plan_type, price, currency, billing_interval, annual_discount_percent, created_at` — no duration field. This story adds `duration_days integer` (nullable — null means "no fixed duration," the correct value for `pay_per_session` plans, which the PRD's own Plan Type table describes as "no fixed expiry"). For every other `plan_type`, `duration_days` is required and positive.
2. **`access type` (AC #1) is deliberately NOT a new column.** FR-025's four plan types (`prd.md#6.6`) are each already described as a distinct access scope in the PRD's own table: *Pay-per-session — pays per visit, no fixed expiry; Monthly — fixed-fee, defined expiry; Coach-inclusive — monthly plan + scheduled coach sessions; Class-only — scheduled classes only, no general floor access.* `plan_type` **is** the access-type discriminator — there is no second, independently-defined enum anywhere in the PRD/architecture for a separate "access type" value set, and architecture.md's own enum inventory (`plan_type`, `subscription_status`, `payment_method` — no `access_type`) confirms this was never designed as a second column. AC #1 is satisfied by the `plan_type` selector plus a short access-scope description surfaced in the UI next to it (Task 5) — not a new field to invent. This mirrors story 1-6's own "Open Question" precedent (`tiers.memberCap` vs the mockup's separate "min" field) for exactly this class of PRD-wording-vs-schema gap. **If this reasoning seems wrong, flag it — but do not invent an undefined second enum to force a literal column match.**

No dedicated "Plans" page exists in the UX design docs (`EXPERIENCE.md`'s AD-01–AD-15 inventory has no plan-configuration mockup — Settings' AD-13 only covers Grace Period/Capacity under "Membership", not plan definitions). This story adds a new dashboard route (`/plans`) and sidebar entry, styled consistently with the existing `dialog`-modal list-management pattern (Task 5) rather than inventing new UI conventions.
