# Story 1.9: Gym Branding & Operational Settings

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a Gym Owner,
I want to configure my gym's branding and operational settings,
so that the dashboard and member app reflect my gym's identity and policies.

## Acceptance Criteria

1. **Given** the Settings page, **When** I upload a logo and set a primary hex color, then save, **Then** the change is reflected in the Settings page's own live preview (logo thumbnail, color swatch) immediately, and any Gym Name change is reflected in the Sidebar on next render, **And** the change is available for the member app's next branding-cache refresh (24h). [Source: epics.md#Story 1.9] — see Dev Notes → "Resolved: what 'sidebar reflects branding immediately' actually means" for why this is *not* a dashboard-wide recolor.
2. **Given** I set timezone, default language, grace period duration, gym capacity, and alert auto-dismiss duration, **When** I save, **Then** all values persist and are available to downstream features (subscription lifecycle, front-desk alerts). [Source: epics.md#Story 1.9]
3. **Given** I click "Regenerate QR code," **When** I confirm the warning dialog, **Then** the old code is invalidated immediately, **And** a new one is generated and downloadable. [Source: epics.md#Story 1.9]

## Dev Notes

### Resolved: what "sidebar reflects branding immediately" actually means

**This is the single most important scope clarification in this story — read before implementing Task 5.** The epics.md AC literally says "the dashboard sidebar/nav reflects the new branding immediately," which could be misread as "override the Sidebar's colors with the gym's `primary_color`." **Do not do this.** `DESIGN.md` is explicit and unambiguous: *"Admin dashboard uses `primary` as the sidebar/navigation color... On authenticated member-facing surfaces the gym's `primary_color` replaces `accent`."* "Member-facing surfaces" means the Member Mobile App only — the Admin Dashboard is staff-facing, not member-facing, and per `EXPERIENCE.md`'s own Sidebar spec, item 1 is "**GymOS platform logo**" (the static platform icon), not the gym's uploaded logo. UX-DR1 (epics.md) reinforces this: *"the platform shell (onboarding, login, Super Admin) always uses the platform accent, never the gym color."* The Admin Dashboard is part of that platform shell.

**Resolved interpretation**: "reflects immediately" is satisfied by (a) the Settings page's own live in-form preview — logo thumbnail updates on file selection, color swatch updates as a valid hex is typed, both **before** any save — and (b) the Sidebar's existing `gymName` display (already wired since Story 1.8) naturally showing an updated Gym Name on next render, since this story adds Gym Name as an editable field. The gym's `primary_color`/`logo_url` values are written to the DB for the *member mobile app* to consume (FR-011/012's 24h cache) — building that mobile-side consumption is explicitly out of this story's scope (no epics.md story currently owns wiring gym branding into the mobile app's header; likely lands whenever the mobile Home screen, Epic 3 Story 3.7, or an explicit branding story is built — flagged here as an ownership gap, same posture as Story 1.8's Open Question 2 about AD-02's stat cards).

### Scope Boundary

This story ships: an owner-scoped `gyms` UPDATE policy, a `gym-logos` Storage bucket, the Settings page UI (Branding/Localization/Membership/Front-Desk Alerts/QR Code sections), and QR code generation/download/regeneration. It does **not**:
