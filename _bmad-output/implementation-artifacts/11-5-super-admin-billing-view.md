# Story 11.5: Super Admin Billing View

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a Super Admin,
I want visibility into every gym's SaaS billing status with manual override actions,
so that I can operate the beta (marking out-of-band payments, granting credits) without waiting on the automated flow.

**Context — read this before touching any AC below.** This story adds a new page to `apps/super-admin` only. It touches no dashboard/mobile code and adds no new lifecycle state — it is a read surface plus manual-override entry points onto machinery Stories 11.1–11.4 already built and shipped.

**What already exists and must be reused, not rebuilt:**
- `gyms.saas_billing_status` (`active`/`past_due`/`grace_period`/`suspended`), `saas_billing_interval`, `saas_billing_anchor_date` (next billing date), `saas_grace_period_days` — all live columns, `0071_saas_subscription_lifecycle.sql`.
- `saas_billing_payments` (`0069_saas_billing_payments.sql`) — one row per Flow B payment attempt, `status` is `payment_status` (`'pending' | 'processing' | 'verified' | 'flagged'`). A Super-Admin-only `SELECT` RLS policy (`super_admin_read_saas_billing_payments`) already exists — no new read policy needed.
- **Suspend/Reactivate is already fully built** — `suspendGym()`/`reinstateGym()` (`apps/super-admin/app/(admin)/gyms/actions.ts`) plus `<GymLifecycleDialog>` (`apps/super-admin/app/(admin)/gyms/components/GymLifecycleDialog.tsx`) already implement exactly SA-07's "Suspend / Reactivate" row action (reason-required, confirm dialog, `logGymLifecycleEvent()` audit write with `gym_suspended`/`gym_reinstated`). **Import and reuse these directly on the new Billing view — do not write a second suspend/reactivate implementation.** `<GymLifecycleDialog>` takes a `GymListRow`-shaped gym and a `runAction` callback; the Billing view's own row type must carry the same `{id, name, status}` shape (or a superset) for this to drop in unchanged.
- `logGymLifecycleEvent()` (`apps/super-admin/services/gyms.ts`) is the established one-helper-many-action-types pattern for `log_audit_event()` writes (`gym_suspended | gym_deactivated | gym_reinstated | gym_tier_changed | gym_cap_overridden | gym_data_escalation`) — **extend its type union with this story's three new action types** (see Task 1) rather than writing a parallel audit helper. `action_type` is a free-text column (no DB `CHECK` constraint), so no migration is needed to add new values.
- The gyms list page/table/dialog conventions (`apps/super-admin/app/(admin)/gyms/page.tsx`, `GymsPageClient.tsx`, `services/gyms.ts`'s `listGyms()`) are this story's structural template: server component fetches page 1 + passes props to a `"use client"` page component that owns search/filter/pagination via `useSearchParams()`/`router.push()`, a `<table>` with a per-row actions cell, `AppError`-shaped `{data, error}` returns everywhere (AD-9), reason-required destructive-action dialogs. Mirror this shape for `/billing`, don't invent a new pattern.
- **UX-DR-specified mockup exists for this exact page** — `EXPERIENCE.md` SA-07 (L1834–1866, `_bmad-output/planning-artifacts/ux-designs/ux-gym_os-2026-07-04/EXPERIENCE.md`) is not a placeholder note; it specifies the table columns, badge colors, filter/search, and all four row actions' confirm-dialog copy verbatim. Read it before building the UI — copy the confirm-dialog strings character-for-character into i18n keys (this project's i18n discipline treats these as compliance text, same as Story 11.4's suspension-screen copy).

**Three genuinely new pieces this story must build (no prior code to extend):**

1. **"Mark payment received (out-of-band)"** — `saas_billing_payments` has zero `INSERT`/`UPDATE` RLS policy for any role (by design, `0069`'s own comment: "the only sanctioned mutation paths are the two completion RPCs, `security definer`, service_role-only"). A Super Admin's authenticated session cannot write this table directly — a new `SECURITY DEFINER` RPC is required, self-enforcing `private.is_super_admin()` internally (AD-5's pattern: "cross-gym aggregates go through `SECURITY DEFINER`... functions that self-enforce `private.is_super_admin()` internally — never a broadened row-level policy"). It must do two things atomically, mirroring `complete_verified_saas_billing_payment()`'s (`0072`) existing reset shape: insert a `saas_billing_payments` row with `status = 'verified'` (amount resolved live from the gym's current `tier`/`saas_billing_interval` join, same resolution `initiate_saas_billing_payment()` already uses — no client-supplied amount), and reset the gym's billing clock (`saas_billing_status`/`status` → `'active'`, `saas_billing_anchor_date` advanced one full cycle forward from its own current value, **never** `current_date + interval`, matching `complete_verified_saas_billing_payment()`'s own reasoning: a late/manual payment doesn't get a full fresh cycle stacked on top of days already elapsed). Guard with `and status <> 'deactivated'`, the same symmetric guard every other billing-clock writer in this codebase already carries (`0071`/`0072`). **Recommended (confirm at dev-story time): factor the "advance anchor by one cycle + reset to active" logic shared with `complete_verified_saas_billing_payment()` into one `private.` helper both call, rather than copy-pasting it** — but this touches already-shipped, already-reviewed code from Story 11.3, so weigh the DRY benefit against the regression risk of editing it, and it is acceptable to duplicate the ~6-line reset instead if a shared helper feels like too much churn for this story's scope.
2. **"Apply credit / free period"** — no existing RPC. Since Super Admin's own session already passes `private.is_super_admin()` inside `private.protect_super_admin_only_gym_columns()` (the trigger that otherwise pins `saas_billing_anchor_date`/`status`/`saas_billing_status` back for everyone else — see `0071`/`0072`), **a direct two-step Server Action (read current value → `UPDATE gyms` → `logGymLifecycleEvent()`) is sufficient here, matching `updateGymStatus()`'s existing shape in `services/gyms.ts` exactly — no new RPC needed for this one.** Advance `saas_billing_anchor_date` forward by either an explicit day count or one full billing cycle (`+ saas_billing_interval`) per SA-07's "grants N days or one billing cycle free" — the UI decides which the Super Admin picked, the service function takes a resolved day count either way (resolve "one cycle" client/action-side to 30 or 365 days, or read the gym's actual interval first — dev's call, document the choice). Also reset `status`/`saas_billing_status` to `'active'` if the gym isn't already active (a credit should be able to lift a `past_due`/`grace_period`/`suspended` gym, consistent with Story 11.6's own framing of a credited period). Guard against `deactivated` gyms the same way. Reason is required (SA-07's confirm-dialog copy shows a mandatory reason field, matching `gymStatusChangeSchema`'s existing pattern).
3. **"Trigger retry" — the crux design problem, not traced to a file during story-writing, confirm the approach with the user before Task 4 starts.** SA-07 describes this as manually re-sending a payment-due notice "outside the normal reminder schedule." The *only* existing code that composes and sends this message is Story 11.3's `apps/dashboard/app/api/cron/saas-billing-reminders/route.ts` (`notifyGym()`) — entirely inside `apps/dashboard`, using `apps/dashboard/lib/messaging/sendTwilioSms.ts` and `EvolutionApiMessageProvider.ts`, neither of which exists in `apps/super-admin` (`apps/super-admin/lib/messaging/` currently has only `sendTempPasswordMessage.ts`, a different concern). Two real options, neither free:
   - **(a) Duplicate the two send helpers into `apps/super-admin`** (mirrors this exact codebase's own established precedent of per-app messaging duplication, AD-7 — `sendTempPasswordMessage.ts` already lives independently in both apps' `lib/messaging/`) and write a new, narrower send-only helper in `apps/super-admin` that composes and fires the same two-channel message directly, recording the outcome via `log_audit_event()` metadata rather than `saas_billing_notices` (that table's `notice_day_offset` has a `CHECK (in (0,1,3,5))` constraint tied to the *scheduled* reminder days — a manual retry doesn't have one of those four offsets, and widening that constraint risks the dedup semantics `notifyGym()` depends on. Do not write to `saas_billing_notices` from this new code path).
   - **(b) An authenticated internal call from `apps/super-admin` into a new single-gym endpoint on `apps/dashboard`**, reusing its already-present `sendTwilioSms`/`EvolutionApiMessageProvider` and avoiding duplication, at the cost of a new cross-app HTTP surface and a second secret to manage (mirroring `CRON_SECRET`'s shape) — this project's Edge Function count is called out in `ARCHITECTURE-SPINE.md` as "a design property... adding a 4th requires a deliberate AD," a similar discipline likely applies to a new cross-app authenticated route.
   - **Recommendation: (a)**, on the strength of this codebase's own existing precedent (duplicated `sendTempPasswordMessage.ts`) and to avoid introducing a new authenticated cross-app network boundary for one row-action button — but this is a real architectural call, not a rubber stamp; **raise both options with the user before writing Task 4's code**, and if the user prefers (b), the endpoint needs its own auth scheme, not reuse of `CRON_SECRET` (that's scoped to Vercel Cron's own header shape).

**"Failed-attempt count" has no dedicated column anywhere in the schema — derive it, don't invent a new counter table.** `saas_billing_payments.status` is `payment_status` (`pending | processing | verified | flagged`) — no `'failed'` value exists. Tracing `payment-webhook/index.ts`'s dispatch: a declined/failed Flow B webhook event calls `complete_flagged_saas_billing_payment()`, transitioning the row to `status = 'flagged'` — this is the closest real analog to "failed" in this schema. **Recommended: `count(*) from saas_billing_payments where gym_id = <gym> and status = 'flagged'`**, all-time (not scoped to the current billing cycle — no column exists to scope it to "this cycle" either, and SA-07's mockup shows a plain integer with no cycle qualifier). Confirm this reading matches the PO's intent once real flagged data exists; it is a reasonable, defensible interpretation of FR-134's "failed attempts," not a literal spec.

**One inconsistency between the SA-07 mockup and Stories 11.2/11.6's own stated behavior — do not silently resolve it, flag it if it looks wrong once real data is in front of you.** SA-07's example row for a Free/Test-tier gym ("Beta Test 1") shows interval/next-billing/last-payment all blank (`—`). But Story 11.2 sets `saas_billing_interval`/`saas_billing_anchor_date` on *every* gym with no Free/Test exception, and Story 11.6's own AC is explicit that "the full reminder/reconciliation machinery executes at the 0 XAF price point — exercising the same code paths as a paying gym" (FR-136). A Free/Test gym's `saas_billing_anchor_date` is therefore a real, meaningful value in the DB, not null. **Recommendation: do not special-case Free/Test tier rows — show the gym's actual interval/anchor date/last-payment like any other row.** This is more operationally useful (it lets Super Admin verify 11.6's "same code paths" claim) and requires no extra branching. Only blank these fields if the user, on seeing the real page, prefers the mockup's blanking.

## Acceptance Criteria

1. **Given** the Super Admin dashboard, **when** I open the new Billing view, **then** I see each gym's tier, interval, SaaS status, next billing date, last payment, and failed-attempt count. [Source: epics.md#Story 11.5; prd.md#FR-134; EXPERIENCE.md SA-07 L1838–1856 — table columns, badge colors (Active=green, Past due=amber, Grace period=orange, Suspended=red), search-by-name + status filter, row-click expands inline]
2. **Given** a gym I need to accommodate (e.g., a beta gym, or a payment I confirmed happened outside Tara Money), **when** I use the Billing view, **then** I can mark a payment received (out-of-band), apply a credit or free period, trigger a retry, or suspend/reactivate the gym directly. [Source: epics.md#Story 11.5; prd.md#FR-134, FR-136; EXPERIENCE.md SA-07 L1859–1863 — all four actions' exact confirm-dialog copy]
3. **Given** any action I take from this view, **when** I confirm it, **then** it is audit-logged with actor, action, target gym, and timestamp (FR-080). [Source: epics.md#Story 11.5; prd.md#FR-080, FR-134]
