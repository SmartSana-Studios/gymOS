# Story 1.11: Gym Owner Activation via Temp Password (SMS/WhatsApp)

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As GymOS platform staff (Super Admin),
I want the new gym owner's account activated with a temporary password delivered as plain text over SMS/WhatsApp,
so that owner activation works on any `OtpDeliveryProvider`-style channel without depending on Meta's WhatsApp Business Platform template/URL-button approval process.

**Supersedes:** Story 1.5's `generateLink({type:"recovery"})`-based invite-link mechanism in `createGym` (`apps/super-admin/app/(admin)/gyms/actions.ts`). That mechanism was never wired to a real provider (`sendInviteSms` was a stub returning `false`) — no real owner has ever received it, so this is a clean swap with no migration/backfill path, not a rollback of working behavior.

## Acceptance Criteria

1. **Given** a new gym is created via `createGym`, **when** the owner's auth account is provisioned, **then** a temporary password is generated (fixed unambiguous alphabet — excludes `0`/`O`/`1`/`l`/`I`, length ≥ 8, comfortably above `config.toml`'s `minimum_password_length = 6`) and the owner's `auth.users` row is created directly via `admin.auth.admin.createUser({ email, phone, password: tempPassword, email_confirm: true, phone_confirm: true })` — **not** `generateLink`. [Source: sprint-change-proposal-2026-07-14.md §4.1 AC1]
2. **Given** the temp password was generated, **when** the invite is sent, **then** it is delivered via WhatsApp, reusing Story 2.1's already-approved `verifications_2fa_template` (Content API, `{{1}}` variable = the temp password) — no link, no URL, no button, and no new Meta template submission needed. [Source: sprint-change-proposal-2026-07-14.md §4.1 AC2; docs/decisions.md 2026-07-15 "Onboarding/account-recovery channel policy" entry; user decision 2026-07-15 — see Dev Notes → Open Question 1, resolved]
3. **Given** the owner's account is created, **when** the `users` row is provisioned, **then** it has `must_change_password = true`. [Source: sprint-change-proposal-2026-07-14.md §4.1 AC3]
4. **Given** an owner with `must_change_password = true`, **when** they successfully log in via `apps/dashboard`'s AD-01 email+password form, **then** they are redirected to the forced password-change screen (`/auth/update-password`) before reaching any `(dashboard)` route. [Source: sprint-change-proposal-2026-07-14.md §4.1 AC4 — scoped to `apps/dashboard` only, see Dev Notes → Open Question 4]
5. **Given** the owner successfully sets a new password on `/auth/update-password`, **when** the update completes, **then** `must_change_password` flips to `false` and normal `(dashboard)` navigation resumes (no further gate on subsequent logins). [Source: sprint-change-proposal-2026-07-14.md §4.1 AC5]
6. **Given** this story lands, **when** implementation is complete, **then** `docs/decisions.md` has a new dated entry recording: the temp-password-over-SMS/WhatsApp mechanism, why `generateLink`/link-via-email was rejected (cross-reference the existing 2026-07-14 and 2026-07-15 entries rather than re-deriving the reasoning), the `email_confirm: true` behavior change, which channel (SMS vs WhatsApp) was actually used for the temp-password message and why, and the `protect_self_managed_user_columns` trigger fix (Dev Notes → Task 1). [Source: sprint-change-proposal-2026-07-14.md §4.1 AC6]
7. **Given** the existing `createGym` compensating-cleanup behavior (gym/owner rollback on partial failure), **when** any step in the new sequence fails, **then** the same cleanup discipline applies — a failed temp-password send must **not** roll back an already-successful gym/owner/member creation (matches Story 1.5's `smsSent`-never-blocks-success precedent), but a failed `createUser` or `members` insert must still trigger `deleteGym`/`deleteAuthUserAndLog` exactly as today.

## Dev Notes

### Open Questions — all resolved by user decision, 2026-07-15

None of these were resolved by the Sprint Change Proposal. All four were decided directly by the user before dev starts (recorded here, not left as defaults, per this project's established practice of writing sign-off decisions into the story — Stories 1.5/1.6/1.9 all did this).

1. **WhatsApp vs SMS for the temp-password message — RESOLVED: WhatsApp, reusing the existing template.** WhatsApp's Business Platform requires an approved template for any business-initiated message (no free-form text outside a 24h user-initiated session window), so "just send free text over WhatsApp" was never actually available the way it is on SMS. Three options were weighed: (a) submit a new plain-text, no-button WhatsApp template worded correctly for a temp password — cheapest long-term, needs a real Meta approval step (likely fast per Story 2.1's own same-day-approval precedent, but not zero-time) and a fallback chain that doesn't exist in code yet; (b) reuse Story 2.1's already-approved `verifications_2fa_template` as-is — ships immediately, zero new approval, at the cost of the template's fixed "is your verification code" wording not quite matching a password; (c) SMS only — no template dependency, costs more per message, doesn't use the already-verified WhatsApp channel. **Chosen: (b).** Reuse the existing template, accept the wording mismatch as a documented, deliberate tradeoff (Task 2/Task 6). No SMS fallback is built in this story — add it to `deferred-work.md` (Task 6) as explicitly deferred, not silently missing.

2. **`must_change_password`'s table — RESOLVED: `users`.** Account-level flag on the `auth.users` mirror, not `members`. Correct because the "must change password" state belongs to the login/account, not to a specific gym-membership relationship (a user could in principle hold more than one `members` row). Task 1 and Task 5 are written against `users.must_change_password` — no `members`-table alternative needs building.

3. **Surface the temp password in the Super Admin UI as a manual fallback — RESOLVED: yes, show it once.** Mirrors Story 1.5's own precedent exactly: the original AC only required "SMS sent," but a later fix (commit `6049e7a`, "surface owner invite link in Super Admin UI") added the invite link to the UI once it became clear delivery couldn't be guaranteed. Same rationale applies here. Task 3's `CreateGymResult` keeps a `tempPassword: string` field (replacing the removed `ownerInviteLink`); Task 4's `GymsPageClient` toast displays it once on gym creation (not gated behind a delivery-failure check — shown unconditionally, matching 1.5's own "show the fallback regardless of the reported send status" precedent, since a `success: true` from Twilio doesn't guarantee the owner actually read/kept the WhatsApp message). Ephemeral only — not persisted to any log/table beyond what `createGym`'s existing return value already carries. **Accepted security tradeoff, record in Task 6**: a reusable password sitting in a toast is a larger exposure window than the single-use, expiring recovery link Story 1.5 originally showed — acceptable for this pilot's scale and staff-facing (not member-facing) surface, revisit if the Super Admin user base grows beyond a small trusted team.

4. **Does `apps/super-admin`'s SA-01 login also need the gate — RESOLVED: no.** Gym owners never authenticate against `apps/super-admin`; that app's login is for GymOS platform staff, a disjoint user population from anything `createGym` provisions. Do not modify `apps/super-admin/app/(admin)/layout.tsx` or its login flow in this story.
