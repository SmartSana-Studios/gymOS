# Story 11.4: Tenant Suspension Enforcement

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As GymOS,
I want a gym's entire tenant suspended at the authorization layer when its SaaS subscription lapses,
so that suspension can't be bypassed by a client ignoring UI state, and access is restored the instant payment succeeds.

**Context — read this before touching any AC below. This story is a pure enforcement layer on top of machinery that already exists; it adds no new billing logic and no new table.**

**What already exists and must not be rebuilt:**
- Story 11.2 (`0071_saas_subscription_lifecycle.sql`) already flips `gyms.status` to `'suspended'` (the existing `gym_status` enum from `0002_gyms_and_tiers.sql`: `'active' | 'suspended' | 'deactivated'`) in the same `UPDATE` that sets `saas_billing_status = 'suspended'`, once `run_saas_billing_lifecycle_job()`'s grace period elapses. That migration's own comment names this explicitly: *"this is the load-bearing linkage point Story 11.4 depends on."* **Do not add a second suspension signal or a new column — `gyms.status` is it.**
- Story 11.3 (`0072_saas_billing_reminders_one_tap_pay.sql`) already reverses it: `complete_verified_saas_billing_payment()` resets `status`/`saas_billing_status` back to `'active'` and advances `saas_billing_anchor_date` the instant a Flow B payment verifies. **AC #2 (reversal) needs no new code — confirm this already works with a pgTAP assertion, don't reimplement it.**
- `private.current_gym_status()` (`0063_staff_edit_deactivation.sql`) already exists — `STABLE`, `SECURITY DEFINER`, live `select status from gyms where id = private.gym_id()`, mirrors `private.current_member_role()`'s never-throws/return-null-on-absence discipline. It has exactly one live caller today: `gym_staff_read_own_members`'s `= 'active'` clause. **This story's entire job is adding more call sites, not building the helper.**
- `initiate_saas_billing_payment()` and `update_own_owner_notification_email()` (both `0072`, both `SECURITY DEFINER`) are **the Owner's escape valve out of suspension** — `initiate_saas_billing_payment()` explicitly only rejects `status = 'deactivated'`, never `'suspended'` (read its guard clause: `if v_gym_status = 'deactivated' then raise exception`). This is deliberate, already-shipped behavior this story must not break: an Owner mid-suspension must still be able to call it. Both RPCs are `SECURITY DEFINER` and read `gyms`/`tiers`/`members` directly as their function owner — **Postgres does not enforce RLS against a table's own owner unless `FORCE ROW LEVEL SECURITY` is set** (never set anywhere in this schema), so neither RPC is affected by any RLS policy this story adds. Confirm this understanding before touching either function; do not add a `current_gym_status()` check inside them.

**The one real design problem this story must solve (read in full — this is the crux of the story):**

`private.current_gym_status()` exists but is called from exactly one RLS policy in the entire schema. NFR-018/AC #1 require *"any staff or member of that gym makes a request... denied at the RLS/auth-hook layer"* — not one policy, all of them. That means retrofitting the gate onto every gym-scoped operational table this codebase has, while leaving three things deliberately unblocked so the Owner can still see and resolve the suspension:

1. **`gyms` itself stays completely unrestricted** (no change to any existing `gyms` policy). This is not new — `"read own gym"` (`0009_auth_hook_gym_claims.sql`) has always been open to every role regardless of any other state; the Sidebar has relied on reading it post-login since Story 1.8 (`docs/decisions.md`, 2026-08-13 entry). Both apps need this read to detect and display the suspended state at all.
2. **`custom_access_token_hook()` (`0009`) is not modified.** It must keep minting a valid `gym_id`/`app_role` claim for a suspended gym's members/staff on login — if it didn't, `private.gym_id()` would return `null` for a suspended-gym Owner and `initiate_saas_billing_payment()` (which calls `private.gym_id()` internally) would break, closing the one recovery path this story must keep open. Suspension is enforced entirely at the RLS/RPC layer, never at the claims-minting layer — this is a deliberate asymmetry with the `deactivated_at`-on-`members` check the hook already does (a *deactivated member* correctly gets no claims at all; a *suspended gym*'s members still get claims, just RLS-denied on business tables).
3. **The Owner's own `initiate_saas_billing_payment()`/`update_own_owner_notification_email()` RPCs stay callable**, per the point above.

**Recommended mechanism: one new `AS RESTRICTIVE` policy per gated table, not a rewrite of every existing policy.** Postgres ANDs every `RESTRICTIVE` policy against the `OR` of all `PERMISSIVE` ones for a given command — so one `create policy "tenant_active_gate" on <table> as restrictive for all using (private.current_gym_status() = 'active' or private.is_super_admin()) with check (private.current_gym_status() = 'active' or private.is_super_admin());` per table adds the gate without touching a single existing policy's business logic (lower regression risk than editing ~15 already-shipped, already-reviewed policy bodies). **`AS RESTRICTIVE` has never been used anywhere in this schema before this story** — confirm this reading of Postgres RLS policy combination (`RESTRICTIVE` policies AND together and AND against the `OR` of `PERMISSIVE` policies) against current Postgres docs before relying on it, and treat this as a new pattern worth a short `docs/decisions.md` note, not a silent one-off. This is a deliberate, narrow exception to `ARCHITECTURE-SPINE.md`'s `AD-1` "never `FOR ALL`" convention — that rule targets differentiated per-action business policies, not a single uniform tenant-liveness gate; flag this reasoning in the migration comment rather than silently violating AD-1's letter.

**The `OR private.is_super_admin()` clause is not defensive boilerplate — omitting it breaks a real, already-shipped feature.** `members` and `payments` each carry a Super-Admin *escalated* read policy (`super_admin_escalated_read_members`/`super_admin_escalated_read_payments`, `0012_super_admin_data_access_escalation.sql`) that Super Admin's audit-logged support-escalation flow (Story 1.7, FR-072) depends on — and `audit_log` carries an unconditional `super_admin_read_audit_log`. Since `RESTRICTIVE` policies apply regardless of which `PERMISSIVE` policy would otherwise pass, a bare `current_gym_status() = 'active'` gate on these three tables would lock Super Admin out of investigating or overriding a suspended gym — the exact opposite of what a suspended gym needs (Story 11.5's Super Admin Billing view, backlog, will depend on this access continuing to work). Apply the `OR private.is_super_admin()` clause uniformly to every gated table, not just these three, so no future Super-Admin escalation policy on another table silently regresses the same way.

**The harder half of this story is not the SQL — it's that the dashboard's own login path reads `members` directly, and gating `members` breaks it unless you fix this first.** `apps/dashboard/services/session.ts`'s `getDashboardShellContext()` — the **sole** gate `app/(dashboard)/layout.tsx` relies on (its own comment: *"the single source of truth for that check"*) — does a direct client-side `.from("members").select("gym_id, role")...` query, subject to RLS via `self_read_own_membership`. Once that policy is gated, this query returns empty for a suspended gym, `shell` comes back `null`, and the layout's existing `if (!shell) redirect("/auth/login")` branch fires — **an Owner trying to reach the "pay to reactivate" screen gets bounced to the login page in a loop instead**, exactly the login-loop failure mode `DashboardLayoutData`'s own comment already warns about for a different case. This is the one regression that will look like "it works" (build succeeds, typecheck passes, the RLS gate is provably correct in isolation) but silently breaks the Owner's one recovery path in a live click-through. Read `apps/dashboard/services/session.ts` (`getDashboardShellContext()`) and `apps/dashboard/app/(dashboard)/layout.tsx` in full before writing any RLS migration.

## Acceptance Criteria

1. **Given** a gym that reaches `suspended` status (Story 11.2), **when** any staff or member of that gym makes a request, **then** they are denied at the RLS/auth-hook layer (via `private.current_gym_status()`, AD-3) — not only hidden by the UI — taking effect on the next request, with no tenant data deleted or mutated (NFR-018). [Source: epics.md#Story 11.4; prd.md#FR-131, FR-132, NFR-018; ARCHITECTURE-SPINE.md#AD-3]
2. **Given** a suspended gym's successful SaaS payment, **when** it is confirmed, **then** the gym returns to `active` and access is restored immediately — reversible, symmetric with the suspension mechanism. [Source: epics.md#Story 11.4; prd.md#FR-132; EXPERIENCE.md L2198 — already implemented by Story 11.3's `complete_verified_saas_billing_payment()`, verify don't rebuild]
3. **Given** a member of a suspended gym, **when** they open the app, **then** the suspension surface never mentions billing or payment — that relationship is between GymOS and the Owner only (FR-132); the member sees a neutral "temporarily unavailable" message, not a dunning notice. [Source: epics.md#Story 11.4; prd.md#FR-132; EXPERIENCE.md L255, L2195, L2197 — this neutral treatment also applies to every non-Owner staff role on the dashboard, not members alone]

## Dev Notes

- **This story adds no new table and no new billing/lifecycle logic** — it is purely an enforcement retrofit onto Stories 11.2/11.3's already-shipped state machine. If a task here starts to look like it's inventing new billing behavior, stop — that's scope creep into 11.2/11.3/11.5's territory.
- **`AS RESTRICTIVE` is new to this codebase.** Confirm the Postgres RLS combination semantics (restrictive policies AND together, AND against the OR of permissive policies) against current docs before relying on it — don't rely on training-data recall for a security-critical mechanism being introduced for the first time.
- **The `or private.is_super_admin()` clause is load-bearing, not defensive boilerplate** — omitting it on `members`/`payments`/`audit_log` breaks Story 1.7's already-shipped escalation feature. Apply it uniformly to every gated table anyway, not just these three, so a future Super-Admin policy on another table doesn't silently regress the same way.
- **The dashboard shell fix (Task 2) is the part most likely to look done when it isn't.** `pnpm typecheck`/lint/the RLS pgTAP suite can all pass while the Owner's actual recovery path is broken by a login-redirect loop — this only shows up in a real click-through (or a Vitest test of `getDashboardShellContext()`'s suspended branch specifically). Do not mark this story done without exercising that path.
- **Do not modify `custom_access_token_hook()` or `private.gym_id()`.** Suspension enforcement lives entirely in the new RLS policies and is deliberately invisible to claims-minting — a suspended gym's users must keep getting valid `gym_id`/`app_role` claims so the Owner's escape valve (`initiate_saas_billing_payment()`) keeps working.
- **Do not modify `initiate_saas_billing_payment()` or `update_own_owner_notification_email()`** to add a `current_gym_status()` check — they are `SECURITY DEFINER` and already correctly unaffected by this story's RLS changes (table owner bypasses RLS by default, no `FORCE ROW LEVEL SECURITY` anywhere in this schema); adding a check would actively break the recovery path AC #2 requires.
- **Naming/conventions** (`ARCHITECTURE-SPINE.md`'s Consistency Conventions table): the one new policy name, `tenant_active_gate`, repeated verbatim across every gated table (not a per-table-unique name) — deliberate, so `grep "tenant_active_gate" supabase/migrations/` finds every site this story touches in one shot; this is the one intentional departure from this project's usual descriptive-unique-policy-name convention, worth a one-line comment explaining why.
