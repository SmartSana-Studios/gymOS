# Story 6.6: Class Reminder Notification

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a member,
I want a reminder before a class I've booked,
so that I don't forget to show up.

## Acceptance Criteria

1. **Given** a class session a member has booked (`class_bookings`, Story 12.2), **when** 60 minutes remain before `class_sessions.scheduled_at`, **then** the member receives N-07 — the class-reminder notification (FR-116) — as an Expo push notification, in their preferred language (EN/FR). Firing precision is bounded by the dispatch job's cron cadence (this story: every 5 minutes — see Dev Notes "Reminder Timing"), not to-the-second; this matches every existing cron-dispatched notification in this codebase (N-01–N-06), none of which fire at exact-second precision either.
2. **Given** my notification preferences (already shipped by Story 6.4's `member_preferences.class_reminder_opted_out`, `not null default false`), **when** I view them in the mobile app, **then** the existing "Class reminders" toggle continues to default to **on** (`opted_out = false`) for new members and reflects my current choice — N-07 is opt-out, not opt-in, per FR-076. This story removes the "(Coming soon.)" / "(Bientôt disponible.)" qualifier from that toggle's copy (both `en.json`/`fr.json`), since the opt-out now has a real, observable effect (mirrors Story 6.5's Task 2 for N-06, deliberately left untouched by that story for this one).
3. **Given** a member who opted out (`class_reminder_opted_out = true`), **when** the 60-minute mark for their booked session is reached, **then** no N-07 is sent for that booking.
4. **Given** a member who cancels their booking (`cancel_class_booking()`, Story 12.2 — a row `DELETE` from `class_bookings`, no status column exists) before the 60-minute mark, **when** the dispatch job runs, **then** no N-07 is sent — this falls out naturally from the job reading live `class_bookings` rows (the cancelled row no longer exists to join against), not from a separate cancellation check.
5. **Given** a gym with `status` other than `'active'` (`'suspended'` or `'deactivated'`), **when** the dispatch job runs, **then** no N-07 is sent to any of that gym's members, regardless of booking state (mirrors Story 6.5 AC #6's gym-status gate, for consistency across both V1.5 notification jobs).
6. **Given** a deactivated member (`members.deactivated_at is not null`) with a still-present booking row, **when** the dispatch job runs, **then** no N-07 is sent to them.
7. **Given** N-07's push delivery (ticket/receipt lifecycle, stale-token cleanup on FCM/APNs-invalid response), **when** it is processed, **then** it follows the exact same two-stage Expo ticket→receipt mechanism already shared by N-01–N-06 (`private.process_notification_deliveries()`, migrations `0045`/`0046`/`0056`) — extended to a fourth delivery-ledger table, not a new, parallel delivery-processing function (FR-077, consistency with AD-25).
8. **Given** a class session a member has booked, **when** the dispatch job evaluates it, **then** at most one N-07 dispatch is ever created for that exact `(class_session_id, member_id)` pair — enforced by a natural-key unique constraint + `on conflict do nothing` at insert time (mirrors N-01–N-05's `0045`/`0046` dedupe pattern, not Story 6.5/N-06's no-natural-key rolling-window pattern — see Dev Notes "Dispatch Dedupe Strategy" for why N-07 uses the other precedent).
9. **Given** all N-07 push copy (title/body, EN/FR), **when** it is sent, **then** it follows the exact per-member-language-preference pattern already established by N-01–N-06 (`users.preferred_language`, `'fr'`/default `'en'`) — no i18n-bundle keys are needed since, like N-01–N-06, this copy is generated inside the Postgres dispatch function, not the mobile app (FR-078).

## Dev Notes

### Reminder Timing — Read This First

FR-116/the epic AC say "60 minutes before the session starts," phrased as an exact instant. This story implements it as **cron-cadence-bounded, not exact-second**: `run_class_reminder_job()` runs every 5 minutes (`*/5 * * * *`) and dispatches any booking whose session `scheduled_at` falls in `(now(), now() + 60 minutes]` and has no existing dispatch row. Because the natural-key `unique(class_session_id, member_id)` + `on conflict do nothing` guarantees exactly one dispatch per booking ever, the *effective* fire time is the first job run after the session crosses into the 60-minute window — anywhere from exactly 60 minutes before down to 55 minutes before, in the worst case. This is the same precision class as every other cron-dispatched notification in this codebase (N-06 at a 15-minute cadence, the subscription-lifecycle notifications at their own cadence) — none of them fire at exact-second precision, and neither should this one. Do not attempt to build tighter timing (e.g. a per-session one-shot `pg_cron` job scheduled dynamically) — that would be new infrastructure this codebase has never used, for a precision gain no AC asks for.

### Dispatch Dedupe Strategy — Read This First

This story deliberately uses the **opposite** dispatch-table shape from Story 6.5's most recent precedent. N-06 (`private.quiet_gym_alert_dispatches`, migration `0056`) has **no** natural-key uniqueness constraint, because a rolling rate limit means the same member can legitimately get a new dispatch row every few hours — rate-limiting is enforced by the caller reading dispatch history, not by a uniqueness constraint. N-07 is different: a given `(class_session_id, member_id)` booking gets **exactly one** reminder, ever — a true one-shot event, the same shape as N-01/N-02/N-03 (`private.notification_dispatches`, migration `0045`, `unique (subscription_id, notification_code)`). Use `0045`'s `insert ... on conflict (class_session_id, member_id) do nothing returning id into v_dispatch_id; if v_dispatch_id is null then return; end if;` pattern inside `private.send_class_reminder()` itself — this both expresses the business rule (one reminder per booking) *and* is the concurrency-safety mechanism against overlapping cron runs, exactly as it is in `0045`. Do not copy Story 6.5's "caller pre-checks eligibility, then unconditional insert" shape here — that shape exists specifically because N-06 has no natural key to conflict against.

**Known accepted gap (code review, 2026-08-19):** because the dedupe key is `(class_session_id, member_id)` rather than the booking row's own identity, a member who is reminded, then cancels and rebooks the *same* session before it starts, will not get a second reminder for the fresh booking — the earlier dispatch row already blocks it. Reachable only for gyms with `class_booking_cancellation_cutoff_minutes < 60` (default 120 structurally prevents it, since cancellation is blocked before the 60-minute reminder window opens). Accepted as-is: rare, config-dependent, and the consequence is a missed reminder, not data corruption.

### Architecture Compliance

- **AD-25** (Push notification dispatch is DB-triggered, not a service-layer responsibility) explicitly names N-07 as landing "under this same mechanism" alongside N-06. This story's `run_class_reminder_job()` + `pg_net`-via-Postgres-function shape is AD-25 applied to a periodic-cron trigger (like `run_subscription_lifecycle_job`/`run_quiet_gym_alert_job`), not an `AFTER INSERT/UPDATE` trigger (like the payments notifier) — periodic is correct here because the job must repeatedly re-check "has this booking crossed the 60-minute threshold yet," which a pure insert/update trigger on `class_bookings` could not express (a booking made 3 hours before a session must not fire immediately at booking time).
- **AD-19** (independent scheduled jobs, one `job_runs` table) — `run_class_reminder_job()` is its own independent cron trigger/transaction/`job_runs` entry, exactly like every other job function in this codebase; it must not be folded into `run_quiet_gym_alert_job()` even though both are V1.5 Epic-6-extension jobs with superficially similar shapes.
