# Story 11.7: Pay Now — Tier Selection & Alternate Payment Methods

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a gym Owner paying my GymOS subscription,
I want to change my tier at payment time and pay through more than one method,
so that Pay Now isn't limited to whatever tier is already on file, paid only by the mobile-money number I happen to be holding.

**Context — read this before touching any AC below.** This is `epics.md`'s Story 11.7 backlog stub (L2086–2112), surfaced live during Story 11.4's manual verification of `PayNowButton.tsx` (extracted from Story 11.3's Settings Billing card, reused unchanged by the suspended-gym Owner recovery screen). The stub explicitly required confirming Tara's hosted-checkout payment methods against real docs before finalizing design — done this session via live fetches of `https://dikalosarl.mintlify.site/` (not a real dashboard/account login, which this session had no credentials for — see the Live-Evidence flag in Task 7). Three real gaps, now designed:

**Gap 1 — no tier/interval selection at Pay Now.** `initiate_saas_billing_payment()` (`0072_saas_billing_reminders_one_tap_pay.sql:170-224`) takes **zero parameters** — it always live-joins `gyms.tier_id`/`gyms.saas_billing_interval` to price the charge. No override path exists anywhere.

**Gap 2 — no hosted-checkout fallback.** `TaraMoneyProvider.ts` (`supabase/functions/payment-webhook/_shared/payment-providers/TaraMoneyProvider.ts`) implements only `initiate()` (direct `mobilePay()` call to `https://www.dklo.co/api/tara/mobilepay`). **Confirmed live this session** (fetching the real docs, not assuming from marketing copy — the stub's own explicit condition): a separate **Payment Links API** (`createPaymentLink()`) exists, taking `{apiKey, businessId, productId, productName, productPrice, productDescription, webHookUrl, productPictureUrl?, returnUrl?}` and returning `{whatsappLink, telegramLink, dikaloLink, generalLink, cardLink, smsLink}` — **`cardLink` is a real, explicitly-documented bank-card payment link**, resolving the stub's open question. By contrast, the `EmbedPay` React SDK component (a different product, `/sdk/react-sdk`) is confirmed **mobile-money only** — its docs mention "Mobile Money" twice and never mention "card" or "wallet" anywhere on the page. **Use `createPaymentLink()`, not `EmbedPay`, for the "Continue on Tara" alternate-method fallback** — it's the one that actually surfaces card payment.

**Gap 3 — no country/operator selector.** `TaraMoneyProvider.initiate()` sends `network: ""` on every call (`TaraMoneyProvider.ts:197`) — **TaraMoney auto-detects the operator from the phone number server-side; the API is never actually told which country/operator applies** (`packages/types/src/schemas/payment.ts:17-24` documents this explicitly for Flow A's identical pattern). **This means a country selector is a phone-input UX/formatting/validation aid only — it must never be wired into the API call as a new parameter.** Confirmed operator list live via `/api/mobile-pay` docs (matches the stub's own pre-researched list exactly): Benin (MTN/Moov), Burkina Faso (Moov/Orange), Cameroon (MTN/Orange), Congo-Brazzaville (Airtel/MTN), Congo-Kinshasa (Vodacom/Airtel/Orange), Côte d'Ivoire (MTN/Orange/Wave), Gabon (Airtel), Ghana (MTN/AirtelTigo/Vodafone), Kenya (MPesa), Rwanda (Airtel/MTN), Senegal (Free/Orange/Wave), Sierra Leone (Orange), Tanzania (Airtel/Vodacom/Tigo/Halotel), Uganda (Airtel/MTN), Zambia (operators undocumented).

**A fourth, previously-untracked but directly-relevant real bug this story must fix while it's in this exact file/table anyway:** `deferred-work.md:6` and `:643` both independently flag that `PayNowButton.tsx`'s client-side polling (`fetchSaasBillingPaymentStatus()`, `apps/dashboard/lib/realtime/paymentStatus.ts:75-87`) reads `saas_billing_payments` as the browser `authenticated` client, but that table's **only** RLS policy is `super_admin_read_saas_billing_payments` (`0069:34-37`) — every poll tick returns 0 rows (RLS-denied, not an error) for a real Owner session, so `onPaymentConfirmed()`/the "verified" toast can never auto-fire; only a manual page reload (which re-reads `gyms` via a *different*, already-Owner-readable query) shows the updated state. `deferred-work.md:6` explicitly recommends "prioritizing the fix ... ahead of most other 11.x deferred items" precisely because this story reuses the same component. **Task 1 adds the missing Owner-scoped SELECT policy** — per AD-3, `private.current_member_role() = 'owner'`, not `deferred-work.md`'s own suggested (legacy, pre-AD-3) `auth.jwt() ->> 'app_role'` shape.

**Design call — when does a Pay-Now tier/interval change take effect?** On payment **verification**, not on dialog submit. Rationale: `saas_billing_payments` gains new `tier_id`/`billing_interval` columns recording what a given payment is *for*; `initiate_saas_billing_payment()` resolves and stores them (falling back to the gym's current `tier_id`/`saas_billing_interval` if the Owner didn't override, so the columns are always populated, not conditionally). `complete_verified_saas_billing_payment()` (`0072:37-75`) — already the sole writer of the post-payment `gyms` reset — additionally applies the *payment row's own* `tier_id`/`billing_interval` onto `gyms` at that same point, atomically with the anchor-date advance. This avoids a gym showing a tier it hasn't actually paid for if the payment fails/times out, and is consistent with OQ-15's "no proration, new price at next cycle" resolution (Story 11.2) — a Pay-Now-time tier change **is** that next cycle's charge event, not a mid-cycle proration.

**Two real-but-narrow trigger changes this requires, both already existing, both requiring extension not replacement:** `private.protect_super_admin_only_gym_columns()` (`0072:95-121`) unconditionally pins `tier_id` back for any non-Super-Admin write (**no bypass check exists for it at all today**) and unconditionally pins `saas_billing_interval` back too (explicitly documented at `0072:90-93` as "never written by either system caller" — no longer true after this story). Both need the existing `app.saas_billing_payment_reset_bypass` GUC (already scoped to exactly `complete_verified_saas_billing_payment()`'s own call site — a `SECURITY DEFINER` RPC nothing else can trigger this GUC from) extended to cover them, mirroring how that same GUC already exempts `status`/`saas_billing_status`/`saas_billing_anchor_date`. **Do not add a third GUC** — this is the same writer, same call site, same trust boundary as the columns already exempted.

**Free/Test tier (`price_locked = true`) must never be Owner-selectable** — it's a Super-Admin-only accommodation mechanism (Story 11.2/11.5), not a self-service downgrade path. `initiate_saas_billing_payment()`'s new tier override must reject any `p_tier_id` where `tiers.price_locked = true`.

**Endpoint-URL caveat, flagged not assumed:** the real, production-verified `mobilePay()` endpoint is `https://www.dklo.co/api/tara/mobilepay` — **not** a `taramoney.com`/`api.taramoney.ai`-style domain the docs site's own branding might suggest. `createPaymentLink()`'s real endpoint must be **confirmed live** (likely also under `www.dklo.co`, per the same account/integration, but do not hardcode from the generic mintlify docs example alone) — see Task 7's required live-evidence session, matching this epic's own established discipline (every prior Epic 11 payment story did a real live test before shipping, e.g. `docs/decisions.md` 2026-08-27/2026-08-28 entries).

**Webhook-scheme caveat, flagged not resolved:** the fetched `/api/webhooks` docs describe `X-Tara-Signature` HMAC-SHA256 verification; the actual, real-production-verified `TaraMoneyProvider.verifyWebhookSignature()` (`TaraMoneyProvider.ts:274-343`) uses a plain shared-secret `tara-webhook-secret` header match instead (confirmed again this session — same discrepancy `docs/decisions.md`'s 2026-08-28 entry already flagged, unresolved). **Do not assume a Payment-Link-originated webhook uses the same shared-secret scheme as the direct `mobilePay()` webhook** — this must be confirmed against a real delivery in Task 7's live-evidence session before this story can be marked done; if it turns out to differ, `verifyWebhookSignature()` needs a second verification branch, not a blind reuse of today's single check.

## Acceptance Criteria

1. **Given** the Pay Now dialog (Settings Billing card and/or the suspended-gym Owner screen), **when** the Owner opens it, **then** they can select a tier/interval to pay for (excluding Free/Test — `price_locked` tiers), not just re-pay whatever is already on `gyms.tier_id`/`saas_billing_interval`; the selected tier/interval is recorded on the resulting `saas_billing_payments` row and applied to `gyms` only once that payment verifies. [Source: epics.md#Story 11.7, L2101–2103; supabase/migrations/0072_saas_billing_reminders_one_tap_pay.sql#initiate_saas_billing_payment, complete_verified_saas_billing_payment]
2. **Given** the Pay Now dialog, **when** the Owner wants to pay via mobile money, **then** a country selector (flags, scoped to Tara's confirmed 14-country list) drives phone-number formatting/validation only — it is never sent to TaraMoney as an API parameter, since `network` is already always empty and TaraMoney auto-detects the operator server-side. [Source: epics.md#Story 11.7, L2105–2107; supabase/functions/payment-webhook/_shared/payment-providers/TaraMoneyProvider.ts:197; packages/types/src/schemas/payment.ts:17-24]
3. **Given** the Pay Now dialog, **when** the Owner doesn't want to (or can't) pay via mobile money, **then** a "Continue on Tara" action calls TaraMoney's `createPaymentLink()` (confirmed to return a working `cardLink`, unlike `EmbedPay` which is mobile-money-only) and opens the returned hosted checkout page — the same `saas_billing_payments` `processing` row, tier/interval selection, and webhook-completion path serve both the direct mobile-money flow and this one. [Source: epics.md#Story 11.7, L2109–2111; live docs fetch, this story's Context section]
4. **Given** a real Owner session (not Super Admin), **when** `PayNowButton`'s polling watch runs after a payment is submitted, **then** it can actually read its own gym's `saas_billing_payments` row (new Owner-scoped RLS policy) and the "verified"/"flagged" branches fire correctly — closing the pre-existing gap `deferred-work.md:6,643` already flagged, which otherwise silently undermines this story's own new UI the same way it already undermines Story 11.4's suspended-screen recovery. [Source: deferred-work.md:6, 643; apps/dashboard/lib/realtime/paymentStatus.ts:75-87; supabase/migrations/0069_saas_billing_payments.sql:34-37]
