# Story 4.12: Notch Pay → Tara Money Cutover

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As the platform,
I want new payment initiations to route to Tara Money while in-flight Notch Pay payments reconcile cleanly,
so that the cutover (FR-102) produces zero double-charges and zero lost payments (NFR-012).

**Context — read this before touching any AC below.** This story's title and literal AC text (epics.md, FR-102) describe a **dual-provider migration that never existed in this codebase**. Exhaustive verification (this story's own research, not an assumption):

- `payment_providers` has had exactly **one** row, ever: `taramoney` (seeded `is_active = true` in `0029_payment_provider_registry.sql`, Story 4.1, 2026-07-31). No `notchpay` row was ever inserted, in this migration or any other — confirmed via `grep -rn "provider_key" supabase/migrations/`.
- No `NotchPayProvider.ts` (or any Notch-Pay-named file) exists anywhere in the repo. The only `PaymentProvider` implementation is `TaraMoneyProvider.ts`.
- `docs/decisions.md`'s Story 4.1 entries (2026-07-31) show the *very first* spike attempt targeted Tara Money's real `9FmIZg9GBB` account directly (which failed activation, then fell back to a stand-in Tara Money business) — Notch Pay was never actually attempted as a provider, only named in the original V1.0 PRD/epics as the planned vendor before this pivot.
- `FR-099`/`FR-100` (prd.md) both say this explicitly: *"Notch Pay remains a documented fallback behind the same interface, never actually carrying live traffic."*

**What this means for every literal AC below:** there are, and will permanently be, **zero** "Notch Pay payments already in `processing` state," zero in-flight legacy transactions to reconcile, and no `notchpay` provider row to revert to. Building any of that machinery (a `NotchPayProvider.ts` stub, dual-provider reconciliation logic, a `notchpay` DB row "for reversibility") would be pure invented work satisfying no real requirement — do not do it. **Do not treat this as license to skip the story, either.** The PRD is explicit about what *is* still open (`prd.md` OQ-7 table row: *"actually routing real member payments through this account is Story 4.12's cutover, still `backlog`"*; `prd.md` FR-100: *"only actually beginning to route real member payments through it remains before production reliance"*). Confirmed via code: `initiatePayment()` (`apps/dashboard/services/payments.ts`) — the only code path that can ever call Tara Money for a real payment — has **zero UI callers** anywhere in the dashboard (`grep -rln "initiatePayment" apps/dashboard --include="*.tsx"` returns nothing). `RenewalModal.tsx`'s `METHOD_OPTIONS` (lines 29-33) only offers `cash` / `bank_transfer` / `manual_momo` — all synchronous, staff-attested manual methods via `confirmRenewalAction`. **No real member has ever been able to trigger a Tara Money charge through any dashboard screen.** That is the actual gap this story exists to close.

**Not in scope:** touching `TaraMoneyProvider.ts`'s `initiate()`/`verifyWebhookSignature()` (Story 4.1/4.10/4.11 territory, already tested), `payment_providers`/`activate_payment_provider()`'s schema (already generic and working, Story 4.1), or `run_payment_reconciliation_job()`'s detection logic (already provider-agnostic, Story 4.4, see AC #2's Dev Notes below). Per-gym credential routing (`{type:'gym', gym_id}`) is Story 4.13/4.14, not this story — this story still routes through GymOS's single platform-level `9FmIZg9GBB` account, same as every prior spike.

## Acceptance Criteria

1. **Given** the `payment_providers` table and `activate_payment_provider()` RPC (AD-13), **when** the cutover is executed, **then** Tara Money becomes the active provider via that RPC — no direct table write — and all new payment initiations route to it; Notch Pay remains a documented fallback behind the same `PaymentProvider` interface, configured but not receiving new traffic. [Source: epics.md#Story 4.12; ARCHITECTURE-SPINE.md#AD-13]
   - **Reality:** Tara Money has been the sole active row since `0029_payment_provider_registry.sql` (Story 4.1) — the RPC-driven-activation half of this AC needs zero new code. The real, unmet half is "all new payment initiations route to it": today, **none** do, because no UI ever calls `initiatePayment()`. This story's Task 2 closes that gap. The "Notch Pay... configured but not receiving new traffic" clause is vacuously true (there is no Notch Pay to configure) — document, don't build.
2. **Given** Notch Pay payments already in `processing` state at cutover time, **when** the reconciliation job runs during the migration window, **then** it polls both providers until each in-flight payment reaches a terminal state under Notch Pay — no payment is re-initiated against Tara Money to prevent a double-charge. [Source: epics.md#Story 4.12; NFR-012]
   - **Reality:** the precondition ("Notch Pay payments already in `processing` state") is permanently an empty set — Notch Pay never processed a payment. `run_payment_reconciliation_job()` (`0032_payment_reconciliation_job.sql`) is already fully provider-agnostic: it queries `payments`/`payment_webhook_events` by state (`status = 'processing'` older than 10 minutes → `stale_processing`; unmatched webhook → `missing_internal_record`; amount disagreement → `amount_mismatch`), never branching on `provider_key`. It already runs nightly and needs no change to "cover" a second provider that doesn't exist. Task 4 verifies and records this rather than adding dead multi-provider logic.
3. **Given** the migration window, **when** it completes, **then** the window's start/end and the reconciliation job's result (zero discrepancies required per NFR-012) are recorded in the audit log. [Source: epics.md#Story 4.12; NFR-012]
   - **Reality:** `job_runs` (written by every `run_payment_reconciliation_job()` invocation, `0032` migration) already records `started_at`/`finished_at`/`status` per nightly run — this generically satisfies "window start/end... recorded" for every run, not just a one-time cutover event, with zero new schema. The genuinely new piece is a `docs/decisions.md` entry recording the day real automated payment initiation actually went live (mirroring this project's own established discipline for every other provider-activation milestone, e.g. the 2026-07-31/2026-08-13 entries) — Task 5 does this once Task 2/3 land and a real transaction confirms clean end-to-end behavior.
4. **Given** a need to revert during the beta, **when** an Owner or Super Admin issue requires it, **then** the cutover is reversible via `activate_payment_provider()` back to Notch Pay — configuration only, no data migration required. [Source: epics.md#Story 4.12]
   - **Reality — genuine open gap, resolved by user decision (2026-08-17):** there is no `notchpay` row to revert *to*, and more importantly, **`activate_payment_provider()` cannot express "no automated provider active" at all** — it always requires an existing `provider_key` to activate, and the partial unique index only enforces *at most* one active row, never *at least* one. **Decision: a UI-level kill switch, not a schema change.** `payment_providers` gets no new column; `activate_payment_provider()`'s contract is untouched. See Task 3 for the concrete mechanism (an env-var-gated flag, server-side enforced).
5. **Given** both MTN Mobile Money and Orange Money, supported under Notch Pay in V1.0 (FR-033), **when** the cutover completes, **then** both are confirmed working under Tara Money too (FR-103) — coverage parity, not a reduction; cash, bank transfer, and manual mobile money are unaffected either way. [Source: epics.md#Story 4.12; prd.md#FR-103]
   - **Reality:** every real Tara Money spike to date (Story 4.1, 4.2, 4.10) exercised **Orange Money only** — confirmed via `docs/decisions.md`. MTN Mobile Money has never been tested against Tara Money's real API. `deferred-work.md`'s Story 4.2 entry flags that `TaraMoneyProvider`'s `initiate()` sends `network: ""` (auto-detect) rather than an explicit operator — this worked for Orange but is unverified for MTN. This is a real, unclosed gap — Task 3 below.
6. **Given** FR-099's amended framing, **when** this story ships, **then** documentation (PRD, `docs/decisions.md`) reflects that Tara Money has been the intended, documented provider since 2026-07-31, and that this story is the one that actually begins routing real member payments through it — not a re-announcement of an already-shipped fact. [Source: epics.md#Story 4.12; prd.md#FR-099]
   - **Reality:** the PRD/decisions.md side of this is already largely done (Story 4.10's 2026-08-17 code-review correction pass already updated `prd.md`'s OQ-7/OQ-13 rows and `ARCHITECTURE-SPINE.md`'s Deferred section). What remains undone is the *fact* this AC asks to be documented — real payments actually flowing — which is this story's Task 2/3/5.
