# Story 13.5: E2E Test Automation Baseline

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As the development team,
I want automated end-to-end coverage of GymOS's four highest-risk V1.5 flows,
so that regressions in privilege escalation, payment cutover, progress-data privacy, or class capacity are caught by CI, not discovered in production.

## Acceptance Criteria

1. **Given** the E2E baseline (`NFR-015`), **when** it is established, **then** it covers exactly four flows: staff provisioning + role enforcement (Epic 9, `NFR-013`), the payment cutover path (Epic 4 extension), progress-data access boundaries (Epic 10, `NFR-016`), and class booking capacity limits (Epic 12, `AD-21`). [`prd.md#NFR-015`]
2. **Given** the existing V1 CI gates (RLS pgTAP tests, payment integration tests, TypeScript checks, i18n parity), **when** the E2E suite is added, **then** it complements those gates rather than replacing any of them — this is the project's first E2E investment, added once all four flows it tests exist to be tested (Epic 13 is the last V1.5 epic in the build sequence, and all four target flows/epics — 9, 4.12, 10, 12 — are already shipped and `done`). [`prd.md#NFR-015`]
3. **Given** the staff-provisioning privilege-escalation guarantee specifically (`NFR-013`), **when** the E2E suite runs, **then** it asserts an Owner cannot mint or promote-to Super Admin, a Supervisor cannot mint or promote-to Supervisor or Owner (including on themselves), and a Manager cannot mint or edit staff roles at all. [`prd.md#NFR-013`]

## Dev Notes

- **This is the project's first E2E investment.** `ARCHITECTURE-SPINE.md`'s own Deferred section (line 274) explicitly left the mechanism unchosen ("Playwright vs. other") — Task 1 resolves it. Every other testing gate in this repo (pgTAP for RLS, Vitest for `apps/dashboard` unit/component tests, `check:i18n` for locale parity) is unit/integration-level; this story is deliberately the first to drive the real HTTP boundary end-to-end.
- **Read this before assuming "no browser automation is available in this project"** — that phrase appears repeatedly across prior stories' Completion Notes (Stories 9.1–9.4, 10.1–10.3, 12.3, 13.4, etc.) and one `deferred-work.md` entry (line 532, "no automated E2E dashboard testing in V1"). Every one of those refers to a **dev-story session's own live, interactive click-through with the user** not being available in this devcontainer — it is not a claim that headless Playwright can't run in CI. This story is the one that closes that gap for CI (not for interactive dev-session verification, which remains the user's own established domain in this project). Do not read the prior pattern as a reason this story is infeasible.
- **All four target flows already exist and are `done`** (Epic 9 — staff provisioning/role enforcement; Story 4.12 — payment cutover, already reflected in the `payment_providers` seed row; Epic 10 — progress-data boundaries; Epic 12 — class capacity). This story adds regression coverage over already-shipped, already-pgTAP-covered behavior — it is not discovering new product requirements. Where a pgTAP suite already proves a boundary at the SQL layer (e.g. `multi_gym_staff_binding_rules.test.sql`'s role-ceiling assertions, `progress_photos.test.sql`'s sharing-flag assertions, `class_booking_with_capacity_enforcement`'s own suite), this story's job is proving the same guarantee holds through the *real* HTTP/UI path, not re-deriving the SQL-level proof.
- **No `supabase/seed.sql` exists in this repo today.** This story's `apps/dashboard/e2e/fixtures/seed.ts` is genuinely new infrastructure, not an extension of anything. Every fixture must be built through real RPCs/service functions (`assign_coach()`, `book_class_session()`, the real progress-entry write path, `supabase.auth.admin.createUser()`), matching this project's consistent "build fixtures through the real code path, never hand-craft rows" convention already established across every prior story's pgTAP suite.
- **`users.must_change_password` defaults `true`** (`0016_owner_must_change_password.sql:7`) — every newly-created staff fixture will hit the forced-password-change gate on first login unless the seed script explicitly clears it (Subtask 3.2). This is an easy, silent way for every staff-login-dependent spec to fail against the wrong page if missed.
- **`[auth.sms.test_otp]` (`supabase/config.toml:268-271`) already exists** for exactly this purpose — two fixed phone→OTP pairs for local/CI testing, bypassing the `send_sms` hook (and therefore the WhatsApp/Twilio provider chain and Edge Functions runtime) entirely for those numbers. Reuse it for the seeded Member fixture rather than inventing a new OTP bypass.
- **The `TMPDIR` devcontainer workaround for `supabase functions serve`** (`docs/decisions.md`, 2026-08-12 entry) is required in *this* devcontainer for any spec that needs the `payment-webhook` Edge Function running (Flow 2 only — member OTP login should not need it, per the `test_otp` bypass above). Do not assume it's needed on GitHub Actions' own runners; verify.
- **`payment_providers` already seeds `taramoney` as active** (`0029_payment_provider_registry.sql:129-130`) — Story 4.12's "cutover" is an operational RPC call already reflected in the migration's own seed data, not something this story's fixture needs to trigger itself. Confirm this hasn't drifted (Subtask 1.3) before designing Flow 2's fixture around that assumption.
- **Concurrency is the actual point of Flow 4 (Task 7).** `book_class_session()`'s `SELECT ... FOR UPDATE` lock (`AD-21`) is specifically about preventing overbooking under *concurrent* attempts — a test that awaits bookings one at a time never exercises the lock at all and would pass even if the lock were silently broken. Use genuinely concurrent requests (`Promise.all`), not sequential ones.
- **Scope boundary, decided, not left ambiguous:** this story does not add Detox/Maestro or any native-mobile UI automation to `apps/mobile`. Member-app-only steps in Flows 3 and 4 are exercised via authenticated `APIRequestContext` calls against the real Supabase REST/RPC boundary instead — a genuine end-to-end proof of the server-side guarantee, with an explicit, documented scope cut on `apps/mobile`'s own React Native code. If the user disagrees with this framing when reviewing the story, it's a scope conversation to have before `dev-story`, not a silent implementation choice to revisit after the fact.
- **Uncommitted prior-story diff, flag before starting:** as of this story's creation, Story 13.4's own code-review-patch diff (5 patches: `handleTakeOwnership` error surfacing, disabled-while-pending button, `canCreatePlan` gating, a new `workoutPlans.takeOwnershipOfWorkoutPlan.test.ts`, and the `database.ts` type fix) is still uncommitted in the working tree on top of commit `c2e9921` — matches `git status`. Per every prior story in this epic's own repeated convention (13.1→13.2→13.3→13.4, each committing the previous story's diff before starting new work), commit that diff first, then set this story's own `baseline_commit` to that new commit.
