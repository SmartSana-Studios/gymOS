# Story 4.14: Flow A Explicit Gym-Account Routing & Auditability

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As GymOS,
I want every member→gym payment to be provably routed to that gym's own account and never GymOS's platform account,
so that FR-125's "GymOS takes no commission" claim is auditable, not merely asserted (NFR-019).

**Context — read this before touching any AC below.**

**What this story actually wires** (Story 4.13 built the storage, this story makes it load-bearing): Story 4.13 added `gym_payment_credentials` (Vault-encrypted per-gym Tara Money credentials) plus `connect_gym_payment_credentials()`/`disconnect_gym_payment_credentials()`/`get_gym_payment_connection_status()` — but explicitly did **not** touch `TaraMoneyProvider.ts`, `PaymentProvider.ts`, or `payment-webhook/index.ts`. Every payment today — even for a gym that has "connected" per Story 4.13's UI — still settles into GymOS's single shared `9FmIZg9GBB` platform account, because `TaraMoneyProvider.ts` reads `TARAMONEY_API_KEY`/`TARAMONEY_BUSINESS_ID`/`TARAMONEY_WEBHOOK_SECRET` from env vars unconditionally (confirmed unmodified, `initiate()` lines 124-125, `verifyWebhookSignature()` line 187). This story closes that gap: real per-gym routing, starting today.

**The core design problem this story must solve, and the recommended resolution (read in full — this is the crux of the story):**

AD-14 says `PaymentProvider` "gains a discriminated routing context — `{type:'gym', gym_id}` selects a gym's Vault-stored Tara Money credentials... at initiation, verification, and reconciliation." Initiation is straightforward: the `payments` row already carries `gym_id`, so `handleInitiate()` in `index.ts` can resolve it directly.

**Webhook verification is the hard part.** Today, `verifyWebhookSignature()` checks the incoming `tara-webhook-secret` header against one global env var *before touching the database at all* — order matters, because Story 4.11's invariant (FR-101/AD-17) is "verified before any DB **write**" (not read). Once the secret becomes per-gym, the handler must know *which* gym's secret to check — but it doesn't know the gym until it can identify the payment, and today identification only happens *after* the (currently global) signature check.

Two candidate resolutions were evaluated:

- **Rejected: resolve gym_id only via the matched `payments` row** (look up `provider_transaction_ref` first, get `gym_id` from that match, then verify). This regresses a documented, accepted V1 gap: `docs/decisions.md`'s 2026-08-01 entry ("webhook-before-ref-persisted race") already accepts that a webhook can legitimately arrive before `handleInitiate()`'s `provider_transaction_ref` UPDATE commits. Under this approach such a delivery has no matched row yet, so its gym is unresolvable and the delivery would have to be hard-rejected (401) instead of today's behavior (verified successfully, then reconciliation's `missing_internal_record` category catches it later if it truly never matches). That's a real regression, not just a design nuance — **do not implement this approach.**
- **Recommended: resolve gym_id from the payload's own `businessId` field, independent of whether a `payments` row exists yet.** TaraMoney's webhook payload already carries `businessId` in cleartext (confirmed via every real spike, `docs/decisions.md` 2026-07-31/2026-08-13/2026-08-17 entries) — it is not itself secret; Story 4.13 already stores a partial cleartext copy (`business_id_masked`) for exactly this "don't require a Vault decrypt for a routine read" reason. Add one more plain (non-Vault) column, `gym_payment_credentials.business_id_plain text`, unique per `(provider_key, business_id_plain)`, populated by `connect_gym_payment_credentials()` alongside the existing masked column. The webhook handler then: (1) parses the raw payload just far enough to read `businessId` and `paymentId`/`transactionId` — no DB write, so this doesn't violate the verify-before-write invariant — (2) looks up `gym_id` from `gym_payment_credentials` by `business_id_plain`, (3) resolves that gym's full decrypted credentials via a **new, service-role-only** RPC (Task 2), (4) verifies the signature using that gym's secret. This preserves `missing_internal_record` detection (an event with a resolvable `businessId` but no matching payment row still gets verified and logged), and it directly closes the exact gap `TaraMoneyProvider.test.ts:316-334`'s cross-tenant test documents today ("a valid header with a mismatched businessId still verifies — no per-account binding") and the deferred-work.md item from Story 4.10's review ("a valid shared secret paired with a mismatched businessId payload was not tested... directly relevant to Story 4.13's [really: 4.14's] per-gym credential design").

**[Review][Decision] if this recommendation is rejected during implementation:** the alternative is querying all connected gyms' Vault secrets and testing each until one matches (works, but is O(n) per webhook and doesn't scale past a handful of gyms) — flag and get explicit sign-off before falling back to it.

**Scope boundary vs. Story 4.15:** this story does not touch the member-app renewal UI (Story 4.15's territory) — AC #6 here is satisfied because Story 4.12 already built one shared `initiatePaymentAction`/`initiate()` path that both the front-desk `RenewalModal` and (eventually) Story 4.15's member-initiated flow call; routing this story adds to that shared path benefits both callers automatically, with zero changes needed on either caller's side.

## Acceptance Criteria

1. **Given** the `PaymentProvider` interface (unchanged in shape since V1.0), **when** this story ships, **then** it gains a discriminated routing context, starting with the `{type:'gym', gym_id}` variant Flow A needs (FR-138, AD-14) — Epic 11's Flow B later extends this same context with a `{type:'platform'}` variant; the type is additive, not a breaking change to this story's Flow A usage. [Source: epics.md#Story 4.14; prd.md#FR-138; ARCHITECTURE-SPINE.md#AD-14]
2. **Given** a member payment (Flow A), **when** it is initiated, **then** the `PaymentProvider` resolves the gym's connected credentials via the `{type:'gym', gym_id}` routing context and routes through them — GymOS orchestrates (create collect, detect confirmation, reconcile, receipt) but never receives or holds member funds (FR-124). [Source: epics.md#Story 4.14; prd.md#FR-124, FR-128]
3. **Given** a gym whose Tara Money credentials are missing, invalid, or revoked, **when** a member attempts a mobile-money payment, **then** initiation fails gracefully, directs the member to the front desk (FR-127's cash fallback), and the Owner is notified their connection needs attention (FR-128). [Source: epics.md#Story 4.14; prd.md#FR-127, FR-128]
4. **Given** the reconciliation job (Story 4.4, extended), **when** it runs, **then** it checks each Flow A payment's settled account against its gym's connected credentials, flagging any payment that settled to or credited the platform account — a misrouted-but-otherwise-clean payment that reference/amount matching alone couldn't catch (FR-137's fourth discrepancy category). [Source: epics.md#Story 4.14; prd.md#FR-137]
5. **Given** a completed audit period, **when** an Owner or Super Admin reviews the audit log, **then** every Flow A payment's settlement account is verifiable against the gym's own credentials — proving no platform-account credit occurred, not merely asserting it (NFR-019, G-2). [Source: epics.md#Story 4.14; prd.md#NFR-019]
6. **Given** a renewal via the front-desk alert panel (FR-050) and a renewal initiated by a member from the app (Story 4.15), **when** either occurs, **then** both route through this same Flow A gym-account path — the subscription lifecycle (FR-027–FR-032) is unchanged either way; money routing is now explicitly the gym's own account regardless of which surface initiated the payment (FR-129). [Source: epics.md#Story 4.14; prd.md#FR-129]
