# Story 13.3: Member Plan View & Completion Tracking

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a member,
I want to view my assigned workout plan and mark exercises or sessions complete,
so that I can follow my coach's program and track my own adherence.

## Acceptance Criteria

1. **Given** my assigned workout plan, **when** I open it in the app, **then** I see the named plan with its ordered exercise list, sets, reps, and any coach notes. [FR-109, FR-122's member-app half]
2. **Given** an exercise or session in my plan, **when** I mark it complete, **then** the completion is logged offline-safely via `client_id`, the same offline pattern as progress-entry logging (Story 10.1). [FR-110]
3. **Given** my completion data, **when** my coach views my plan, **then** they see what I've completed — completion data is visible to the authoring coach. [FR-110]

- [x] Task 1: Migration `0081_member_plan_view_completion_tracking.sql` — `workout_plan_completions` table, RLS (AC: #2, #3)
  - [x] Subtask 1.1: **Design decision, read before writing any SQL.** `workout_plan_completions` rows must key completion history by `(plan_id, exercise_id)` — **never** by `workout_plan_exercises.id`. Reason, confirmed by reading `0080_coach_authored_workout_plans.sql`'s `update_workout_plan()` (lines 251–276): every edit to a plan (including a mere reorder, or fixing a typo in a note) does `delete from workout_plan_exercises where plan_id = p_plan_id` and reinserts a fresh row set with brand-new `id` values. A completion FK'd to `workout_plan_exercises(id) on delete cascade` would silently wipe a member's entire completion history the next time their coach saves *any* edit to the plan — a real data-loss bug, not a hypothetical. `exercise_id` (a stable `exercise_library` row) is the only identity in this schema that survives a plan edit, so it is the join key. This also means a completion for an exercise later removed from the plan stays queryable (a genuine adherence-history record), which is the more correct behavior for "track my own adherence" anyway — do not treat this as a shortcut, it is the deliberately correct design.
    - **Known, accepted limitation this design trades away — document, do not silently fix:** 13.2's own code review explicitly dismissed "duplicate `exercise_id` within one plan" as *intentional* (warm-up vs. working sets, supersets, drop sets — `13-2-coach-authored-workout-plans.md` Review Findings, first entry). Because this story keys completions by `exercise_id` alone (not by row instance), when a plan has two rows for the same exercise, marking either row complete shows as completed on **both** — there is no way to distinguish which occurrence a member meant, since `exercise_id` is the only identity stable enough to survive a plan edit at all. This is an inherent trade-off of the fix above, not an oversight: precise per-instance tracking would require reusing `workout_plan_exercises.id`, which reintroduces the data-loss bug this subtask exists to prevent. Task 3 (dashboard) and Task 4 (mobile) must render the identical completion state/badge on every row sharing an `exercise_id` within one plan — do not invent per-row disambiguation. Flag this to the user as a known limitation, not a bug to silently patch around.

## Dev Notes

- **Read `0080_coach_authored_workout_plans.sql` in full before writing this story's migration** — the delete-then-reinsert behavior of `update_workout_plan()` (lines 251–276) is the single most important fact this story's schema design depends on (Task 1, Subtask 1.1). Getting the completion table's join key wrong (keying off `workout_plan_exercises.id` instead of `exercise_id`) would ship a feature that silently loses member data on the very next coach edit — this is exactly the class of "leave the system working end-to-end" requirement this workflow's own guardrails exist to catch before it ships, not after a review finds it.
- **AD-23 ("Offline support is scoped per-domain... workout completion: idempotent upsert, no backfill concept needed") is explicitly flagged in `ARCHITECTURE-SPINE.md` as "extrapolation from precedent, not a proposal-sourced decision — confirm during Epic 13 story-writing."** This story is that confirmation. "Idempotent upsert" is implemented the same way `progress_entries` already implements it — a partial unique index on the client-generated id plus a client-side `23505`-catch-and-treat-as-success, **not** a literal SQL `ON CONFLICT DO UPDATE`. There is nothing to "update" on a conflict (a completion row has no mutable fields beyond its own identity) — a plain insert-or-ignore-on-conflict is the correct, precedent-matching implementation. Do not add an `ON CONFLICT DO UPDATE` clause; there is nothing for it to update.
- **No "session" entity exists anywhere in this schema, and this story does not add one.** FR-110/AC #2's "exercises or sessions" is resolved as: completion is always logged per-exercise; a "whole session" is just "every currently-visible exercise got a completion row with the same timestamp," achievable client-side via an optional "Mark all complete" convenience action (Subtask 4.5) with zero new schema. If a future story needs a first-class session/workout-instance concept (e.g., a structured "did you do this today?" prompt with adherence-streak tracking), that is out of this story's scope — flag it as a possible future story, do not build it speculatively here.
- **No "un-complete" / delete / edit path for a logged completion.** Matches `workout_plans`' own "no delete path" precedent (13.2) and `progress_entries`' immutable-log precedent — no AC calls for undoing an accidental tap, and adding one now would need its own RLS policy + UI + a decision about whether a coach should be notified, none of which any AC or mockup asks for.
