# Story 10.3: Member Progress Screen

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a member,
I want a dedicated Progress screen showing my trends over time,
so that I have a concrete reason to open the app between gym visits.

## Acceptance Criteria

1. **Given** the app's new Progress tab (FR-123), **when** I open it, **then** I see my current weight and change since my starting weight, a weight trend chart, logged measurements with their trends, and a photo timeline (visible only to me unless I've shared a given photo). [Source: epics.md Story 10.3, AC #1; prd.md FR-096, FR-123; EXPERIENCE.md MA-15]
2. **Given** the Progress screen, **when** I want to log a new entry, **then** a log-entry action is available directly from this screen (Story 10.1). [Source: epics.md Story 10.3, AC #2] — Satisfied by mounting the existing, route-agnostic `LogEntrySheet` component (built by Story 10.1 specifically so this story could do this without rework) — no new log-entry UI is built here.
3. **Given** I am offline, **when** I open Progress, **then** previously-synced charts and data render from local cache; logging a new entry still queues per Story 10.1. [Source: epics.md Story 10.3, AC #3; prd.md FR-096] — **Narrowed, see Dev Notes "What 'Local Cache' Means Here":** this codebase has no persistent (cross-app-restart) read cache anywhere — the closest and only precedent (`useGymAccentColor`'s branding cache) is an in-memory, session-lifetime cache despite FR-011's own "24-hour on-device cache" wording never having been literally built that way either. This story ships the same class of cache: an in-memory, session-lifetime snapshot of the last successfully-loaded Progress payload, reused when a fresh fetch fails or `isConnected === false`. A cache that survives a full app restart while offline is a heavier, unprecedented lift and is explicitly out of scope — flagged as a possible future enhancement, not a gap in this story's coverage. The logging-still-queues half of this AC needs no new code: `LogEntrySheet` already routes through `useOfflineSync().queueOfflineProgressEntry` exactly as `profile.tsx` already wires it.

### Scope boundary — cross-story commitments this story must resolve, plus this story's own scope decisions

Both prior Epic 10 stories explicitly deferred pieces of their own ACs to *this* story, because this is the first story that builds any Progress-related list/detail UI. Re-litigating these would contradict already-recorded decisions in those stories' own files:

- **Entry soft-delete affordance (Story 10.1 AC #4).** Story 10.1 shipped soft-delete completely at the data layer (RLS `self_soft_delete_own_progress_entries`, pin-back trigger, pgTAP) but built no UI, stating explicitly: *"Story 10.3 owns the Progress screen, which is the first place a list of past entries — and therefore a delete action — has anywhere to live."* This story must ship that UI. **New scope decision this story makes:** `EXPERIENCE.md`'s MA-15 mockup (lines 895–940) shows only a weight chart, a measurements-summary list (latest value + delta per field), and a photo grid — it has no raw chronological list of individual entries for a delete action to attach to (an entry with only a note and no weight/measurement/photo would be invisible on the mockup's own screen as literally drawn). Resolution: this story adds a small "View all entries" link from the main Progress screen to a new `apps/mobile/src/app/(tabs)/progress/entries.tsx` list screen (mirrors `(tabs)/history/index.tsx`'s list/pull-to-refresh shape), where each row shows its logged date + populated-field summary and a delete action (`Alert.alert` confirm, same shape as `profile.tsx`'s `handleLogOut`). This is the first list view for entries in this codebase, exactly as 10.1 anticipated.
- **Photo per-photo share toggle UI (Story 10.2 AC #4/#5).** Story 10.2 shipped the entire sharing/revoke *mechanism* (schema, RLS, storage policy, `setProgressPhotoSharing()`) with zero UI callers, stating explicitly: *"Story 10.3 wires the toggle onto its new photo detail view exactly as it already plans to mount Story 10.1's `LogEntrySheet`... the toggle service function is built now, called later."* `EXPERIENCE.md:927,932` also textually attributes "the per-photo share toggle" interaction to this story's screen. This story must build that photo detail view and call `setProgressPhotoSharing()` from it — the first caller.
- **Mobile tab bar addition.** `apps/mobile/src/components/app-tabs.tsx` currently has exactly 4 triggers (`index`, `checkin`, `history`, `profile`) — no `progress` tab exists yet, matching what Story 10.1/10.2 both already confirmed. `EXPERIENCE.md`'s full V1.5 target (line 172) is a 5-tab bar — Home, Check-In, **Classes**, **Progress**, Profile — reached by *both* adding Progress and Classes *and* moving History off the bar into a Profile row, specifically to stay under the stated 6-tab usability ceiling. Classes (Story 12.4, `epic-12` in sprint-status.yaml) is still `backlog` — it does not exist in this app yet. **This story's scope decision:** add `progress` as a 5th native tab trigger now (`index`, `checkin`, `progress`, `history`, `profile` — Progress placed ahead of History to match its eventual final adjacency to Profile), and leave `history` as a tab trigger, unmoved. The History→Profile-row move is deferred to whichever story adds the Classes tab (Story 12.4) — that is the story that will actually push tab count to 6 and need to solve the ceiling problem, mirroring this epic's own established pattern of resolving each sequencing gap in the story that actually needs it, not preemptively. Do **not** move History or touch `(tabs)/history/index.tsx`'s own layout in this story.
- **No new migration, RLS, or pgTAP surface.** This story is 100% UI + read queries + one already-covered write (soft-delete update, already RLS/pgTAP-covered by Story 10.1) + one already-covered write (`setProgressPhotoSharing`, already RLS/pgTAP-covered by Story 10.2). Nothing here needs a new `supabase/migrations/*.sql` file or new pgTAP test file — confirm this understanding is still correct in Task 1 before writing any code, don't assume it's still true without checking.

### Review Findings

- [x] [Review][Patch] Session-lifetime `cachedProgressPayload` has no member/session key, so it survives sign-out and a same-device member switch — a second member on a shared/kiosk device (or the same person switching accounts) could momentarily see the first member's weight/measurements/photos if a fresh fetch is slow, fails, or the screen is opened offline right after switching. User decision: clear the cache on sign-out (same call site as other session state, `profile.tsx:348`) AND key it by `member_id` so a fetch for a different member can never return another member's cached data mid-session either. Fixed — `getCachedProgressPayload(memberId)`/`clearCachedProgressPayload()`, cache cleared in `profile.tsx`'s `handleLogOut`. [apps/mobile/src/services/progress.ts:397-401]

- [x] [Review][Patch] Cache is never invalidated after `deleteProgressEntry` or `setProgressPhotoSharing`, and `progress/index.tsx` only refetches on mount (no `useFocusEffect`) — a deleted entry can resurface via the cache-fallback path, and the photo-sharing lock icon can stay stale after navigating back. Violates this story's own Task 9 verification text ("confirm it disappears... on next load", "confirm the icon updates"). Fixed — both write functions now update the cache in place, and `progress/index.tsx` refetches via `useFocusEffect` (mirrors `(tabs)/index.tsx`'s own precedent). [apps/mobile/src/services/progress.ts (no cache setter/invalidator); apps/mobile/src/app/(tabs)/progress/entries.tsx:108-120; apps/mobile/src/app/(tabs)/progress/photo/[id].tsx:60-75; apps/mobile/src/app/(tabs)/progress/index.tsx:203-205]

## Dev Notes

### What "Local Cache" Means Here

AC #3's literal wording ("previously-synced charts and data render from local cache") reads as if a persistent, cross-app-restart cache already exists somewhere in this codebase for the app to reuse. It doesn't. The single closest precedent, `useGymAccentColor`'s branding cache (`apps/mobile/src/hooks/use-gym-accent-color.tsx`), is itself only a module-level in-memory variable — despite FR-011 describing branding as cached "24 hours on-device," the actual shipped implementation is session-lifetime only, re-fetching fresh on every cold app start. This story deliberately follows that same precedent rather than inventing a new, heavier persistence mechanism (AsyncStorage or SQLite) that has no other consumer in this codebase and no stated requirement strong enough to justify the added surface. The achievable, shipped guarantee is: once a member has successfully loaded Progress once this app session, losing connectivity afterward (backgrounding the app, a dead zone at the gym) does not blank the screen — it keeps showing what was last successfully fetched. Losing connectivity *before* ever successfully loading this session (e.g., a fully offline cold start) has nothing to fall back to and shows the existing empty/error pattern, same as any other screen's first-load failure.

### Why `build_muscle` Maps to a Weight *Increase*

`EXPERIENCE.md:924` states directional goals get colored "toward" the goal, but the only numeric trend this screen has is body weight — there is no muscle-mass, body-fat-percentage, or strength metric anywhere in this schema (`progress_entries` has weight + 5 circumference measurements only, per Story 10.1's migration). Reading "Build Muscle" as "weight should trend up" is an imperfect proxy (a member recomposing body fat for muscle at a stable weight would see no green ever, despite real progress) but it is the only interpretation available from data this schema actually captures. This is a deliberate, recorded scope decision, not an oversight — a future story adding a body-composition metric could revisit it.

### Reusing, Not Rebuilding, Story 10.1/10.2's Write Paths

This story adds exactly one new write function (`deleteProgressEntry`) and reuses two already-shipped ones (`setProgressPhotoSharing`, and `LogEntrySheet`'s existing save/queue paths) unchanged. Resist any temptation to "improve" or refactor `logProgressEntry`/`queueOfflineProgressEntry`/`syncPendingProgressEntries` while working in this area of the codebase — they are out of this story's diff scope and already have a full review history (see both prior stories' Review Findings sections) that a drive-by refactor would need to re-litigate.
