# Story 9.2: Staff Activation via Temporary Password

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a newly created staff member,
I want to receive my login credentials and set my own password on first login,
so that I can access the dashboard securely without GymOS involvement.

## Acceptance Criteria

1. **Given** a staff account just created via Story 9.1's `create_staff_member()` RPC (already shipped: the ceiling check, the `members` insert, and the `auth.users` provisioning via `admin.auth.admin.createUser` all already happen inside `createStaffMember()`, `apps/dashboard/services/staff.ts`), **when** the RPC call succeeds, **then** a real WhatsApp message is sent to the new staff member's phone containing the temporary password and the dashboard login link, and the account is `pending_activation` — FR-088. (**"Marked `pending_activation`" is already true structurally**: `users.must_change_password` defaults `true` at the DB level, 0016/Story 1.11, and `listStaff()` already derives `"pending_activation"` display status from it, Story 9.1 Task 4 — this story adds no new column and no new write for that half of the AC. The only net-new work is the message send itself.)
2. **Given** a `pending_activation` staff account, **when** the staff member logs in with the temporary password for the first time, **then** they are required to set a new password before reaching the dashboard, and the account transitions out of `pending_activation`. (**Already fully implemented, role-agnostically, by Story 1.11**: `apps/dashboard/app/(dashboard)/layout.tsx`'s `if (shell.mustChangePassword) redirect("/auth/update-password")` gate and `update-password-form.tsx`'s flip-to-`false` write key on `claims.sub`/`auth.uid()` alone — never on role or on how the account was created. A newly created staff member logging into `apps/dashboard` hits this exact gate today with zero code changes. This story's job is to verify this with a real click-through, not to build it.)
3. **Given** a staff account that has already completed first login, **when** they log in again, **then** no password-reset prompt appears — the temp-password flow only triggers once. (**Also already covered** by the same `mustChangePassword: false` state the flip-write in AC #2 leaves behind — no new logic.)
4. **Given** a staff member who has lost/forgotten their password — whether it is still the original temp password (never completed first login) or a real password set after activation — **when** an Owner or Supervisor clicks "Resend password" for that staff member on the Staff List, **then** the system generates a brand-new temporary password, invalidates the old one, forces `must_change_password` back to `true` (so the staff member is routed through the existing first-login change-password gate again regardless of prior activation state), sends the new temp password to the staff member's phone via WhatsApp, and shows the new temp password in the dashboard UI as an unconditional fallback (same discipline as AC #1's creation toast) — scope added per explicit user instruction during this story's dev pass (2026-08-19): "not forgetting the possibility to resend code just like for members, this in case one has forgotten the password, and this can also apply to members." Investigated during this pass and confirmed members do **not** need an equivalent change: `sendMemberInvite()` has no password concept at all (member invites are a plain re-sendable WhatsApp message, and the Invite button is already always-clickable per Story 2.10 AC #4) — member scope is a no-op, explicitly confirmed with the user.

## Dev Notes

### Scope Addition: Staff Password Resend (AC #4, Tasks 7-11) — User-Directed, 2026-08-19

Added during this story's dev pass per explicit instruction: *"not forgetting the possibility to resend code just like for members, this in case one has forgotten the password, and this can also apply to members."* Two things were investigated and resolved before writing Tasks 7-11:

1. **"Just like for members" turned out not to be a reusable pattern.** Investigated `sendMemberInvite()` (`apps/dashboard/app/(dashboard)/members/actions.ts:222`) and its UI call site (`MembersPageClient.tsx`): members have no password/credential involved in their invite at all — it's a plain WhatsApp message, and the Invite button is already unconditionally re-clickable (Story 2.10 AC #4's explicit "resending is not blocked" requirement). There is nothing to invalidate and nothing to regenerate, so "resend" for a member is already just "click Invite again," today, unchanged. **Confirmed with the user**: no new member-facing work is needed; members are out of scope for Tasks 7-11.
2. **Staff genuinely have no recovery path today, and the gap is real.** Unlike members, staff authenticate with phone+password (`admin.auth.admin.createUser({ phone, password, phone_confirm: true })`, `services/staff.ts`), and the temp password generated at creation is never stored in plaintext anywhere after the creation-toast is dismissed (by design — same as `apps/super-admin`'s owner-activation flow). The app's one existing "forgot password" surface, `apps/dashboard/app/auth/forgot-password/page.tsx` (`components/forgot-password-form.tsx`), is Supabase's stock **email**-based `resetPasswordForEmail()` scaffold — staff/member accounts in this codebase are phone-based and are never given an email, so that flow is structurally unreachable for a staff member who lost their password, whether before or after first login. Tasks 7-11 close that gap with an Owner/Supervisor-triggered reset, reusing the exact ceiling (`owner`/`supervisor`) `StaffPageClient.tsx`'s own `CAN_CREATE` array already established for staff creation (Story 9.1, AD-16) — the same two roles that can create a staff account can reset one's credential.
3. **Applies after first login too, per explicit instruction** ("*it should apply even after a first login, for a non-temp password*") — the RPC/service function does not check or care about the target's current `must_change_password` state; it works identically whether the staff member never logged in yet (still on the original temp password) or logged in long ago and forgot their real password since. Both cases converge on the same fix: force a new temp password, flip `must_change_password` back to `true`, and route them through the existing (Story 1.11) first-login change-password gate again.

This is a real deviation from this story's original scope (`epics.md`/`ARCHITECTURE-SPINE.md` text for Story 9.2 says nothing about a resend/reset capability, and this story's own original Dev Notes explicitly said not to build "any SMS-fallback/retry chain for the activation message" — that exclusion was about retrying a *failed send of the same still-valid password*, a different problem from *the password itself being lost*, which is what AC #4 actually addresses). Recorded here and in Task 6's `docs/decisions.md` entry per this story's existing "flag deviations, don't silently decide" discipline.

### Why Evolution API, Not Story 1.11's Twilio Mechanism — A Documented Judgment Call

`epics.md`'s Story 9.2 text, `ARCHITECTURE-SPINE.md`'s AD-6, and `EXPERIENCE.md`'s AD-17 note all say, in nearly identical words, that staff activation "reuses Story 1.11's existing WhatsApp/SMS temp-password mechanism." Taken literally, that means porting `apps/super-admin/lib/messaging/sendTempPasswordMessage.ts` (Twilio Content API, the pre-approved `verifications_2fa_template`) into `apps/dashboard` as a new file, the same way Story 9.1 ported `generateTempPassword()` into `apps/dashboard/lib/temp-password.ts`.

**This story deliberately does not do that.** Three converging reasons, strongest first:

1. **The Twilio template structurally cannot carry this AC's content.** `verifications_2fa_template` has exactly one `{{1}}` body variable, already spent on the temp password by Story 1.11's own design. FR-088/this story's AC #1 require the message to carry *both* the temp password *and* the dashboard link. Story 1.11 hit this exact wall for the owner-activation flow and was forced to drop the link from the message entirely (see `1-11-gym-owner-activation-temp-password-sms.md`'s own Completion Notes: *"getDashboardAppUrl() is retained... not passed into the message itself"*) — a **documented deviation from its own Task 3, not a clean precedent to copy**. Submitting a second Twilio template to carry a link is a new Meta approval step this story's scope doesn't include. `sendEvolutionApiMessage(phone, message)` (Story 2.10, `apps/dashboard/lib/messaging/EvolutionApiMessageProvider.ts`) sends arbitrary free text with no template constraint — it is the only one of the two mechanisms that can actually satisfy the AC as written.
2. **The architecture has already moved past Twilio-as-primary since AD-6 was written.** AD-6 is dated 2026-08-11, the same day as the rest of the spine — but Story 2.9 (Evolution API sandbox spike, done 2026-08-13) and Story 2.10 (automated member invite via Evolution API, done 2026-08-13) both landed *after* the spine, adding `EvolutionApiMessageProvider.ts` to `apps/dashboard` for exactly this shape of problem (a free-text WhatsApp send from a Server Action). AD-12, in the *same* spine document as AD-6, explicitly binds "member invitations (FR-082), **any future non-OTP send**" — a temp-password message is a non-OTP send by the same reasoning Story 1.11 itself used to accept its template's OTP-wording mismatch as a known cosmetic tradeoff (it isn't an OTP code either way). AD-6's specific "reuse Story 1.11" clause reads as carried-forward text from before Evolution API's adoption, not a decision made with knowledge of `EvolutionApiMessageProvider.ts`'s existence.
3. **`apps/dashboard` has zero Twilio footprint today, and porting Story 1.11's mechanism would introduce a third messaging vendor into the codebase for one story's use.** `apps/dashboard/.env.example` already carries `EVOLUTION_API_BASE_URL`/`EVOLUTION_API_KEY` (Story 2.10) and nothing Twilio-shaped. Adding `TWILIO_ACCOUNT_SID`/`TWILIO_AUTH_TOKEN`/`TWILIO_WHATSAPP_FROM_NUMBER`/`TWILIO_WHATSAPP_CONTENT_SID` here would be new, dashboard-specific Twilio configuration alongside the Edge Function's own separate Twilio secrets (`send-sms-hook`) and `apps/super-admin`'s own separate Twilio env — a third independent copy of the same vendor's credentials for a codebase that has otherwise been consolidating onto Evolution API for exactly this kind of send (AD-11, AD-12).

**Flagged, not silently decided**: this is a real deviation from three planning artifacts' literal text, made on concrete technical grounds (reason 1 alone is dispositive — the literal reading is impossible without a scope-expanding new Meta template). Task 6 requires recording this in `docs/decisions.md` so it's easy to revisit or correct if the user disagrees. **This is the one part of this story's design worth a second look before implementation starts** — if the user has a reason to prefer the Twilio path anyway (e.g. Evolution API's self-hosted-with-no-SLA risk profile, `ARCHITECTURE-SPINE.md`'s own "Named infra risk" callout), that would change Task 1/2's approach materially.
