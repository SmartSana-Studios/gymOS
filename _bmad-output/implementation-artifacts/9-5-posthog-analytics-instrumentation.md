# Story 9.5: PostHog Analytics Instrumentation

Status: done

## Story

As GymOS,
I want product analytics events flowing from both the dashboard and mobile app,
so that V1.5's success metrics (PRD Section 3.2) — beta gym self-sufficiency, non-visit-day app opens, and the rest — are measurable, not just asserted.

## Acceptance Criteria

1. **Given** the dashboard and mobile app, **when** PostHog is integrated (NFR-014), **then** events are routed with the same dev/staging/prod environment tagging already used for Sentry (NFR-007). [Source: epics.md Story 9.5] **(See Dev Notes "The Sentry Pattern This AC Points To Does Not Exist Yet" — this story must define the env-tagging scheme from scratch, not mirror an existing one.)**
2. **Given** any event involving a member, **when** it is captured, **then** it carries no body-measurement or photo content — PostHog integration ships alongside Epic 9 specifically so this constraint is enforced before Epic 10's progress-tracking events exist to violate it. [Source: epics.md Story 9.5] **(See Dev Notes "AC #2 Is a Guardrail for Epic 10, Not Something This Story's Own Events Can Violate" — no member body/photo data exists in any event this story adds; the AC is satisfied by the *shape* of the shared event-type contract this story establishes.)**
3. **Given** the V1.5 success metrics in PRD Section 3.2, **when** instrumentation is complete, **then** at minimum, staff-creation events (this epic), and hooks for non-visit-day app opens and beta-gym support-ticket-free weeks are wired, so later epics only need to add their own event calls, not a new analytics integration. [Source: epics.md Story 9.5] **(See Dev Notes "What 'Hooks' Means for Each of the Three Named Metrics" — the three named items resolve to three different concrete deliverables, not three identical event calls.)**

## Dev Notes

### The Sentry Pattern This AC Points To Does Not Exist Yet

AC #1's text ("the same dev/staging/prod environment tagging already used for Sentry (NFR-007)") reads as if it's copying an established pattern. It is not. This story's own research confirmed, via a repo-wide search: **zero** `@sentry/*` packages in any `package.json` (dashboard, super-admin, mobile, or root), **zero** Sentry SDK calls anywhere including `supabase/functions/`, and the only trace of Sentry in the entire codebase is a placeholder line in the root `.env.example`: `# Sentry (dashboard, super-admin, mobile) — wired in a later story` / `SENTRY_DSN=`. `architecture.md`'s own text ("Sentry is the only exception/crash log... environment-tagged dev/staging/prod") describes the *intended* V1 design, not shipped code — Sentry was apparently never actually wired despite being named as a V1 (not V1.5) NFR. This is a pre-existing gap, not something this story introduces or is responsible for closing (no AC here asks for Sentry itself). Task 3 defines the env-tagging scheme (`VERCEL_ENV` → `prod`/`staging`/`dev`) from scratch for PostHog, and Task 7 documents it in `docs/decisions.md` specifically so that whenever Sentry is eventually wired, it adopts the *same* convention this story establishes rather than inventing a third one.

### AC #2 Is a Guardrail for Epic 10, Not Something This Story's Own Events Can Violate

Epic 10 (Client Progress Tracking, body-profile/photo data) doesn't exist yet — it's `backlog`, not yet elaborated. Neither event this story adds (`staff_created`, `app_opened`) touches member body-measurement or photo data at all, so there's no literal violation to prevent right now. AC #2 is satisfied by the *shape* of the contract this story establishes in `packages/types/src/analytics.ts`: closed, named payload interfaces per event (Task 2) instead of a generic properties bag, so that whenever Epic 10's own create-story pass adds a progress-tracking event, its author is forced to define a new named interface rather than silently reusing an open one that could carry body data unnoticed. Don't over-build this into a runtime validator or allowlist-checker — no AC asks for enforcement machinery, just the type-level discipline plus the `docs/decisions.md` note (Task 7) making the rule explicit for whoever writes Epic 10's story file.

### What "Hooks" Means for Each of the Three Named Metrics

AC #3 names three things and they resolve to three different concrete deliverables — resist the temptation to treat them as one uniform "add an event" instruction:

- **Staff-creation events (this epic)** — a real, concrete event: `staff_created`, capturable today, wired in Task 4.
- **Non-visit-day app opens** — also concrete and capturable *today*, not deferred: the literal minimal signal this metric needs is "the app was opened," which nothing about Epic 10/11/12/13 would naturally add on its own (it's not any of those epics' subject matter). Task 6 wires `app_opened` capture now, in this story, from `apps/mobile/src/app/_layout.tsx`.
- **Beta-gym support-ticket-free weeks** — this is the one genuinely different case. This story's research confirmed **there is no support-ticket feature anywhere in this codebase**, current or planned in any epic — the PRD's own Success Metrics table (Section 3.2, "Founder-intervention rate per gym/week") is the only place "support ticket" appears at all, and G-7's text ("staff itself... with no support ticket") frames this as founder-support happening *outside* the product (e.g. a beta-gym owner calling/messaging the founder directly), not an in-app ticketing system. There is nothing to hook into in-app. This story's reading: the "hook" this metric needs is simply that **every captured event carries `gymId`**, so that whenever/if a support-interaction log is ever built (in GymOS or, more likely, external — a spreadsheet, a WhatsApp thread log), it can be joined to PostHog activity data by gym and week. Both `staff_created` and `app_opened` already carry `gymId` per Tasks 4/6, satisfying this reading. **Do not build a support-ticket stub, table, or event for this AC** — that would be scope invention with no source-document backing. If the user disagrees with this reading during review, that's a scope clarification to raise, not something to have guessed further on.

### Latest Technical Information

- `posthog-js` (client) + `posthog-node` (server) — the standard split for a Next.js App Router app capturing both client-side (page views, UI interactions) and server-side (Server Action-originated) events. Do not add `@posthog/next` (Task 3 — unjustified extra abstraction for this codebase's `{data,error}` Server Action pattern).
- `posthog-node`'s short-lived-serverless-function guidance: explicitly flush after each capture rather than relying on a background timer, since a Vercel function invocation can end before a timer-based flush fires. Since this codebase's Server Actions are always awaited to completion by their callers, an explicit `await flush()` immediately after `capture()` inside the same async call is sufficient — no `waitUntil()`/background-task mechanism needed.
- `posthog-react-native` on Expo requires its documented peer-package set (`expo-file-system expo-application expo-device expo-localization`) alongside the core package — installing only `posthog-react-native` misses device/session-context enrichment the SDK expects, per Expo's own PostHog integration guide.
- PostHog + Next.js App Router: default `capture_pageview: true` only fires once at SDK init and does not re-fire on client-side route transitions — a known, current gotcha, not an edge case to skip. Disable the default and capture pageviews manually on route change if pageview tracking is included in this story's client-init work.
