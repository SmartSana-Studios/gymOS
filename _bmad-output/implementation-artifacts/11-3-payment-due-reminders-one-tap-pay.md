# Story 11.3: Payment-Due Reminders & One-Tap Pay

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a gym Owner,
I want to be notified when my platform subscription payment is due, with a one-tap way to pay,
so that I never lose access to GymOS because I missed a bill I didn't know about.

**Context — read this before touching any AC below.**

**What already exists and must not be rebuilt:**
- Story 11.1 shipped `saas_billing_payments` (Super-Admin-only RLS, `gym_id`/`amount`/`currency`/`status`/`provider`/`provider_transaction_ref`/`provider_fee_amount`), `PaymentProvider`'s `{type:'platform'}` routing context, `TaraMoneyProvider.ts`'s already-real `{type:'platform'}` `initiate()` branch (reads `TARAMONEY_API_KEY`/`TARAMONEY_BUSINESS_ID`/`TARAMONEY_WEBHOOK_SECRET`, live-verified against GymOS's own `9FmIZg9GBB` account since Story 4.10) and its webhook-verification platform-match branch, and `payment-webhook/index.ts`'s receive-route dispatch to `saas_billing_payments` on a verified webhook. **None of this needs to change.**
- Story 11.2 shipped `gyms.saas_billing_status`/`saas_billing_interval`/`saas_billing_anchor_date`/`saas_grace_period_days`, the `run_saas_billing_lifecycle_job()` nightly clock (`active → past_due` at `anchor_date < current_date`, i.e. day+1; `past_due → grace_period` at `anchor_date + 5 < current_date`, i.e. day+6; `grace_period → suspended` at `anchor_date + 5 + saas_grace_period_days < current_date`), and the `protect_super_admin_only_gym_columns()` trigger's `app.saas_billing_lifecycle_job_bypass` GUC (exempts exactly `status`/`saas_billing_status` from pin-back when set).
- **Two gaps 11.2's own Dev Notes explicitly left for this story, confirmed still open by reading the current migration:** (1) `complete_verified_saas_billing_payment()` (0069) has **no side effect at all** today — a successful Flow B webhook currently just flips the payment row to `verified` and does nothing to the gym. This story must add the reset (`saas_billing_status` → `active`, `status` → `active` if it was `suspended`/pinned by the billing clock, `saas_billing_anchor_date` advanced forward one `saas_billing_interval`). (2) Nothing yet creates a `saas_billing_payments` row on any schedule or user action — Story 11.2 deliberately stayed a pure `gyms`-table clock. This story is where a row is actually created, at the moment the Owner taps "Pay Now" — matching how Flow A's `payments` rows are created at `initiate()` time (Story 4.2), not pre-created by a cron job.
- **`handleInitiate()`'s own Story 11.1 Dev Notes flagged this exact gap:** "`handleInitiate()`... still only ever constructs `{type:'gym', gymId: paymentRow.gym_id}` by reading from the `payments` table... this story does not add a platform-initiating caller (that's Story 11.3's job, which will need its own route/lookup shape since it initiates against `saas_billing_payments`, not `payments`)." **This story is that caller.**

**The two real design problems this story must solve (read in full — this is the crux of the story):**

**1. How does an Owner's own dashboard session get a `processing` `saas_billing_payments` row into existence, safely?** `saas_billing_payments` has exactly one RLS policy (`super_admin_read_saas_billing_payments`, SELECT-only) — no role can INSERT it directly. Mirroring Story 4.15's already-accepted resolution for the analogous Flow A problem (`initiate_member_payment()`): a new `SECURITY DEFINER` RPC, `initiate_saas_billing_payment()`, self-scoping via `private.gym_id()` (never a client-supplied gym id), resolving the gym's own `tier_id → tiers.monthly_price/annual_price` (keyed off `gyms.saas_billing_interval`, live at call time — no proration, matching Story 11.2's Task 3 no-proration precedent exactly) and `active_payment_provider()`, then inserting the row itself and returning its id. Because it's `SECURITY DEFINER`, no new RLS policy is needed.

   **Do not copy `initiate_member_payment()`'s exact role-check line.** That function (Story 4.15, predates AD-3) reads `(auth.jwt() ->> 'app_role') = 'member'` directly — the *retired* pattern. **AD-3's text describes a CI grep-lint gate forbidding new `auth.jwt() ->> 'app_role'` call sites, mirroring the i18n hardcoded-string gate's shape — confirmed at this story's writing time that gate is NOT yet actually wired into `.github/workflows/ci.yml` (grepped, no match; the i18n gate it's meant to mirror does exist there, e.g. `pnpm run check:i18n`). Do not rely on CI catching this — AD-3's rule is binding regardless of enforcement automation, and if the gate does land before/during this story's implementation, a new `auth.jwt()->>'app_role'` call site would fail it anyway.** `initiate_saas_billing_payment()` must call `private.current_member_role() = 'owner'` instead (live lookup, already exists since Story 9.1/AD-3, no new helper needed). Manager/Supervisor/etc. must not be able to trigger a platform charge — this is explicitly Owner-only per the story's own "As a gym Owner" framing and FR-133/FR-135's exclusive Owner-facing wording.

**2. Where does the "one-tap Tara Money payment link" sent over SMS/WhatsApp actually land, and what does "one-tap" mean given Tara Money's real API shape?** `TaraMoneyProvider.ts`'s `initiate()` for Cameroon MTN/Orange returns no redirect URL (`authUrl` is Wave-only, never populated for Cameroon) — it triggers a USSD push directly to the phone number passed in the API call. A payment can only be *initiated* by an authenticated call carrying the Owner's own gym context (problem 1 above); there is no way to make a bare SMS link itself trigger a real mobile-money charge without landing somewhere that can call `initiate_saas_billing_payment()`.

   - **Rejected: an unauthenticated, signed-token payment link** (e.g. `/pay/<signed-token>` bypassing login). Doable, but opens a new unauthenticated financial-action surface this codebase has never needed before (Flow A's own self-service equivalent, Story 4.15, requires the member to already be logged into the app) — a real security-surface expansion for a "nice to skip one login" convenience, contradicting AD-1's "RLS is the sole tenancy/authorization layer" spirit (a signed token would become a second, parallel authorization mechanism).
   - **Recommended: the link points to the Owner's existing, already-authenticated dashboard** (`{DASHBOARD_APP_URL}/settings`, the exact same env var and "send a plain dashboard link, no token" pattern Story 9.2's `resendStaffTempPassword`/Story 1.5's owner-activation message already use). If the Owner isn't logged in, the dashboard's own existing auth redirect handles that (no new code) — from the Owner's perspective this is still "one tap" once they're in: a single "Pay Now" button in a new Billing section of the existing Settings page (`apps/dashboard/app/(dashboard)/settings/SettingsForm.tsx`), which already hosts every other Owner-facing gym-level control (branding, payments connection, staff). No new route needed.

**Third gap, orthogonal to the two above — Owner notification email has no capture path today.** `members.email` (the column FR-020 already defined for member records) already exists and is nullable — Owner accounts are `members` rows too (`role = 'owner'`, per AD-6's hierarchy), so **no new column is needed**. But `insertOwnerMember()` (`apps/super-admin/app/(admin)/gyms/actions.ts`) only ever sets `name`/`phone` at gym-creation time, and **no RLS policy lets an Owner update their own `members` row at all** — `manager_or_owner_update_own_members` (0018) explicitly restricts its `with check` to `role = 'member'` rows (i.e., it lets a Manager/Owner edit *other* members, never their own Owner row). This story adds the missing narrow write path: a second new `SECURITY DEFINER` RPC, `update_own_owner_notification_email(p_email text)`, self-scoping via `auth.uid()` + `private.current_member_role() = 'owner'`, touching only `members.email` for the caller's own row — deliberately an RPC, not a raw RLS UPDATE policy, since a raw policy has no clean way to restrict which *columns* an Owner can touch on their own row without a second pin-back trigger (this codebase's established RPC-for-narrow-writes convention, e.g. `initiate_member_payment()`, `switch_active_gym()`, is the simpler fit here).

**Fourth, flagged and deliberately deferred, not silently skipped: no transactional email provider exists in this stack.** `prd.md` FR-135/addendum §A are explicit — email is "a best-effort third channel until that provider is selected and integrated," and V1.0/V1.5's stack table lists none. This story ships the *capture* (the RPC/UI above) so the field exists and the reminder job's own logic branches on "email on file or not" (satisfying the AC's literal conditional), but the actual send is coded as an explicit no-op with a `saas_billing_notices.email_status = 'skipped_no_provider'` record — never a silent gap, never a thrown error, and never invented email-sending code against a provider this stack doesn't have. Do not integrate a real email provider in this story.

**Fifth — the scheduling mechanism is new to this codebase, flagged for confirmation before Task 2 starts.** Every existing scheduled job (`run_subscription_lifecycle_job`, `run_saas_billing_lifecycle_job`, the push-notification dispatch jobs) is a `pg_cron`-invoked Postgres function (AD-19). But the actual channel sends this story needs (Evolution API WhatsApp, Twilio SMS) require credentials that **only exist as Deno/Node runtime env vars** (`EVOLUTION_API_KEY`, `TWILIO_ACCOUNT_SID`/`AUTH_TOKEN`) — never in Postgres/Vault (AD-15's Vault-encryption pattern is scoped to *per-gym payment* credentials specifically, not platform messaging credentials). A pure-SQL `pg_cron` + `net.http_post` job (the pattern `0045_subscription_lifecycle_notifications.sql` uses to call Expo's push API directly) cannot carry these secrets. **Recommended: the project's first Vercel Cron job** — `apps/dashboard/vercel.json`'s `crons` array triggers a new authenticated API route (`apps/dashboard/app/api/cron/saas-billing-reminders/route.ts`) once daily, which queries `gyms` directly via a service-role client, computes which gyms are due for a notice today, and calls the two Node-side send helpers (Task 3) directly — the exact runtime where `EVOLUTION_API_BASE_URL`/`EVOLUTION_API_KEY` and `TWILIO_ACCOUNT_SID`/`TWILIO_AUTH_TOKEN` already live (confirmed: `apps/dashboard/lib/messaging/EvolutionApiMessageProvider.ts` already reads the former via `process.env` today for Story 2.10's member-invite send). This is a genuine, deliberate architectural divergence from AD-19's all-`pg_cron` convention — **confirm this reading holds at dev-story time before building Task 2**; the alternative (a new 4th Edge Function invoked by `pg_cron`/`net.http_post`, `ARCHITECTURE-SPINE.md`'s own text explicitly allows a 4th "with a deliberate AD") duplicates Evolution/Twilio-calling code a third time (Deno OTP-shaped, Node free-text, now Deno free-text) for no clear benefit over reusing what already runs in Node. If rejected in favor of the Edge Function path, get explicit sign-off first — it changes Task 2/3's file locations, not their logic.

## Acceptance Criteria

1. **Given** my gym's billing anchor date, **when** it arrives, **then** I receive a payment-due notice with a one-tap Tara Money payment link, sent via both SMS and WhatsApp (both fire — not a fallback chain, since missing this notice risks suspension), reusing the Evolution API/Twilio infrastructure from FR-118. [Source: epics.md#Story 11.3; prd.md#FR-133, FR-135]
2. **Given** I have an email on file (a new optional field on my Owner account, mirroring FR-020's optional member email), **when** the notice is sent, **then** email is attempted as a best-effort third channel — SMS and WhatsApp remain the guaranteed channels regardless of email delivery success. [Source: epics.md#Story 11.3; prd.md#FR-135]
3. **Given** I don't pay by the due date, **when** the reminder schedule runs, **then** I receive re-sent notices on the default 1/3/5-day-after-due schedule before my gym moves to `grace_period`. [Source: epics.md#Story 11.3; prd.md#FR-133]
4. **Given** every notice sent and payment attempt made, **when** they occur, **then** each is recorded, giving GymOS a complete audit trail of the billing conversation with each Owner. [Source: epics.md#Story 11.3; prd.md#FR-135, FR-080]
5. **Given** I am never auto-debited (mobile money doesn't support it, OQ-14 resolved), **when** I receive any payment-due communication, **then** the copy is explicit that I must take action to pay — no language implies an automatic charge is coming. [Source: epics.md#Story 11.3; prd.md#FR-133; EXPERIENCE.md's "SaaS payment reminder" Voice and Tone row]

## Dev Notes

- **This is the largest story in Epic 11 so far** — it touches 3 layers (DB/RPCs, a new Node-runtime scheduled job, dashboard UI) and introduces one genuinely new architectural pattern (Vercel Cron, Context section point 5). Read the Context section in full before starting any task; it contains the reasoning for every non-obvious design choice below, not just a summary.
- **AD-3 is binding on both new RPCs in this story.** `initiate_member_payment()` (Story 4.15) and `check_in()` (Story 3.4) both predate AD-3 and are grandfathered — do **not** copy their `auth.jwt() ->> 'app_role'` line into `initiate_saas_billing_payment()` or `update_own_owner_notification_email()`. Use `private.current_member_role()` (already exists, live since Story 9.1). AD-3's text describes a CI grep-lint gate for this, but it is **not yet wired into `.github/workflows/ci.yml`** as of this story's writing (confirmed by grep) — compliance is manual/code-review-enforced for now, not automated; don't assume a red CI check will catch a mistake here.
- **Two separate bypass GUCs, not one shared.** Story 11.2's `app.saas_billing_lifecycle_job_bypass` (exempts `status`/`saas_billing_status`) and this story's new `app.saas_billing_payment_reset_bypass` (exempts `status`/`saas_billing_status`/`saas_billing_anchor_date`) are deliberately separate names even though both exist to let a no-session system writer through the same trigger — keeps each system writer's exemption independently provable/testable, matching the trigger's own established "narrow to exactly what this specific write touches" discipline applied per-caller.
- **`saas_billing_notices` lives in `public`, not `private`, unlike every prior push-notification dispatch/delivery table** — this is a deliberate divergence, not an oversight; the reasoning (Node-runtime writer vs. Postgres-trigger writer) is in Task 1 above. If a future story ever moves the actual send logic into Postgres/pg_net, revisit whether `private` becomes the better fit at that point — don't preemptively build for that now.
