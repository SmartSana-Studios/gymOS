# Story 11.2: SaaS Subscription Lifecycle & Free/Test Tier

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As GymOS,
I want each gym's platform subscription to progress through its own lifecycle independent of member subscription states,
so that billing status and gym-access status are cleanly separable concepts.

## Acceptance Criteria

1. **Given** a gym on a paid tier, **when** its billing lifecycle runs, **then** it progresses `active` → `past_due` (missed notice or failed charge; gym stays operational, reminders begin) → `grace_period` (retries exhausted; Super-Admin-configurable window, default 7 days; "renew to avoid suspension" banner shown to Owner) → `suspended` (grace elapsed).
2. **Given** a mid-cycle SaaS tier change, **when** it is applied, **then** the new price takes effect at the next billing cycle — no proration (OQ-15, resolved).
3. **Given** the existing three tiers (Hustle/Grind/Elite), **when** the Free/Test tier is added (FR-139, amending FR-073), **then** it has a Super-Admin-configurable member cap and monthly/annual price fixed at 0 XAF; assigning a gym to it is a tier change like any other, and the full billing reminder/reconciliation machinery still runs at the 0 XAF price point so those code paths stay exercised during the beta.

  - [x] **Security-critical — extend the existing column-protection trigger.** `owner_update_own_gym` (`0014_gym_settings_owner_access.sql`) gives every gym Owner row-level UPDATE access to their own `gyms` row. That migration's own comment already identifies the risk this creates and fixes it with a `BEFORE UPDATE` trigger, `private.protect_super_admin_only_gym_columns()`, which pins `status`/`tier_id`/`member_cap_override` back to their old values for any non-Super-Admin session (RLS is row-level, not column-level, and the app's own `updateGymSettings` allow-list is not a substitute for a DB-level guard against a direct/bypass write). **The four new columns above are exactly this same class of Super-Admin-exclusive column and must be added to that trigger's pin-back list** — without this, an Owner could self-modify `saas_billing_status` back to `'active'` via a raw `supabase-js` update, silently defeating the entire billing lifecycle this story builds:
    ```sql
    create or replace function private.protect_super_admin_only_gym_columns()
    returns trigger
    language plpgsql
    set search_path = public
    as $$
    begin
      new.created_at := old.created_at;
      if not private.is_super_admin() then
        new.status := old.status;
        new.tier_id := old.tier_id;
        new.member_cap_override := old.member_cap_override;
        new.saas_billing_status := old.saas_billing_status;
        new.saas_billing_interval := old.saas_billing_interval;
        new.saas_billing_anchor_date := old.saas_billing_anchor_date;
        new.saas_grace_period_days := old.saas_grace_period_days;
      end if;
      return new;
    end;
    $$;
    ```
    `create or replace function` — the trigger itself (`protect_super_admin_only_gym_columns` on `gyms`) does not need to be recreated, only the function body.

## Dev Notes

- **Scope boundary — this story does not touch `saas_billing_payments` at all.** Story 11.1's own Dev Notes guessed that "Story 11.2 owns... actually writing `saas_billing_payments` rows on a schedule" — this story's research (epics.md's actual Story 11.2 ACs, verbatim above) found no AC requiring that. The cleaner reading, consistent with Story 11.1's "resist building ahead" discipline: this story is a pure `gyms`-table clock (mirrors `run_subscription_lifecycle_job()`'s pure `subscriptions`-table clock, Story 3.1); Story 11.3 ("Payment-Due Reminders & One-Tap Pay") is where a `saas_billing_payments` row is actually created, at the moment the Owner taps "pay" or a reminder fires — matching how Flow A's `payments` rows are created at `initiate()` time (Story 4.2), not pre-created by a cron job. If dev-story disagrees after re-reading the epic, that's a legitimate call to revisit, but don't silently split the difference — pick one and document why.
- **Known gap this story deliberately leaves for Story 11.3: nothing resets `saas_billing_status` back to `'active'` on a successful payment.** FR-132/AC of Story 11.4 require "a successful SaaS payment restores access immediately," which needs `gyms.saas_billing_status` (and `gyms.status`, and `saas_billing_anchor_date`, advanced forward one interval) to reset — but that reset naturally belongs beside whichever story wires payment completion (Story 11.1's `complete_verified_saas_billing_payment()` RPC currently has no side effect by design; Story 11.3 is the natural owner of adding one). Do not build the reset path in this story — it would be guessing at Story 11.3's exact shape. This gap is safe to leave open short-term per Task 4's operational-flag note (weeks of runway before any gym is actually affected).
- **`private.current_gym_status()` already exists and is already live** (`0063_staff_edit_deactivation.sql:19`, added for Story 9.3) — this story does not need to create it, only make sure `gyms.status` ends up `'suspended'` at the right time for it to read. Story 11.4 owns wiring it more broadly into the JWT claims hook / general RLS.
- **The `owner_update_own_gym` + `protect_super_admin_only_gym_columns` trigger pattern (`0014_gym_settings_owner_access.sql`) is the single most important precedent in this story** — re-read it in full before Task 1. Every new Super-Admin-exclusive column this story adds to `gyms` MUST go into that trigger's pin-back list; forgetting one is a real access-control bypass, not a cosmetic gap.
- **Enum/column reuse discipline** (established by Story 11.1's `payment_status` reuse and this codebase's Consistency Conventions table): `saas_billing_interval` reuses the existing `billing_interval` enum rather than inventing a parallel one; `saas_billing_status` is a **new** enum despite 3 of 4 values overlapping with `subscription_status`, because the fourth value (`suspended` vs. `expired`) and the underlying entity (gym vs. member subscription) are genuinely different — conflating them would be the wrong kind of reuse.
- **Free/Test tier is one seeded row, not a general "locked tier" mechanism.** `price_locked` exists to enforce FR-139's "fixed at 0 XAF" for this one specific tier; nothing in this story adds UI for Super Admin to create additional price-locked tiers via the normal Add Tier flow (`createTier` doesn't accept `priceLocked` as user input) — out of scope, FR-139 describes exactly one Free/Test tier.
- **Naming/conventions** (`ARCHITECTURE-SPINE.md`'s Consistency Conventions table): snake_case columns, RPCs as snake_case `verb_noun()` (`run_saas_billing_lifecycle_job`), soft/lifecycle state as an enum column (not booleans), `idx_<table>_<column>` if any new index is needed (none required by this story's own queries — `gyms.saas_billing_status`/`saas_billing_anchor_date` are read by a nightly batch job scanning the whole small `gyms` table, not a per-request lookup, so no new index is justified; add one only if `EXPLAIN ANALYZE` during dev-story shows it's needed).
