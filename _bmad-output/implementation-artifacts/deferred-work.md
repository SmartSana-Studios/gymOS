## Made outside story scope: action-menu trigger styling, sidebar sticky-position fix, password-reset double-submit fix (2026-08-21)

- **User-requested UX change to the just-shipped action-menu trigger, not tied to any tracked AC:** `spec-action-button-dropdown-consolidation.md`'s icon-only `variant="ghost" size="icon"` `MoreVertical` trigger (with an `aria-label`/`title` for discoverability) was found insufficiently discoverable during manual QA — user feedback: "just : is not enough... make it a full button." Changed to `variant="outline" size="sm"` with visible text content (`t("<page>.actions.button")`, literal string `"Action :"` in both `en.json`/`fr.json`) followed by the same `MoreVertical` icon, across all 4 files (`MembersPageClient.tsx`, `StaffPageClient.tsx`, `PaymentsPageClient.tsx`, `PlansPageClient.tsx`). `aria-label` retained unchanged (still the per-row `"Actions for {{name}}"` string) for screen-reader context beyond the now-generic visible text; the redundant `title` tooltip was dropped since the label is now always visible. New i18n keys: `members.actions.button`/`staff.actions.button` (nested, matching those namespaces' existing `actions` object) and `payments.actionsButton`/`plans.actionsButton` (flat, matching those namespaces' shape) — same nesting-convention split already established for the `menu`/`actionsMenu` aria-label keys in the original spec.

- **Real bug found during the same manual QA session, unrelated to the dropdown work: `DashboardChrome`'s sidebar scrolled away with page content instead of staying pinned.** `Sidebar.tsx`'s `<aside>` had no bounded height or position (`"hidden shrink-0 md:block md:w-16 lg:w-60"`), so as a flex item inside `DashboardChrome`'s `min-h-screen` row it stretched to match the main content column's full height (default flex `align-items: stretch`) rather than staying capped to the viewport — `SidebarContent`'s own internal `overflow-y-auto` on its `<nav>` had no effect since the parent `<aside>` was never height-constrained in the first place. Fixed: `<aside className="sticky top-0 hidden h-screen shrink-0 md:block md:w-16 lg:w-60">` — `h-screen` caps it to the viewport (beating the stretch), `sticky top-0` pins it as the page scrolls.

- **Real, reproducible bug found during the same session: the forced first-login "must change password" flow (Story 1.11 AC #5) could present itself twice in a row, the second attempt always failing with GoTrue's own "New password should be different from the old password."** Root cause confirmed by inspecting `apps/dashboard/components/update-password-form.tsx` and the live DB state (the affected test account's `users.must_change_password` was already correctly `false`, proving the first submission *had* succeeded): `handleForgotPassword`'s `finally { setIsLoading(false) }` ran immediately after firing `router.push("/")` — which only starts a client-side navigation, it doesn't wait for it — re-enabling the still-mounted form's submit button (and leaving the password `<Input>` enabled) for however long the `(dashboard)` layout's redirect check took. A user who didn't perceive an instant page change would resubmit the same password into the still-live form, which GoTrue then correctly rejected as identical to the password it had just accepted moments earlier. **Fix:** removed the `finally` block; `isLoading` (and now also the `<Input>`, via a new `disabled={isLoading}`) is only reset on the error/early-return paths that keep the user on this page — never on the success path, so the form stays fully disabled through the entire redirect transition and a resubmission is no longer possible.

- **Clarification, not a bug, recorded for future reference:** user asked whether the member-invite "share via WhatsApp" manual modal (`InviteMemberModal`, Story 2.10) being visible meant invites weren't being sent through the automated Evolution API provider. Confirmed working as designed (AD-12): `handleSendInvite` always attempts the automated send first; the manual modal is the deliberate fallback for a `sent: false` result, not a leftover manual-only path. In this local sandbox specifically, `messaging_provider_config.instance_id` is `null` (no Evolution API instance configured for local dev — normally set via the Super Admin `/messaging` page), so every automated attempt fails immediately and the fallback fires every time; this is expected in this environment and does not indicate a broken pipeline in a real deployment with a configured, paired instance.
