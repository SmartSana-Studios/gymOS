# Story 2.4: CSV Member Import

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a Manager or Owner,
I want to bulk-import members via a standardized CSV template,
so that I can onboard an existing member base without manual entry.

## Acceptance Criteria

1. **Given** the CSV Import modal, **when** I download the template and upload a filled CSV, **then** all rows are validated before any are written. [Source: epics.md#Story 2.4]
2. **Given** any row fails validation (e.g., invalid phone format, unconfigured plan_type, missing expiry_date for a non-session plan), **when** I submit, **then** the entire import is rejected, zero records are written, and each failing row shows its row number and reason. [Source: epics.md#Story 2.4, prd.md#FR-008]
3. **Given** a CSV with all rows valid, **when** I confirm the import, **then** all members are created with a clean history (no historical payments/attendance migrated). [Source: epics.md#Story 2.4, prd.md#FR-009]

## Scope Note — Read Before the Tasks

This story reuses almost all of Story 2.3's schema, RLS, and member-provisioning machinery — no new migration, no new table, no new RLS policy. What it adds is a batch validation/orchestration layer on top. Ten decisions below, each forced by a real gap discovered while researching this story — read before writing code.

1. **The CSV's `plan_type` column is a plan *name* lookup, not the `plan_type` enum.** FR-008's template lists a column literally named `plan_type`, and AD-07's own per-row rule table says it must "match a plan configured for this gym (case-insensitive)" with the example error `Plan "Premium" is not configured for this gym`. "Premium" is not one of the four `plan_type` enum values (`pay_per_session`/`monthly`/`coach_inclusive`/`class_only`) — it's an example of a gym-specific plan *name* (Story 2.2's `plans.name`, unique per gym via `idx_plans_gym_name_unique`). A gym can have multiple plans sharing the same `plan_type` enum value (e.g. two different "monthly" plans at different prices), so matching by enum alone would be ambiguous about which specific plan to assign — only a name match resolves to exactly one plan. Resolve each row's `plan_type` CSV value against `listPlans()`'s (`apps/dashboard/services/plans.ts`) already-existing per-gym result, matching case-insensitively, exact string (no wildcards — mirrors `planNameExists`'s existing `.ilike("name", escaped)` call with no `%` added).
2. **No new migration, table, or RLS policy.** CSV import's actual writes go through the exact same `members`/`subscriptions` INSERT paths Story 2.3 already built and RLS-protected (`manager_or_owner_insert_own_members`/`manager_or_owner_insert_own_subscriptions`, `enforce_member_cap`, `enforce_subscription_expiry_matches_plan_type`, all in `0018_member_management.sql`). This story adds zero new persisted state — do not create a `csv_import_jobs` table or any tracking table (see Decision 3 for why).
3. **The ">100 records" progress-polling indicator (AD-07, UX-DR9) is scoped down to an indeterminate spinner, not real "X of Y" polling.** AD-07's mockup shows "Importing 43 of 450 members…" with real-time counts. Building that literally needs out-of-request background execution (the synchronous Server Action that performs the import would have to keep running after the response is sent, e.g. via Vercel's `waitUntil()`) plus a persisted progress row a second Server Action can poll, plus a client-side polling library (`@tanstack/react-query`, named in `architecture.md` for exactly this feature but not yet a dependency of `apps/dashboard`). Given this platform's pilot scale (NFR-009: ~30 members per gym across 1-3 gyms), a >100-row import is already outside realistic V1 usage, and building real background-job infrastructure for an effectively unreachable case is disproportionate — consistent with this project's own repeated "not justified at current scale" deferrals (see `deferred-work.md`). **Resolution:** `confirmCsvImport` runs synchronously inside one Server Action call, exactly like `createMember`'s existing orchestration, just looped per row. The UI shows a plain "Importing…" spinner while the action is in flight; for >100 rows, show "Importing… this may take a moment" (still indeterminate — no fabricated running count, since none is available in this architecture). Do not add `@tanstack/react-query` or any job/progress table for this story.
4. **CSV parsing is hand-rolled, not a new dependency.** No CSV parsing library exists anywhere in this monorepo (confirmed via `apps/dashboard/package.json`), and the template is a fixed, well-defined 6-column shape. Write a small RFC4180-subset parser (`apps/dashboard/lib/csv.ts`, pure function: `parseCsvRows(text: string): string[][]`) supporting quoted fields (embedded commas/newlines, `""`-escaped quotes) and both `\n`/`\r\n` line endings — enough for real-world Excel/Sheets exports, without pulling in a library.
5. **Header matching is by column name, not position.** The 6 expected column names (`member_name, phone, plan_type, join_date, subscription_status, expiry_date`, verbatim from FR-008) must all be present in the uploaded file's header row, in any order; extra/unrecognized columns are ignored. Build a name→index map from the header row rather than assuming fixed column positions — more forgiving of a user who reorders columns in Excel, and the AD-07 mockup never claims order is significant, only that the columns exist.
6. **Per-row validation reuses `createMemberSchema`'s cross-field invariants conceptually, but as its own schema with AD-07's exact copy.** `createMemberSchema` (Story 2.3, `packages/types/src/schemas/member.ts`) validates the same underlying fields but with different error strings (e.g. "Enter a valid phone number" vs. AD-07's "Invalid format — expected E.164 (e.g. +237...)") and a `planId` (uuid) field this CSV flow doesn't have yet at the schema-parsing stage (plan resolution is a separate, DB-dependent step — see Decision 1). Add a new `csvMemberRowSchema` in `packages/types/src/schemas/csvImport.ts` structurally mirroring `createMemberSchema` (same `e164Phone`/date-string-comparison discipline, same expiry-vs-join-date and status-vs-expiry-date `.refine()`s) but with a `planName: string` field (not `planId`) and AD-07's own per-column error copy. This is deliberate duplication, matching this codebase's own "no shared cross-file consts, redeclare per file" convention already established across `gym.ts`/`plan.ts`/`tier.ts`/`member.ts`.
7. **Two validations not in AD-07's literal per-row table, both necessary for a coherent "all rows validated before any written" pass (AC #1):** (a) a phone number repeated across two rows of the same CSV — without this check, both rows would resolve to the same platform user via `findOrCreateUserByPhone`'s existing find-or-create, and the second row's `members` insert would fail the `idx_members_active_gym_user` constraint (mapped to `member_already_active_at_gym`) — but only *during* the write phase, defeating AC #1's "before any are written" guarantee. Detect in-file duplicates with a plain `Set` over normalized phone values during Step 1 validation. (b) a phone that already belongs to an active member at this gym (queried once, batched: `.in("phone", allCsvPhones)` scoped to the caller's gym — not one query per row) — reuses the exact `members.errors.memberPhoneTaken` copy Story 2.3 already added to `packages/types/src/locales/{en,fr}.json`, for the same real-world condition (AD-05's own "This phone number is already registered" rule), just surfaced per-row here instead of per-field.
8. **A batch-level member-cap fast-fail runs before any row is written**, mirroring `createMember`'s existing two-layer cap defense (Scope Note #4/#7 of Story 2.3: `memberCountForGym()` fast-fail + `enforce_member_cap` DB trigger backstop) but scaled to the whole import: call the existing `memberCountForGym()` once, and if `cap !== null && count + validRowCount > cap`, reject the entire import upfront with a friendly message before attempting any insert — much better UX than discovering the cap mid-loop after already committing (and having to roll back) N members. The trigger remains the real backstop for the race window between this check and the writes.
9. **`createMember`'s existing 3-step provisioning orchestration (find-or-create user → insert member → insert subscription, with compensating cleanup) is extracted into a new shared `provisionMemberRow()` function in `apps/dashboard/services/members.ts`**, called by both the refactored `createMember` Server Action and this story's new per-row CSV import loop — avoiding a ~40-line duplicate of the delicate compensating-cleanup logic (`findOrCreateUserByPhone` → `insertMember` → `insertSubscription`, deleting the just-created member if the subscription insert fails, deleting a freshly-provisioned auth user if the member insert fails). This is a deliberate, sanctioned touch to Story 2.3's `actions.ts`/`members.ts` — not scope creep — the alternative is copy-pasting that exact orchestration block into this story's own loop.
10. **All-or-nothing at the batch level requires tracking successes across the loop, not just per-row.** `provisionMemberRow()` already cleans up *its own* partial failure (e.g. member insert succeeds, subscription insert fails → that one member row and its freshly-created auth user, if any, are deleted). What it does not do — because it doesn't know about the batch — is undo *earlier, fully-successful* rows if a *later* row in the same CSV import fails. The confirm loop must track each successful row's `{ memberId, authUserCreated }` and, on any later failure, loop back through all prior successes calling the existing `deleteMemberForCleanup`/`deleteAuthUserForCleanup` (conditionally, only when `authUserCreated` is true — never delete a reused account, same rule as Story 2.3's own single-create cleanup) before surfacing AD-07's exact copy: "Import failed. No records were saved (all-or-nothing). Fix and re-import."

## Dev Notes

- **This story adds no new persisted state.** No migration file, no new table/column/trigger/RLS policy (Scope Note #2) — everything writes through Story 2.3's existing `members`/`subscriptions` INSERT paths and their existing RLS/triggers (`0018_member_management.sql`). If implementation reveals a genuine need for schema change, stop and reconsider — that would mean a Scope Note assumption above was wrong.
- **The CSV's `plan_type` column is a plan-name lookup (Scope Note #1) — this is the single most consequential, non-obvious decision in this story.** Get this wrong (matching against the `plan_type` enum instead of `plans.name`) and multi-plan-per-type gyms will silently get members assigned to the wrong specific plan (wrong price/duration) with no error, since an enum match would succeed even when the "correct" plan was ambiguous.
- **`provisionMemberRow()`'s extraction (Task 4) must not change `createMember`'s observable behavior.** It is a pure relocation of already-shipped, already-reviewed (Story 2.3, two review rounds) orchestration code — resist the temptation to "clean up" or alter its cleanup semantics while moving it.
- **AD-07's ">100 records" progress copy is deliberately not built as literal real-time polling (Scope Note #3)** — if a future story needs real background-job progress (e.g. once a real job queue exists for some other feature), revisit this decision rather than retrofitting a one-off queue just for CSV import.
- **CSV row numbers shown to the user are 1-indexed including the header row** (Excel's own convention) — row 2 is the first data row, not row 1. Get this off-by-one right; AD-07's example errors ("Row 3", "Row 7", "Row 12") are what a gym manager would see counting rows in their own spreadsheet app, not a 0-indexed array position.
- **`i18next/no-literal-string` ESLint gate + `check-i18n-key-parity.mjs`** — same CI-gate discipline as every prior Epic 1/2 story; run both before marking `review`.
