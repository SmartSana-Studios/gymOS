# Story 6.4: Notification Preferences

Status: done

<!-- Ultimate context engine analysis completed - comprehensive developer guide created. -->

## Story

As a member,
I want to control which non-critical notifications I receive,
so that I'm not overwhelmed with alerts I don't want.

## Acceptance Criteria

1. **Given** a member record, **when** it is created, **then** a corresponding `member_preferences` row is created automatically (one-to-one with `members`, not `users` — a platform user with memberships at multiple gyms gets one preferences row per gym, matching FR-076's "stored per member" and the architecture's `members (1) ──< member_preferences` relationship), defaulting every non-critical category to opted-in (`false` = not opted out).
2. **Given** the member's own `member_preferences` row, **when** they view Profile (MA-12) in the mobile app, **then** they see a "Notifications" section listing the two V1.5 non-critical categories named in FR-075/PRD §Notification Schedule Table — Quiet-gym alerts (N-06) and Class reminders (N-07) — each as an independent toggle reflecting its current opt-out state.
3. **Given** either toggle, **when** the member switches it, **then** the change persists to their own `member_preferences` row immediately (optimistic UI update, same pattern as the existing Language toggle on the same screen: revert the toggle on a failed persist, no separate error toast).
4. **Given** N-01–N-05 (mandatory lifecycle and payment notifications, Stories 6.2/6.3), **when** dispatch eligibility is evaluated for any of them, **then** `member_preferences` is never consulted — this story adds no opt-out path for mandatory notifications and makes no change to migrations `0045`/`0046`.
5. **Given** N-06 (quiet-gym alert) and N-07 (class reminder) are V1.5 features with no dispatch mechanism yet (confirmed: no notification code besides `N-01`–`N-05` exists anywhere in the codebase), **when** this story ships, **then** the opt-out state it collects has no observable effect on any notification sent today — it exists so a member's preference is already on record before V1.5 ships N-06/N-07's actual sending logic, avoiding a second onboarding/re-ask when that logic lands.
6. **Given** a member attempts to write to another member's `member_preferences` row, or to change their own row's `member_id`/`gym_id` via a raw update, **when** the write is attempted, **then** it is rejected (RLS scope + column pin-back trigger, same discipline as `protect_self_managed_member_columns`, migration `0020`).
7. **Given** all Notifications-section copy (toggle labels, descriptions, any error text), **when** it is rendered, **then** it is available in English and French, served per the member's language preference, with zero missing keys (CI `pnpm run check:i18n` gate).

## Dev Notes

### Scope and Non-Negotiable Decisions

- **This story is the odd one out in Epic 6: it is real, mostly-inert scaffolding, not dead work.** FR-076's two opt-out-able categories (N-06 quiet-gym, N-07 class reminder) are both explicitly V1.5 (`epics.md` Epic 6 intro; PRD Notification Schedule Table). No dispatch mechanism for either exists anywhere in the codebase today, and none is added by this story. What this story delivers is real: the `member_preferences` table (with correct RLS, tenant-scoping, and self-service semantics) and a live, working Profile toggle UI that persists a member's choice *now*, so that whenever V1.5 implements N-06/N-07's actual sending logic, it only needs to add a `where not (select quiet_gym_alerts_opted_out from member_preferences where member_id = ...)` guard — no new onboarding flow, no re-asking members, no schema migration required at that point.
- **N-01–N-05 remain completely untouched.** Do not add a `member_preferences` lookup to `private.send_push_notification()` (0045) or `private.send_payment_push_notification()` (0046) — FR-076 and Stories 6.2/6.3's own ACs are explicit that mandatory notifications cannot be opted out of in V1. If you find yourself editing either of those functions or their triggers, stop — that is out of scope for this story.
- **Per-member, not per-user.** `member_preferences.member_id` references `members.id`, not `users.id` — a platform user with memberships at multiple gyms (FR-001) gets independent preferences per gym, matching the architecture's explicit `members (1) ──< member_preferences` relationship (Entity Relationships section) and because N-06 (a specific gym's occupancy) and N-07 (a specific gym's booked class) are inherently gym-scoped concepts, not account-wide ones.
- **`public` schema, not `private`.** This is a deliberate divergence from Stories 6.2/6.3's `private.notification_dispatches`/`private.payment_notification_dispatches` precedent. Those are server-internal transport ledgers no client ever reads. `member_preferences` is the opposite: a member must read and write their own row directly via `supabase-js` from the mobile app (architecture's "no custom API — apps call Supabase directly through the service layer" rule), so it needs real client-facing RLS, not a `service_role`-only grant.
- **No UX design source exists for this screen.** Neither `EXPERIENCE.md` nor `DESIGN.md` defines an MA-xx notification-preferences screen, unlike every other mobile screen this epic/product touches. Placement (a new section on the existing Profile screen, MA-12) and copy are this story's own reasonable extrapolation, following the same screen's established Language-toggle pattern — record this as a documented judgment call (Task 7), not a silently invented requirement.
- **No Edge Function, no new cron job, no change to the two-Edge-Functions boundary.** This is a plain CRUD table plus a mobile settings UI — the simplest story in the epic infrastructure-wise.

### Architecture and Security Guardrails

- Every new tenant-scoped table gets RLS enabled in the same migration as its `CREATE TABLE`, and carries a `gym_id` column even when today's policies don't filter on it directly — both are hard architecture invariants (Data Architecture / Data Boundaries sections), not stylistic choices, and every existing migration in this repo follows them without exception.
- RLS is row-level, not column-level (the recurring lesson from `protect_self_managed_user_columns` 0015 and `protect_self_managed_member_columns` 0020): a `for update using (...)` policy alone would let a member overwrite `member_id`/`gym_id` on their own row via a raw client update. The pin-back trigger is the only mechanism that can say "this column, not that one" — do not skip it because "the UI never sends those fields," since RLS must hold against any client, not just this story's own UI.
- `create_default_member_preferences()` needs `security definer` for the same reason `public.handle_new_user()` (0003) does: it writes into a different table than the one being inserted into, from a trigger context that doesn't itself carry the necessary grant. `protect_self_managed_member_preferences_columns()` does **not** need `security definer` — it only reads `auth.uid()` and the row already in scope under the caller's own RLS (same reasoning documented in 0015/0020's sibling triggers; do not copy `security definer` onto it out of caution).
- Never expose another member's preferences row shape or values in an error message or client-visible log.

### Testing Requirements

- Follow the exact pgTAP fixture pattern established in `supabase/tests/subscription_lifecycle_notifications.test.sql` and `supabase/tests/manual_payment_verification_queue.test.sql` (whichever is more directly analogous to this story's simpler CRUD-plus-RLS shape): transaction + `plan(...)`, deterministic UUIDs, direct table/policy assertions, `finish()`, rollback.
- **Highest-risk regressions, in priority order:** (1) a member reading or writing another member's preferences row (cross-member and cross-gym); (2) the pin-back trigger failing to block a `member_id`/`gym_id` spoof attempt while still allowing the two boolean columns through in the same statement; (3) a `members` insert that does not produce exactly one `member_preferences` row (breaks AC #1 for every future member creation path — CSV import, manual create, onboarding — all of which insert into `members` and must all pick up the new trigger for free without their own story needing changes); (4) the pre-existing member backfill leaving any current member without a row.
