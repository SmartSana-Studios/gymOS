# Story 4.15: Member Self-Service Renewal

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a member,
I want to renew my own subscription from the app without visiting the front desk,
so that I don't have to wait for a receptionist when my membership is expiring or has lapsed.

**Context — read this before touching any AC below.**

**What already exists and must not be rebuilt:** Story 4.14 made Flow A's routing real end-to-end — `payment-webhook`'s `handleInitiate()` resolves a gym's own connected Tara Money credentials from the `payments` row's `gym_id`, and `complete_verified_payment()` (the shared webhook-verified completion RPC, `0030_payment_initiation_and_renewal.sql:76-157`, `service_role`-only) performs the actual FR-032 subscription reset (new expiry, alert dismiss, payment-history visibility) — **already shared by every Flow A caller regardless of who initiated it.** N-04 "Payment confirmed" push notification also already fires automatically via a DB trigger on any `payments` row's first transition into `verified` (`0046_payment_notifications.sql:225-242`), independent of caller. **None of this needs to change.** This story's entire job is adding the second caller: a member's own mobile-app session.

**The core design problem this story must solve, and the recommended resolution (read in full — this is the crux of the story):**

Today only staff (`owner`/`manager`/`receptionist`) can create the `processing` `payments` row that authorizes a Tara Money charge. The `payments` table's only INSERT policy is `gym_staff_insert_own_payments` (`0031_*.sql:50-56`): `with check (gym_id = private.gym_id() and status = any(array['pending','processing']) and (auth.jwt()->>'app_role') = any(array['owner','manager','receptionist']))`. **No member INSERT policy exists.** Meanwhile, `payment-webhook`'s `handleInitiate()` (`supabase/functions/payment-webhook/index.ts:29-42`) performs **zero role/JWT checks of its own** — its own doc comment states the design premise explicitly: the RLS INSERT that got the `processing` row to exist *is* the authorization proof; `verify_jwt = false` in `supabase/config.toml:311-316` (required because this same function is also polled unauthenticated by e-ink hardware). So the only real gate to close is: how does a member's own session get a `processing` payments row into existence, safely?

Two candidate resolutions:

- **Rejected: add a member-scoped RLS INSERT policy on `payments`.** Doable in principle, but the client would still supply `amount`/`currency` directly in the INSERT payload — a `with check` clause that also validates `amount` against the member's actual plan price requires an unpleasant correlated subquery inside the policy itself, duplicating pricing logic that already lives in `apps/dashboard/services/payments.ts`'s `initiatePayment()` (lines 80-99). It also diverges from this codebase's established pattern for member self-service actions.
- **Recommended: a new `SECURITY DEFINER` RPC, `initiate_member_payment()`, mirroring `check_in()`'s exact shape** (`0023_member_check_in_one_open_session_enforcement.sql:62-166`, called from mobile today at `apps/mobile/src/services/checkin.ts:80` via `supabase.rpc('check_in')`). Like `check_in()`: role-checks `(auth.jwt()->>'app_role') = 'member'` first; derives the caller's own `gym_id`/`member_id` from `private.gym_id()` + `auth.uid()` (never a client-supplied id); looks up the member's own most-recent `subscriptions → plans(price, currency)` row (same join `initiatePayment()` already uses, `apps/dashboard/services/payments.ts:80-87`); calls `active_payment_provider()` (already `grant execute ... to authenticated`, `0029_payment_provider_registry.sql:112` — safe to call from inside the definer body); inserts the `payments` row itself (`gym_id`, `member_id`, `amount := plan price`, `currency := plan currency`, `method := 'mobile_money'` — a free-text label since `0036_open_payment_method.sql` widened `payments.method` off the old closed enum, confirm this migration exists and the column is `text` before assuming), `status := 'processing'`; returns the new `payment_id`. Because it's `SECURITY DEFINER`, **no new RLS policy is needed at all** — the function bypasses RLS internally, same as `check_in()` does for `attendance_events`. The client never supplies `amount`; the server computes it. `grant execute on function initiate_member_payment to authenticated;` (never revoke from `authenticated` — unlike the service-role-only RPCs Story 4.14 added, this one *is* meant to be called by a member's own session, mirroring `check_in()`'s grant, not `get_gym_payment_credentials_for_service()`'s).

Once `initiate_member_payment()` returns a `payment_id`, the mobile app calls **the exact same, already-shared** `payment-webhook/initiate/<providerKey>` route the dashboard calls today (`apps/dashboard/services/payments.ts:136-139`) via `supabase.functions.invoke('payment-webhook/initiate/' + providerKey, { body: { paymentId, phoneNumber } })` — no Edge Function change required; it already trusts any caller holding a valid `processing` `paymentId`.

**Second gap this story must close: the mobile-money kill switch doesn't reach mobile.** `isMobileMoneyInitiationEnabled()` (`apps/dashboard/lib/featureFlags.ts`) reads `TARAMONEY_INITIATION_ENABLED` via `process.env` — a Next.js server-side env read, invoked today only from the dashboard's `initiatePaymentAction`/`getMobileMoneyAvailability()`. A member's Expo session calling `initiate_member_payment()` + the Edge Function directly **bypasses that check entirely** unless it's also enforced at a point both callers share. **Recommended:** add the same env-var check inside `handleInitiate()` itself (`supabase/functions/payment-webhook/index.ts`, Deno — `Deno.env.get('TARAMONEY_INITIATION_ENABLED')`), returning a distinguishable failure (e.g. `code: "mobile_money_disabled"`, mirroring Story 4.14's existing `gym_credentials_unavailable` pattern at `index.ts`'s failure-response construction) before calling `provider.initiate()` at all. This is the one point already common to both dashboard and mobile initiation, so it closes the bypass without needing a new mobile-reachable RPC. **[Review][Decision] if rejected:** the alternative is a new `authenticated`-granted RPC that just echoes the env var's effective state (parallel to `get_gym_payment_connection_status()`) — more mobile-UI-friendly (can hide the button proactively) but is a second source of truth for the same flag; get explicit sign-off before choosing this over the Edge-Function-level check.

**Gym-connection status, unlike the kill switch, already has a mobile-reachable check today:** `get_gym_payment_connection_status(p_provider_key)` (`0052_gym_payment_credentials.sql`) is `security definer`, `grant execute ... to authenticated`, and resolves `private.gym_id()` internally — no client-supplied gym id, self-scoping exactly like `check_in()`. A member's own session can call `supabase.rpc('get_gym_payment_connection_status', { p_provider_key: 'taramoney' })` directly today to implement AC #3's "Tara Money connected vs. not" branch. Reuse it; do not build a second connection-status check.

## Acceptance Criteria

1. **Given** my subscription status is `expiring_soon`, `grace_period`, or `expired`, **when** I open the app, **then** a "Renew" action is surfaced showing my current plan and the renewal price. [Source: epics.md#Story 4.15; prd.md#FR-140]
2. **Given** my gym has Tara Money connected, **when** I tap Renew, **then** I pay by Tara Money, routed through my gym's connected account (Story 4.13/4.14) — the same Flow A path as a front-desk renewal, just member-initiated. [Source: epics.md#Story 4.15; prd.md#FR-140, FR-126, FR-129]
3. **Given** my gym does not have Tara Money connected, **when** I tap Renew, **then** I see "See front desk to renew with cash" instead of a payment action (FR-127). [Source: epics.md#Story 4.15; prd.md#FR-127, FR-140]
4. **Given** a successful self-service payment, **when** it completes, **then** my subscription resets per FR-032 (new expiry, alert dismissed, appears in payment history immediately) and I see an immediate in-app confirmation — the same outcome as the front-desk renewal panel (FR-050), just self-initiated. [Source: epics.md#Story 4.15; prd.md#FR-032, FR-050, FR-140]

## Dev Notes

- **Read the Context section above first.** It contains this story's two real design decisions (the `initiate_member_payment()` RPC shape, and where the kill switch must be enforced) and why the naive alternatives (a new RLS policy; leaving the kill switch dashboard-only) were rejected.
- This story adds **zero changes** to `TaraMoneyProvider.ts`, `PaymentProvider.ts`'s routing-context types, or `complete_verified_payment()` — Story 4.14 already made every downstream step (credential resolution, webhook verification, subscription reset, push notification) caller-agnostic. If implementation pressure tempts touching any of those files, stop and re-read the Context section — that's a sign of solving the wrong problem.
- `payments.method` is a free-text column (`text`, not a closed Postgres enum) since `0036_open_payment_method.sql` — `'mobile_money'` is a valid, precedented literal (already used by the dashboard's `initiatePayment()`/`RenewalModal.tsx` today), not a new value requiring a migration.
- Mobile's established data-access convention is **plain `supabase-js` calls, no TanStack Query, no Server Actions** (Expo can't run Next.js Server Actions) — `AD-7`'s "thin per-domain service layer" applies per-app, and mobile's version is a flat `services/*.ts` file per domain, not shared with `apps/dashboard`'s equivalent files despite similar names/shapes.
- Mobile i18n (`apps/mobile/src/locales/en.json`/`fr.json`) is a fully separate key set from dashboard's — do not attempt to share or merge keys.
- **Known local-dev limitation, not this story's bug to fix:** Story 4.14's live-evidence session found local Supabase's Kong gateway always reports `http://` as an Edge Function's own request origin, which TaraMoney's real API rejects for webhook URLs — blocks a fully-chained single-session demo locally, not in production. Expect to hit this again in Task 6 and reuse the same documented acceptance rather than re-diagnosing.
