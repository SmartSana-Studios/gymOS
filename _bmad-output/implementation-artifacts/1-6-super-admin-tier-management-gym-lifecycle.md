# Story 1.6: Super Admin — Tier Management & Gym Lifecycle

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As GymOS platform staff,
I want to manage subscription tiers and suspend, deactivate, or reinstate gyms,
so that I can adjust pricing and handle account lifecycle without a code deployment.

## Acceptance Criteria

1. **Given** the Tier Management page, **When** I create, edit, or delete a tier, **Then** the change takes effect immediately for new gym assignments, **And** existing gyms are not automatically reclassified. [Source: epics.md#Story 1.6]
2. **Given** a tier currently assigned to one or more gyms, **When** I attempt to delete it, **Then** deletion is blocked with an error naming the affected gym count. [Source: epics.md#Story 1.6]
3. **Given** an active gym, **When** I suspend, deactivate, or reinstate it and provide a reason, **Then** the status change is reflected in the Gym List, **And** the action is audit-logged. [Source: epics.md#Story 1.6]
4. **Given** the Platform Metrics page, **When** I view it, **Then** total gyms, total members, and total payments processed are displayed as platform-wide aggregates. [Source: epics.md#Story 1.6]

## Dev Notes

### Scope Boundary (read first)

This story delivers Tier Management (SA-06), Gym Lifecycle status changes (SA-02 row actions), Platform Metrics (SA-05), and the Gym Detail page (SA-03) to the extent its tier/cap-override controls are needed. It does **not**:
- Build the "Access gym data" escalation or an Audit Trail view on SA-03 — both Story 1.7 (FR-072).
- Build any member-cap **enforcement** (the `BEFORE INSERT` trigger comparing a gym's member count against its effective cap) — that's Epic 2 (FR-086), which reads the `member_cap`/`member_cap_override` columns this story adds but does not itself enforce anything with them.
- Build the responsive icon-rail/hamburger sidebar (UX-DR4/UX-DR13) — that's the gym-admin dashboard's (`apps/dashboard`) job, a different app with different role-filtering needs; Super Admin gets a flat nav bar in this story instead.
- Send any real-time notification when a gym is suspended/deactivated — out of scope for any V1 FR found in the epics/PRD.

### Open Questions for User/Architect Sign-Off

These weren't fully resolved by the PRD/epics/architecture and materially affect this story. Recommended defaults are already written into the Tasks above (same pattern as Stories 1.2–1.5):

1. **SA-06's mockup lists "Member cap (min)" as a distinct form field with its own validation rule, but `tiers` has only one `member_cap` column (architecture.md, 0002 migration) and no FR ever describes storing a minimum threshold.** Recommended default (in Tasks above): treat "min" as a **derived display value** computed from tier ordering (previous tier's cap + 1), not a stored or user-editable field — the Tier Create/Edit form only collects one "Member Cap" field (blank = unlimited, resolving Story 1.5's Open Question 1 the way SA-06's own validation table already implies: "blank = unlimited"). Confirm this is acceptable, or direct the dev to add a real `member_cap_min` column instead (a bigger schema change with no FR driving it, and a real risk of the two tiers' ranges silently overlapping or gapping if min/max aren't validated against each other).
2. **epics.md's literal Story 1.6 ACs cover tier CRUD, gym suspend/deactivate/reinstate, and Platform Metrics — they do not explicitly mention gym tier reassignment or per-gym cap override**, even though FR-071 ("gym tier assignment/cap override") is mapped only to Epic 1 with no other story owning it, and SA-03's mockup (`[Change]` tier, `[Override cap]`) builds exactly these controls. Recommended default (in Tasks above): build them in this story (Task 4/7) — deferring them would leave FR-071 permanently unimplemented, since no later story in the sprint plan revisits Super Admin gym-detail actions before Epic 2 needs the `member_cap_override` column to exist. Confirm this is acceptable, or direct the dev to split them into a follow-up story instead (would require inserting a new story into the sprint plan, since none currently owns this).
3. **"Total payments processed" (AC #4) isn't defined precisely** — recommended default (in Tasks above): sum `payments.amount` where `status = 'verified'` (the only status meaning confirmed/reconciled money). This has zero current business impact (no payment flow exists before Epic 4 ships), so the risk of guessing wrong here is low, but confirm the intended semantics before Epic 4's dashboards start relying on the same aggregate logic elsewhere.

### Technical Requirements & Architecture Compliance

- **RLS remains the sole tenancy/role enforcement layer** — every new mutation (tier CRUD, gym status/tier/cap-override changes) is backed by an explicit, per-action RLS policy, never `FOR ALL`. The one deliberate exception is the two new aggregate-only `SECURITY DEFINER` functions (`platform_metrics()`, `gym_member_count()`), which must self-enforce `is_super_admin()` inside the function body since `SECURITY DEFINER` bypasses RLS entirely — get this right, it's the one place in this story where a missing check is a real data-leak, not just a UX gap.
- **Server Actions return `{ data, error }`, never throw for expected errors** — every new Server Action in this story (`createTier`, `editTier`, `deleteTier`, `suspendGym`, `deactivateGym`, `reinstateGym`, and the tier/cap-override changes on SA-03) follows this exactly, matching `createGym`'s established contract.
- **`packages/types` Zod schemas remain the single source of validation** — do not redefine any of this story's field rules inline in a modal or Server Action.
- **snake_case at the DB boundary, camelCase in UI-local state** — `memberCap`/`monthlyPrice`/etc. in Zod schemas map to `member_cap`/`monthly_price`/etc. at the actual `tiers`/`gyms` insert/update call sites, same convention as Story 1.5.
- **`log_audit_event()` is the canonical write path** for every lifecycle/tier-change/cap-override audit record this story creates — never insert into `audit_log` directly (blocked by deny-all RLS for anything but `service_role` anyway). Its signature (unchanged since Story 1.4): `log_audit_event(p_action_type text, p_gym_id uuid default null, p_target_entity_id text default null, p_target_entity_type text default null, p_metadata jsonb default '{}'::jsonb, p_system_actor_label text default null) returns uuid`. Tier actions pass `p_gym_id = null` (tiers are platform-wide, not gym-owned — architecture.md Entity Relationships); gym lifecycle/tier/cap-override actions pass the gym's own id — this function already exempts Super Admin callers from the "`p_gym_id` must match caller's own gym" check (Story 1.5 confirmed this exemption path works correctly), so no changes to `log_audit_event()` itself are needed here either.
- **Destructive-confirmation buttons must name their specific target** (UX-DR12: "Suspend FitZone Yaoundé", "Delete Grind" — never a bare "Confirm") — applies to every new confirmation dialog this story adds (tier delete, gym suspend/deactivate/reinstate, tier reassignment).
