# Story 1.7: Super Admin — Escalated Gym Data Access

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As GymOS platform staff,
I want to access a specific gym's member or payment data only through an explicit escalation,
so that routine platform administration never silently exposes tenant data.

## Acceptance Criteria

1. **Given** a Gym Detail page with no active escalation, **When** I view the page, **Then** I cannot see individual member or payment records for that gym. [Source: epics.md#Story 1.7]
2. **Given** I click "Access gym data" and enter a mandatory reason, **When** I submit, **Then** access is granted, **And** the escalation is audit-logged with my identity, the reason, and a timestamp. [Source: epics.md#Story 1.7]

## Dev Notes

### Scope Boundary (read first)

This story builds the escalation **mechanism**: the RLS gate on `members`/`payments` keyed off an `audit_log` row, the "Access gym data" button + mandatory-reason dialog, the audit-logged grant itself, and a read-only "Audit trail" tab on SA-03. It does **not**:
- Build any member-list or payment-list browsing UI for the Super Admin app. No FR, epics.md story, or architecture.md file-tree entry describes one for V1 (`apps/super-admin`'s directory structure lists only `gyms/`, `gyms/[id]/`, `metrics/`, `tiers/` — no `members`/`payments` routes anywhere). The RLS policies this story adds make that data *reachable* once escalated, for whichever future feature needs it (there is currently none planned) — AC #1/#2 are both about the *gate*, not about a browsing surface that doesn't exist yet.
- Add an expiry, TTL, or revocation flow for an escalation grant. Flagged as Open Question 1 below.
- Touch Epic 7 Story 7.2's (AD-12, gym-admin-facing) Audit Log page or its own read policy — that page's Manager/Owner-scoped RLS policy on `audit_log` does not exist yet and is explicitly out of scope here; this story's `super_admin_read_audit_log` policy is additive and Super-Admin-only.

### Open Questions for User/Architect Sign-Off

1. **Resolved 2026-07-10 — no PRD/epics/architecture text specifies escalation duration, expiry, or revocation.** Decision: permanent, per-`(actor, gym)` grant with no expiry — once Super Admin X escalates to gym A, X's session can always see gym A's member/payment data going forward, until/unless a future story adds revocation. This is the simplest mechanism that satisfies both literal ACs without inventing unspecified session/time semantics. Confirmed acceptable for V1's support/compliance posture; revisit with a TTL/revocation flow only if a future security review calls for it.
2. **The "Audit trail" tab shown in SA-03's mockup has no field-level spec anywhere in EXPERIENCE.md** (unlike every other screen, which has a Components/Layout breakdown). Recommended default (in Tasks above): show this one gym's full `audit_log` history (all action types, not just escalations) — actor, action, metadata summary, timestamp — with no filter controls, distinct from Epic 7's fuller AD-12 page. Confirm this is the intended scope, or direct the dev to scope it to escalation events only (a narrower, arguably more literal reading of "the tab next to the escalation button").

### Technical Requirements & Architecture Compliance

- **RLS remains the sole tenancy/role enforcement layer.** The new `members`/`payments` SELECT policies OR with existing policies for the same command (Postgres RLS semantics) — adding them cannot accidentally narrow any existing visibility, only add to it.
- **`audit_log` is both the audit record and, for this story only, the access-grant mechanism** — this is a deliberate, narrow design choice (Task 1), not a precedent to generalize: don't reuse "check for a matching audit_log row" as a general-purpose authorization pattern elsewhere without a similarly explicit design decision.
- **Server Actions return `{ data, error }` / `{ error }`, never throw for expected errors** — `escalateGymAccess` follows the same contract as every other action in `gyms/actions.ts`.
- **`log_audit_event()` is the canonical write path** — never insert into `audit_log` directly from application code (blocked by deny-all RLS for `authenticated` anyway, since only `service_role`/the function's own `SECURITY DEFINER` context can INSERT).
- **Destructive/sensitive-confirmation buttons name their specific target** (UX-DR12) — applies to `EscalateAccessDialog`'s submit button, matching every prior dialog in this app.
- **Validate on submit only** (UX-DR11) — the reason textarea, matching `GymLifecycleDialog`'s existing pattern.
- **snake_case at the DB boundary, camelCase in UI-local state** — `escalated`/`actorDisplayName`/etc. in the service layer map to `action_type`/`actor_display_name`/etc. at the actual query boundary.
