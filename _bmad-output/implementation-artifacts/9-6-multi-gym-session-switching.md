# Story 9.6: Multi-Gym Session Switching

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a staff member who holds an active role at more than one gym (Story 9.4),
I want to choose which gym I'm acting on behalf of and switch between them without logging out,
so that I can actually do my job at both gyms, not just have the platform correctly record that I hold both.

## Acceptance Criteria

1. **Given** a staff member with 2+ active, non-deactivated `members` bindings across different gyms, **when** they view the dashboard, **then** the Sidebar shows a gym switcher (not a forced login-time gym-selection step — see Dev Notes "Resolving the Epics Stub's Open Design Question") listing every gym they hold an active binding at. [Source: epics.md Story 9.6, AC #1 — resolved to the "dashboard shell shows a switcher" branch of its either/or]
2. **Given** a logged-in multi-gym staff session, **when** they use the switcher to select a different gym they hold an active binding at, **then** their session's `gym_id`/`app_role` claims update to that gym without a full logout/login, and every RLS-scoped query — including the page already on screen, not just subsequent navigations — reflects the newly-selected gym immediately. [Source: epics.md Story 9.6, AC #2]
3. **Given** a staff member with only one active gym binding (the overwhelming majority case), **when** they view the dashboard, **then** no switcher is shown at all — this story must not add friction to the common single-gym login path. [Source: epics.md Story 9.6, AC #3 draft]
4. **Given** a request to switch to a gym the caller does **not** hold an active binding at (e.g. a direct RPC call bypassing the switcher UI, or a stale switcher option for a binding deactivated moments earlier), **when** `switch_active_gym()` runs, **then** it is rejected server-side — not merely hidden in the UI. **(Added by this story, not in the epics stub — matches every other Epic 9 RPC's own "structural, not just UI-hidden" enforcement discipline: `create_staff_member()`'s ceiling check, `update_staff_role()`'s self-edit block, `staff_account_for_reset()`'s role ceiling. No story that mutates session/role state in this codebase has ever relied on UI-hiding alone.)**

- [x] [Review][Patch] `switchActiveGym()` has no distinct handling for the partial-failure window between its two calls — `active_gym_id` already durably changed but the UI reports a generic failure [apps/dashboard/services/session.ts:231-245] — if `supabase.rpc("switch_active_gym", ...)` succeeds but the following `supabase.auth.refreshSession()` call then fails (e.g. a transient network blip), the server-side preference has already changed permanently while the user is shown `sidebar.gymSwitchError` and sees no gym change in this session. **User decision:** retry the `refreshSession()` call once before giving up, rather than failing on the first attempt — keeps the common transient-blip case invisible to the user; only surface the error if the retry also fails.
- [x] [Review][Defer] The single most load-bearing assumption in this story — that `supabase.auth.refreshSession()` re-invokes `custom_access_token_hook()` with fresh claims — has zero automated regression coverage [apps/dashboard/services/session.switchActiveGym.test.ts mocks `refreshSession()`; `supabase/tests/multi_gym_session_switching.test.sql` calls the hook directly, never through an actual refresh]. ### Resolving the Epics Stub's Open Design Question

The stub (`epics.md:1792`) explicitly left the switching mechanism as "a real design decision for create-story/architecture to make, not assumed by this stub," listing three candidates. This story resolves it as follows, and Task 2/4/5 are written against this resolution — do not re-litigate the choice during `dev-story` without flagging it first:

- **Mechanism**: a new `users.active_gym_id` column (schema-tracked preference — the stub's third option), read preferentially by `custom_access_token_hook()`, falling back to the existing most-recent-wins default when unset or stale.
- **Trigger for re-resolving claims**: `supabase.auth.refreshSession()`, which GoTrue re-invokes the hook for on every token refresh (not just initial login) — confirmed by Supabase's own docs and this codebase's one existing precedent (`apps/mobile/src/app/onboarding/plan.tsx:222`), but Task 1 requires hands-on re-verification specifically for this story's use case before building on it further.
- **UI placement**: the dashboard shell (Sidebar footer), not a forced login-time gym-selection screen — the stub explicitly offered both ("they are shown a gym-selection step, **or** the dashboard shell shows a switcher"); the shell-switcher branch avoids restructuring the login/auth flow for a case that affects a small minority of sessions, and reads more naturally as "which gym am I acting on behalf of right now," a thing that can change mid-session, not just at login.
- **Persistence scope**: `active_gym_id` is a durable per-user preference, not session-scoped — it persists across logout/login (the user's last-chosen gym is where they land next time, not reset to "most recent binding created"). This is also the only mechanism GoTrue's hook can actually read (it has no access to any session-scoped app state — a Postgres column is the only persistent channel available to it), so "per session" from the stub's own third option is realized as "per user, durable" in practice.

### Why the Existing `self_read_own_membership` Policy Already Does Half the Work

`0013_dashboard_shell_self_read.sql:23-25`'s `self_read_own_membership` policy on `members` (`user_id = auth.uid()`, deliberately **no** `gym_id` predicate) already lets any caller read every `members` row they hold, across every gym — its own header comment explicitly anticipated this ("a user can hold historical/other-gym membership rows per FR-001... callers that only want the row for the currently-active gym filter by `gym_id` themselves"). This story is the first to actually need that unfiltered read. **Do not add a new `members` RLS policy for Task 4's "list my other gyms" query** — the existing one already covers it. The one genuine gap is on `gyms`: `"read own gym"` (`0009_auth_hook_gym_claims.sql:154-156`) is scoped to `id = private.gym_id()` (the *current* claim only), so reading *other* gyms' names requires Task 2's new additive policy. Missing this distinction is the most likely way to under- or over-build this story's RLS surface.

### Why `private.current_member_role()`/`private.gym_id()` Need Zero Changes

Both helpers (`0009_auth_hook_gym_claims.sql:20-43`, `0061_staff_creation_role_ceiling_enforcement.sql:31-51`) read entirely off the `gym_id`/claims already present in the session's JWT — after a switch, once `refreshSession()` mints a new token with the new `gym_id` claim, every existing RLS policy and `SECURITY DEFINER` function that calls these helpers (which is nearly all of them) automatically scopes to the newly-selected gym with no code change. The entire surface area this story needs to touch is: (1) how the hook *picks* `gym_id` in the first place (Task 2), and (2) the app-layer plumbing to trigger a refresh and show a switcher (Tasks 4-5). Resist the temptation to touch any RLS policy or RPC beyond the one new `gyms` policy — everything downstream of the claim already works correctly by construction.
