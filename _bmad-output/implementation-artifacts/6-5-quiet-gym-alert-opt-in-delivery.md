# Story 6.5: Quiet-Gym Alert Opt-In & Delivery

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a member,
I want to opt in to being notified when my gym is quiet,
so that I can pick a less crowded time to train if I prefer that.

## Acceptance Criteria

1. **Given** my notification preferences (already shipped by Story 6.4's `member_preferences.quiet_gym_alerts_opted_out`, `not null default false`), **when** I view them in the mobile app, **then** the existing "Quiet-gym alerts" toggle continues to default to **on** (`opted_out = false`) for new members and reflects my current choice — this is a deliberate divergence from FR-113's literal "default off" text; see Dev Notes "Default-Polarity Contradiction" for why the already-shipped Story 6.4 default is authoritative and is not changed by this story. This story removes the "(Coming soon.)" / "(Bientôt disponible.)" qualifier from that toggle's copy (both `en.json`/`fr.json`), since the opt-out now has a real, observable effect.
2. **Given** I've opted in (`member_preferences.quiet_gym_alerts_opted_out = false`) and my `members` row is not deactivated, **when** my gym's occupancy is in the Low band (FR-047, `< 30%` of configured capacity) during the gym's configured opening hours, **then** I receive N-06 — the V1.5 activation of the reserved N-06 notification type (FR-075) — as an Expo push notification, in my preferred language (EN/FR).
3. **Given** the occupancy calculation used to decide whether to fire N-06, **when** it runs, **then** it reuses the exact FR-046 calculation already implemented in `member_occupancy_band()` (Story 3.6, migration `0025`) — same checked-in-count/capacity formula, same Low-band threshold (`< 30%`) — via one shared, single-source-of-truth helper function, not a second, independently-maintained copy of the arithmetic (FR-115, "no new presence-detection mechanism").
4. **Given** N-06 has recently fired for a member, **when** occupancy would trigger it again for that same member, **then** delivery is rate-limited to a maximum of 2 sends per rolling 24-hour window per member, with a minimum 3-hour gap since that member's most recent N-06 send (FR-114).
5. **Given** a gym has no `opening_time`/`closing_time` configured (both nullable, no gym today has these set — see Dev Notes "Opening Hours Gap"), **when** its occupancy drops into the Low band, **then** N-06 is still eligible to fire for that gym (unconfigured = unrestricted, not blocked) — but once a gym does have both configured, N-06 must never fire outside that local time-of-day window, evaluated in the gym's own `timezone` column.
6. **Given** a gym with `status` other than `'active'` (`'suspended'` or `'deactivated'`), **when** the dispatch job runs, **then** that gym is skipped entirely — no N-06 is sent to any of its members regardless of occupancy or opt-in state.
7. **Given** N-06's push delivery (ticket/receipt lifecycle, stale-token cleanup on FCM/APNs-invalid response), **when** it is processed, **then** it follows the exact same two-stage Expo ticket→receipt mechanism already shared by N-01–N-05 (`private.process_notification_deliveries()`, migrations `0045`/`0046`) — extended to a third delivery-ledger table, not a new, parallel delivery-processing function (FR-077, consistency with AD-25).
8. **Given** all N-06 push copy (title/body, EN/FR), **when** it is sent, **then** it follows the exact per-member-language-preference pattern already established by N-01–N-05 (`users.preferred_language`, `'fr'`/default `'en'`) — no i18n-bundle keys are needed since, like N-01–N-05, this copy is generated inside the Postgres dispatch function, not the mobile app (FR-078).

## Dev Notes

### Default-Polarity Contradiction — Read This First

FR-113 says quiet-gym alerts "default to off" and the member "can opt in explicitly." But Story 6.4 already shipped `member_preferences.quiet_gym_alerts_opted_out boolean not null default false` — `false` means **not opted out**, i.e. alerts are **on by default** — and its mobile toggle (`profile.tsx`) renders accordingly. This matches FR-076's general "opt out of non-critical notifications" framing and Story 6.6/N-07's own AC ("on by default but I can turn it off"), but directly contradicts FR-113's specific "default off" wording for quiet-gym alerts. **This is a genuine, pre-existing contradiction between two FRs in the PRD, already resolved in shipped code by Story 6.4 — not something this story introduces or should "fix."** Changing the default now would silently flip the opt-in state for every existing member without their action, which is out of scope and actively harmful. Treat the live schema default (`false` = on) as authoritative. Do not add a migration changing `member_preferences`' default, and do not write a test asserting "default off" for quiet-gym alerts — assert the actual shipped default instead.

### Opening Hours Gap — Read This First

FR-113/FR-114 (and the epic's own AC text) refer to "the gym's configured opening hours" as an existing concept. **It is not.** A full-repo search (`gyms` table definition across `0002`/`0011`/`0023`, every dashboard Settings field in `SettingsForm.tsx`/`gym-settings.ts`, both UX design docs) confirms no gym in this codebase has ever had opening/closing hours as a stored, configurable field — `checkin_timeout_hours` (FR-045) is a *duration*, not a time-of-day window, and is unrelated. This story resolves the gap the minimal way: two new nullable `time` columns on `gyms` (`opening_time`, `closing_time`), evaluated against the gym's own `timezone` column, with **unconfigured (either or both null) treated as unrestricted** — not as "never eligible." No Settings-page UI is added in this story; every existing gym today has both columns null, so N-06 is effectively unrestricted by time-of-day until a future story adds a way to configure them. This is a deliberate, minimal-scope call, not an oversight — do not expand this story to add a Settings UI field for it.

### Rate-Limit Semantics

"Max 2 per day per member with a minimum 3-hour gap" (FR-114) is implemented as a **rolling 24-hour window** read from `private.quiet_gym_alert_dispatches.sent_at` at evaluation time (`count(*) where sent_at > now() - interval '24 hours' < 2`), not a calendar-day counter that resets at midnight. The PRD does not specify which; the rolling-window reading is the safer one (a calendar-day reset could let 2 sends land minutes before midnight and 2 more minutes after, momentarily violating the "2 per day" spirit even if not the letter). The 3-hour gap check is independent and always applies: `max(sent_at) where member_id = ... is null or < now() - interval '3 hours'`.

### Architecture Compliance

- **AD-25** (Push notification dispatch is DB-triggered, not a service-layer responsibility) explicitly names N-06 as landing "under this same mechanism" — this story's `run_quiet_gym_alert_job()` + `pg_net`-via-Postgres-function shape is not a new pattern, it is AD-25 applied to a periodic-cron trigger (like `run_subscription_lifecycle_job`) rather than an `AFTER INSERT/UPDATE` trigger (like the payments notifier) — periodic is the right shape here because the rate limit ("up to 2/day with a 3-hour gap") implies re-evaluating a sustained quiet period more than once, which a pure event-triggered design (fire only on the exact moment occupancy crosses into Low) would not naturally support.
- **FR-115** ("reuses the existing occupancy calculation exactly — no new presence-detection mechanism") is satisfied by extracting one shared `private.gym_occupancy_band()` helper that both the pre-existing `member_occupancy_band()` and this story's new job call — not by copy-pasting the threshold arithmetic a second time. Do not duplicate the `< 30` / `<= 70` logic anywhere else.
- Every new table follows the established RLS-enabled-in-same-migration, `gym_id`-carrying, `private`-schema-for-server-internal-state conventions (`0045`/`0046` precedent, not `0047`'s client-facing-table precedent — no member or staff ever reads these two new tables directly).
- `run_quiet_gym_alert_job()`, `private.send_quiet_gym_alert()`, and `private.gym_occupancy_band()` all follow the codebase's `revoke ... from public` + narrow `grant` discipline — none of the three should ever be callable from `authenticated`/`anon`.
