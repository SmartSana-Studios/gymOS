## Findings

Sources are the files and commits cited. Findings from sub-agents were re-checked against the code where marked **verified**; the rest are reported as read by the reviewer and are not independently reproduced.

### Spec-to-implementation reconciliation

**F1. Session limits are not enforced on most Super Admin Server Actions** (adoption gap across 22-4 and 22-7). Disposition: **fix now, before the aal2 flag is enabled.**
- `touchSessionGate` runs only inside `authorizePlatformAction` (`apps/super-admin/lib/authz.ts:60-65`). Only `createGym` (`gyms/actions.ts:294`), `triggerRetry` (`billing/actions.ts:181`), `admins/*`, `security/*` and `step-up-actions.ts` call it.
- Not gated: `suspendGym`, `deactivateGym`, `reinstateGym`, `changeGymTier`, `overrideGymCap`, `escalateGymAccess`, `revokeGymAccess`, `changeGymCategory` (`gyms/actions.ts:618-811`), `markPaymentReceived`, `applyCredit` (`billing/actions.ts:22,63`), and the `tiers`, `messaging`, `payment-providers` actions. Verified by grep and reading `gyms/actions.ts`.
- `docs/decisions.md:12` states "every layout render and Server Action is gated". That is not what the code does.
- RLS side (`is_super_admin`) checks aal2, session-row existence and lock, not idle or absolute age, so an idle or over-age cookie keeps working on these actions until a gated route runs.
- Latent today: the flag is off. It becomes live when `enable-super-admin-aal2.mjs` is run.
- Sources: verification-gap lens #1 and adversarial lens #2 (independent, same conclusion); commits e8de0c4, 5a28fe3.

**F2. A Super Admin created or promoted while the flag is on has no path to enroll a first factor.** Disposition: **fix now (needs a human decision on the intended flow).**
- With the flag on, `(admin)/layout.tsx:59-75` sends aal1 sessions to `/auth/mfa`, which only verifies (`mfa-form.tsx:69`, "Contact the platform operator"). `/security` sits under the same layout and `guard()` requires aal2 (`security/actions.ts:36-41`). `createOrPromoteSuperAdmin` has no factor handling.
- Result: every admin added after go-live is locked out until the reset script runs, and that script turns the flag off platform-wide (F6).
- Verified by reading layout, guard and actions. Not exercised in a browser. Distinct from the deferred item about existing admins with factors.
- Sources: adversarial lens #1; commits e8de0c4, f6187b8, 2e3c70d.

**F3. `docs/decisions.md` and the runbook overstate scope.** Disposition: **spec reconciliation (human applies).** The "every Server Action" claim in F1; `/auth/mfa` attempts are intentionally not counted toward lockout (decision recorded in `spec-22-7`, runbook "Locked after wrong codes"). Both adversarial #4 and edge-case #4 re-flagged the second as a gap; it is an **accepted deviation** with a recorded reason (a password holder must not be able to lock the sole Super Admin). Record it as accepted so later retros stop re-flagging it, and state in the runbook that only the provider's rate limit covers the aal1-to-aal2 step.

### Pattern divergence and cross-story seams

**F4. `authorize_action('platform.*')` is flag-blind by design and the boundary is unpinned.** Disposition: **fix now (test).** The platform branch (`0125_authorize_action.sql:64-72`) checks `users.is_super_admin` only; aal2, session and lock live in the TypeScript wrapper and in `is_super_admin()`. `authorize_action.test.sql` tests `platform.gym_create` allowed/denied, `platform.admin_access` denied only, and `platform.billing_retry` / `platform.super_admin_manage` not at all (verification-gap #2, #3; adversarial #5). Deleting a `WHEN` arm would lock every Super Admin out without failing a test. Add one allowed assertion per `platform.*` capability and one assertion that records the flag-on contract.

**F5. Step-up subject binding is tested only against mocks.** Disposition: **defer.** `issueStepUp` and `createOrPromoteSuperAdmin` each normalize the subject with `trim().toLowerCase()`; both are tested with `consumeStepUp` mocked (`createOrPromote.authz.test.ts:72`, `security/actions.authz.test.ts:166`). They match today. A shared `normalizeSubject` helper or one real round-trip test removes the drift risk (verification-gap #4).

**F6. Lockout can only be cleared by the destructive reset.** Disposition: **fix now (small).** `scripts/reset-super-admin-factors.mjs:74-80` is the only way to clear `super_admin_lockout`; it deletes all the target's factors and turns the flag off for the platform. Five wrong step-up codes from a stolen aal2 session therefore force an operator into a platform-wide downgrade. Add an unlock-only mode with an audit row (adversarial #3). Related deferred item: no audited way to turn the flag off without destroying factors (`deferred-work.md`, 22-6).

### Diff-scope review: defects

**F7. `removeFactor` skips the global sign-out when the audit write fails.** Disposition: **fix now.** `security/actions.ts:178-183` returns `audit_failed` after a successful `unenroll`, before the sign-out block at `:186-200`. The factor is gone, other sessions stay alive, and the UI does not report `removed`. Verified in source. Sources: adversarial #6, edge-case #2 (independent).

**F8. The new-admin password re-auth replaces the Super Admin session.** Disposition: **fix now, confirm in browser first.** `admins/actions.ts:151` calls `session.auth.signInWithPassword` on the session client. The code comment calls this a no-op for session identity. It mints a new session, so the cookie becomes aal1 (next request goes to `/auth/mfa`) and the 8 h absolute age restarts, because age is read from `auth.sessions.created_at`. Verified that the call is on the session client; the aal1 downgrade is the reviewer's reading of Supabase behavior and **was not run**. Browser checklist steps 26-27 will show it. Source: edge-case #1; commits e8de0c4, 3f9eafb.

**F9. `billing.saas_pay` is exempt from the gym-status check for every non-active status.** Disposition: **decide, then fix.** `0125_authorize_action.sql:97-99` comments "suspended" but exempts `deactivated` too (`gym_status` is `active | suspended | deactivated`, `0001_extensions_and_enums.sql:6`). An Owner of a deactivated gym can still initiate SaaS payments. Verified in source. Source: edge-case #8.

**F10. Lower-severity items.** Disposition: **defer** (full list in the action items; none verified beyond the reviewer's reading unless noted).
- `consumeStepUp` runs before `unenroll`; a provider failure burns the single-use grant and counts toward nothing, but forces a re-prompt (edge-case #3, low).
- Denial branch in `payment-webhook/index.ts` leaves a `processing` row orphaned, unlike other rejection branches (edge-case #6).
- Nonexistent `paymentId` returns 400 while another gym's returns 403, a UUID existence oracle (adversarial #8).
- Suspended-gym denial surfaces as a generic `permission_denied` to mobile and dashboard, hiding the existing `gymSuspended` handling (adversarial #7).
- `member.registration_fee_state` now denies `coach`; whether coaches reach the member modal is unconfirmed (edge-case #7; already in `deferred-work.md` for 22-4).
- `authorize_action` `initiate_own` denies staff paying their own row (adversarial #11, unconfirmed).
- `private.support_session_state` rows are never purged for sessions that end by sign-out or expiry; no FK to `auth.sessions` (adversarial #9).
- `guard()` runs `requireSuperAdminAal2` twice (adversarial #10).
- `enable-super-admin-aal2.mjs` does not re-check factor counts after the typed confirmation (edge-case #5; already deferred under 22-6).
